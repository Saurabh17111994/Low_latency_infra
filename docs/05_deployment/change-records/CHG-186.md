# CHG-186 — harness manifest path resolves to the approved instrument manifest (wave 36)

- **Status:** recorded — fixes a pre-existing bring-up defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** discovered while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`, after the stack restart and
  CHG-185 unblocked the earlier bring-up failures. Not one of the wave's 18
  findings — the live run surfaced it once ingestion could finally reach its
  manifest step.

## What happened

`pipeline-lib.sh` resolved the instrument manifest with two `..` segments:

```bash
LIB_MANIFEST="$ROOT/../../Arrow_broker/instruments/cash_stocks/NSE_CM_EQUITY.csv"
```

`$ROOT/../../` from the repo root lands in `/home/saurabh/Jupyter_notebook/`, a
different `Arrow_broker` tree from the one the repo is developed against. That
tree's only NSE cash file is a 7-column export whose header is
`Exchange,Segment,ExchSeg,Token,FullName,TradingSymbol,InstrumentType` — it has
**no `LotSize` column**.

Since `d09e9795` (2026-09-07) the Java loader refuses such a manifest, because
`LotSize` is load-bearing (quantity math, and an input to the P1-070 hash):

```text
ERROR com.trading.ingestion.InstrumentManifestLoader - instrument-manifest: CSV missing LotSize column; refusing to load
ERROR com.trading.ingestion.IngestionService - ingestion: FATAL — manifest load returned empty instrument set
```

`pipeline_start_ingestion` then times out after 120s waiting for a readiness
marker that can never appear, and every harness sourcing this library dies during
bring-up at manifest load. The wave-36 run reproduced exactly this: `SMOKE FAIL —
main measurement SKIPPED`.

**Why every other consumer was unaffected.** Five other places resolve the same
manifest correctly — one level up and with the approved filename:
`bench-throughput.sh` (L65), `run-full-suite.sh` (L47), `start-all.sh` (L30),
`docker-compose.yml` (L31, via `INSTRUMENT_MANIFEST_HOST_PATH`), and
`run-signal-chain-e2e.sh` (L73). The last of these carries a comment recording
that it fixed *this same too-deep default* in an earlier wave:

> The instrument manifest lives OUTSIDE the repo, one level above PROJ_ROOT
> (Flink_Fluss_Infrastructure/Arrow_broker/...), not inside it. The pre-fix
> `$PROJ_ROOT/Arrow_broker` default exported a nonexistent path…

`pipeline-lib.sh` was the remaining copy of the bug, and it is the copy that the
wave-36 harness depends on. Three sibling scripts carried their own identical
two-level copy and are fixed here with it: `loadtest-run.sh` (L29),
`tiering-smoke.sh` (L23), and `test-loadtest-guards.sh` (L53, L56 — the guard
whose own G7 assertion was validating the wrong file).

**Independent corroboration.** The Java author's P1-086 comment states the column
was verified against "all 3 cash CSVs, 5,777 rows". The 5,777-row / 3-file set is
the one-level-up tree; the two-level-up tree holds a single 2,431-row file. The
G3 fingerprint fix (`65da1e26`) likewise describes its root cause as "the full
2,431-row CSV" — the very file this path selected, which is why the bench's Java
side and its 1,024-token slice never agreed.

## The fix

Resolve the manifest one level up, with the approved filename, in all four files:

```bash
LIB_MANIFEST="$ROOT/../Arrow_broker/instruments/cash_stocks/NSE_CM_EQUITY (1024).csv"
```

This restores the path `REQ-ING-004` already specifies as the approved manifest
for the current testing phase, and it is the file the compose `ingestion` service
loads successfully today (fingerprint `c68f50f7f716`).

**Token-set change is intended and unavoidable.** The pre-fix path's first 1,024
tokens and the approved manifest's 1,024 tokens overlap in only 419 positions;
the approved manifest is the set the rest of the platform, the docs, the
requirements and the compose stack all use. The alternative — adding `LotSize` to
the file outside the repo — was not taken, because that tree is not the repo's
manifest tree and other consumers already treat the approved file as canonical.

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*Requirement*. `REQ-ING-004` pins the approved manifest path for the current
testing phase, and the pre-fix library deviated from it — the deviation is the
defect. The `deployment` axis also applies: this is the manifest the shared
bring-up library resolves for the containers it starts. This record carries both
scopes rather than only `requirement`, because the affected files are the shared
bring-up library and its sibling harnesses.
