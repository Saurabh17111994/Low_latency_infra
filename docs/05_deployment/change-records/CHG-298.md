## Why

Each hit carries a `class` of `in-repo` or `outside`. The field exists to separate the
two situations that differ in consequence: a value inside this public repository is
potentially published, a value outside it is local. In name mode the field is not merely
printed — `failed` is `bool(outside) or (args.strict and bool(in_repo))`, so the label
decides the exit code.

The classifier compared an absolute `REPO_ROOT` (`SCRIPT_DIR.parents[2]`) against the
path as walked. When `--root` is relative, every walked path is relative too, and
`REPO_ROOT in path.parents` is then false for every hit.

Met in the field on 2026-09-22: a value-equality scan of the repository
(`--root .`, 5,134 files, nine hits, all of them in `secrets.env` and
`images.published.env`) reported `counts: {outside: 9, in_repo: 0}`. Every one of those
nine files is inside the repository. The count was wrong in the direction that matters
least for a leak hunt — it over-reported the alarming class — but a field that cannot be
trusted is worse than no field, because the next reader will believe it.

`hit_class()` now resolves both sides before comparing. Nothing else changes: the paths
are still printed as walked, and the fix does not touch which values are matched, which
files are opened, or any counter.
