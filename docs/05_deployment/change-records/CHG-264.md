# CHG-264 — nothing checked the cluster, only the machines and the stack file

## Why

Three gates existed before this change, and none of them could see a deployed swarm:

```text
code/01_platform/04_scripts/prod_node_check.py   machines: SSH, disk >= 500 GB, role, labels, swarm identity
code/01_platform/04_scripts/tests/test_09_stack.py   the FILE: schema, placement keys, healthchecks, ports
make gate                                        the repo: builds, unit tests, checkers
                                                 -> what the cluster did with that file: nothing
```

Every observability defect found on 2026-09-20 lived in that gap, and each was invisible from the
file that caused it. `docker stack deploy` reported success while `prod_fluss-snapshot` sat
`Pending`; a bind-mount source that existed on the workstation did not exist on the node the task
landed on; a global agent could cover one node while three others had no metrics. Worked around by
hand each time, by running `docker service ps` and reading the `Error` column — a procedure, not a
check.

## What changed

- **`code/01_platform/04_scripts/cluster_check.py`** (new) — a read-only validator for a deployed
  Swarm: `docker info`/`node ls`/`node inspect`/`service ls`/`service ps`/`service inspect`, no SSH,
  stdlib only, exit code = number of FAILs. It reports two verdicts because they need different
  reactions: **FAIL** = the cluster could satisfy the check and does not; **WARN** = the nodes
  present cannot satisfy it (three replicas with `max_replicas_per_node: 1` on one node). Checks:
  swarm active, nodes Ready/Drained, replica counts, tasks waiting on a placement or a mount,
  single-replica-per-node spread, global coverage against the labels each service selects, which
  service publishes a port, and — with `--expect` — cluster size and `observability` labels against
  `prod_vms.json`. Holds the same runner seam as `prod_node_check.py` (`DockerRunner` swapped for
  `FixtureRunner` in tests and in `--self-check`).
- **`code/01_platform/04_scripts/tests/test_11_cluster_check.py`** (new) — 22 offline tests whose
  fixtures are the CLI shapes actually measured on the rehearsal swarm, not the shapes the code
  hoped for.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — new **S8b** step: run it after every deploy,
  with the FAIL/WARN distinction and the rehearsal result written down.

## Measured

The shapes the docker CLI really prints, each of which broke the checker when it assumed otherwise:

```text
$ docker node ls --format '{{json .}}'
{"Availability":"Active","Hostname":"saurabh-MS-7D90",...}          # no Labels key at all
$ docker node inspect saurabh-MS-7D90 --format '{{json .Spec.Labels}}'
{"observability":"true","role":"worker"}                            # the only source of labels
$ docker service ps prod_node-exporter --format '{{json .}}'
{"CurrentState":"Running about an hour ago","DesiredState":"Running",...}   # capitalised
$ docker service ps prod_ingestion --format '{{.DesiredState}} {{.CurrentState}} {{.Error}}'
Shutdown Failed about an hour ago "task: non-zero exit (1)"         # 0/1, and not "desired running"
$ docker service ls --format '{{.Name}} {{.Replicas}}'
prod_openobserve 1/1                                                # stack-prefixed
```

Two of those four produced **false PASSes** — with labels unread every constraint evaluated to "no
node matches", so a coverage gap passed and a real replica shortfall was downgraded to a topology
warning; with `DesiredState` compared lowercase, stuck-task detection matched nothing at all. Both
were caught by running the checker against the live rehearsal cluster, not by reading it.

The live result on that cluster (1 node, 18 services), after the fixes:

```text
PASS  swarm-active — state=active control_available=True
PASS  nodes-ready — 1 node(s) Ready
FAIL  replicas-complete — short of replicas: prod_ingestion 0/1
WARN  replicas-topology-limited — prod_flink-jobmanager 1/2, prod_flink-taskmanager 1/3
                                         (only 1 node(s) match its constraint, max 1 per node)
FAIL  no-stuck-tasks — short of replicas with tasks dying: prod_ingestion 0/1 — "task: non-zero exit (1)"
PASS  placement-spread — 8 single-replica-per-node service(s) spread correctly
PASS  global-coverage — 3 global service(s) run on every node their constraint selects
PASS  published-ports — only the allowed service publishes: {'prod_openobserve': [5080]}

2 failure(s), 1 warning(s)                                          # exit code 2
```

Both FAILs are the same known production blocker (missing `ARROW_*` vendor credentials, which the
schema gate passed but ingestion cannot start without). Nothing else was flagged — that is the
signal worth having: on a four-VM deploy this should be the only remaining FAIL.

## Limitation

**It is not part of `make gate`, and cannot be.** It needs a live cluster; the gate must run on a
workstation. S8b is the seam, and an operator who skips S8b gets no protection from this — the
validator cannot fail a deploy that never calls it.

**It checks the shape of the deployment, not its behaviour.** Replica counts, placement, coverage and
publishes are visible from the swarm; whether Flink is checkpointing, whether Fluss serves reads, or
whether a metric is actually scraped are not. The per-node observability gap (VM1–VM3 host metrics
and logs until the placement decision is made) shows up here only as far as the labels and the
global-service coverage reveal it.

**A `Pending` task that the topology could satisfy is reported once, without a root cause.** The
checker prints the task's `Error` text verbatim and stops there: "invalid mount config" is the
cluster telling you what is wrong, and reinterpreting it in this script would mean inventing a
mapping from error strings to causes that the daemon may reword.
