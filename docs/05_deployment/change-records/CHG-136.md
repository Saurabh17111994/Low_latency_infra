# CHG-136 — The live forward leg claims and records the attempt before the bridge sees it

- **Status:** recorded — the durable attempt store gains its live caller (Workstream D swap,
  default OFF)
- **Filed:** 2026-09-14
- **Source:** the D-table deferral discharged by CHG-135, which landed the stores and named the
  remaining piece: "the attempt store's live caller remains the Workstream-D swap"

## What happened

After CHG-135 an operator could enable `DURABLE_ATTEMPTS_ENABLED`, get a real file-backed store, and
still watch the running service send orders with nothing durable written: the only caller of the
store was `ExecutionGate`, which the service constructs nowhere. The enabled flag was honest
evidence of a *store*, not of a guard.

The live path had everything the guard needs, though, which is why this was a wiring change rather
than a design one:

* `intent.rs` mints a fresh `execution_attempt_id` per attempt and derives the deterministic
  `client_order_ref` from it — the attempt identity already existed;
* the signed envelope carries `instruction_id` (from the payload) and `payload_hash` (`n`), and
  `gateway_protocol::verify` already proves `n == sha256(payload)` and covers `n` with the HMAC — so
  `(instruction_id, n)` is an authenticated identity;
* that pair is exactly the key the Java gateway's durable dedup index uses
  (`Execution_Intent_Processed` / `FlussIntentDedupStore`, whose contract reads: re-record with the
  SAME hash is a no-op, re-record with a DIFFERING hash must not overwrite — `HASH_VIOLATION`), so
  both sides classify "same instruction, same content" identically;
* `ServerState::safety_halt` already exists — the drift monitor's own fail-closed mechanism.

## What changed

**The store the server can share.** `durable_file::{FileAttemptStore, FileGateStore}` now hold one
mutex over their log *and* their indexes, so they are `Send + Sync` and classify-and-claim is atomic
against a concurrent caller rather than merely single-actor (pinned by
`durable_file::tests::a_racing_second_claim_is_refused`: two threads, same identity, one `Claimed`
and one `Duplicate`). `durable::LiveAttemptStore` (`AttemptStore + Send + Sync`, blanket-implemented)
is the narrower view the HTTP server asks for, and `DurableClients::live_attempts` hands out the same
object as `attempt_store` — one log, two trait-object views, because the writer lock refuses a second
`open` of the same log by design. The in-memory store stays single-actor: it is held as
`Arc<dyn AttemptStore>` (an unsized object that cannot cross a thread boundary) precisely so it
cannot be mistaken for a shareable guard.

**The guard.** `http::claim_for_send`, called by the ENABLED `/v1/intents` forward leg after the
envelope is mapped and before the bridge lock is taken:

| Durable state | Answer | Bridge called? |
|---|---|---|
| new identity | record `SUBMITTING`, then send | yes |
| `Existing` `PREPARED` | resume: the record is written *before* the send, so no call was made | yes |
| `Existing` `ACCEPTED` / `REJECTED` | answer from the record (broker id / reason) | no |
| `Existing` `SUBMITTING` / `UNKNOWN` | `safety_halt` + 503 `UNRESOLVED` | no |
| `Duplicate` (same instruction + `n`, other attempt id) | 409, no halt — the gateway's ordinary retry | no |
| `ContractViolation` (same instruction, different `n`) | `safety_halt` + 409 | no |
| store cannot record | 503 `STORE_UNAVAILABLE` | no |

The last row is the guard's reason to exist: no durable record, no send. After the send the terminal
phase is recorded from the same report the response is built from; if that write fails the response
still stands (the bridge outcome outranks bookkeeping) and the attempt stays `SUBMITTING`, which is
the safe direction — a later retry of it halts instead of sending again. The failure is logged, never
silent.

`main` keeps the bundle alive for the process and arms the guard only when
`DurableClients::live_attempts` is `Some`; with the flag OFF `ServerState::attempts` is `None` and
the forward leg is byte-for-byte what it was (the pre-existing route tests pin that path).

## What this does and does not mean

Compatibility is `COMPATIBLE`: the flag defaults OFF, and flag-OFF behaviour is pinned by the
existing `/v1/intents` tests (they construct `ServerState` without a guard).

It means the live *forward leg* is guarded: an intent that reaches the bridge has a durable record,
and a replay — same process or a restarted one — is refused rather than forwarded twice. It does not
mean the executor is durable in general:

* `ExecutionGate` is still constructed only by tests; this change wires the **route**, not the gate;
* fencing, approvals, and the epoch authority remain the gateway's (`GateStateStore`, Java side), and
  the executor's own gate state is still in-memory and boots HALTED by construction;
* the store is one-actor and single-host by construction (pid lock + `/proc` liveness); the
  Fluss-backed, multi-host store is the Java client's, as CHG-135 states;
* `Duplicate` is answered with a refusal, not with the previously recorded outcome. Resolving it
  positively needs an `(instruction_id, request_hash) → attempt` index; the store currently exposes
  existence, not that lookup. Left out deliberately — the gateway's reconciliation path (query) is
  the reader of outcomes, and inventing an ack shape the gateway is not coded to expect would be
  worse than a refusal it already handles.

## Rollback

No flag is enabled by this change, so the default deployment is unaffected: `git revert` of the
commit restores the unguarded forward leg, and any durable directory an operator did enable remains
plain JSONL that can be inspected or deleted without a migration.

## Follows

- CHG-135 (D1/D2 stores) — this is the deferral it named, discharged by wiring the store's caller
  rather than by widening the store.
- The Java `Execution_Intent_Processed` contract — the `(instruction_id, n)` duplicate/violation
  reading here is deliberately the same one, so the two guards cannot disagree about what a retry is.
- `docs/08_implementation/05-execution-core.md` — the T5 row and the Nautilus→Fluss row are updated
