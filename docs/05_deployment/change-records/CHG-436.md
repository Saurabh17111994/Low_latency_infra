# CHG-436 — the DDL-corpus smoke guard runs in the image builder too

- **Status:** complete — `make images` failed on the ddl-apply builder's shipped-engine test step because CHG-435's new guard could not resolve the DDL corpus there; the builder now COPYs the same corpus the runtime stage serves, so the guard runs in the image gate instead of being skipped.
- **Filed:** 2026-09-29
- **Source:** `make images` after CHG-435 (builder stage `#101 [ddl-apply builder 9/11]`, exit 2).

```text
change_record_id: CHG-436
scope: CHG-435 added DdlSmokeTwinSweepUnitTest.everyDdlColumnTypeHasASmokeDefaultMatchingTheSignature, which reads the committed DDL corpus to walk every column type through the smoke machinery. The ddl-apply Dockerfile's builder stage runs a shipped-engine test subset (P4-325) but only COPYs code/pom.xml, the module POMs and code/common — the DDL corpus enters only in the runtime stage (COPY code/01_platform/02_sql/ddl /app/code/01_platform/02_sql/ddl), so resolveDdlDir() threw "cannot locate 01_platform/02_sql/ddl" and `make images` died (eod-controller rides the same Dockerfile target). ## Notes
```

- **Why not `assumeTrue` (skip without the corpus):** a guard that skips wherever its input is missing silently loses coverage — the exact failure mode this wave exists to remove. The corpus is always in the build context (compose's context is the repo root), so the builder can and should carry it.
- **Layer order:** the COPY sits after the go-offline prefetch (unchanged) and before the shipped-engine test layer, so DDL edits invalidate exactly the test+package layers that must re-verify them.
