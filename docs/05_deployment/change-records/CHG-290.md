## Why

C2 was scoped as "wire the EOD scheduler to the lake path", and the scoping found there was no writer to
build: the copy is performed continuously by the Fluss tiering job, and `EOD_OFFLOAD=lake` only READS
evidence through `r2-list.sh`. What was missing was the wiring — a container has no `01_docker/.env` or
`secrets.env` for that script to read, and `eod-scheduler` had none of the R2 variables.

Wiring it made the path reachable for the first time, and the first real listing showed the path could
not have worked. `r2-list.sh` emits `key<TAB>size<TAB>LastModified` — its own header says so, and
`tests/test_lake_guard.py`'s `tsv()` helper calls that "the r2_list_lake TSV contract" — while
`parseSize` parsed everything after the first tab as the size, so it was handed
`50\t2026-09-21T16:22:40.399Z`. Every real listing threw `IllegalStateException`, which the controller
maps to FAILED_RETRYABLE: the day would retry forever and never reach VERIFIED. The Java fixtures were
two-column, so the tests passed while the live path could not. That is the case this record fixes.

## What changed

- `eod_controller.py` — when `EOD_OFFLOAD=lake` and the script's default config files are absent, stage
  `R2_ENV_FILE` / `R2_SECRETS_FILE` from the environment and the mounted secret files (mode 600, private
  directory, removed after the run, values never printed). A missing or unwritable value fails closed
  with a named reason instead of producing a config whose emptiness would read as "the tiering job is
  behind". A host run is untouched: the script keeps finding the repo's own files.
- `docker-stack.yml` — `eod-scheduler` gains `R2_LIST_SCRIPT`, `R2_LAKE_PREFIX`, the three required R2
  values, `FLUSS_DATABASE`, the two `*_FILE` credential paths, and the `aws_*` secret mounts.
  `EOD_OFFLOAD` still defaults to `none`.
- `R2LakeTieringEodOffloadExecutor.parseSize` — read the second column, not the whole tail.
- Docs: the plan's C2 bullet now says what the path is (wiring, not a writer), the lake runbook's EOD row
  covers the stack form, and the plan records the proof's findings.

## Evidence

`~/.p6v/evidence/c2-lake-20260921/` — a throwaway TLS MinIO on `127.0.0.1:9443` with a self-signed
certificate, a real-shaped lake fixture, `r2-list.sh` run against it (rc=0, SigV4 and TLS accepted, five
objects listed), and the executor's own `parseEvidence` run over that listing twice: before the fix it
threw on the timestamp column, after the fix it reported `dataObjects=2 dataBytes=300`. The container and
all key material were removed at the end; the transcript and the listing (fake keys only) remain.

## Open

The same proof measured a second disagreement, which is recorded in the plan and **not** resolved here:
the executor counts a manifest only when its key contains `event_day=<day>`, while `lake-guard.sh`,
`tiering-smoke.sh` and `test_lake_guard.py`'s stated contract all scope manifests by the table's
`metadata/` prefix with no day component. On a real-shaped listing with two `.avro` objects present the
count was 0, so `offload()` would still fail the day. That is a decision, not a bug fix, so it is left to
the operator with the evidence attached.
