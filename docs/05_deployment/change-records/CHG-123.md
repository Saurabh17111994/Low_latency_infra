## Problem

Two defects on the gateway's durable write path, both found by auditing rather
than by a report:

1. **A request had no bound of its own.** `BoundedRetry` (CHG-119) bounded each
   Fluss call — 3 attempts, 2 × 200ms backoff — but nothing bounded the
   *request*, and a single `/v1/events` makes many calls. Counted on the tree:
   **11 retried awaits + 1 retry-exempt Fills append**. Worst case
   `11 × 6400ms + 2000ms ≈ 72.4s` of hold, against a caller that gives up after
   **10s** (`code/02_services/04_executor/src/bridge/transport.rs:85`, the
   bridge read timeout; `/v1/events` POST at
   `code/02_services/04_executor/src/events.rs:149`). Measured, not assumed:
   HTTP dispatch is **serial** — two concurrent `/v1/events` cost 6019ms and
   3051ms, and `/healthz` goes 45ms → 5620ms behind one — so a hold that long
   also parks other requests' traffic.

2. **Every retry was load-bearing, at 100%.** The first write to a freshly
   created table must retry to succeed: `writeAudit` at the production 2000ms
   attempt bound measured min 2305ms / p50 2336ms / max 2392ms, with
   **attempt-1-ok 0/15, attempt-2-ok 15/15**. So on every cold table the retry
   that CHG-119 documented as insurance was in fact the only path to success —
   and the caller had no headroom if attempt 2 were slow too.

## Root cause (measured)

- **The post-CREATE window is real but shorter than CHG-119 assumed, and it is
  not leader election.** Leader election measures ~4ms. The cost is the
  post-election tiering task: `LogTieringTask.maybeUpdateCopiedOffset` →
  `remoteLog.getRemoteLogEndOffset()`, with lake tiering enabled in this stack
  (R2/S3), logged 0.4–1.1s apart per bucket and sequential. Quiesced, the first
  write after CREATE costs **2294–2383ms (p50 2336ms, 15/15 over the 2s
  bound)**; the next writes are 9–29ms. CHG-119's "~5s settle" was an inferred
  figure (see the correction appended to that record).
- **The window is time-based, not write-triggered.** Create six tables, wait
  5s, then write: 112–251ms. So moving the cost off the request path is
  possible at all — that is what made the pre-warm the prerequisite of the
  budget rather than an optimisation.
- **A failed read consumes nothing; a successful one consumes the window.**
  Probe: a lookup that fails costs ~100ms and leaves the window intact (3/8
  iterations), while a lookup that succeeds costs 507–510ms and the next write
  then costs 109–112ms. This is why the pre-warm's read is retried and why the
  pre-warm is not "handle warming only" (handles alone: 0/8 over 2s but p50
  1175ms — a residual one slow attempt away from the bound).

## Referenced IDs given a home

`P3-268`, `P3-269`, `P3-270` and `P3-476` are cited in code comments in
`common` and the gateway but appear **nowhere in `docs/`** (verified by
repo-wide search). This record is where they are pinned. What each means is
recoverable only from its uses, so that is what is recorded — not an
interpretation:

- **P3-268** — the idempotency justification attached to every retried Fluss
  await ("retry the X read/write; point read / KV upsert keyed by …"), and the
  `retry-exempt: P3-268` marker on the paths that must not be retried (the
  Fills append).
- **P3-269** — interrupt handling: an action interrupted mid-flight must have
  the interrupt flag restored before the failure propagates.
- **P3-270** — retry-predicate scope: the earlier check inspected only the
  direct cause of an `ExecutionException`, and every call site outside the
  ledger paths silently opted out of the policy.
- **P3-476** — failure context: the transient that prompted a retry is kept
  attached (suppressed) to the failure that finally surfaces.

## Known limits

- **The pre-warm test falsifies the feature, not the read step.** It asserts
  the production requirement (no request-path write over the caller's bound)
  and is satisfied by handle warming alone; it does not gate the row-free read.
  Removing that read would pass the test and re-add a ~1s p50 residual.
- **Startup is now a failure point.** A gateway whose projection tables are not
  readable, or whose deployed kind contradicts its call sites, exits instead of
  coming up. That is the intended trade (fail fast at deploy time rather than
  serve with a 100%-fired retry), and it is the limitation named in
  `compatibility_class`.
- **The dev window is not the production window.** These numbers come from a
  local stack tiering to R2/S3; the production discovery window may be longer
  and more variable. The budget bounds the hold regardless; the pre-warm's
  sufficiency at production latency is unverified.
- **Serial dispatch is unchanged.** The debt and the measurement are recorded at
  `GatewayHttpServer`'s executor javadoc. Amended 2026-09-13: the ordering
  analysis those notes called for has since been done, and it clears a
  same-process pool — the applier already fences one `postbackEventId` behind its
  own stripe lock, and the shed path rejects before it writes. What keeps dispatch
  serial is a decision and a test, not ordering: enabling a pool makes
  `MAX_PENDING_PROJECTION_RECORDS` reachable, so intake starts shedding (503 +
  `durableWrites(false)`) instead of queueing on the dispatcher thread, and the
  ledger's LWW still has no cross-process writer fence.
