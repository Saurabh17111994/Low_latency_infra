## Problem

The C2 main drill (tm-kill-full-load-20260901-234448) failed F4: 84 TENTATIVE
signal rows in the immutable `Signal_Candidates` LOG never received a
CONFIRM/CANCEL partner, though their windows closed >30 s before run end.
Pre-existing in every main drill (48 on 20260901-194149, 18 on 20260901-203706)
but masked by the G7c parity failure; exposed once CHG-120's RocksDB memory fix
closed G7c (34,816 pairs, 0 mismatches).

## Root cause (row-level evidence)

- Tentatives are decided on PARTIAL preview state and appended to the immutable
  LOG before the tracking Flink state (`pending` MapState) is checkpointed.
- A TM SIGKILL between the LOG write and the next checkpoint rolls the state
  back; the LOG row survives. All 84 orphans were emitted in exactly the
  24 s gap between the last checkpoint (epoch 1788286757) and the kill (1788286781).
- On replay the watermark advances in bursts; replayed previews carry
  FULL-window accumulators (150 ticks vs the 49-tick partial that fired the
  tentative), so `lookback.evaluate(open, close)` on the full window differs
  from the partial decision and the tentative is NOT re-derivable.
- The final candle then arrives with `pending == null` → the settle path is
  silent → the tentative dangles forever.

Verified: orphans = tentative-only groups with exactly ONE pre-kill row, zero
post-kill re-emits; non-orphan groups re-emitted and settled normally.

## Fix

Durable marker table + reconcile-on-final (same raw-client KV pattern as
`FlussFormingBarStateStore`):

1. New KV table `Signal_Tentative_Markers` (PK `candidate_id`, bucket key
   `candidate_id`, `kv.format-version=2`, TTL 2d — DDL
   `31_signal_tentative_markers.sql`, manifest regenerated, 29 tables).
2. `EarlySignalFunction.processElement1` upserts a marker BEFORE emitting the
   tentative LOG row (marker write survives the crash the state does not).
3. `processElement2` (final candle): when `pending == null`, looks the
   deterministic candidate_id up in the marker table. Marker present →
   settle CONFIRM/CANCEL by the FINAL-candle rule (strictly-before lookback
   semantics, identical to the normal settle) and clear the marker. Marker
   absent → no tentative existed → silent as before (no false signals).
4. Wiring: `FlussTentativeMarkerStore` (upsert/lookup/delete) +
   `FlussTentativeMarkerHook` (lazy task-side open, fail-closed if the table
   is configured but absent). Config `SIGNAL_TENTATIVE_MARKERS_TABLE`
   (default `Signal_Tentative_Markers`; empty string disables — legacy
   behavior for embedded tests).
5. Drill setup: `pipeline_ensure_tentative_markers_table` (create-if-absent,
   never drop — markers must survive phases) in tm-kill-full-load.sh.

## Semantics guarantees

- No false ENTRY: a reconcile row is emitted ONLY when a marker proves a
  tentative existed; the settle decision follows the final candle rule.
- Idempotent under replay: deterministic candidate_ids; marker upserts
  converge; double-settle impossible in the LOG sense (each settle row
  supersedes the same tentative id).
- Steady-state cost: one KV upsert per tentative (~68/s at 10 Hz drill) and
  one lookup per final with pending==null — negligible next to the forming-bar
  per-record KV writes already at 10k/s.
- Fallback: markers disabled (empty env) → exact pre-CHG-121 behavior.

## 2026-09-02 rework: synchronous → asynchronous marker I/O

**Failure that forced it** (drill tm-kill-full-load-20260902-005900): the
first main drill with synchronous markers recovered from the kill normally
(48 s, checkpoint 10 completed), then at ~t+140 s the job went RESTARTING
again: checkpoint 11's `triggerCheckpoint` RPC to the TM sat 30 s in queue
and timed out → Flink escalated to a global failure → 152 tasks restarted →
drill FAIL. No task exception — the task mailbox was starved.

**Root cause:** every marker op was a BLOCKING Fluss call on the task
thread (5 s ceiling). Worst offender: `exists()` ran once per final candle
with `pending==null` — during post-crash replay catch-up finals arrive in a
burst, so dozens of serialized 5 s-ceiling lookups froze the mailbox;
checkpoint barrier RPCs (dispatched through the same mailbox) starved.

**Rework:**

1. `TentativeMarkerHook` is now async (`CompletableFuture` API); the
   cluster hook runs all store ops on a single dedicated background thread.
   The task thread never blocks on Fluss I/O.
2. `EarlySignalFunction` stages work and drains completed futures on
   subsequent elements/250 ms processing-time timers of the same key:
   - **Tentative:** the marker write is submitted first; the LOG row,
     `pending` state, and settlement timer are applied only when the marker
     future completes (marker-durable-before-row ordering preserved — that
     ordering IS the F4 guarantee). A FAILED marker suppresses the tentative
     entirely: no row, no state → nothing to orphan, no false signal; the
     final-candle detection path is unaffected.
   - **Reconcile:** the settle rule is evaluated on the task thread at final
     arrival (correct lookback order); only the marker lookup and row
     emission are deferred. Lookup failure or absent marker → silent.
   - In-flight work is capped (4096 staged entries) as a replay backstop;
     over-cap drops degrade to pre-CHG-121 behavior (bounded by the same
     counter metric `compute.signals.early.marker_dropped`).
3. Bug fixed en route: `FlussTentativeMarkerStore.clear()` passed a java
   String where the PK schema expects BinaryString — every marker delete
   was a silent no-op (never caught by unit tests, which use an in-memory
   hook). Without this fix, settled markers would never be cleared and the
   2d TTL would be the only reclamation.
4. Smoke-mode change (user rule 2026-09-02): `C2_MODE=smoke` is now the
   compressed main drill — the real SIGKILL, recovery, new checkpoint,
   post-kill progress, and a new single-restart gate
   (`restarts-since-kill.txt`, G-TMK-10b, active in BOTH modes) — with
   short windows (~30 s warm-up / 60 s pre-kill / 120 s post-kill). The old
   no-kill smoke could not have caught this class of failure.

Residual risk (documented, accepted): a crash in the sub-second window
between "marker durable" and "LOG row emitted" can leave a marker whose
tentative row never existed; a later replayed final would then emit a
settle superseding a nonexistent candidate. This window existed in the
synchronous design too (between mark() and collect()); the async rework
widens it by at most one drain interval (~250 ms). The 2d TTL bounds the
stale-marker lifetime.

Validation (rework): EarlySignalFunctionTest 15/15 (+2: marker-failure
suppresses tentative; marker-before-row ordering gate); compute suite
429/429; smoke→main drill pending.

## 2026-09-02 second root cause: markerHook was transient (never shipped)

**Failure that found it** (drill tm-kill-full-load-20260902-014318): after
the async rework, the main drill still failed F4 — 34 orphans, G7c clean.
Probe evidence (F4Probe against the live tables): **zero markers in
`Signal_Tentative_Markers` for the entire run — all 34 orphans AND 30
sampled settled groups** — while 5,914 tentatives were emitted. In the async
design a tentative is emitted ONLY after its marker future completes, so
5,914 completed futures with an empty table is contradictory... unless the
markerless (`hook == null`) path ran.

**Root cause:** `EarlySignalFunction.markerHook` was declared
`private final transient`. Flink ships the function from the client to the
TaskManager by Java serialization — transient fields arrive **null**. So
every cluster run had markers silently disabled (the synchronous first
build AND the async rework); only unit tests — which construct the function
directly without serialization — ever exercised the marker paths.
Consequences: 34 orphans = the classic pre-CHG-121 kill-gap F4; and the
2026-09-02-005900 restart-storm diagnosis ("marker lookups stalled the
mailbox") was **wrong** — no marker I/O ran at all in that drill either
(that storm's cause remains unexplained; the new G-TMK-10b single-restart
gate now detects it deterministically if it recurs).

**Fix:**

1. `markerHook` is no longer transient; `TentativeMarkerHook` extends
   `Serializable`.
2. `FlussTentativeMarkerHook` implements `Serializable` with
   `serialVersionUID`; its task-side resources (`store`, `executor`) are
   `transient` — created in `open()` on the TaskManager, never on the
   client, never serialized.
3. Regression test `markerHookSurvivesJobGraphSerialization` (Java
   serialization round-trip, reflection assert on the shipped hook) — this
   is the test that would have caught both broken deployments.

Validation: EarlySignalFunctionTest 16/16; compute suite 430/430.
Cluster validation (markers actually written, F4=0) pending:
smoke → main drill.

## 2026-09-02 third fix: bounded retry for transient reconcile-lookup failures

Drill tm-kill-full-load-20260902-022843 (markers live for the first time):
G7c 0 mismatches, orphans 84→34→4. Probe: all 4 residual orphans have
markers PRESENT and uncleared, windows ~4.5 min AFTER the kill (normal
running, not the crash gap) — the reconcile lookup future failed (5 s
ceiling; the store created a fresh Lookuper per call at ~68 lookups/s) and
the drain gave up permanently on first failure.

Fix: (1) `FlussTentativeMarkerStore` reuses ONE Lookuper (single background
thread — race-free); (2) drain retries a failed reconcile lookup up to
3 attempts (re-arm the 250 ms drain timer), give-up only after
`MAX_SETTLE_ATTEMPTS` (still never a false signal). Regression test
`transientLookupFailureRetriesAndStillSettles` (2 failures → retry →
settle still emitted, marker cleared).

Validation: EarlySignalFunctionTest 17/17; compute suite 431/431.
Cluster: smoke → main drill pending.

## 2026-09-02 fourth fix: end-of-run backlog drain + marker hygiene

Drill tm-kill-full-load-20260902-030521 (retry fix in, markers live): G7c
0 mismatches but 31 orphans — probe: ALL markers present, ALL in the last
1-2 windows (34-64s before run end). Root cause: NOT dropped decisions.
Post-CHG-120 the pipeline sustains ~9,950/s against a 10,000/s feed — only
~0.5-3% drain margin, so the kill's ~500k-row replay backlog never drains
while the feed runs; the job is cancelled trailing the event clock by
~50s, and tentatives (decided 1s into a window) are in the LOG while their
finals are still in the backlog. F4's 30s grace misread the lag tail as
orphans.

Fixes:
1. Drill drain phase (G-TMK-10c, `drill_drain_backlog` in
   tm-kill-full-load.sh, both modes): after the post-kill phase, STOP the
   feed and poll the source counter until stable (3×5s polls,
   DRAIN_TIMEOUT_S=180). The drain gate itself is the guard — a pipeline
   that cannot drain fails the drill instead of producing a bogus F4
   verdict.
2. Marker hygiene bug found while probing: only the reconcile path cleared
   markers — the NORMAL settle, early-confirm, and late-drop cancel all
   left stale markers (2d TTL), and a stale marker + replayed final could
   emit a DUPLICATE settle. Every settle path now clears its marker
   (fire-and-forget). Guard: `everySettlePathClearsItsMarker` (normal
   settle clears; replayed final emits nothing; late-drop cancel clears).
3. Restart-storm root cause (drills 20260902-005900/025251): a catch-up
   checkpoint EXPIRED (barriers crawled through backpressured replay, 20s
   queue-sat) and the default tolerable-failed-checkpoints=0 escalated ONE
   expired checkpoint to a global failure (152 tasks restarted at t+75s).
   Drill submit now sets tolerable-failed-checkpoints=3 (drill-only;
   TOLERABLE_FAILED_CHECKPOINTS env): a transient catch-up miss no longer
   restarts the job; the next checkpoint must still complete (existing
   gate) and G7c still verifies end-state integrity. Bounded: 4
   consecutive failures still fail the job.

Validation: EarlySignalFunctionTest 18/18; compute suite 432/432.
Cluster: smoke → main drill pending.

## 2026-09-02 fifth fix: G7c/F4 trailing-window bound (checker artifact)

Drill tm-kill-full-load-20260902-034813 (drain phase live): recovery,
drain, and settlement all worked, but G7c FAILED with 1024 mismatches —
every one in the single last window (1788301710000), all "NO final
candle". Root cause: the drain phase stops the feed mid-window, so no
successor event ever advances the watermark past that window — it can
NEVER emit a candle or settle its tentatives. G7c's trailing cutoff used
wall-clock run_end (analysis runs minutes after run end, so wall clock is
always past the stall), demanding a candle for a window that provably
never closed. Previous runs passed only because the feed kept running
DURING the minutes-long analysis, pushing the watermark past trailing
windows.

Fix: bound trailing windows by the EVENT HORIZON (max event ts from the
raw recount), not wall clock. A window can only be demanded when the
watermark (horizon - 500) passed its end.
- G7c (`g7c_compare`): comparable windows now need `wend <= min(run_end -
  10s, horizon - 500)` — a window that never closed is excluded, a
  mid-run closed window with no candle STILL fires (real loss is not
  masked).
- F4 (`f4_orphan_check`, extracted for testability): a tentative is only
  an ORPHAN when the horizon is past its window end + 30s grace (window
  closed + final processed under drain, settle still missing). Trailing
  tentatives whose windows never closed are counted as unverifiable and
  excluded — this is also the correct retroactive explanation of the
  030521 "31 orphans" (0 of them were dropped decisions).

Guards (tests/test_holistic_g7_parity.py 15→23):
- G7c: unclosed-tail-window-not-demanded (034813 regression),
  closed-window-gap-still-fires-with-horizon (horizon must not mask real
  loss), horizon-governs-when-narrower-than-run-end.
- F4: settled-group-not-counted, trailing-tentative-is-unverifiable,
  never-closed-window-excluded, midrun-dropped-settle-still-fires,
  no-horizon-falls-back-to-wall-clock (pre-drill behavior preserved).

Validation: replayed the analyzer (G7_REUSE_RAW=1) over the EXACT failed
034813 evidence — G7c 33,792 compared / 0 mismatches (was 1024), F4 0
orphans, exit 0: the run's data was clean end-to-end; only the checker
was wrong. Python script tests 30/30 in the file.
