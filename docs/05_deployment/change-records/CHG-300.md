# CHG-300 — make the negative-path test waits configurable, defaults unchanged

## Summary

Three Python test files spend most of their wall clock waiting out production-sized
timeouts that the test is not actually asserting the size of. Each wait is now driven by
an environment variable whose default is the shipped value, so the harness can run the
same assertion against a shorter bound. Nothing about production behaviour changes: the
defaults are pinned by assertions added to two of the tests.

Measured on the same harness, same tree, same cluster (pytest `--durations`, all three
files together):

| metric | before | after |
|---|---:|---:|
| all 51 items in the three files (pytest view) | 277.68 s | **190.14 s** |
| the gate's unittest half (34 class tests) | 146.65 s | **74.00 s** |
| `test_fencing_not_enforced_while_the_holder_runs_is_a_failure` | 60.02 s | 12.04 s |
| `test_probe_hang_bounded` | 40.51 s | 26.11 s |
| `test_explicit_bootstrap_address_is_actually_dialled` | 30.05 s | under 6 s |
| verdict | 51 passed, 5 subtests passed | **51 passed, 5 subtests passed** |

The pass count is identical, no assertion was relaxed and no test was skipped: the waits
got shorter, the claims did not.

The two rows measure different collectors on purpose. These files mix unittest classes with
module-level test functions; pytest collects both, while the gate runs them in two halves
(`unittest discover` for the classes, `pytest -p no:unittest` for the functions). So the
gate's saving splits rather than landing in one place: 72.6 s in the unittest half (fencing
and dial are class methods) and 14.4 s in the pytest half (the probe-hang function). The
unittest half was measured separately by restoring the pre-edit files, running the gate's
own collector, and restoring the edits -- verified byte-identical afterwards.

## What each wait actually was

1. `eod-controller-test.sh` — the fencing guard waits out the controller's *lease window*,
   which was hardcoded as `--lease-ttl 60s` at both call sites. Now
   `--lease-ttl "${EOD_LEASE_TTL_S:-60}s"`, and the bounded wait that follows tracks the
   same value instead of a separate literal `60`.
2. `test_eod_controller_wave45.py` — the fake `eod` stub matched the literal string
   `--lease-ttl 60s`. That pattern had to widen to `--lease-ttl ` first, or shortening the
   window would have silently stopped the stub from recognising its own call. `_run_guards`
   then defaults `EOD_LEASE_TTL_S` to `5`.
3. `stage-capture.sh` — each of the three probes runs under a hardcoded `timeout 20`
   (the P6-560 bound). Now `timeout "${PROBE_TIMEOUT_S:-20}"`.
4. `test_stage_capture_wave38.py` — the hang test runs the same bound at 5s. The test's
   claim is that a hung probe is *bounded*, not that the bound is 20s.
5. `test_raw_table_admin_args.py` — the dial test allowed the admin CLI 30s, but it only
   asserts that the bootstrap address was dialled, and it records that on `accept()`, which
   is immediate. The 30s was the CLI's own retry loop; the allowance is now 5s.

## Why the defaults are safe

`test_probe_db_table_params` asserts `PROBE_TIMEOUT_S:-20` is still present in
`stage-capture.sh`, and `test_a_missed_window_is_retried_and_then_passes` asserts
`EOD_LEASE_TTL_S:-60` is still present in `eod-controller-test.sh`. A future edit that
changes a shipped default fails a test instead of passing quietly. The guards live inside
existing tests rather than as new ones, so the documented test counts do not move.

## Verification

- Same harness before and after: `pytest --durations=30` over the three files, 51 passed /
  5 subtests passed / rc 0 in both runs.
- `shellcheck` on both edited shell scripts: warning sets identical before and after
  (4 findings in `eod-controller-test.sh`, 3 in `stage-capture.sh`, all pre-existing).
- `bash -n` and `py_compile` clean on all five files.

## Rollback

Revert this commit. Every environment variable is optional and read with a default, so
reverting restores the hardcoded values with no state to unwind.
