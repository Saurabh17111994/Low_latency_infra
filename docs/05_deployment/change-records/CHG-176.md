## 1. A restart read as a decode-error spike

Run `20260915-215449` failed window 1 with `decode_errors delta=-4 != 0`. That
message is the bench's verdict for bad ticks arriving from the feed. The feed
was healthy: windows 2 and 3 measured 20,460 and 20,445 rows/s with a zero
delta, and the run's own journal carried the full 1024-token ack.

OpenObserve's series around the run shows what actually happened. The container
ran 16:24:58–16:28:32, and O2 serves the newest sample in its window:

```text
append_latency_ms_count   16:20:45     0.0   |  16:25:13  202006     <- new process
decode_errors             16:20:45     7.0   |  16:25:13       3     <- new process
```

The baseline read `append_latency_ms_count=0` **and** `decode_errors=7` — a pair
no live process can produce, since a process appending at 20k/s has a non-zero
append count by its first OTLP tick. Both values belonged to the DEAD process,
still newest because the live one had not flushed yet; the live process's first
point landed at 16:25:13, just after the baseline's fixed 15s settle. Window 1's
opening read then took the same stale pair (7), its closing read took the live
process's 3, and the difference was -4.

Two defects, one cause — the bench had no way to tell two processes apart:

1. The baseline settled for a **fixed** 15s and never verified the sample it
   read was the process it had just started. The settle was a guess about
   timing, and the guess was wrong by a hair.
2. The rows counter refused to measure across a process boundary (`append
   counter went backwards` -> skip), but the decode-error counter had no such
   guard. Only negative deltas slipped through, and they were reported as
   evidence of bad ticks.

## 2. What changed

**The baseline must be seen to advance.** Instead of sleeping once, the bench
polls `append_latency_ms_count` until it is **greater** than the previous read.
A stopped process cannot advance its own counter and the previous container is
stopped before the baseline runs, so an advance proves the sample is this
process's. Both counters ride in one OTLP payload on one tick, so a fresh append
sample proves the decode-error sample of the same moment is fresh too. The
budget is 6 polls x the existing `BENCH_BASELINE_SETTLE_S` (15s), so a correctly
started container still baselines in well under a minute and the tests stay
free (they set the settle to 0).

**Frozen and absent are distinguished.** A counter that never advances after the
full budget fails the run with `baseline counter frozen at <value>`; an O2 that
answers nothing at all keeps the existing `baseline unavailable`. They are
different faults — one is a dead emitter, the other a dead query path — and the
suite already pinned the second message.

**The decode-error counter got the guard its sibling had.** A negative delta
cannot be produced by a live counter, so it is now a skipped window naming the
stale sample, not a throughput verdict blaming the feed. `skip_window` calls
`fail`, so the run still exits non-zero: unmeasurable stays fail-closed.

## 4. Not covered

- The freshness poll reads one counter to judge the other. That is sound only
  because both ship in a single OTLP payload on one tick; if the emitter ever
  splits them across payloads, the coupling assumption breaks and the poll must
  read both.
- The guard detects a backwards counter. A restart that lands between two
  windows whose counters happen to be monotonically increasing across the
  boundary would still be measured — the deltas would simply be small, which
  the rate floor catches rather than the decode-error gate.
- The bench was run on this host's dev stack, not under production load.
