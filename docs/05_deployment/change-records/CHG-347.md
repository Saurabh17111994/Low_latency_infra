## What changed

| Site | Change |
|---|---|
| `FeatureRegistry` | Static table of `FeatureDef` lines; precomputed routing (tick ids, per-tf row ids, per-tf close update ids); RETIRED entries excluded everywhere. Javadoc carries the add/remove procedure. |
| `FeatureDef` / `FeatureStatus` / `FeatureCadence` | One registry line's shape; status makes removal a one-word edit that never deletes an id (DEC-057). |
| `FeatureComputer` + `LastPriceComputer` / `SmaComputer` / `RsiComputer` | O(1), allocation-free update contract; NaN-until-ready; SMA ring buffer and Wilder RSI. |
| `PerInstrumentFeatures` | `double[] tickLatest` + `double[feature][tf]` close values + per-slot computers; `onTick`/`onClosedCandle`/`snapshot`/`latest`. |
| `FeatureRegistryDump` | Prints the pin ledger (`id\tname`) or a full dump with status/cadence/timeframes. |
| Guard | `FeatureRegistry.validate` (contiguous ids, unique names, fails at class load) + `FeatureRegistryPinTest` (ledger must match exactly; failure message names the fix) + `AGENTS.md` hazard + the plan's procedure table. |

## Findings recorded (not fixed here)

- The first test run caught a real design bug: one `latest` slot per feature leaked a 1 m
  CLOSE value into the 3 m snapshot. State now stores CLOSE values per `(feature, timeframe)`;
  `closeValueNeverLeaksAcrossTimeframes` pins it.
- TICK features are timeframe-independent by construction (one computer per instrument). A
  future tick feature that needs per-timeframe semantics must declare cadence CLOSE or the
  state contract must gain a tf dimension deliberately.
- The pin ledger is exact-match, so adding a feature is: one registry line + one ledger line
  (two lines total, no production code beyond the registry). The trade-off is deliberate: a
  rename/renumber/delete can then never slip through silently.
