## 1. The forked probe was abandoned on every early exit (P6-562)

`stage-capture.sh` forks the host disk-latency probe before its sampling loop and
only `wait`s for it at the very end. Every fail-fast exit in between — the t+30
leg-liveness check, the t+65 bridge check, job-left-RUNNING, the TM-scrape death,
the post-run evidence verification — returned before that `wait`, so the probe
was reparented to init and kept writing into `$OUT_DIR` after the capture had
died. It burned iostat load for up to `DURATION_S + 30` seconds and raced the
next run's teardown.

The fix is a `cleanup` trap on EXIT/INT/TERM that TERMs the probe, waits 5s, then
KILLs it, plus one line at the tail clearing `IO_PROBE_PID` after the normal
`wait` so the EXIT trap cannot signal a recycled pid.

## 2. Two corrections to the finding's prescription, both measured

The audit prescribed `cleanup_io_probe() { kill "$IO_PROBE_PID"; wait ...; }`
with `trap cleanup_io_probe EXIT INT TERM`. Two things about that are wrong, and
each was measured rather than reasoned about:

**The signal exit codes.** `$?` inside an `INT`/`TERM` trap is not the signal.
A signal landing while bash waits on a child (`sleep`, `curl`) leaves `$? = 0`,
so a trap forwarding a bare `$?` reports **success** for a capture that was
killed. Verified directly: a `sleep 30` script signalled with TERM prints
`rc=0` from its trap. The signal traps therefore pass explicit `130`/`143`,
while the EXIT trap takes `$?` — there it is the real pending status, so a
fail-fast `exit 2` stays 2.

**Not on the normal path.** The existing tail deliberately waits the probe out,
with a comment saying never to kill mid-write: the probe runs `DURATION_S + 30`
seconds of iostat, so at the moment the sampling loop ends it is usually still
writing its tail samples. An unconditionally-killing trap would truncate exactly
the evidence the tail waits for. The test that pins this asserts the probe
reaches its own ending (its own verdict line in its log) and that the script's
exit stays 0 — a failed probe is a WARN, not a capture failure.

## 3. What the pair with P6-862 buys

Signalling one pid is sufficient only because the probe now reaps its own
reader and its own iostat from its own handler (P6-862, commit `4e816ed5`). With
only this caller-side trap the probe would die but its grandchild iostat would
not; with only P6-862 the fail-fast exits would still never signal the probe at
all. The map already flagged this coupling before either fix landed, and the
caller-side test now asserts the pair together: a fail-fast exit and both
signals must leave no probe process — and no iostat — behind.

## 4. Note on an unmapped defect seen but not fixed

The tail's `WARN — io-latency probe failed` line has no `>&2`, so it goes to
stdout while its siblings go to stderr. This predates the wave (present in the
pre-fix script at the same anchor) and is **not** mapped as a P6 finding. It was
left alone rather than folded in silently: the new test asserts the line on the
combined streams, and the location is noted here so it can be mapped on its own
terms.
