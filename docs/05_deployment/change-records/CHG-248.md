# CHG-248 — secrets bootstrap from one values file (`secrets-bootstrap.sh`)

## Why

Build-plan item 2 of `docs/08_implementation/09-production-swarm.md` and the §6.1 gap row of
`docs/05_deployment/PROD_VM_PROVISIONING.md` recorded the same blocker: the stack declares nine
`external: true` secrets, while `docs/05_deployment/06-swarm-secrets.md` created five
ingestion-era names — two of which (`arrow_app_id`, `arrow_user_id`) are **not** secrets at all —
and there was no single values file, so S6 was a hand-typed sequence with no verification.

Four facts were settled by reading and measurement on 2026-09-19, and one of them contradicted the
guide:

1. **`o2_auth_basic` must be bare base64.** `otel-collector-config.swarm.yaml` (three reads at
   lines 139, 154, 170) writes `Authorization: "Basic ${file:/run/secrets/o2_auth_basic}"` — the
   scheme comes from the config, so the secret holds only `base64("<user>:<password>")`. The §9 S6
   text and CHG-243-era notes claimed the opposite ("the complete header value"); a prefixed secret
   would have authenticated as `Basic Basic …` and returned 401 with nothing useful in the log.
2. **`docker secret create` stores byte-exact values.** Measured live: a 6-byte stdin produced a
   secret whose mounted content is 6 bytes (`od -c` shows no trailing newline). A stray newline
   here is the classic silent auth failure for base64 and TOTP values, so the negative is worth
   recording.
3. **The documented command idiom leaked the value.** `docker secret create name <(printf '%s'
   "<value>")` runs `printf` in a subshell with the secret as an argument — visible to `ps` — so
   the document's own "never pass secrets on a command line visible to `ps`" rule was defeated by
   its example. `printf` with the value already in a variable is a shell builtin: no child process
   and no argument list.
4. **`arrow_token` is stale.** The stack declares and mounts nine secrets; none is `arrow_token`,
   and the live bridge rejects a non-blank `ARROW_TOKEN` outright (removed 2026-08-24). A Swarm
   secret of that name exists on the development node, so a reader could reasonably believe it is
   still required.

## What changed

- **`code/01_platform/04_scripts/secrets-bootstrap.sh` (new)** — creates all nine secrets in one
  pass. Reads the five operator-held values from a git-ignored values file (keys matched
  case-insensitively), generates the four internal or derivable ones on the host, and derives
  `o2_auth_basic` from the O2 user and whichever `o2_password` is in play so the pair cannot drift.
  A supplied value always wins over generation, so a hand rotation is not fought. Every value
  reaches `docker secret create <name> -` on stdin. It validates the whole set before creating
  anything (exit 3), refuses when a name already exists because Swarm values are immutable (exit 4,
  with the rotation path printed), and refuses to run outside a Swarm manager (exit 2).
  `--values-file /dev/stdin` lets the file arrive over SSH, so no secret value lands on a VM's disk.
  Modes: `--values-file FILE [--o2-user USER]`, `--check`, `--print-names`, `--self-check`.
- **`code/01_platform/04_scripts/tests/test_15_secrets_bootstrap.py` (new)** — 14 offline tests
  driven through a fake `docker` on `PATH` that records every argv and stdin body. They assert the
  script's name list equals the stack's `secrets:` block (read with `yaml.safe_load`, so the stack
  file stays authoritative); that all nine values travel on stdin and **never** in an argument; that
  `o2_auth_basic` is bare base64 with no `Basic ` prefix; that a missing value creates nothing; that
  an existing name refuses the whole run; that a supplied value beats generation; that no value is
  ever printed; that the values file works as a pipe; and that a non-manager is refused.
- **`docs/05_deployment/06-swarm-secrets.md`** — rewritten (106 → 78 lines). It now lists the nine
  authoritative names with the services that mount them, documents the one-command path, records the
  leaking idiom above, states the `o2_auth_basic` format, and separates what is *not* a secret. The
  stale stack-file and entrypoint excerpts were removed rather than corrected: a duplicated copy of
  the stack is what rotted this document in the first place, and the stack file is authoritative.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — §9 S6 rewritten around the script and the
  corrected `o2_auth_basic` format, with the SSH-stdin invocation so the values file never reaches a
  VM's disk; the §7 S6 exit criterion is now the script's own `--check`; the §6.1 "secret bootstrap"
  gap row is removed (resolved) and the §6.1/§6.2 image rows now state the residual gap (the push
  path has never run against a real VM1) instead of claiming nothing exists.
- **`docs/08_implementation/09-production-swarm.md`** — build-plan item 2 records the script, the
  corrected format and the test that now owns the parity claim.

## Limitation

The `compatibility_class` value follows the guide rather than the code. The nine names, the formats
and the refusal behaviours are verified offline, but the **create path itself was not rehearsed end
to end on a real swarm**: the development node already holds all nine secrets from an earlier
session, and deleting pre-existing state to make room for a test is not this change's business. What
*was* verified live on the development node: `--check` reports all nine present and exits 0, the
immutability refusal (exit 4) fires against real pre-existing names, and a throwaway secret proved
byte-exact storage before being removed. The create loop therefore rests on the fake-docker tests
plus those live checks, not on a full real creation. The SSH-stdin workflow was exercised with a
pipe, not over SSH, because no VM exists yet.
