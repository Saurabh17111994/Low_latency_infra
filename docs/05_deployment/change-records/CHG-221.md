# CHG-221 — a deterministic KV fixture for the census legs

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** todo #21 — the certification-hygiene plan's B1 item, deferred as B0+ when that
  batch closed earlier the same day.

## What happened

`SignalLatencyContractTests`' three live census legs cannot assert the property they are named
for. `FlussSignalLatency.checkAgainstServer` refuses to print a census whose read disagrees with
`Admin.getTableStats`, and on the live tables it always disagrees: `Execution_Intent` is a LOG
table, so the probe's read is a *paged log read* returning a bucket's first stored segment
(measured: `census read 23 rows but Fluss reports 27`). The legs therefore assert the refusal
contract and skip — honest, but the agreement itself went unverified. CHG-217 made that visible;
this record makes it tested.

## The change

`ProbeFixtureSeeder.java` (new, in `code/01_platform/04_scripts/fluss-probes/`) creates two
scratch KV tables and drops them again:

```
zz_probe_fixture_intent   fx-a fx-b fx-c fx-d fx-e   (5 rows)
zz_probe_fixture_signal   fx-a fx-b fx-x             (3 rows)
orphans = fx-c fx-d fx-e                             (3 — not 0, not 5)
```

- **KV, not LOG**, is the whole point: `checkAgainstServer` labels a primary-key table a "KV
  snapshot" — one exact read — so `read == expected` is reachable there and nowhere on the live
  LOG tables.
- **Shape**: one STRING column as the primary key, so the bucket key is the whole PK (the
  single-field case the pinned COMPAT-FLUSS-005 matrix documents as writable by the raw client),
  plus `table.kv.format-version=2`, explicit `table.datalake.format=iceberg`, and tiering OFF so
  a scratch table cannot write to the lake.
- **It waits**: after the upserts the seeder polls `Admin.getTableStats` until it agrees with what
  it wrote (bounded 20 s) and throws otherwise. That count is what the probe compares against, so
  a lagging count would produce a refusal — or a flaky green. A count that never converges is its
  own finding, not test flakiness.
- **No leak**: `create` drops both tables first, and the legs register the drop as cleanup BEFORE
  creating, so a half-created fixture is still removed. Verified after a full run: the live
  catalog is back at 33 tables.
- Two **new** legs in `SignalLatencyContractTests` assert the pass path (exact `rows`,
  `distinct_candidates`, `duplicate_rows=0`, no refusal) and the exact orphan set (3 distinct ids,
  none of them present on the signal side). The three live legs keep their refusal assertions
  untouched: this adds coverage, it does not rewrite reviewed assertions.

## Verification

- Probe suite against the live stack: `Ran 35 tests in 94.990s` → `OK (skipped=5)` — was 33 tests
  with the same 5 skips. The two new legs never skip while the stack is up; the live refusal legs
  still do.
- Rehearsal, every command measured: seeder `create` → `fixture: intent_table=zz_probe_fixture_intent
  intent_rows=5 signal_table=zz_probe_fixture_signal signal_rows=3 orphan_intents=3`, rc=0 ·
  `FlussSignalLatency intents zz_probe_fixture_intent` → `table=zz_probe_fixture_intent rows=5
  distinct_candidates=5 duplicate_rows=0`, rc=0 — **no refusal, the agreement reached** ·
  `orphans zz_probe_fixture_intent zz_probe_fixture_signal` → `intent_candidates=5
  signal_candidates=3 orphan_intents=3` with `orphan=fx-c`, `orphan=fx-d`, `orphan=fx-e`, rc=0 ·
  `drop` → rc=0 · catalog back at 33.
- `javac` against the ingestion classpath: clean.
- One bug found while wiring, kept in the code as a comment: the first parse assumed adjacent
  counts, but the seeder's line interleaves `signal_table=` between `intent_rows=` and
  `signal_rows=`, so a successful create read as "the seeder said nothing".
