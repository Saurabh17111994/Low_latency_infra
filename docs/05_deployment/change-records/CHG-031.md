## What happened

Following CHG-030 (which scoped the integration tests to the window-driven rule), the
forming-bar placeholder's own emission profile was investigated: the deterministic flat P6
feed produced ~17 forming-bar candidates per token (≈34 LOG rows) in the replay test and 14
per token in the RocksDB test — despite the fire-once-per-window semantics. This record
documents the root cause and pins the deterministic invariants in unit tests.

## Root cause — the drift feed IS a breakout to the mirrored rule

- Every P6 window `w` carries a **+50 paise high tick** (prices `10000+w`, `10050+w`,
  `9950+w`, `10000+w`) and prices drift **+1/window**.
- The placeholder compares the live forming close against the max HIGH of the
  `FORMING_LOOKBACK_CANDLES` (default 5) strictly-prior completed candles —
  `maxHigh ≈ 10050+(w−1)`.
- At the +50 tick, the forming close `10050+w > maxHigh` → breakout ✓, bullish ✓,
  trend ✓ → **every warm window qualifies once** (w5..w22 = 18 per token).
- **Fire-once per (instrument, window) IS honored** — each fire is a distinct window; there
  are no duplicate-window fires.
- **Which windows actually fire is scheduling-dependent:** the lookback ring fills from the
  completed-candle stream racing the tick stream at the `connect`; a window's +50 tick is its
  only qualifying instant, so if the ring was not yet warm at that instant the window is
  skipped permanently. w5 usually loses (the ring fills exactly then); heavier scheduling
  (RocksDB + checkpoints) loses more → the observed 17 vs 14 per token, and the stall test's
  non-deterministic 3–5.

## The fix — document (deliberately not a detector redesign)

The detector is an explicit placeholder (the real strategy replaces the rule without pipeline
changes; candidates are observational — no consumer). A deterministic redesign (evaluate only
at candle close) would contradict the handoff's core requirement (REQ-FC-007: Business Logic
sees the live forming state before the candle closes). So:

1. **Javadoc corrected** in `FormingBarDetectionFunction` — the "exists for deterministic
   integration testing" claim was an overclaim: fire-once is deterministic, WHICH windows fire
   is not (warm-up race). The profile is now documented at the source.
2. **+2 unit tests** pin the deterministic invariants through the operator harness:
   `driftingFeedFiresOncePerWarmWindow` (every warm window on a drifting feed fires exactly
   once; fire-once holds across updates and windows) and
   `qualifyingTickBeforeWarmUpIsLostForThatWindow` (a window whose qualifying tick arrived
   before the ring was full never fires, even after the ring completes).
3. **Dossier note** in `04-signal-job.md` §Forming-bar and candidate interface — the emission
   profile, the ~14–18-of-18 range, and the rule that integration tests must scope to the
   window-driven rule (CHG-030) rather than pin forming-bar counts.
