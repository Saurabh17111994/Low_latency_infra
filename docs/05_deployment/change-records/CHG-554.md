# CHG-554 — ConfigGuard's source walk no longer reads build outputs (flaky-guard fix)

- **Status:** implemented (robustness fix; the guard's verdict is unchanged for a stable tree).
- **Filed:** 2026-10-06
- **Source:** an unrelated red test found while gating a release commit.
  `ConfigGuardTest.ignoredKeysDoNotBlockStartup` failed during `make test` with
  `java.io.UncheckedIOException: java.nio.file.NoSuchFileException:
  code/common/target/surefire-reports/TEST-com.trading.common.config.ContainerMemoryGuardTest.xml`
  raised from `ConfigGuard.readCorpus`'s `Files.walk(...).toList()`. The guard walks the whole
  `code/` tree while Maven is rewriting `target/surefire-reports` under the very JVM that is
  verifying it, and the walk's own attribute read on a just-deleted report file aborts the walk.
  It passes in isolation, which is what makes it a flake rather than a signal.

## What changed

`readCorpus` now filters out any path containing a `target` segment before `Files.walk` is
consumed. The corpus is defined as *source* (`*.java` under `code/`), and a key can never be read
only from `target/`: its files are generated from `src/`, so the filter cannot turn a real read into
a missed one (the false-positive direction that would refuse startup). It also removes the walk's
own reason to touch a directory another process is deleting from.

## What deliberately did NOT change

* **No change to the guard's verdict logic** — `keyReadInCode`, the declarations-file exclusion and
  `warnUnverifiable` (packaged runs) are untouched.
* **No swallow of read errors.** The fix narrows what is walked; it does not catch and ignore
  `IOException`, so a genuinely unreadable source tree still fails loudly.
