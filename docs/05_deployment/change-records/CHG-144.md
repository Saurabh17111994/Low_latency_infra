# CHG-144 — The R2 lake scripts stop trusting their own copies

- **Status:** recorded — all sixteen wave-7 findings verified and fixed in two commits
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 7 ("R2 lake migration and restore"):
  P6-013, P6-014, P6-158, P6-159, P6-160, P6-161, P6-164, P6-165, P6-166, P6-490, P6-491,
  P6-492, P6-493, P6-497, P6-498, P6-768

## What happened

Both scripts were re-read line by line before anything was edited, and all sixteen findings held.
These are the two scripts an operator runs during an incident, and neither had a test — so the wave
wrote the tests first pieces of evidence for each guard. Read the two CRITICAL items as one story:
the migration could lose objects, and the restore could be quietly wrong about what a day contains.

**The migration deleted the source before it knew the copy landed (`P6-013`).** A 2xx PUT was treated
as proof. A truncated body (proxy, disk, interrupted request) or a same-key substitution therefore
deleted the only good copy — in a migration whose whole point is that the source prefix is the
backup. Each object is now GET → temp file → PUT with the SHA-256/MD5 digests computed up front →
`HEAD` → **only then** DELETE, and the HEAD must report the byte count that was copied plus (when the
backend publishes a single-PUT ETag) the MD5 of exactly those bytes. A mismatch prints
`REFUSING TO DELETE`, leaves both copies in place and exits non-zero. The failure mode is now "the
migration stopped", never "the data is gone".

**The restore reported success for days it did not have (`P6-014`, `P6-164`, `P6-166`, `P6-498`).**
`DAY` went straight into the glob, so `2026-08-31` matched nothing, `COPY` created an empty parquet
at `OUT` and the script exited 0 — over the top of the previous good restore, which was the only
copy of that day outside R2. `OUT` was equally unchecked, and the SQL plus both secrets were passed
as a `duckdb -c` argument, i.e. visible in `ps`/`/proc/<pid>/cmdline` to every user on the box.
Now: a 0600 temp file on stdin carries the SQL and secrets; `DAY` must match `yyyyMMdd` **and** be a
real calendar date (`date -d` rejects 20260230); `OUT` must be a plain filename; the export writes
to `OUT.tmp.<pid>` and renames only after both counts come back non-zero. A refused run writes
nothing and exits 2.

**A restore of a day with deletions returned the deleted rows (`P6-165`).** `read_parquet` does not
read Iceberg delete files, and `union_by_name := true` hid schema drift by filling mismatched columns
with NULLs — both silent, both wrong in the direction that matters for a compliance export. The run
now counts `*delete*.parquet` in the day folder first and aborts if any exist, and `union_by_name`
is gone, so a schema that does not match the day path fails loudly instead of producing a
plausible-looking table.

**Everything else was the same class of "assume it worked".** Credentials came from argv in both
scripts (`P6-158`); the endpoint was split on `"//"` so a missing scheme raised `IndexError` and a
trailing path silently corrupted the host (`P6-491`, `P6-497`); the prefix was compared as a raw
string, so `table` also listed `table_backup/` (`P6-160`); whole objects were read into memory
(`P6-159`); the first throttled object aborted a multi-hour migration (`P6-161`); a list response was
unpacked as if it always had exactly one page (`P6-493`); the `Content-Type` was dropped
(`P6-492`); and config parsing pattern-matched the file per call instead of tolerating missing keys,
CRLF and quotes (`P6-490`). Retries are bounded (5 attempts, exponential backoff from 0.5 s, only
408/429/5xx and transport errors) and the status check now runs *inside* the retry — the wave's own
test caught the first version of that helper checking outside it, which would have re-introduced
`P6-161` under a comment claiming to fix it.

## Judgement calls (review these)

1. **A day with Iceberg delete files now fails instead of exporting approximate rows.** Read-only
   exports cannot honour deletes without `iceberg_scan`, and a compliance restore that silently
   includes deleted rows is worse than one that refuses. The upgrade path is written into
   `docs/06_operations/07-lake-archive-ops.md`: use `r2-query.sh` with `iceberg_scan` for those days.
   This is the one place where the wave removes a capability rather than tightening it.
2. **The stricter behaviour is a deliberate change to the operator interface, not just a fix.** Exit
   2 now means "refused before DuckDB ran, nothing read or written" and exit 1 "DuckDB ran and the
   result is not trustworthy"; a zero-row day and a day with delete files used to exit 0. No code
   parses these exit codes (references are documentation only: `COMMANDS.md`, `01-runbooks.md`,
   `07-lake-archive-ops.md`), but a cron job or runbook that treats non-zero as noise would need to
   be updated — hence `COMPATIBLE_WITH_LIMITATION` rather than `COMPATIBLE`.
3. **Multipart ETags are not compared.** `HEAD` verification compares the MD5 only when the ETag is
   32 hex characters with no `-`; a multipart object's ETag is a digest-of-digests, so only the byte
   count is checked there. The byte count catches truncation, which is the realistic failure; an
   equal-length substitution of a multipart object is beyond what an ETag can show. Stated here
   rather than fixed with a re-download comparison (which would double the migration's R2 traffic).
4. **The mover has no resume ledger; it re-lists instead.** An interrupted migration is resumed by
   running the same command: already-moved objects are simply listed again on the destination side.
   This keeps the script stateless, and the failure it guards against (a second run double-deleting)
   cannot happen because a moved source object is not in the listing.
5. **A hard kill can leave the 0600 SQL temp file and a `OUT.tmp.<pid>` behind.** Both are removed by
   an `EXIT` trap on every normal failure path, including the refusal paths; `OUT.tmp.<pid>` is
   overwritten by a later run of the same day and never mistaken for a restore, because the rename is
   the only thing that creates `OUT`. The secrets file is mode 0600 in the operator's `TMPDIR`.

## Verification

1. **Red before green, and the red run was sandboxed.** The two new suites were first run against the
   previous revisions copied into a scratch directory next to a fixture `01_docker/.env` +
   `secrets.env` and a stub `bin/duckdb`, so the old `r2-restore.sh` (which reads the repo's real
   config path) never touched the real credentials file and never reached the network: **25 red
   results across 17 tests** — 10 for the mover (no HEAD before DELETE, no overlap/equal-prefix
   guard, no retry on a 503, credentials visible in the process command line) and 15 for the restore
   (no stdin/SQL-file path, no day or output validation, no delete-file or zero-row abort, no
   endpoint normalization). The scratch directory was removed afterwards; both repo scripts hash-check
   identical to the copies taken before the run (sha256 prefixes `25d26988c6a1f0be` /
   `9ee02e35a13bdfcd`).
2. **Green on the fixed code: 17 tests, 0 failures** — `test_r2_move_prefix.py` 8 (verification
   order GET/PUT/HEAD/DELETE, short destination and substituted MD5 both refused with the source
   intact, equal/overlapping prefixes refused with zero requests, prefix normalization not catching a
   sibling, 503 retried, incomplete config and schemeless endpoint refused) and
   `test_r2_restore_guardrails.py` 9 (SQL on stdin from a 0600 file with an escaped secret and no
   secret in `/proc/self/cmdline`, endpoint scheme+path stripping, incomplete config refused, four
   bad days and four bad output paths refused before DuckDB starts, delete files abort, zero rows do
   not clobber an existing restore, silence from DuckDB is a failure, and the success path renames
   into place with the counts printed).
3. **The whole helper suite: 488 tests, OK** (was 471 before the wave: +17, exactly the new tests).
4. **`full_audit.sh` on the real tree: exit 0, 213 PASS / 0 FAIL** (197 on the wave-6 tip).
5. **Both scripts stay gate-clean:** `bash -n` plus `shellcheck -S warning` with no findings, which
   is what the Monday gate's step 1/19 requires of every script under `04_scripts/`.
6. **Not run in this wave:** the Monday gate itself; no live R2 call (the mock server is local and
   the tests assert they made no outbound request); the ingestion/compute suites (no module code
   changed). `r2-query.sh` and `r2-list.sh` were not in this wave and are unchanged.
