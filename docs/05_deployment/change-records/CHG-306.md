## Applied (Flink half), after an incident and its recovery

`flink-jobmanager` and `flink-taskmanager` were recreated on
`ghcr.io/saurabh17111994/trading-flink-runtime:prod@sha256:70b04617bea29ea927d4e4daec4366854af7ed497a6a14ca2fa08bfd487d96b3`
(both `running`, 0 restarts, 0 ERROR lines at startup), chosen post-market so the gap cost no live ticks.

**The recreate dropped the live job.** This stack is a non-HA session cluster, so a JobManager restart
does not recover its jobs. Evidence, in order:

- the JobManager log: `SessionDispatcherLeaderProcess - Recover all persisted job graphs ... Successfully
  recovered 0 persisted job graphs`;
- `/jobs/overview` returned zero jobs;
- the JobManager's resolved config (`/jobmanager/config`) contains **no** `high-availability.*` key, and
  its blob store is container-local (`Created BLOB server storage directory /tmp/jm_816744da`);
- this is by design for the current stage: `DEC-033` bootstraps production on one VM **non-HA**, and
  `DEC-032` plus `docker-stack.yml:687-691` / `:797-798` place Flink JM HA (`high-availability.type:
  zookeeper`, quorum `zookeeper-1..3:2181`, `high-availability.storageDir` = encrypted S3) in the
  three-VM Swarm stage, which is not this host.

The expectation that HA would cover the restart was mine and it was wrong: `docker-compose.yml` carries
zero `high-availability` keys, so there was never a recovery path to rely on.

**Recovery, using the site's own submitter.** The job was restored with the documented one-shot `compute`
launcher (`docker compose up -d --no-deps --no-build compute`), which is the same path that submitted it
in the first place. It is safe by construction: `COMPUTE_SUBMIT_SIGNAL != 1` so SignalJob is not
submitted (no `raw_table_1` split-brain), `SAFETY_MANIFEST_TOKENS` is unset so SafetyHaltJob is skipped as
before, `restart: "no"` so nothing loops, and it skips a job whose Flink name is already RUNNING
("idempotent restart, no duplicate submit"). A pre-check confirmed zero RUNNING jobs before it ran.

Verified end state: exactly one RUNNING job, `Babysitter Positions observer`
(`f0906075c438590343c0aa1846da4aa0`), checkpoint 1 completed about 57 s after start, no SignalJob, no
duplicate.

Two observations left open, both pre-existing rather than introduced by the recreate:

- the launcher's readiness gate reports `FATAL ... did not complete a checkpoint within timeout (last
  completed=0)` because its timeout is shorter than the job's first checkpoint interval; it continues as
  a nonfatal warning and the checkpoint does land. Judge readiness from `/jobs/<jid>/checkpoints`, not
  from that line.
- the TaskManager logged one ERROR from the Fluss client at job start:
  `DefaultSecurityTokenManager - Failed to obtain security token`, cause
  `SecurityTokenException: Failed to get file access security token: Region is not set.` It is
  **config-driven and understood**, not a symptom of this cutover: Fluss 1.0 constructs an S3
  delegation-token provider on the client read path (`FlussConnection.getOrCreateRemoteFileDownloader`
  -> `TableScan.createLogScanner` -> `FlinkSourceSplitReader`) because the table's `remote.data.dir`
  is `s3://...`; that provider asserts a region (`S3DelegationTokenProvider.REGION_KEY =
  "fs.s3a.region"`, `checkArgument(region != null, "Region is not set.")`). The servers set the
  counterpart keys (`s3.endpoint.region` and `datalake.iceberg.iceberg.hadoop.fs.s3a.endpoint.region`,
  both `${AWS_REGION:-auto}`), and compose already notes the R2 plugin maps these "into fs.s3a.* for
  the client" -- but `fs.s3a.region` appears nowhere in the repo. The manager logs the ERROR, then
  WARNs `Failed to update tokens, will try again in 3600000 ms` and retries hourly; the servers
  logged zero token traffic, so nothing rejected the client: it is a local precondition check.
    **(Superseded:** the trigger is the client read path, but the provider that asserts the region
    is constructed server-side in the coordinator/tablet JVM -- see the correction at the end.)**  The job runs and checkpoints normally.
  **Untested consequence:** a *remote (tiered)* log segment is the path that needs the file-access
  token, and no job here has read one yet.
  **Fix (applied 2026-09-23, server-side -- see the correction at the end):** the provider that
  asserts the region is constructed in the coordinator/tablet JVM, not in the job, so the five
  `fs.s3a.*` keys were mirrored into the Fluss services in `docker-compose.yml`. No Java change
  and no jar rebuild was needed.

**Lesson recorded in the runbook:** for a non-HA stack, a JobManager/TaskManager image swap is a job
restart. The sequence is stop the job, recreate, then re-submit via the launcher, and verify the job
list. Recreating and expecting the job to return is the one variant with no recovery path.

## Correction (later the same evening): the token path is server-side, and the fix is applied

The observation above was right about the symptom and wrong about the location. Read from source:

- `DefaultSecurityTokenProvider.obtainSecurityToken()` calls
  `adminReadOnlyGateway.getFileSystemSecurityToken(new GetFileSystemSecurityTokenRequest())` -- the
  client **asks the server** for a file-access token; and
- the error text the job logged is wrapped server-side at `RpcServiceBase:496`
  (`new SecurityTokenException("Failed to get file access security token: " + e.getMessage(), e)`).

So the `S3DelegationTokenProvider` that asserts `fs.s3a.region` is constructed in the **coordinator and
tablet JVMs**. The compose keys that mattered are theirs, not the job's -- which is why the proposed
one-line job-side fix would have done nothing.

**Applied.** Five keys were mirrored into both Fluss services in `docker-compose.yml`, immediately after
each service's `s3.connection.ssl.enabled: true` anchor:

| key | value |
| --- | --- |
| `fs.s3a.region` | `${AWS_REGION:-auto}` |
| `fs.s3a.endpoint` | `${R2_ENDPOINT:?set R2_ENDPOINT for tiering}` |
| `fs.s3a.path.style.access` | `true` |
| `fs.s3a.access.key` | `$${env.AWS_ACCESS_KEY_ID}` |
| `fs.s3a.secret.key` | `$${env.AWS_SECRET_ACCESS_KEY}` |

`docker compose config -q` rc=0; the pair was recreated (`--no-deps`, 0 restarts) and the tablet log
shows the keys loading (`Loading configuration property: fs.s3a.endpoint=https:`). Two new WARNs of the
form `Value of 'fs.s3a.access.key' looks like a config provider` appear; they are the client-side
heuristic for the `env.` form and are cosmetic -- the values resolve.

**Measured outcome at the next window.** The region assertion is satisfied: no new `Region is not set`.
The mint now proceeds one step further and fails at the **STS** call --
`DefaultSecurityTokenManager - Failed to obtain security token.` /
`SecurityTokenException: Failed to get file access security token: Received an UnknownHostException when
attempting to interact with a...`. R2 has no STS endpoint, so the delegation-token path cannot complete
on this deployment: that was the predicted ceiling, and it is where the path now stops. It is
**non-fatal**: the manager retries hourly (`will try again in 3600000 ms`) and the job runs and
checkpoints normally.

**What this leaves open.** The read side is the part that needs a token, and the proof is still pending:
`code/01_platform/04_scripts/tiering-remote-read-verify.sh` writes a probe table whose segments tier to
R2 with no local copy, then reads it back. Either outcome is informative -- a pass means the Fluss
client does not need the token for remote segments (the practical question), and a credential failure
means it does, which points at client-side credentials. The alternatives there are a jar rebuild (the
Babysitter's compute jar predates `5feea717` by 13 days, so that path drags in unrelated drift) or a
documented defer, which is defensible today because dev tiering is off (`FLUSS_REMOTE_LOG_TASK_INTERVAL=0s`)
and nothing currently needs a remote read.

**Also applied in the same window:** the Babysitter was restarted onto the corrected pair (cancel via
REST, then the launcher). Cancel -> launcher -> RUNNING took about 10 s, the first checkpoint landed
about 60 s later, one job, no duplicate submission -- new jid `330837aba126c306218dfee4d8f941aa`,
checkpoint 1 completed.

## Correction (later): what "tiering verified" covers, and the read proof's status

Two claims needed sharpening before T6.3 can rest on them.

**Datalake and remote-log tiering are different mechanisms with different destinations.** The
`tiering-1.0-verify.sh` evidence is *datalake*: tables with `table.datalake.enabled` land in the lake
warehouse (`S3_WAREHOUSE_PATH`, i.e. `lake-scratch-*/fluss/<table>/`). Remote *log* tiering is
separate: it ships rolled log segments to `remote.data.dir` (compose: `s3://<R2_BUCKET>/remote-data`)
as `remote-data/log/<db>/<table>-<tableId>/<bucket>/metadata/*.manifest`.

**Remote-log tiering does work here.** A full-bucket listing on 2026-09-23 found 193 objects under
`remote-data/log/default/` from six long-lived catalog tables (`suspected_discontinuities-19` 79,
`Signal_Candidates_current-22` 55, `Execution_Intent-26` 25, `Safety_Halt_Requests-18` 23,
`Signal_Candidates-7065` 10, `candle_closed-30` 1); the newest is 2026-09-22T08:52Z, which is
expected because dev tiering is off (`FLUSS_REMOTE_LOG_TASK_INTERVAL=0s`) outside a proof window.

**No purpose-created probe table has ever tiered.** Zero objects for any `rr_probe_*` (three
attempts) and zero for the write proof's `t63_tiered_*`. The live tables above set no tiering options
at all, so their eligibility comes from server config alone; the probe set
`table.log.tiered.local-segments=1` + `table.log.local-ttl=1s` (both legal) and wrote ~0.7 MB against
a 1 MB `log.segment.file-size`, so the leading explanation is that its segment never rolled and there
was nothing to ship. Not measured: the probe's segment size, and the tablet's roll/tier lines
(discarded when the tablet was recreated).

**The remote read remains unproven.** The proof aborted at its own phase-3 gate with "tiering did not
run" -- and that gate was wrong: it polled `r2_list_lake`, scoped to the lake warehouse prefix, so it
could not see objects written under `remote-data/`. It would have aborted even if tiering had worked.
Fixed in `tiering-remote-read-verify.sh`: the gate derives the prefix from `remote.data.dir` and
aborts rather than proceeding on a templated value (regression test
`tests/test_tiering_read_proof_prefix.py`), the payload is ~7.8 MB so a roll is expected, the tablet
log is captured into the run window before the revert, and the lister's stderr is kept. Re-run
deferred until after T5.1.
