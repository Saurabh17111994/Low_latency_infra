## Notes

- **Why a window, not an unbounded set:** fills are append-only evidence at the venue; a restart
  can replay recent updates, but an unbounded per-order id set grows all day for no benefit. 64
  recent ids cover every replay episode the protocol produces; memory stays bounded per order.
- **Why dedup runs before payload validation:** a replay is not new evidence — a replayed fill
  with a damaged payload must be absorbed, not halt the gate.
- **Keyed per `ClientOrderId`**, independent of which leg placed the order; the window applies to
  any fill the client books.
- **The empty-id path is not a normal one:** the Go bridge sets `postback_event_id` from the
  postback fingerprint on every publishable report, and a fingerprint failure publishes
  `OutcomeUnknown` + `postback_event_id_unavailable` instead (`postback.go:311-324`). The counter
  therefore watches the rollback window, not the live shape.
- **Verification follow-up (test-only):** the H1-2/H1-4 tests asserted an exact-zero delta on the
  process-global `order_rejected` counter, which parallel tests increment — a race, not a code
  defect. Both now tap the node's execution-event stream and assert zero `OrderRejected` events
  for their own order; the restored-defect mutation turns the H1-2 assertion red.
