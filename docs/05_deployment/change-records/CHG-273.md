## Why

The audit finding behind issue #54: **in the four-VM topology, VM1–VM3 wrote logs nobody collected.**

The stack declared `otel-collector` as `mode: global` **and** `constraints: [node.labels.observability == true]`.
Those contradict, and the engine resolves them in favour of the constraint — one task, on the observability
node (VM4) — while a reader sees "global" and assumes four. Two of the four `filelog` receivers read paths
that are **node-local** by construction: the host's `/var/log` bind mount and the named volumes
(`ingestion-logs`, `flink-logs`, `fluss-logs`), which Swarm keeps on the node that writes them. So the
single collector read its own copies of every volume, and the directories the other three nodes wrote to
were read by nobody. An empty directory is not an error in a `filelog` receiver — it emits nothing, no
stream is created, and every deploy stays green. `node-exporter` and `cadvisor` had already been corrected
to `mode: global` with no constraint (CHG-265); the collector kept the same defect one layer up.

## What changed

The collector is split by **transport**, because the two requirements point in opposite directions:

| Service | Placement | Owns | Why |
| --- | --- | --- | --- |
| `otel-collector` | `replicas: 1`, `observability == true` | `otlp` receivers + `prometheus` scrapes | it scrapes `tasks.node-exporter` / `tasks.cadvisor` — **every** node's agent. On four nodes each host metric would be stored four times and every `rate()` and `sum()` in a panel would be wrong |
| `otel-collector-logs` | `mode: global`, no constraint | the four `filelog` receivers | a file exists on exactly one node, so the reader must run on every node |

- The service **name** `otel-collector` is unchanged, so `OTEL_COLLECTOR_HOST=otel-collector:4318`
  (the `SignalJobConfig` and `IngestionService` default, plus the scripts that pass it explicitly) keeps
  working. The file half exposes **no** OTLP receiver by design: emitters keep targeting the singleton, and
  shipping logs to a per-node service would scatter one service's records across nodes.
- `hostname: "{{.Node.Hostname}}"` plus a `resource/node` processor (`host.name` from `HOSTNAME`) is what
  tells four nodes' lines apart inside one stream — the same mechanism `node-exporter` uses for `nodename`.
- The singleton drops the three volume mounts, the `/var/log` bind and `user: "0:4"`; the file half takes
  them. One file, one reader — and no root-owned process that does not need to be one.
- Dev and swarm stay one contract: the two `otel-collector-logs*` files differ only in the credential
  source (`${env:O2_AUTH_BASIC}` vs `${file:/run/secrets/o2_auth_basic}`), and a test asserts exactly that.

## Measured while verifying (not part of the change)

- **The memory limiter refuses data when an exporter cannot reach OpenObserve** — measured in the file
  half (740 MiB, `data refused due to high memory usage`, while `openobserve` failed DNS because a
  half-created dev container had no network), and **also at HEAD**: the rehearsal collector, running the
  pre-split single config, logged 88 identical refusals in three hours. So the refusal is pre-existing
  behaviour of the `memory_limiter` (512 MiB, unchanged by this record), not a regression — and it is the
  mechanism that turns a broken export path into a visible error instead of silent loss.
- **The dev compose OpenObserve and the rehearsal Swarm OpenObserve both publish `:5080`**, so only one
  of the two stacks can run its observability at a time on this machine. Restoring the rehearsal stack
  required stopping the dev OpenObserve; no configuration was changed to achieve it.

## Not verified

- **The four-VM behaviour.** No VMs exist. What is proven is the placement and config contract, and the
  live dev-stack behaviour on one node — not that VM1–VM3 logs reach OpenObserve in the four-VM topology.
- **Per-node attribution of the file half's own metrics.** The file half sends its self-metrics
  (`otelcol_fileconsumer_*`, `otelcol_exporter_*`) to the singleton's OTLP endpoint, as the original
  config did, so on four nodes they are attributed to the singleton's host. The log records themselves
  carry `host.name`, which is what the requirement needed; telling *which node's* file consumer is
  refusing records is not yet possible.
- **A production deploy.** The stack is not deployed anywhere; `docker stack config` compiles it, and the
  rehearsal stack is the only Swarm this has run on.
