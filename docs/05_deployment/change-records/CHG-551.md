## What changed

`code/01_platform/01_docker/docker-compose.yml`, the `fluss-tablet` `FLUSS_PROPERTIES` block:

```yaml
metrics.reporters: ${FLUSS_METRICS_REPORTERS:-}
metrics.reporter.prometheus.port: ${FLUSS_METRICS_PROMETHEUS_PORT:-9249}
```

## Why the tablet is worth an instrument at all

`org.apache.fluss.rpc.netty.server.RequestsMetrics$Metrics` (verified in
`fluss-server-1.0.0.jar`) registers per-request histograms — `requestQueueTimeMs`,
`requestProcessTimeMs`, `responseSendTimeMs`, `totalTimeMs`, `requestBytes` — plus `requestsPerSecond`,
`errorsPerSecond` and, per request-processor, `requestQueueSize`. The image already ships
`fluss-metrics-prometheus-1.0.0.jar` under `/opt/fluss/plugins/prometheus`, and its reporter exports
Fluss histograms as Prometheus **summaries** with `quantile` labels (0.5/0.75/0.95/0.98/0.99/0.999),
so a single scrape gives the server-side split of `request="produceLog"` — the append RPC.

This matters because the tablet's 900 s JFR trace (2026-10-06) could only produce negative evidence:
no blocking, no lock contention (`jdk.JavaMonitorEnter` 53 events) and an empty request queue
(`RequestChannel.pollRequest` was *idle-waiting*). Absence of blocking is not a latency number; the
histogram is.

## Verification

* `Configuration.get(ConfigOptions.METRICS_REPORTERS)` with `""` -> `[]` (no exception) — the default
  path cannot change tablet behaviour.
* Recreated the tablet with `FLUSS_METRICS_REPORTERS=prometheus`:
  `/opt/fluss/conf/server.yaml:180 metrics.reporters: prometheus`, `:181 metrics.reporter.prometheus.port: 9249`;
  the container's `/metrics` answered with 3 605 lines.
* The measurement arm that spends this instrument (fleet-only, 3 × ~1 600 rows/s) is recorded in
  `logs/tracker-14/20261006-tablet-metrics/` (arm script, per-scrape samples, parser).

## What deliberately did NOT change

* **No reporter by default.** Production stays as certified; enabling the tablet reporter is an
  operator decision (it opens one container-local HTTP port, 9249).
* **No otel-collector scrape entry.** The collector currently scrapes only
  `flink-jobmanager:9249` / `flink-taskmanager:9249`. Adding the tablet there is a separate,
  production-facing decision (and the ZK/coordinator would presumably follow); this change only makes
  the numbers reachable.
* **No `make gate` step.**
