## Finding 1 — adopting the changelog on a restore needs CLAIM

**Symptom (drill A, first run):** the job restored from the CT-2 retained checkpoint, reached
RUNNING, then failed 4/4 checkpoint triggers:

```text
java.lang.IllegalStateException: Configured state backend
(org.apache.flink.state.changelog.ChangelogStateBackend@...) does not support enforcing a
full snapshot. If you are restoring in NO_CLAIM mode, please consider choosing CLAIM mode.
```

**Mechanism:** a restore in `NO_CLAIM` mode does not take ownership of the restored state
files, so the checkpoint coordinator schedules a `FULL_CHECKPOINT` on the next trigger;
`StreamTask.checkForcedFullSnapshotSupport` raises because the changelog backend reports
`supportsNoClaimRestoreMode() == false`. The controlling option is
`StateRecoveryOptions.RESTORE_MODE` (key `execution.state-recovery.claim-mode`, deprecated
alias `execution.savepoint-restore-mode`; its `DEFAULT` constant is `NO_CLAIM`). CLAIM takes
ownership of the restored state, so no forced full snapshot is scheduled.

**Fix:** inside the changelog block, when a recovery path is present:

```java
if (config.stateRecoveryPath() != null && !config.stateRecoveryPath().isBlank()) {
    flinkConfig.set(StateRecoveryOptions.RESTORE_MODE, RecoveryClaimMode.CLAIM);
}
```

The disable direction (flag off) keeps the default mode — RocksDB supports the forced full
snapshot there (drill B proves it).

## Finding 2 — changelog storage selection is TaskManager-level; job-level keys are no-ops

**Symptom (drill A):** the deployed job carried `state.changelog.storage=filesystem`, while the
TaskManager logged `Creating a changelog storage with name 'memory'`.

**Mechanism (verified in the pinned 2.2.1 bytecode, not inferred):** `TaskExecutor` builds the
per-job changelog storage as
`changelogStoragesManager.stateChangelogStorageForJob(jobId, taskManagerConfiguration.getConfiguration(), ...)`
— the storage name and the `dstl.dfs.base-path` are read from the **TaskManager cluster
configuration**. The job configuration controls only whether the backend is wrapped
(`state.changelog.enabled=true`, which is why the backend came up). A job-level
`state.changelog.storage` is silently ignored.

**Fix:** the job no longer writes the storage keys at all (enabled + CLAIM only). The
TaskManager-configured storage is the deployment's responsibility:

- The stock `flink:2.2.1` image does **not** ship the `flink-dstl-dfs` plugin
  (`FsStateChangelogStorageFactory` lives in `flink-dstl-dfs-2.2.1.jar`, absent from the
  image's `lib/` and `plugins/`) — so filesystem storage needs that plugin on the TaskManager
  `plugins/` classpath plus `state.changelog.storage: filesystem` and
  `state.changelog.dstl.dfs.base-path` in the TaskManager configuration.
- The dev trial therefore runs the changelog on **TaskManager memory** (`memory` storage,
  inline in the checkpoint metadata — verified: the ON checkpoint `_metadata` carries the
  changelog bytes). The latency mechanism under test (snapshot the changelog instead of
  pausing on the synchronous RocksDB snapshot) is storage-independent.
- **Production adoption prerequisite (recorded, not done):** ship the plugin and set the
  TaskManager keys; then re-verify the drills on that storage.

**Drill A final-jar note (documented, not a code defect):** after checkpoint 26 the job's next
checkpoint expired (30 s) and the failure threshold failed the job. Root cause: the anchor
`b0ac9e19/chk-25` came from a **pre-purge table epoch** — its restored Fluss source split
offsets no longer matched `raw_table_1` (the profiler purges/rewrites the table between runs),
so a checkpoint stalled. The first adoption anchor (`chk-95`) was from the current epoch and
ran clean for 56 checkpoints. Operational rule: adoption anchors must be taken from the
current table epoch (in production that is exactly the running job's last savepoint/retained
checkpoint). The final-jar restore + first checkpoint is valid evidence for the CLAIM fix; the
subsequent death is anchor-epoch incoherence, unrelated to the changelog.

Also observed and recorded: a claimed anchor's state files are consumed/cleaned as the claiming
job checkpoints (retrying an adoption drill from the same old checkpoint is not possible;
`chk-95` failed to re-restore on a later attempt for exactly this reason).
