## 1. The false all-clear

`orphans` printed `orphan_intents=0` on a stack where it was provably wrong. The
default table was chosen by `"intents".equals(mode) ? "Execution_Intent" :
"Signal_Candidates"`, so every mode except `intents` defaulted to the signal
table; that value was handed to `reportOrphans` as the *intent* path, while the
signal side was hardcoded to the same `Signal_Candidates` literal. The join was
therefore `Signal_Candidates` minus `Signal_Candidates`, which is empty for any
input. Measured live, on a stack holding 11 intents and 25 signals:

```text
pre-fix   java ... FlussSignalLatency orphans          -> orphan_intents=0
post-fix  java ... FlussSignalLatency orphans Execution_Intent Signal_Candidates
          -> intent_candidates=11 signal_candidates=25 orphan_intents=2
```

Two genuine orphans existed the whole time. The failure mode is the dangerous
one for a diagnostic: a phantom-intent check that always reports "no phantoms"
and exits 0 looks exactly like a healthy system.

The fix requires both tables on the command line and refuses a request that
names only one, refuses the same table twice, and prints both table names
alongside the counts so a zero can be read as an answer rather than as a
default. The unused `intentTable` parameter (P6-733) disappeared with it.

## 2. A poll timeout read as end-of-bucket (P6-088, P6-379)

`pollBatch` is time-bounded and its two failure shapes are different. Read from
`LimitBatchScanner` (the scanner `.limit()` selects) in fluss-client 0.9.x:

```java
if (endOfInput) { return null; }            // end of input
} catch (TimeoutException e) {
    return CloseableIterator.emptyIterator();   // timeout — NOT end of input
```

The probe broke on `batch == null || !batch.hasNext()`, so one contended poll
ended the bucket and the census under-reported with no warning. `FlussRuleCounter`
had already been fixed for exactly this (P6-377, `EMPTY_POLLS_TO_DRAIN = 3`); the
probe had four copies of the old loop. They are now one `drainBucket` helper that
breaks only on `null`, requires three consecutive empty polls, and uses a short
500ms timeout for the two confirmation polls so a multi-bucket census does not
pay full timeouts for proof.

The same helper refuses to be silently truncated by the per-bucket
`.limit(1_000_000_000)` cap (P6-379): on reaching it, the run fails with the cap
named rather than printing a confident total.

**Deviation from the audit's prescribed fix, recorded deliberately.** P6-376
removed that limit from `FlussRuleCounter` to make its census uncapped. That
approach cannot work here: `TableScan.createBatchScanner(TableBucket)` throws
`UnsupportedOperationException` when the limit is null, so a limit is mandatory
— verified live, see §4. The probe therefore keeps the cap and detects
saturation. The audit's `P6-379` fix (a TODO comment) and `P6-087`/`P6-089`
(HdrHistogram/TDigest) were not applied as written; see §3.

## 3. Memory: bound and refuse, not OOM (P6-087, P6-089)

The census retains one entry per kept latency and per distinct id, so it cannot
be both exact and unbounded on a multi-billion-row LOG table. Rather than add a
streaming-estimator dependency, the probe keeps exact counts to
`MAX_RETAINED` (5,000,000) and then fails with a message naming the limit and
saying to aggregate in Flink/Fluss SQL. An OOM kill loses the entire answer; a
refusal is diagnosable. This is a documented limitation, not a fix: the probe is
a dev census tool, and exact cardinality at that scale belongs in a parallel
engine.

`P6-734`'s full sort of the orphan set was replaced with a bounded max-heap, and
a truncated listing now prints `orphan_truncated=` so 20 rows cannot read as the
whole set.

## 4. Evidence, and one defect this wave did not fix

- **Red legs discriminate.** `W34_PRE_FIX_SRC=<HEAD~ source> pytest -k RedLeg`
  passes; pointed at the fixed source the same two tests fail with
  `IllegalArgumentException: unknown mode`. A red leg that passes either way
  would prove nothing.
- **The drain pins fail on the pre-fix source.** All four `SignalLatencyDrainPins`
  tests were run against the pre-fix file and failed, then passed again after
  restoring — they are pins, not decoration. They remain non-discriminating for
  the live defect: a 25-row table cannot provoke a mid-bucket timeout.
- **`FlussRuleCounter` is broken, and the map says it is done.** While verifying
  the `limit == null` behaviour above, the sibling probe failed on a live table:
  `UnsupportedOperationException: Currently, BatchScanner is only available when
  limit is set. Table: default.Signal_Candidates`. P6-376 removed the limit it
  needs. Its wave-13 test runs the probe against a dead port and only asserts a
  non-zero exit, which this exception also satisfies, so nothing caught it; the
  test's own docstring calls itself non-discriminating. The file is ticked 3/3
  (P6-376, P6-377, P6-378). This is out of wave 34's scope and is **reported, not
  fixed** — the fix is the same shape as `drainBucket`.
- **`--add-opens` was never a probe concern**, because no test ran a probe that
  decodes rows: `run_probe` spawns `java -cp` with no flag, and without
  `--add-opens=java.base/java.nio=ALL-UNNAMED` the Fluss client's shaded Arrow
  dies in `MemoryUtil`. The flag is now passed once in `run_probe` (17 other
  sites in the repo pass it, including `docker-entrypoint.sh`).
