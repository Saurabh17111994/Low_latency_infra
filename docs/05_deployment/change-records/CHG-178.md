## 1. The defect: a total that was a lower bound

Wave 13 removed the per-bucket `.limit(1_000_000_000)` from `FlussRuleCounter`
because `createBatchScanner` rejects a null limit. That turned every census into
a throw, and the cap was restored to stop the throw. The cap was never the
problem. `Replica.limitLogScan -> LogTablet.read -> LocalLog.read` returns as
soon as one segment yields data (`LocalLog:356-425` exits on the first non-null
`fetchDataInfo` with `maxLength=Integer.MAX_VALUE`), and
`LimitBatchScanner.pollBatch` does a single RPC and then sets `endOfInput`. So a
batch scan of a LOG table returns the first stored **segment** of a bucket, and
no limit value makes it a census.

The same read path is why a tiered segment made the number *smaller* rather than
failing: the client logs the fetch failure and then skips those rows. A probe
without an S3 filesystem plugin and without S3 client settings simply cannot
reach anything that rolled off local disk, and says nothing about it.

## 2. The fix, and the one part that is not free

| Question | Answer, and how it was settled |
|---|---|
| Where does the total come from? | The server. `Admin.getTableStats().getRowCount()` — `highWatermark - logStartOffset()`, and `logStartOffset` already accounts for retention and for what tiering moved out |
| Is the read still a read? | Yes, and any disagreement with the server count fails loudly (`IllegalStateException`, exit 1) with no census printed. The pairing is the point: a read alone cannot tell a drained table from an unreadable one |
| How are LOG tables read? | The offset-paged `LogScanner`, which advances by offset and so is genuinely uncapped |
| Why not for KV tables? | A KV log is a changelog carrying `UPDATE_BEFORE`/`UPDATE_AFTER` and deletes, so offset-reading double-counts. The snapshot stays on `BatchScanner`, capped, and reaching the cap fails loudly. `-Dfluss.probe.bucket.row.limit=N` makes that failure reachable in dev |
| When is a bucket done? | After three consecutive empty polls, not one (P6-377): `pollBatch` is time-bounded, so one contended poll would end a bucket early |

**How the S3 settings reach the probe is not a free choice.** Passing them as
Fluss client options does not work: `FlussConnection` forwards only
`client.fs.`-prefixed keys, while the shipped plugin matches `s3.`, `s3a.` and
`fs.s3a.` and never strips the prefix — measured against
`fluss-fs-s3-0.9.1-incubating.jar`, where `client.fs.s3.*` is ignored and the
read fails `NoAwsCredentialsException`, while the same values in `core-site.xml`
resolve to `S3FileSystem` and read the object. Hadoop picks the file up off the
classpath, so the gate puts the conf dir and the plugin jars on the census JVM's
classpath. Credentials stay out of the repository: `core-site.xml` holds
`${env.NAME}` references fed from the git-ignored `01_docker/.env` and
`secrets.env` through `r2_var`, and an unset variable leaves a literal
placeholder that fails loudly instead of falling back to a default.

## 4. Not covered

- **The delegated-download path is still broken and is not fixable by config.**
  The server-side delegation-token route logs "Region is not set" because R2
  exposes no STS service: it rejects `GetSessionToken` while answering S3 list
  normally. Reported in `21a78cbe`, not fixed.
- **No live proof of a tiered read.** `21a78cbe`'s own negative control — a
  bogus endpoint still returning 46 — shows the wired path is exercised without
  depending on a live tiered read. Every segment on R2 also exists on the local
  volume, so a local read and a tiered read are indistinguishable on this
  stack; see CHG-180's correction note for the full measurement.
- **A tiered read from a Flink task manager** was out of scope here and is
  CHG-180's subject on the dev side. On the production side the Fluss servers
  still write `remote.data.dir` to a node-local volume — recorded in CHG-180's
  residual risk, not fixed in either record.
- **No live differential for the KV row cap or `MAX_RETAINED` at scale**; both
  need a table far larger than the dev stack's 48 rows.
