# CHG-214 — B4's intent append gets the drill's measured write budget

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** gate step 9 (`make drill-live`) red on
  `B4HaltedIntentConsumeDeferE2ETest` in the first certifying run after CHG-213.
  Root-caused from that run's own `write-await` lines and its `NotLeader` count.

## What happened

CHG-213 made the class wait for its fresh tables' replica placement and keep its
scratch DB when a write cannot be resolved. In the next certifying run the class
failed — but on a budget, not on the invariant it guards:

```
org.opentest4j.AssertionFailedError:
[the intent append must resolve; when it cannot, the scratch DB is kept instead of
 being dropped under a pending write]  expected: RESOLVED  but was: UNRESOLVED
```

The guard itself behaved correctly: it kept the DB and printed
`b4-halted: KEPT scratch DB b4_halted_…`, and the storm stayed at **0** lines
where the same class had produced 115,251 of them before CHG-213. Nothing was
dropped under a pending write.

**The budget was the problem, and the same log proves it.** Other writes in that
run hit their first wait and then succeeded:

```
write-await: LOG append to …smoke_twin_raw_table_1 did not resolve within 30s — waiting once more   (RESOLVED)
write-await: LOG append to …smoke_twin_Signal_Candidates did not resolve within 30s — waiting once more   (RESOLVED)
write-await: intent append to b4_halted_… did not resolve within 20s — waiting once more
write-await: intent append to b4_halted_… unresolved after 40s
write-await: matrix cell upsert unresolved after 40s
```

`NotLeader` appears **1,542** times in that log, against 0 storm lines and 0
`TableNotExistException`. While a fresh replica finds its leader the cluster
answers `NotLeader`, so a write to a table created seconds earlier takes 20-60 s
to ack. The two writes that stalled longest were the two given the 20 s budget;
the ones given 30 s resolved on their second wait.

One boundary this run drew clearly: **a readiness probe that reads is not proof a
table will accept a write.** The lookup-based probe reported `ready after 1
attempt(s)` for `b4_halted_…`, and the append to that same table still could not
be acked inside 40 s. The lookup path was satisfied while the write path was not.

## What changed

`code/02_services/06_execution_gateway/src/test/java/com/trading/execution/gateway/B4HaltedIntentConsumeDeferE2ETest.java`,
two timing budgets and their rationale:

- `TIMEOUT` 20 s → **45 s**: the append is awaited through
  `com.trading.common.schema.fluss.WriteAwait`, which allows exactly one more wait
  for the SAME future, so the write now gets up to 90 s of real waiting.
- the test's `assertTimeoutPreemptively` envelope 120 s → **420 s**, so the envelope
  sits *above* the worst legitimate case (fixture readiness 240 s + a write needing
  both waits + the reader's poll) instead of below it.

**No assertion changed.** A write that never resolves still fails the run; it just
no longer fails at 40 s while the cluster is merely slow.
