# CHG-268 — the gate checks the deploy template, so a bad deploy fails here and not on the VMs

## Why

CHG-267 added a preflight that can only be useful if something runs it. Nothing did: the invocation
lives in the runbook, and a runbook line is not a check. A template that drifts away from the stack
file — a new `${VAR}` the stack interpolates with no default and no entry in `.env.example`, an image
pointing at a loopback registry — would be discovered at provision time on the VMs.

Two facts decided the design:

- **`.env` is not tracked** (only `.env.example` is). A gate step that read `.env` would pass on this
  workstation and fail on a fresh clone, which is the wrong shape for the certificate.
- **The ops test suites were already in the gate.** Step 3 has run pytest with `-p no:unittest` since
  CHG-219 precisely because the function-style files under `tests/` are invisible to `unittest`
  discovery. So `test_11`…`test_14` need no wiring at all; what was missing was the *script* call.

## What changed

- **`code/01_platform/04_scripts/run-monday-gates.sh`** — step 3 runs
  `deploy_preflight.py --env-file …/01_docker/.env.example --expect dev`, log kept, and the step fails
  unless the log's summary line is exactly `0 failure(s)` (an empty pass is not evidence). No
  `--check-lake`: a gate step that needs the network fails for the wrong reason.
- **`code/01_platform/04_scripts/tests/test_14_gate_wiring.py`** (new) — four guard tests over the
  gate script itself, including that its 19 step headers stay 1..19 in order.
- **`docs/commands/COMMANDS.md`** — the step-3 sentence names the new sub-check.

## Measured

The preflight against the **tracked** template, dev expectation:

```text
$ python3 code/01_platform/04_scripts/deploy_preflight.py \
      --env-file code/01_platform/01_docker/.env.example --expect dev
[PASS] all 41 variable(s) the stack interpolates resolve to a non-empty value
[INFO] --expect dev: the production-only value checks are skipped
[PASS] every image a node would pull is pinned: 0 digest-pinned, 6 upstream image(s) left to their author (tag or digest)
[INFO] the lake is not contacted without --check-lake (a signed LIST needs the real credentials)
0 failure(s)
```

That `0 failure(s)` is why this can be a gate step: it is a template-versus-stack check that currently
holds, so a red result means something changed, not that the gate was born failing.

**The subset run happens after this commit, not before it** — the gate's own drift preflight refuses a
dirty tree, measured while preparing this change:

```text
$ bash code/01_platform/04_scripts/run-monday-gates.sh --steps 3
=== [preflight] environment drift (tree, compose convergence, catalog, stack) ===
FAIL: preflight — environment drift, this run cannot certify anything
SUBSET RESULT: FAIL
```

That refusal is correct behaviour and is the reason a `--steps` run cannot double as preparation
evidence for the very change it is testing.

## Limitation

**A subset run never certifies.** `--steps 3` says the step runs and passes; it says nothing about
steps it did not run, and the SUMMARY ends in `SUBSET RESULT` for exactly that reason. The 19-step
certificate is a separate, later run.

**Dev mode is the only mode the gate can use.** The production rules (checkpoint URI, endpoint scheme,
required values) need a real production environment, so the gate checks shape and coherence, not
production values — that remains `deploy_preflight.py --expect production` in the runbook's S4.

**The guard tests pin structure, not behaviour.** They would not notice a step-3 sub-check that runs
but checks nothing; only the `0 failure(s)` requirement and the preflight's own tests cover that.
