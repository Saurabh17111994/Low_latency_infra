## What changed

1. **`ContextView.slice(token, tf, newestWindowStart, count)`** — a run of consecutive
   windows, newest first; cached entries are served, missing ones are scheduled exactly
   like `candle(...)` (single flight, in-flight cap, cooldown all unchanged). Bounded by
   `MAX_SLICE = 64`: beyond that the approved path is scalars, not raw slices
   (decision #4).
2. **`ContextView.warmUp(token, tf, newestWindowStart, count)`** — schedules the same run
   without reading it back (the optional warm-up on first touch / at a close), counted
   once per call as `compute.context.warmups`; the windows show up in the provider's
   normal fetch/miss counters.
3. **Retained scalars** — `ContextView.retainScalar(token, name, value)` /
   `hasScalar` / `scalar` back onto a fixed **4096-entry** access-ordered LRU in the
   provider (`compute.context.scalar.writes`, `compute.context.scalar.evictions`, gauge
   `compute.context.scalars`). Contract in the Javadoc: a retained value MUST be a pure
   function of immutable closed-candle data (deterministic re-derivation after a
   restore); the provider stores, it never derives. 4096 × ~96 B ≈ 0.4 MB, far inside
   the decision-#4 8 MB/subtask budget.
4. **`ContextProbeStrategy`** — first-touch usage now exercises both mechanisms in the
   live path: on the first ready decision it retains `prevClosePaise` (derived from the
   fetched candle) and warms up the two windows behind the fetched one.
