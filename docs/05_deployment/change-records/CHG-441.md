## What was wrong

At the pinned 10 s checkpoint cadence, every completed checkpoint costs each stateful subtask a
400–600 ms synchronous state snapshot (`sy`) measured with the CT-1 phase capture. About 4–6 % of
ticks arrive during that window and take the pause as latency, pushing p99 of
`compute.latency.tick_to_strategy` to ~440 ms — far over the 100 ms SLO — while the calm path
stays at p99 60–67 ms. State size is not the driver (≤ 8 MB total, ≤ 4.6 KB per checkpoint
persisted); the cost is the flush mechanics on every checkpoint.

## What changed

- **`SignalJobConfig`** gains the `changelogStateBackend` component, read from
  `CHANGELOG_STATE_BACKEND` (strict `true`/`false`, default **false** — opt-in rollout flag).
- **`SignalJob.applyRuntimeOptions`** translates the flag when on:
  `state.changelog.enabled=true`, `state.changelog.storage=filesystem`,
  `state.changelog.dstl.dfs.base-path=<CHECKPOINT_DIR>/changelog`. Fail-closed preconditions:
  `STATE_BACKEND=rocksdb` (heap has no changelog to snapshot) and `MAX_CONCURRENT_CHECKPOINTS=1`
  (Flink limits the changelog to one concurrent checkpoint); a missing checkpoint directory is
  rejected. Keys verified against the pinned 2.2.1 dist (`StateChangelogOptions` in flink-core,
  `FsStateChangelogOptions.BASE_PATH` string-verified) — the changelog classes ship inside
  `flink-dist-2.2.1.jar`, so no image or classpath change is needed.
- **`pipeline-lib.sh`** passes `CHANGELOG_STATE_BACKEND="${CHANGELOG_STATE_BACKEND:-false}"`
  through to the job (same mechanism as `UNALIGNED_CHECKPOINTS`), so a submit environment can
  drive the trial; harness guard **G29** pins both the pass-through and the off-by-default
  contract.
- **`rollout-savepoint.sh`** forwards `CHANGELOG_STATE_BACKEND` in `JOB_ENV_NAMES`, so the CT-4A
  restore drill can flip the flag in either direction (off→on adoption, on→off rollback);
  pinned by a new static pin in `tests/test_rollout_savepoint.py`.
- Docs: `04-signal-job.md` config row with the measured rationale and limits.
