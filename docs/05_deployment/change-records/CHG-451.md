## Why (evidence)

The large-tail outliers (200–430 ms) were not explained by the TM JVM: its `gc.log` + JFR
over the combined run show the longest stop of the whole run at 107 ms (no spike window)
and ~6 ms at the 354/424 ms outlier. W3-i was scoped for the remaining suspects: the
ingestion-writer JVM, the Fluss tablet and host scheduling.

**Correction (2026-09-30, during implementation).** The claim "ingestion writer has no
GC/JFR instrumentation" was **wrong**. `stage-profile.sh` launches the writer with
`-Xlog:gc*,safepoint:file=/logs/gc.log` on the `java` command line (`pipeline-lib.sh`'s
loadgen launcher likewise), so every run already carried `capture/j1-*/gc.log`. Running
the new summariser over the combined run's writer logs **exonerates the ingestion-writer
JVM as well**: max stop 27.1 ms (11:08:32 IST), no pause/safepoint ≥ 28 ms in the whole
900 s, nothing near the 11:12:23 IST (05:42:23 UTC) outlier. Only the JFR was genuinely
missing. The remaining suspects are the **Fluss tablet** and **host scheduling**.

## What changed

1. **`stage-profile.sh`**
   - `INGESTION_JAVA_TOOL_OPTIONS` (configurable, default =
     `-Xlog:gc*,safepoint:file=/tmp/gc.log:time,uptime,level,tags:filecount=1,filesize=50m
     -XX:StartFlightRecording=settings=profile,duration=1800s,filename=/tmp/ing-diag.jfr,maxsize=64m`),
     applied to **both** ingestion launch branches (faketool + real). GC logging already
     existed on the command line; the JAVA_TOOL_OPTIONS copy hardens the branch wiring and
     the **JFR is the genuinely new part**.
   - `stop_fleet()` **stops each ingestion container gracefully** (`docker stop -t 10`)
     before copying artifacts: a JFR recording with `filename` only materialises when the
     recording ends (duration expiry or JVM exit — verified 2026-09-30: the TM's 900 s
     recording wrote 35.7 MB at T0+900 s; a trivial `java -version` run wrote 175 KB on
     exit), so a `docker rm -f` (SIGKILL) would leave 0 bytes.
   - `stop_fleet()` then pulls `gc.log` + `ing-diag.jfr` from every ingestion container and
     `gc.log` + `tm-diag.jfr` from `$FLINK_TM_CONTAINER` into the phase evidence
     (best-effort; a missing file never fails a round).
   - `start_stats_sampler()` samples `docker stats` (CPU%/memory, all containers) **plus
     host pressure (`/proc/pressure/{cpu,io,memory}` PSI "some" line)** at ~1 s per phase
     into `stages/docker-stats.log`; killed by `stop_fleet`. PSI is the host-level
     discriminator: 8 % psi-cpu at the 354 ms outlier vs 0–4 % elsewhere.
   - After each phase: `stage_gc_summary.py <phase>` writes `stages/gc-summary.txt`.
2. **`code/01_platform/04_scripts/stage_gc_summary.py`** — parses `-Xlog:gc*,safepoint`
   output: stop-the-world `Pause …` lines and safepoint events ≥ 15 ms with IST timestamps;
   ignores per-phase detail lines (validated against the 2026-09-30 TM log: max 107.2 ms,
   matching the hand analysis).
3. **Tests (gate step 3)**
   - `test_stage_instrumentation_pins.py` — static pins: the variable + both launch
     branches; all four evidence copies; the stats sampler wiring; the PSI line; the
     graceful stop; the summariser call.
   - `test_stage_gc_summary.py` — parser/summariser behaviour on real line shapes,
     including the phase-line trap; CLI and no-logs cases.

## Findings harvested during implementation (read-only)

- **Ingestion-writer JVM exonerated for the known outliers** — combined run
  `capture/j1-*.gc.log`: max stop 27.1 ms; zero ≥ 28 ms events. Supersedes the design
  note's "no GC instrumentation existed" premise (recorded there too).
- **JFR materialisation rule confirmed**: the TM's recording (restarted 11:41 IST by the
  smoke's preflight, duration 900 s) wrote **35.7 MB at expiry** (11:56 IST) — not before.
  A phase shorter than the recording's duration therefore harvests 0 bytes at teardown
  (the smoke's TM JFR) while a ≥ 900 s phase harvests the full file. The writers' JFRs are
  materialised by the graceful stop instead of waiting for their 1800 s duration.

## Limitations / follow-ups

- **Fluss tablet JFR is not captured.** The digest-pinned `FLUSS_IMAGE` strips the JDK's
  attach tooling (no `jcmd`, no `jdk.jcmd` module — only `java/jfr/keytool/rmiregistry`),
  and its JVM-level recording is a fixed 900 s window from container start (long expired).
  A host-`jcmd` copy fails on module resolution. Per-phase tablet restart was **rejected
  for the certification round** (cold-tablet bias); if the round's PSI/per-container-CPU
  evidence points at the tablet, run a dedicated diagnostics round that restarts it.
- The smoke phase's `stages/tm-diag.jfr` stays 0 bytes by the rule above; the main phase
  (900 s) is the one that harvests a real TM JFR.
