## What changed

### audit_r2.py — bucket-lock rules read is fail-closed (AS-286, AS-287)

New module helper `bucket_lock_rules(body)` (current file L249) raises
`UnsupportedFeature` when the Cloudflare bucket-lock GET has no list-typed
`result.rules` — instead of the previous chained `.get(..., {})` default of
`[]`. Both call sites use it:

| Site | Before | After |
|---|---|---|
| `provision --set-lock` (L491) | malformed 200 → `rules=[]` → merge PUTs `[new rule]` | `READ/SET FAILED` step, **no PUT** |
| `validate` check (L557) | malformed 200 → `checks["bucket_lock"]="NONE"` | `checks["bucket_lock"]="ERROR"` |

`cf_put_bucket_lock`'s docstring is explicit that the PUT REPLACES the whole
configuration, so the old default could wipe every existing bucket-lock (WORM)
rule on an unexpected 200 body. HTTP-level failures were already handled by
`cf_get_bucket_lock` (it raises `UnsupportedFeature`); the gap was only the
shape of a 200 response.

### soak-o2-evidence.py — error/data-less 200 is a failure, not "zero series" (AS-303)

The query loop now rejects a payload that is not a dict, carries
`status:"error"`, or has no `data` object, raising `ValueError` into the
existing handler (`query <name> BAD PAYLOAD`, `rc=1`, remaining queries
continue). Previously such a body fell through the chained get to `result=[]`
and was recorded as an intentional empty-result row ("an empty result is data,
not a failure") — a false zero-series row in the soak evidence.
