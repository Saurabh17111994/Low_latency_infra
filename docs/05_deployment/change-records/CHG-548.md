# CHG-548 — stage-profile: an empty `INGESTION_JAVA_TOOL_OPTIONS` must disable the JVM instrumentation

- **Status:** implemented (harness only — no cluster, job, image, DDL or config change).
- **Filed:** 2026-10-04
- **Source:** the 2026-10-04 JFR A/B (plan `docs/plans/2026-10-03-p99-50ms-combined-plan.md`
  C2c) needed a capture with the profiler OFF. `stage-profile.sh` documents "an empty
  value disables it", but the assignment used `${INGESTION_JAVA_TOOL_OPTIONS:-…}`, and the
  `:-` form substitutes the default when the value is set-but-empty — so the documented
  way to disable it silently re-enabled both the GC log and the JFR recording. The arm was
  only valid because it passed a single space instead, and even then the first env-proof
  file was empty (a guessed container name), so the treatment had to be re-proved by
  inspecting the live containers. A measurement whose subject is "is our own instrumentation
  perturbing the p99" cannot depend on that kind of workaround.

## What changed

`code/01_platform/06_stage_profiler/stage-profile.sh` (the ingestion JVM
instrumentation assignment, one character of behaviour):

| value of `INGESTION_JAVA_TOOL_OPTIONS` | before (`:-`) | after (`-`) |
|---|---|---|
| unset | default flags | default flags (unchanged) |
| empty (`""`) | **default flags** (silently instrumented) | empty — instrumentation off |
| explicit value | passed through | passed through (unchanged) |

The comment above the assignment now names the reason, so the next editor does
not "tidy" it back to `:-`.

`code/01_platform/04_scripts/tests/test_stage_instrumentation_pins.py` gains the
pin described in `test_updates`, next to the existing static pin that
`JAVA_TOOL_OPTIONS` reaches both ingestion launch branches.

## Not changed

- The default flag string is untouched (`-Xlog:gc*,safepoint:…` +
  `-XX:StartFlightRecording=settings=profile,duration=1800s,…`), so every
  existing round's evidence stays comparable.
- Both launch branches (`-e "JAVA_TOOL_OPTIONS=$INGESTION_JAVA_TOOL_OPTIONS"`,
  faketool + real) are untouched.
- No new `make gate` step, no deploy artifact, no dependency.
