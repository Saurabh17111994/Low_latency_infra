## What landed and why

The SignalChainLiveE2ETest investigation
(`logs/tracker-14/16-signal-chain-e2e-investigation-20260817.md`, 2026-08-17)
first root-caused the E2E failure to a harness config gap (RocksDB
managed-memory starvation under local execution — CHG-021). After CHG-021's
memory/network passthrough landed, the smokes 8–16 (12:50–14:20) exposed a
SECOND, structural blocker that the harness fixes cannot remove: on the DEC-038
topology the dedup hot path performs a **synchronous Fluss lookup**
(`FlussFingerprintDedupStateStore.lookup` → `lookuper.lookup(...).get(...)`) on
every cache miss, and in every smoke the lookup futures never completed — all 8
`fingerprint-dedup` subtasks parked in `CompletableFuture.get()`, the checkpoint
barrier could not pass, and **checkpoint 1 expired at exactly 30 s → global
restart** (`Checkpoint expired before completing`, zero acks).

The Fluss 0.9.1 client source confirms why the hang is structural for the
DEC-038 design: the client's netty layer has **no timeout on inflight requests**
(``ServerConnection`` TODO), `client.lookup.max-retries` defaults to
`Integer.MAX_VALUE`, and the operator's synchronous `.get()` couples the
checkpoint barrier to an RPC round trip. The native Fluss–Flink connector
(`FlinkTableSource`) *does* offer an async lookup join with native partial
caching — the maintained, non-blocking way to consult Fluss — but a per-record
RPC is the wrong tool for the per-tick dedup hot path regardless.

**Decision (user, 2026-08-17): the fingerprint dedup set is authoritative Flink
keyed state (Design B)** — `MapState<String, DedupEntry>` keyed
`version|token|fingerprint` + `MapState<Long, List<String>>` expiry index +
one event-time timer per entry at `first_seen + DEDUP_TTL_MS`. **CHG-023 item 2
(2026-08-17): the expiry index + event-time timers were then REMOVED — expiry
is native `StateTtlConfig` (300000 ms, `OnCreateAndWrite` + `NeverReturnExpired`,
ProcessingTime) on the MapState; the index/timers were the hand-rolled
replacement for the event-time TTL Flink 2.2.1 lacks, and native TTL is the
correct wall-clock semantics for the 5-minute real-time dedup rule.** This is
Flink's native answer to streaming dedup (no hand-rolled client code), and it
is the topology the smokes proved: 88/88 then 120/120 clean checkpoints, 0 restarts,
feature table grew +124 855 rows, restore ~1.1 s, and the checkpoint-1 zero-ack
stall is structurally impossible (no RPC on the hot path). Fluss remains fully
native on the input (FlussSource) and output (FlussSink) sides — the only role
it ever needs in this job.

## Trade-off (recorded, not hidden)

The dedup set (~6.1M entries ≈ 628 MB at 20 480 t/s × 300 s TTL) now rides in
the Flink checkpoint instead of living only in Fluss. Evidence that this is
acceptable at the current envelope: `DedupRocksDbThroughputMemoryIT` (~51k/s,
checkpoints 0.9→14.4 MB, durations 20→120 ms) and the E2E's 179 checkpoint-stable
run at p8 + 2048 m managed memory. The "checkpoint must be small" rule
(DEC-038) was born from the pre-RocksDB-incremental incident (1.74 GB heap
state at 53k t/s); RocksDB + incremental checkpoints + managed memory — all
native Flink — remove that constraint. If a future envelope (e.g. 3,000
instruments / 50k t/s) makes the checkpoint too heavy, the native path is the
connector's async lookup join with partial caching, not a return to the raw
client.
