# CHG-255 — the TaskManager reads the leader election through the same HA backend

## Why

CHG-253 pinned the RPC ports, and run9 showed the jobmanager finally binding the port its peers
dial (`PASS: JM is listening on 6123 (tcp LISTEN 0x17EB) after 10s`). The taskmanager's
registration message then **reached** the ResourceManager for the first time — and the
ResourceManager threw it away, with the token printed on both sides:

```text
FencingTokenException: Fencing token mismatch: Ignoring message RemoteFencedMessage(00000000000000000000000000000000, RemoteRpcInvocation(ResourceManagerGateway.registerTaskExecutor(TaskExecutorRegistration, Duration))) because the fencing token 00000000000000000000000000000000 did not match the expected fencing token 9f3175f098076291f8095be45eee44b3.
```

`{"taskmanagers":[]}` followed, and the taskmanager retried every ten seconds forever
(`Pausing and re-attempting registration in 10000 ms`) while the jobmanager reported itself
healthy with leadership granted.

The fencing token is not a TaskManager setting: it is part of the **leader information the HA
service hands out**, and it is what stops a stale or split-brain client from talking to the
wrong ResourceManager instance. A component that has no HA configuration has no leader
retriever, so it falls back to the static `jobmanager.rpc.address` and registers with token
`0` — which is exactly the value the log shows. The jobmanager declares five
`high-availability.*` keys; the taskmanager declared none, so the two roles were reading two
different sources of truth for the same cluster.

This is the second half of the same rehearsal failure as CHG-253, and it is why the two fixed
port numbers alone were not enough: a port that answers is not a peer that is accepted.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** (5 lines + prose above the taskmanager
  properties block) — the taskmanager declares the same `high-availability.type`,
  `.zookeeper.quorum`, `.storageDir`, `.zookeeper.path.root` and `.cluster-id` as the
  jobmanager, with the rationale above the block because a `#` inside `FLINK_PROPERTIES`
  reaches Flink verbatim (rule 8).
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — new
  `test_taskmanager_reads_the_leader_through_the_same_ha_backend` collects the
  `high-availability.*` keys from both Flink role blocks (roles found by their declared
  `command`) and requires the taskmanager to carry every jobmanager key with an equal value.
  Green unmutated, file 44/44, and it fails all eight HA mutations: taskmanager block removed,
  type removed, storageDir removed, quorum pointed at another ensemble, cluster-id renamed,
  root path moved, jobmanager block removed, jobmanager quorum changed.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — rule 10 now states the second half: both

## Limitation

The rehearsal has a single node, so the run9 proof shows the taskmanager registering and the
ResourceManager listing it; a ZooKeeper failover that re-issues a fencing token is not
exercised (two jobmanager replicas cannot be placed on one node). The keys are asserted by
value and against the live registration, which is the strongest evidence this environment can
produce.

## Rehearsal result (run9, fourth attempt)

```

```

The registered TaskManager advertises `pekko.tcp://flink@10.0.1.31:6123/user/rpc/taskmanager_0`
with 8 slots, i.e. the pinned port it binds is the port the ResourceManager will dial back —
the other half of the CHG-253 failure, now closed from the same run.

Two scaffolding defects had to be fixed for this run to mean anything, both in the local
rehearsal scripts rather than the repository: the render step's failure was counted as a FAIL
and then **ignored**, so the third attempt deployed the *previous* rendered file and reported a
meaningless verdict (`FAIL: generator failed` followed by a stale `{"taskmanagers":[]}`); and
the renderer itself still expected exactly one `high-availability.storageDir` line, so
CHG-255's second one made it fail. The render step is now fatal and asserts the line in both
role blocks.
