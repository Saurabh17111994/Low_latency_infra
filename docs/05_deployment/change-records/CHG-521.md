## What changed

- `run-monday-gates.sh`, inside step 9 right after `PASS: Java suite`:
  `if [ "$POOL_ENABLED" = 1 ]; then pool_launch 10; fi`. The child re-runs the
  script with `--steps 10`; `pool_launch` records it in `POOL_LAUNCHED`, so the
  parent's existing `if step_active 10` skips the inline run — no duplicate.
- `pool_require_step 10` next to `pool_require_step 6`: step 12 rewrites the
  ingestion surefire XML the audit reads, so the audit must be reaped first
  (in practice a no-op: it finishes ~5 min before step 12 starts).
- Comments at the step-9 launch site and the step-10 banner updated to state
  the new ordering.
- Scoped/serial runs (`--steps`, `--sweep`, `GATE_PARALLEL=0`) are unchanged:
  the guard keeps step 10 inline because `POOL_ENABLED=0`.

## Why it is safe

- The audit is file-only (`stale_table_kind_scan.py`, `docs_audit.py`, DDL
  parity, sweeps, trio) — no docker, no Fluss, no curl.
- It reads the ingestion/common plain reports; those are complete when the Java
  suite exits, and the drills write `target/surefire-reports-drills` — already
  proven by the serial gate, where the audit runs after the drills and C6 still
  matches the plain suite.
- `full_audit.sh`'s gate-in-flight guard exempts its own gate by ancestry
  (`inside_gate()` walks the parent chain and finds `run-monday-gates.sh`), so
  the pooled child may start while the gate is running.
- Failure semantics unchanged: a failing audit is reaped at the boundary after
  the drills (`pool_fail_if_any`, line 1123) and fails the gate naming step 10
  — ~5 min earlier than before.
