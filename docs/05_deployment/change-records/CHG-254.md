# CHG-254 — the OpenObserve root password is supplied and policy-checked, never generated

## Why

OpenObserve validates its own root password at startup. In the rehearsal the container never
served, with a message that names the rule and then a second message that hides it:

```text
ZO_ROOT_USER_PASSWORD is too weak: Password must be 8-128 characters and contain at least one
lowercase letter, one uppercase letter, one digit, an[d special char]
Error: backend job init failed: channel closed
```

The value in the rehearsal came from the values file, so it was the operator's choice — but
`secrets-bootstrap.sh` had the same trap one path over: `o2_password` was in its `GENERATED`
list and its generator is `gen_hex`, i.e. 64 characters of `[0-9a-f]`. That value has **no
uppercase letter and no special character**, so it fails the policy above by construction:
any deployment that let the script generate the password handed OpenObserve a value it
refuses, and the observability stack — the destination every log and metric is shipped to —
never started. The failure also appears late and indirectly (a container that panics, an otel
exporter that gets 401), which is the expensive way to learn a password rule.

The generated path could never have worked anyway. The stack passes the same secret to the
container as a **deploy value** (`ZO_ROOT_USER_PASSWORD: ${O2_PASSWORD:?set O2_PASSWORD}`),
because OpenObserve v0.91.5 has no `_FILE` support, and the deploy shell can only export a
value the operator knows. A secret generated inside `secrets-bootstrap.sh` is never printed —
by design, values never appear in that script's output — so it can never be exported to
match. Requiring the value and validating it is both the fix and the honest description of
what S6 already told the operator to do.

## What changed

- **`code/01_platform/04_scripts/secrets-bootstrap.sh`** — `o2_password` leaves the `GENERATED`
  list (four generated becomes three: the two internal tokens plus the derived
  `o2_auth_basic`); a new `o2_password_ok` implements OpenObserve's policy as four
  presence checks over `tr -d` output under `LC_ALL=C`, so a UTF-8 locale cannot blur
  `[a-z]` against `[A-Z]` and pass a weaker value; `create_mode` fails closed with exit 3 and
  the policy spelled out when the value is missing or weak, instead of creating a secret that
  panics a container minutes later. The missing-values message explains why this one value
  cannot be generated. `--self-check` now also proves the validator: it accepts a compliant
  password, rejects 64 hex characters (the shape the script used to produce) and rejects
  anything under 8 characters.
- **`code/01_platform/04_scripts/tests/test_15_secrets_bootstrap.py`** — the shared values
  fixture carries a compliant `o2_password`; the generated-secret test now covers the two
  tokens and asserts the password that reaches the secret is the supplied one; new
  `test_o2_password_must_be_supplied_and_meet_the_policy` refuses a missing value and four
  weak shapes (64 hex characters, no uppercase, no digit, under 8 characters) with no secret
  created, and accepts the compliant one. File 15/15.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — S6 states the six supplied values and the
  three generated ones, and says the script refuses a run without a policy-compliant
  `o2_password`.
- **`docs/05_deployment/06-swarm-secrets.md`** — the summary table and the creation paragraph
  carried the old split (five supplied, four generated) and claimed OpenObserve mounts
  `/run/secrets/o2_password`, which the stack does not do: the service declares no secrets and
  takes the value as the deploy variable `ZO_ROOT_USER_PASSWORD`. Both are corrected, so the
  table matches `docker-stack.yml`.

## Limitation

The policy text comes from OpenObserve v0.91.5's own error message and is asserted only for
the five shapes the tests name; a future OpenObserve release that tightens or loosens the rule
would make the validator wrong in one direction, so the policy is quoted in the script and in
rule 10 rather than silently encoded. The rehearsal proof of the container accepting the
stronger dummy password is a live run of the same image (`prod_openobserve` Running 1/1 with
`Rehearsal-Only-1!`); no test calls the real OpenObserve.
