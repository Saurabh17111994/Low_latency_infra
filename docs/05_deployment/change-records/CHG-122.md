## Problem

The three CRITICAL Wave 0 findings (P3-010/P3-012/P3-013) were blocked on a claim
that is false: that Fluss 0.9.1 offers no conditional write, so a stale or zombie
executor could always clobber the live owner's fence row under last-writer-wins.
`VersionedRowMerger` drops a lower-version write server-side, and `fence_token BIGINT`
is already a valid version column — the gate DDL already documented it as
"monotonically increasing per partition, never reused".

## Change

**Options-only — the column set, order and indices are unchanged, so the row contract
stays v3 and the header is not bumped.** Only the WITH block changed:

- `'table.merge-engine' = 'versioned'`
- `'table.merge-engine.versioned.ver-column' = 'fence_token'`
- `'table.delete.behavior' = 'ignore'` — declared explicitly because VERSIONED rejects
  `allow`; the coordinator would otherwise inject it, and the apply-parity step compares
  every option the DDL declares against the live table.

Applicability was verified, not assumed: a VERSIONED table is an ordinary primary-key
table, so `newUpsert()` and `newLookup()` both work unchanged, and the gate store
satisfies VERSIONED's constraints — exactly one write site, full-row writes, and no
deletes anywhere.

Three code obligations follow, because a version-dropped write still returns SUCCESS
(Fluss 0.9.1 carries no "ignored" result on `UpsertResult`):

1. **`fence_token` is retained as the write-ordering version.** `withFenceCleared` no
   longer resets it to `0L`; the unfenced marker is `owner_instance_id IS NULL`, which
   `fenceValidFor` already required. Resetting to 0 would make the revoke/halt write
   version-dropped — and separately let a restarted process mint token 1 again, reusing
   a token a stale holder still holds as evidence (P3-374).
2. **Every mutator re-reads and confirms its write landed** (`verifyPersisted`), so a
   dropped write fails loud instead of silently. `revoke` alone tolerates being
   superseded by a strictly newer token — a newer owner taking the fence makes the
   revoke moot, not lost.
3. **`halt` mints a strictly greater token**, so a safety halt can never be the
   lower-version write the tablet drops, and it retires the stale holder in the same
   write.

`NautilusIntentClient.forward` gained the matching fail-closed checks (P3-374): a null
owner now defers, and a null lease no longer skips the expiry check — without these, a
revoked row (token retained, lease null, state still ENABLED) would have forwarded.

## Compatibility

INCOMPATIBLE for the table itself: it is dropped and recreated, so the table id changes
and gate KV fence state is lost. The **row** contract is unchanged (v3 columns, order and
indices), so readers and the pinned column layouts keep working.

Residual, unchanged and explicitly not closed by this record: equal versions are still
accepted (`compare <= 0`), so two hosts minting the same next token both win.
Single-active-owner remains deployment-owned (ASM-EXE-005).

## Evidence

- Offline reactor green 2026-09-11: 582 / 469 / 95, zero failures (was 581 — the +1 is
  the new restart-reuse case).
- `GateTableAdmin show` against the edited DDL parses all three new options and retains
  datalake, proving the descriptor the recreate applies carries the merge engine.
- Guard falsification: disabling `checkPersisted` made the stale-token, wrong-epoch/state
  and missing-row cases fail with "nothing was thrown"; restored and re-verified green.
- Live proof still required (tracked in the Wave 0 plan): VERSIONED combined with
  `table.datalake.enabled` is **untested upstream**, so the option parity, the actual
  stale-token drop, and "halt still lands" must be demonstrated on a live cluster before
  this is treated as verified in production.
