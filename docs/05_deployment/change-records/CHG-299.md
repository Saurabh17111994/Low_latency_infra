## Why

Gate step 9's live drill spent most of its time in `DdlSmokeTwinSweepTest`: 336 s of a 12.5 min
drill, of which 277 s was the 27 smoke writes alone. The tool created each twin inside the smoke
loop, immediately before smoking it, so every write waited for that twin's replica to be placed.
`DdlApplyTool` already states the mechanism in its own words: *"Writes to tables that already have
their replica stay at ~100 ms throughout, so this is placement-only."*

A timestamped single-class run (see Measurement) shows the wait is not uniform: it fell from 20 s
on the first twin to 5 s on the last, consistent with a client/cluster warm-up over a fixed
per-write placement cost. The placement is unavoidable; paying it *serially, once per twin, in
front of the write that needs it* is what the ordering chose to do.

## What changed

`DdlApplyTool.run` step 7 now creates **all** twins before the first smoke, in their own loop, and
the smoke loop no longer creates them. Twins that fail to create are recorded there (`twin create
failed: ...`) and their smoke is skipped rather than attempted.

Unchanged: the drop-immediately-after-smoke rule, the KEPT-twin rule for a write that never
resolved (`WriteAwait`), `--allow-live-smoke`, the `--skip-smoke` path, the drain probe, and the
`dropIfExists` sweep of any twin left by a previous run.

## Measurement

Both halves of this comparison were run back to back on the **same freshly-restarted cluster**,
with the same harness and the same 27-table catalog. The without-change half was measured by
temporarily restoring `DdlApplyTool.java` to its parent commit, then restoring HEAD (verified: clean
`git status`, empty `git diff HEAD`).

| metric | without the change | with the change |
| --- | --- | --- |
| `DdlSmokeTwinSweepTest` (surefire) | 327.2 s | 67.5 s |
| maven total | 5:30 | 1:08 |
| tests run / failures / errors / skipped | 2 / 0 / 0 / 0 | 2 / 0 / 0 / 0 |
| verdict | PASS | PASS |

That is 4.85x, or 260 s saved, per sweep.

An earlier uncontrolled pair (336.2 s -> 97.9 s) was taken on a cluster whose accumulated state was
not controlled and is **superseded** by the figures above. Note the direction: the improvement is
larger under control, not smaller.

The mechanism was located with timestamped single-class runs (a separate measurement, not the
controlled pair above): the per-twin wait declined smoothly from 20 s on the first twin to 5 s on
the last, and per-write times went from min 5 / p50 10 / max 20 s to min 0 / p50 1 / max 2 s. A
smooth decline is warm-up over a fixed placement cost, not partition correlation. Writes to tables
that already have their replica stay near 100 ms throughout (see `drainScratchTeardown`), so the
cost was placement-only - which is exactly what pre-creating the twins overlaps.

Reproduce with a single-class run (`mvn -o test -Pdrill-reports -pl common
-Dtest=DdlSmokeTwinSweepTest -DforkCount=0`, `FLUSS_BOOTSTRAP=localhost:9123`,
`MAVEN_OPTS=--add-opens=java.base/java.nio=ALL-UNNAMED`) and timestamps on the tool's progress
lines.

## Known trade-off

At most one twin used to exist at a time; now up to 27 do. If the JVM dies mid-smoke-loop (OOM,
external timeout) the remaining pre-created twins leak instead of being dropped one by one. The
leak is self-healing - the pre-create loop's `dropIfExists` clears any twin a previous run left -
and the sweep test's zero-leftovers assertion still holds, but the window exists and is recorded
here rather than left implicit.
