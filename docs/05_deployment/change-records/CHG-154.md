# CHG-154 — The pipeline helpers fail closed

- **Status:** recorded — all 28 wave-17 findings fixed
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 17 ("Pipeline lib: the helpers behind
  every sweep"): P6-142…P6-152 (high) and P6-467…P6-483 (medium) in
  `code/01_platform/04_scripts/pipeline-lib.sh` (the helpers behind the load, soak and
  full-load sweeps), with caller contract repairs in `holistic-measure.sh`,
  `test-pipeline-lib.sh`, and the compose/metric/lake-guard test files it broke.

## What happened

The library behind every sweep normalised, then measured, then reported — and at each step
a failure used to mean "carry on with garbage".

**The library died wrong or never died (`P6-142`, `P6-467`, `P6-469`, `P6-470`,
`P6-474`).** Executing it directly ran the whole body; a caller that forgot `ROOT` or
`RATE_HZ` got thousands of lines of fallout instead of one line at the top; `FAKETOOL_PORT`
and the port helpers accepted non-numbers through `ss`/`awk`/`/dev/tcp`; the Fluss probe's
"timeout" reached only one of two branches, so a filtered host hung the sweep for the
kernel's SYN budget; `INJECT_AFTER_MS=5s` passed validation and died inside `[` long after
`docker run -d` had started. A source contract (`ROOT` + `RATE_HZ`, `OUT` deferred to
`pipeline_preflight` because `holistic-measure.sh` assigns it inside its phase functions),
one `pipeline_validate_port`, a bounded `/dev/tcp` probe, and INJECT validation before
any docker call.

**Build identity was forgeable (`P6-143`, `P6-471`, `P6-473`).** A deleted
Dockerfile/pom contributed nothing to the build-stamp file list and the stamp was computed
from whatever remained — a rebuilt tree could verify against a different image's stamp. A
manifest with no comma or one field passed as "two-column". The verify gate read the stamp
only after everything else. The three listed inputs must exist, the digest is NUL-safe
(`xargs -0 -r`), the stamp is a `:?` input to verify (checked first now), and the
manifest header is shape-checked.

**Secrets and evidence crossed the container boundary in the wrong direction (`P6-146`,
`P6-475`).** `ARROW_APP_SECRET` and the TOTP key were baked into the lib as `-e` literals
(visible to `docker inspect`, the daemon log, and every argv dump); the input slice was
mounted read-write, so the container could rewrite the evidence its own run would later
verify. Credentials now arrive via `--env-file` from the same `secrets.env` compose uses
(the run refuses without it), the slice is bound `readonly`, and the non-secret ids stay
as `-e` only as overridable `${ARROW_APP_ID:-testd}` defaults (secrets.env carries no app
id, and the documented source for those two is the operator's file — see judgement 7).

**Stale data passed as measured data (`P6-148`, `P6-152`, `P6-480`, `P6-481`,
`P6-482`).** A failed purge said "drop skipped" and the sweep carried on with yesterday's
rows; a failed curl or non-JSON answer appended nothing and exited 0, so an empty
`checkpoints.jsonl` was indistinguishable from "the job made zero checkpoints"; an empty
`JOB_ID` curled `/jobs//checkpoints`; a failed REST fetch printed an EMPTY dump that
callers parsed as "zero progress"; a subtask-0-only view printed in the same shape as a
full sum. The purge refuses without `ALLOW_STALE_TABLE`; checkpoint fetch/parse failures
return 1 and never touch the evidence file; capture needs preflight + a job id; the dump
checks the fetch; the fallback source prints to stderr so the stdout shape stays
`name|read|write`; and a stale `JOB_ID` is cleared *before any failure point* in submit,
not after the copy — a failed container resolution used to leave the previous run's id
behind for cleanup to cancel (caught by the new test, fixed in this record).

**Identity and lifecycle bugs in submit, start and cleanup (`P6-149`, `P6-150`,
`P6-145`, `P6-151`, `P6-479`, `P6-468`, `P6-478`, `P6-147`, `P6-476`,
`P6-483`).** A failed `compose exec` left `submit_out` from the previous line and rc from
whatever ran before; only lowercase-hex JobIDs parsed (`0A1B2C3D` → empty → "no JobID");
the faketool/start-faketool partial-start path leaked mirrors and containers on the second
half failing; installing the cleanup trap discarded the caller's; the mirrors were never
killed and `JOB_ID` survived cleanup; `$COMPOSE` word-split under a ROOT with spaces; the
jobmanager was a hardcoded container name `01_docker-flink-jobmanager-1`; the DDL helpers
compiled in shared `/tmp` with fixed filenames (cross-run collision, and a sweeper could
take a live file); `wait_state` looped the whole timeout on a job that could never reach
the wanted state. rc is captured, the JobID regex is case-insensitive, the partial-start
path kills what it started (and the per-start log mirrors gained PIDs + a wait so the nohup
rump cannot outlive the run), the trap chains, cleanup kills the mirrors and clears the
id, `COMPOSE` is an array, container resolution goes through `pipeline_compose_cid`
(`compose ps -q`, fail-closed), the DDL helpers compile in a `mktemp -d` private dir, and
the timeout is validated with an abort on terminal states.

## Judgement calls

1. **OUT is required by `pipeline_preflight`, not at source time.** The finding asked for an
   `OUT:?` guard in the source block, but `holistic-measure.sh` assigns OUT inside its phase
   functions *after* sourcing (verified at its lines 295/393) — a source-time guard would
   break a live caller. The requirement moved to `P6-467`'s validation block in
   `pipeline_preflight`, which runs before anything touches OUT.
2. **No `${ARROW_APP_SECRET:?}` at source time.** Non-exporting callers (the generated
   `eod-controller-test.sh` inner script does not export secrets) would break. The values
   are required where they are used: the run refuses without `secrets.env`.
3. **P6-477 (heredoc duplication of the TableEnsure/TablePurge helpers) deferred.** The
   finding's race (fixed `/tmp` filenames) is closed by the private temp dirs; the
   remaining duplication is a maintainability note, not a correctness defect, and a rewrite
   risks the two call paths. A static test pins that the deduplication has *not* silently
   happened (it would change error strings callers grep for).
4. **P6-481's per-vertex fan-out stays.** The finding suggested parallel subtask fetches;
   unmeasured perf work on the evidence path is exactly what this wave does not do. The
   failure mode it named (one slow vertex stalls the dump) is not observed; the fix is the
   fail-closed fetch.
5. **P6-482's source marker goes to stderr, stdout schema untouched.** Downstream parsers
   consume `name|read|write`; adding a column would break them. The err file already exists
   (`flink-metric-fetch.err`), so the source lands where a human looks.
6. **Two test bugs of mine, found by running the tests before committing.** (a) The curl
   stub's default body nested double quotes inside `${…:-…}` which bash de-quoted, so every
   default response carried a `state:RUNNING}` tail — the checkpoint "parse failed" this
   produced is what surfaced it; the stub now assigns then prints. (b) A P6-482 line used
   single quotes inside a `python3 -c '…'` block and silently broke `flink_metric_dump` in
   production — `bash -n` and shellcheck cannot see it, the suite did. Both are the reason
   the wave rule says fix-before-the-commit.
7. **`ARROW_APP_ID`/`ARROW_USER_ID` are overridable defaults, not file reads.** They are
   identifiers, not credentials (secrets.env carries no app id), and dropping the `-e` args
   would change the container's environment for operators who never set them. They are now
   `${VAR:-default}` — same value when unset, overridable when set.
8. **The compose-form contract test moved with the code.** The array form changes six
   registered sites plus the definition; the registry and DEFS moved in the same commit so
   the gate stays green. The two dead TEXT rows (`$COMPOSE build loadgen` message hints)
   were removed rather than re-pointed — the scanner only matches real invocation faces.
9. **A stray `sleep 300` from an earlier hand-probe polluted one full-suite test.**
   `test_cleanup_kills_children…` counted a leftover sleep of mine as a leaked child. It was
   killed and the suite is green; the probe discipline (no stray sleeps) is noted here so
   the next red run of that file starts from a clean process table.
10. **The lake-guard `LAKE_GUARD_TODAY` seam is test-only**, mirroring the existing
    `LAKE_GUARD_CHECK_DAY` hook, unset in production. It exists because two guard tests
    went red when IST rolled past midnight mid-session — the after-deadline tests pin today
    instead of reading the wall clock.
