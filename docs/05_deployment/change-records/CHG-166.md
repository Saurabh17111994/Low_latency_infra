## Judgement calls

1. **P6-252's second half is partly a residual.** The finding asks to "gate on
   lag/consumer progress (or ingestion total) rather than counter flatness alone".
   This change requires the job to stay RUNNING and both counters to be flat and
   non-`-1`, which removes the stalled/deadlocked misreport the finding names — but
   a job that stays RUNNING while both counters freeze is still read as drained.
   That residual is documented in the code comment at the gate (the drain deadline
   and the post-kill gates bound it) rather than closed with a lag metric this
   wave did not have a source for.
2. **P6-642 was closed by asserting, not by documenting.** The finding offered
   "or document why informational"; a TaskManager-down alert that never fires is
   the failure the drill exists to catch, so it is now a finding.
3. **P6-643 was closed by routing `fatal()` through RESULT.txt**, not by
   documenting the bypass — the artifact is what the post-run analyzer consumes.
4. **P6-636's smoke half is scoped, not extended.** Smoke mode still does not assert
   tiering recovery (that needs the full drill), so the limit is now written into
   the verdict itself instead of being invisible.
5. **P6-845's `flink_metric_dump ... || true` sits inside the kill window**, where
   the TaskManager is expected to be gone; that best-effort pattern is deliberate
   and stays. Its absence now flows into gates rather than passing silently: the
   drain gate refuses to call a `-1` window drained and the alert gate refuses to
   call an unreadable feed clean.
6. **`alert_count` returns `-1`, not an error exit**, so a caller inside a command
   substitution keeps reading a number and the *gate* decides — the same shape as
   `metric_totals`.
7. **The two new test cases for P6-251 live in the existing
   `test_c2_progress.py`** rather than a new wave file, because the module already
   had a suite and the cases belong to it.
