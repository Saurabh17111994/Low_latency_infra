## What changed

| Piece | Change |
|---|---|
| `RetryClassifier` | New `isMetadataNotReady(Throwable)` — chain walk, case-insensitive `update metadata`. Deliberately narrow; the stale-handle fatal patterns (NotLeaderOrFollower / PartitionNotExist / UnknownTableOrBucket) are not covered |
| `RawTickWriter` | New constructor overload with a startup grace; the grace clock starts at the FIRST append (the bridge may connect minutes after JVM start); inside the window and only while no append was ever acked, that class is retried with capped backoff (250/500/1000 ms) instead of FATAL; the reservation stays held across grace retries (same as the RETRYABLE path); expiry restores the R-285 FATAL; every other class is untouched. **SUPERSEDED (M4-5, CHG-386):** the "only while no append was ever acked" conjunct is dropped — the metadata class retries for the whole window regardless of an intervening ack |
| `IngestionService` | The zero-ack watchdog stands down while the grace is running AND no append was acked (`zeroAckSuppressed`): the deliberate un-acked retries are not a wedge. After the first ack, or after expiry, wedge detection has full authority (cold-start baseline unchanged) |
| `IngestionConfig` | `INGESTION_WRITE_STARTUP_GRACE_MS` (default 180 000 ms, range 0-600 000; `0` disables); logged with the other effective values; the default matches `FLUSS_STARTUP_WAIT_MS` |
| Docs | `docs/08_implementation/03-ingestion.md` env table + startup-sequence note; foundation test-truth line 743/527/540 |

## Why this is bounded and safe

- **Cold start only:** the retry requires no append ever acked. A post-success
  stale handle still halts (R-3xx) — the 2026-09-03 incident guard is intact.
- **Bounded:** after `INGESTION_WRITE_STARTUP_GRACE_MS` the same failure is
  FATAL exactly as before; the container restart policy is the next line.
- **One class:** everything except `update metadata` keeps R-285 fail-closed.
- **Watchdog continuity:** the stand-down needs both the running grace and no
  ack, so a genuine wedge after the first success is detected as before.

## Trade-off (recorded)

During the grace, retried records stay pending, so an in-session cold start
with a long metadata stall can accumulate pending rows and hit the pending
limit (ticks then rejected/dropped and counted). The alternative (the observed
behavior) was a JVM restart every ~10-30 s with re-subscription and replay.
Both lose some data under a stall; the grace keeps the process alive, avoids
the restart churn, and is bounded to 60 s by default.

## Drill findings (2026-09-26 integration drill)

The first drill (fresh `make day ARGS="stop"` + `start`) exercised the grace
against a real fresh-Fluss start and produced two facts the unit tests could
not:

1. **The mechanism works.** At `18:03:52` the writer logged
   `append metadata not ready — startup-grace retry` and kept retrying
   (`attempt=27`, capped backoff) until `remaining=1ms`, then failed closed at
   `18:04:16.97` exactly at the 60 s window boundary. No zero-ack restart
   happened during that window (the stand-down worked). Evidence:
   `logs/chg-326/drill/ingestion-flap-evidence.txt`.
2. **The 60 s bound was too tight for a fresh-Fluss cold start.** The
   metadata outage outlasted the window and recovered within ~105 s of the
   first append (the next incarnation's first success was at ~18:05:02). The
   platform's own read-side bound is `FLUSS_STARTUP_WAIT_MS` (180 s), so the
   write-grace default was raised to **180 s** to match it (still bounded,
   still `0`-disableable). This is a default change only; the mechanism and
   the fail-closed expiry are unchanged.

The subsequent zero-ack restart (`18:05:21`) was a **post-success** stall: an
append had been acked, so the watchdog keeps full authority by design — not a
grace failure. Off-hours `FEED_STALLED`/reconnect cycles and the
`assigned_token_set_hash` cross-check warnings in the same logs are the known
off-hours broker behaviour, not regressions.

**Drill 2 (after the 180 s bound + CHG-327), 2026-09-26 23:55 IST:** a fresh
`make day ARGS="stop"` + `start` came up clean — the restored SignalJob reached
`RUNNING` with its first checkpoint, ingestion started with **0 restarts and 0
grace retries** (the metadata came up inside the window this time), the board
read `7/9 invariants · data predicates judged in session` with **I8 OK**, and
the runner exited 0. Evidence: `logs/chg-326/drill/console-start-2.log`,
`logs/chg-326/drill/console-stop-2.log`,
`logs/chg-326/drill/check-image-stale-after.txt`.
