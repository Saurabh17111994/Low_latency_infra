# CHG-146 — The tablet repair can no longer cut a segment it has not verified

- **Status:** recorded — all twenty-one wave-9 findings verified and fixed across two commits
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 9 ("Repair and admin tooling"):
  P6-004, P6-091, P6-384, P6-385 (RawTableAdmin.java) and P6-092, P6-093, P6-094, P6-095,
  P6-096, P6-097, P6-098, P6-099, P6-100, P6-386, P6-387, P6-388, P6-389, P6-390, P6-391,
  P6-392, P6-393 (repair-tablet.sh)

## What happened

`repair-tablet.sh` truncates Fluss log segments to the end of the last complete batch, so every
mistake it makes is a data-loss bug. `RawTableAdmin.java` is the same tooling's table-level
counterpart. Both were re-read line by line before anything was edited, and all twenty-one findings
held.

**The admin CLI dialled the wrong host with the partition it was asked to create (`P6-004`,
CRITICAL).** `args[1]` was read twice: as the bootstrap address and, for `add-partition`, as the
partition name. `RawTableAdmin add-partition 20260101` therefore tried to reach a host called
`20260101`, and no invocation could pass both a partition and a bootstrap address. The bootstrap is
now an option (`--bootstrap HOST:PORT`), positional arguments belong to the subcommand, and
`add-partition` takes a dedicated value that must be a real `yyyyMMdd` date (`P6-091`) — a wrong
shape silently created a second, non-auto partition that nothing ever writes to. Subcommand and
arity are validated before `ConnectionFactory` (`P6-384`), so a typo fails instantly instead of
after a cluster round-trip, and the success line prints the partition that was created rather than
`argv[1]` (`P6-385`).

**The tool scanned a tablet it had not stopped (`P6-096`, `P6-097`, `P6-100`, `P6-390`,
`P6-391`).** Segments were scanned while the tablet could still be `Up`/`Restarting`, then the tool
stopped it, then it cut to offsets measured before the stop — appends landing in that window were
amputated by an offset that no longer described the file. Single-table mode also never pinned the
restart policy, so with `--restart=always` the daemon could restart the tablet mid-truncate and
re-open a segment being cut, and `docker stop` was followed by a fixed `sleep 2` (sweep) or no wait
at all. Both modes now pin `--restart=no`, stop, and poll until the container has really left
`running` before anything is scanned. On the way back the fixed `sleep 12` became a poll (a slow
recovery read as a crash loop, a fast flake as success) that fails unless the state is `running` —
`Exited`/`Dead`/`Created` used to be reported as a successful recovery.

**The restart policy leaked, and the scratch directory was deleted mid-sweep (`P6-092`,
`P6-093`).** The EXIT trap only removed `$TMP`. Any `set -e` failure, signal or `exit 1` between
`docker update --restart=no` and the restore left the tablet stopped with auto-restart disabled —
including the sweep's own error path. And because bash runs EXIT traps inside `$(...)` subshells,
the first `--all` iteration's `rm -rf "$TMP"` deleted `segments.txt`/`scan.log`/`pairs.tsv` that
every later iteration still needed. The trap now restores the policy on every path out (INT/TERM
re-raise through `exit 130`, which runs it) and refuses to clean up from a subshell.

**A destroyed tail was treated as a clean scan (`P6-095`, `P6-098`, `P6-099`, `P6-386`).**
`python3 LogScan.py "$seg" || true` masked a missing scanner, a python crash and an empty scan as
"No truncated segments — nothing to repair"; the per-segment status is now propagated, every segment
must report back, and the scan container mounts the tablet volume and the script directory
read-only. The truncate step itself checked only `0 < end < size`, so a scanner bug or a stale
offset would still have discarded complete records, and the check ran *inside* the truncate loop, so
a later failing segment left the earlier ones already cut while the caller reported "refusing a
partial repair". Verification and truncation are now one all-or-nothing pass in
`verify-and-truncate.py`: every pair is checked (boundary, size, and that the bytes `[end, size)`
are really zeroed, read in chunks) and nothing is cut unless all of them pass.

**The sweep, the table argument and the dry run (`P6-094`, `P6-387`, `P6-388`, `P6-389`, `P6-392`,
`P6-393`).** `TABLE_ARG` became a path under `/d/default` unvalidated, so `../../etc`, an absolute
path or a glob escaped the table directory; `TABLE_DIR` was then interpolated into a `sh -c find`
command, so a name with spaces, `*`, `;` or `$(...)` executed arbitrary commands in the throwaway
container. The argument is now validated against `[A-Za-z0-9._-]+` and passed as an argument, never
as script text. `docker ps --filter name=X` is a substring match, so the health reads could
aggregate `fluss-tablet` with `fluss-tablet-helper`; status is now read with `docker inspect` on the
one resolved container. `--all` enumerated tables with an unquoted `for` over `ls` output (breaking
on whitespace) and a zero-table result swept nothing and *succeeded*, masking a volume layout change
as a clean bill of health; enumeration is NUL-delimited and empty is an error. Finally `DRY_RUN=1`
was not dry: it still refused when the tablet was `Up`, and when it did report, the single-table
path fell through to `docker start` on an already-running container. A dry run now stops nothing,
changes no policy, cuts nothing and starts nothing.

## Judgement calls (review these)

1. **Stopping the tablet before the scan changes when the tool may be run.** The old flow scanned a
   running tablet and refused if the result looked torn; the race that produced the torn-looking
   result is exactly `P6-096`, so the scan now happens only after the tablet has stopped. A healthy
   tablet that the operator points this tool at is therefore stopped and started again (and the
   clean case restarts it explicitly rather than leaving the stack down). That is a real behaviour
   change for a tool that used to be read-only until it found something; it is the price of never
   measuring an offset against a file that is still being appended to.
2. **The unverified half stays unverified, and that is recorded.** The scan, the truncation and the
   post-repair recovery check need a live Fluss tablet with a genuinely torn segment, so no test in
   this wave ran them against real docker. The new suite drives the script through a stub `docker`
   — it asserts the order of the calls (policy pinned, stop, scan, verify, restore, start), the
   refusals and the policy restore on every exit path — and drives the verification/truncation logic
   directly against real files on the host, where the data-loss risk lives. What is *not* executed
   is LogScan.py itself and a real docker stop/start cycle.
3. **`--bootstrap` replaces a positional that no in-repo caller used, and that is still a CLI
   change.** `RawTableAdmin` is documented in three places and called from `tiering-smoke.sh`, which
   passes no positional argument, so nothing in the repository breaks. Any out-of-repo script that
   passed a bootstrap address positionally now gets an argument error instead (exit 2) rather than
   silently keeping the old meaning — hence `COMPATIBLE_WITH_LIMITATION`. The alternative, guessing
   whether `args[1]` is a host or a partition, is what caused `P6-004`.
4. **`add-partition` validates the calendar date, not just the shape.** `20260230` has the right
   shape and would create a partition no writer ever targets; `LocalDate.parse` with
   `BASIC_ISO_DATE` rejects it. This is one step stricter than the finding asks for.
5. **Two pins were updated rather than deleted, and one check moved files.** `P6-098` turned
   `test_repair_tablet_parser.py`'s `assertIn("unsafe truncation", script)` into an assertion about
   the verifier the script now calls, because the boundary check moved into
   `verify-and-truncate.py`. `test_tiering_restart_guard.py` was already updated in wave 8. Both
   keep asserting the property; only its location changed.
6. **`P6-654` is still open and this wave does not touch it.** Its remaining half — the
   strictly-increasing date rule rejecting legitimate same-day multi-table chains — must change in
   `AuditHashChain.java` and its byte-exact Python mirror in `r2_legal_hold_check.py` together, in
   the wave that owns that file.

## Verification

1. **Red before green, per half.** The admin suite was run against the pre-fix source
   (`sha256 6da4c746…`) with the same classpath: **9 failing checks** — the date cases dialled the
   bad string as a bootstrap address, the missing/extra-argument cases exited 1 *after* opening a
   connection, and the `--bootstrap` address was never dialled. The guard suite was run against the
   pre-fix script (`sha256 e949b4b5…`) with the same stub `docker` and fixtures: **every one of its
   10 tests failed** (9 at test level plus 7 failing subtests — pytest reports a subtest-only
   failure as a passed test plus `SUBFAILED` entries). Its 6 verifier tests pass in that run because
   `verify-and-truncate.py` is new code; the behaviour they pin away (a bare range check, no
   zero-tail verification, a non-atomic truncate loop) is the pre-fix truncate body quoted in
   `P6-098`/`P6-099` and the recorded red run shows the pre-fix script never consulted any verifier.
2. **Green on the fixed code.** `test_raw_table_admin_args.py`: **5 tests, 5 subtests, 0 failures**.
   `test_repair_tablet_guards.py`: **16 tests, 12 subtests, 0 failures** (the verifier is also
   exercised directly: clean tail truncated, non-zero tail refused and left byte-identical, unsafe
   boundaries refused, malformed/empty/missing pairs files refused, and one bad pair leaving the
   good segment untouched). `test_repair_tablet_parser.py` stays green.
3. **The helper suite: 524 tests, OK** (503 before the wave; +5 admin, +16 guard).
4. **`full_audit.sh`: exit 0, 200 `[PASS]` / 0 `[FAIL]`**, including the change-control check
   that reads this record.
5. **Not run in this wave:** the Monday gate (a certificate re-run needs its own decision); any real
   docker stop/start/truncate cycle against a live tablet; no Java build change — `RawTableAdmin`
   is compiled by `tiering-smoke.sh`'s GUARD-D with the same command the new test uses, and the new
   code adds no import beyond `java.time`/`java.util`.
