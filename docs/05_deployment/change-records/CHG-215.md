# CHG-215 — steps 14/16 stop re-running step 9's live drill classes

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** certifying gate run 4b, step 14 (`Execution gateway module suite`)
  red. Root-caused from that run's own surefire report, its 1.65 GB
  `gateway-suite.log`, and the classes' own `FLUSS_BOOTSTRAP` gating.

## What happened

Step 14 failed with `Tests run: 153, Failures: 1` — `B4HaltedIntentConsumeDeferE2ETest`
alone, on its 420 s preemptive envelope:

```
Tests run: 1, Failures: 1, Errors: 0, Skipped: 0, Time elapsed: 420.0 s <<< FAILURE!
org.opentest4j.AssertionFailedError: execution timed out after 420000 ms
```

The class had already run and passed in the same gate run, in step 9's drill
(62.11 s, green). It ran a **second** time because every drill class self-gates on
`FLUSS_BOOTSTRAP` (`Assumptions.assumeTrue(System.getenv("FLUSS_BOOTSTRAP") != null …)`)
and step 14 invokes the module suite with the gate's environment, in which that
variable is set. So the whole live set — the same classes `make drill-live` names —
executed again against the live cluster on top of the drill's own table churn.

That second run arrived while the coordinator was working through the
table-deletion backlog left by the run's DDL-heavy steps (~one deletion per 10 s;
`TableManager.resumeTableDeletions()` completes a drop only after every bucket
replica confirms). B4's fresh scratch tables did not get replicas placed inside the
envelope, the preemptive timeout interrupted the test, and its cleanup dropped the
scratch DB while a write was still pending — 628,185 lines, 1.65 GB, all
`TableNotExistException: Table 'b4_halted_…Execution_Intent' does not exist.`

Step 9's java suite never had this problem: it runs the same modules under
`env -u FLUSS_BOOTSTRAP`, so those classes self-skip there (`Tests run: 0` in the
plain reports). Steps 14 and 16 had no such guard.

## What changed

`run-monday-gates.sh` now excludes the drill-owned classes from both module suites:

```
DRILL_OWNED_CLASSES_GATEWAY='GatewayFlussIntegrationTest,GatewayFlussDurableReplayIntegrationTest,B4HaltedIntentConsumeDeferE2ETest,GatewayStartupPrewarmTest,FlussProjectionWriterIntegrationTest'
DRILL_OWNED_CLASSES_COMPUTE='B4SignalIntentE2ETest'
surefire_exclude() { printf '!%s' "$(printf '%s' "$1" | sed 's/,/,!/g')"; }   # A,B -> !A,!B
```

step 14 → `mvn -o test -pl 02_services/06_execution_gateway "-Dtest=$(surefire_exclude "$DRILL_OWNED_CLASSES_GATEWAY")"`,
step 16 → the same with `_COMPUTE`. An exclusions-only `-Dtest` list runs everything
else, so each module's remaining tests (readiness, HTTP approval authority, halt
tails, the reader-death pin, …) still run exactly as before.

The exclusion is by name rather than by `env -u FLUSS_BOOTSTRAP` on purpose: a
blanket unset would also skip any live class a module suite runs that the drill
does *not* cover — step 16 has such classes. Excluding only the drill's own list
keeps coverage identical while removing the duplicate.

**Coverage argument.** The 9 tests those 5 + 1 classes carry still run in the same
gate run, in step 9's drill, against the same live cluster — where they passed
this run: B4 62.11 s, `GatewayStartupPrewarm` 379.4 s, `FlussProjectionWriter`
22.48 s, `GatewayFluss` 33.08 s, `GatewayFlussDurableReplay` 77.56 s,
compute `B4SignalIntentE2E` 86.51 s. No assertion, test or module was removed from
the harness.

## Evidence

`test_gate_drill_exclusions.py` (new, harness guard suite) keeps the two lists from
drifting: it parses the `drill-live` target out of the Makefile, locates each
class's module, and fails if any drill class of the gateway or compute module is
missing from the matching exclusion list, if a module suite stops passing the list
to surefire, or if an exclusion names a class the drill no longer runs (which would
otherwise stop being tested anywhere).

- Guard green on this tree (4 checks); negative control: blanking
  `DRILL_OWNED_CLASSES_GATEWAY` turns it red with the missing class named.
- Step 14's exact command, `FLUSS_BOOTSTRAP=localhost:9123` (i.e. the failing
  condition reproduced): `BUILD SUCCESS`, `Tests run: 144, Failures: 0, Errors: 0,
  Skipped: 0`, total 11.3 s — against 11+ minutes and 1 failure before.
- No fresh surefire report for any excluded class (their `.txt` mtimes stayed at
  16:04–16:19 from run 4b across the 16:22 verification run).
- `bash -n` and `shellcheck -S warning` clean on the edited script.

## Placement, and the guard that caught the first attempt

The first version of this change defined the two lists immediately above step 14.
The harness's own `test_gate_variable_scoping` rejected that in the next gate run
(step 3: `Ran 1477 tests … FAILED (failures=1)`) with:

```
step14: DRILL_OWNED_CLASSES_GATEWAY, step16: DRILL_OWNED_CLASSES_COMPUTE
a step reads a variable that neither it nor the shared region assigns — a --steps
run that skips the assigning step will abort
```

A variable assigned inside step 14's guard region is unset for
`run-monday-gates.sh --steps 16`, so that subset run would have aborted. The lists
and `surefire_exclude()` now live in the shared region above the preflight, next
to `DRILL_LOG`; `test_gate_variable_scoping` (3 checks) and
`test_gate_drill_exclusions` (4 checks) are both green after the move.
