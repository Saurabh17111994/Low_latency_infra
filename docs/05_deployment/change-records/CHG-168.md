## 1. `soak-monitor.sh` — watch the subject it claims to watch (7 findings)

### 1.1 Which process is sampled (P6-018, CRITICAL)

| Finding | Was | Now |
|---|---|---|
| P6-018 | `awk -v pat="$1" '$3 ~ pat { print $1, $2 }' \| sort -k2 -n \| tail -1`. The third ps column is the first token of args (`java`), never the service class in argv[4+], so the startup check and every sample missed the real process; and the largest elapsed time is the oldest process, contradicting the `Newest matching PID` comment | the pattern matches the full command line, passed through the environment so the awk sibling cannot self-match, the monitor's own PID is excluded, and the smallest elapsed time (most recently started) wins; no match prints nothing at all |

| Finding | Was | Now |
|---|---|---|

| P6-199 | a rotated or truncated journal was read past EOF and the offset reset to the new small size, silently skipping bytes; a briefly absent journal kept a stale offset | rotation/truncation is detected by inode + size before each read and counted from the start of the new file; a vanished journal is fatal |

## 2. `soak-reconnect-loop.sh` — force one real crash and prove no leak (7 findings)

### 2.1 Which process is found and killed (P6-201, P6-203)

| Finding | Was | Now |
|---|---|---|
| P6-201 | `sort -k2 -n \| tail -1` picked the largest elapsed time — the oldest match — so with a stale leftover process the loop sampled and SIGKILLed the wrong bridge | the smallest elapsed time (most recently started) wins, with the same full-line environment match as the monitor |

| Finding | Was | Now |

| P6-202 | discovery and SIGKILL went through the container namespace while `count_progress` grepped the host journal path, so container-mode cycles read stale data and reported NOT RECOVERED | the count is taken through the same namespace wrapper as discovery: container mode probes the container path, host mode the host path |
| P6-204 | a single fixed `sleep SETTLE_SEC` made recovery flaky both ways: slow restarts failed spuriously, fast ones waited out the clock | `wait_recovery` polls for Java alive AND a bridge child AND journal progress until the settle deadline, and prints the three values for the caller to judge |

### Red leg — what it proves and what it does not

Every `disc`-marked case fails against the pre-wave scripts (51/55: 23 monitor +
28 reconnect). Four probes that pass pre-fix carry no marker and are documented as
non-discriminating: the monitor's no-match probe (both copies print nothing) and its
dead-PID fd probe (both copies read zero through the fixture tree), plus the reconnect
no-match probe (both copies print nothing) and its host-mode journal probe (container
namespacing is orthogonal to host counting). Twelve contract probes that also fail
pre-fix are marked as regression pins (functions are top-level, journal readers use
the fixture tree, TSV/column shapes stay stable for the caller), not as behaviour
evidence. Most red failures are structural: the pre-wave
monitor had no `validate_args`/`journal_inode`/`count_window`/`main` decomposition and
the pre-wave reconnect loop had no `validate_args`/`resolve_restart_budget`/
`bridge_pid_ok`/`kill_bridge`/`wait_recovery`/`main`, so the driven gates did not exist
under those names. That demonstrates the suite is not vacuous; it does **not**
demonstrate that each individual behaviour was wrong (the per-finding evidence for that
is the audit's line-level findings, quoted in the tables above). P6-018 is the
exception: it is additionally demonstrated behaviourally, both sides running against
one fixture, with the pre-fix line taken verbatim from the parent commit.

### Live evidence — no soak was run (approved)

This wave was verified by tests only. No soak was sampled, no bridge was killed and no
container was touched for this record; every claim above about script behaviour is
either a line-level reading of the script or a stubbed execution of it. The live stack
also could not have hosted a soak here: the Monday-gate preflight for this wave series
refused to start on environment drift — the Fluss coordinator/tablet containers are
`exited (127)` and the dev journal endpoint has been down for ~20 h — and both scripts
need a live ingestion process plus its bridge child. Consequently the live half of both
scripts including the real crash-restart window and the multi-hour fd/thread trend
remains unverified by this change; it is verified on a live stack only when a soak is
next run against one.

## 4. Residual, not closed here

- The monitor's bridge OS-thread column stays a weak proxy: the runtime multiplexes its
  workers over a small thread pool, so the authoritative worker signal remains the
  bridge's own in-process telemetry event (noted in the script header, unchanged).
- The reconnect loop still drives at most the service's restart budget (1 by default):
  a second crash in one process run is terminal by design, and cycles above the budget
  stay refused rather than attempted.
- Both scripts keep their existing CLI and evidence shapes (`<duration> <interval>` /
  `<cycles> <settle>`, TSV column orders byte-identical to the parent) so the
  `run-full-suite.sh` caller needs no change.
