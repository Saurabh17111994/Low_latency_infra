## What changed

- `JAR_FRESHNESS_ROOTS` + `require_fresh_jar()` in the helpers region: fails
  closed when any file under the compute module `src/main`/pom, the `common`
  dependency `src/main`/pom, or `code/pom.xml` is newer than the jar.
  `ALLOW_STALE_JAR=1` is the documented escape hatch for a deliberate rollback.
- Preflight call `require_fresh_jar "$JAR"` immediately after the jq check —
  before any cluster interaction and before the savepoint/stop, so a stale jar
  can never leave the job stopped.
- Corrected the deploy-time "build it first" hint: compute is **not** in the
  `code/` reactor (R-272); the working command is
  `cd code/02_services/02_compute && mvn -o package -DskipTests`.

## Why

- The rollout deploys a **prebuilt** module jar; nothing rebuilt it after the
  source edit, and no probe can tell which artifact is running.
- The jar shades `common` (312 classes) and bundles dependency classes, so
  common sources, the parent pom and the module pom all belong to the input
  set.
- Failing before the savepoint protects both correctness (no old-code restore)
  and availability (the running job is untouched on refusal).

## Residuals

- The check is mtime-based, not a content stamp: touching a source without a
  content change forces a rebuild (safe direction); a content change always
  bumps the mtime.
- `pipeline-lib.sh` also copies `compute.jar` to the JobManager (submit path,
  ~line 1082) and has no freshness check, so the fresh/day-start submit path is
  still unguarded. Candidate: reuse this helper there.
