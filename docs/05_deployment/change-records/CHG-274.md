## Why

Decision 2026-09-21 (recorded in `docs/08_implementation/09-production-swarm.md`): images come from
**public GHCR**, not from a `registry:2` container on VM1. The first claim made about the change — that
it needed configuration only, because `image-publish.sh` already accepts an `https://` registry and
already treats a 401 probe as "answers" — **was wrong**, and a rehearsal caught it. Two code paths
assume a plain-HTTP registry reached at `host:port`, and both fail a *correct* GHCR setup:

1. **The reachability probe used the owner path.** The script probed `${scheme}://${registry}/v2/`, and
   for a GHCR target `--registry` carries an owner (`ghcr.io/<owner>`), so the probe requested
   `ghcr.io/<owner>/v2/`. GHCR answers that **404** — the v2 API root lives at the registry host, never
   under a repository path — and the run stopped with "no registry answered … bring it up on VM1 first"
   for a registry that was healthy. Measured first against a local `registry:2` under the same owner
   path: `no registry answered at http://localhost:5000/saurabh17111994/v2/ (http 404)`.
2. **`vm-bootstrap.sh --check` failed every GHCR host.** With no `--registry` argument it required a
   non-empty `insecure-registries` list in `daemon.json` and called a host without one a failure ("the
   nodes cannot pull from the registry"), and it failed outright when `daemon.json` was absent. That is
   the correct rule for a plain-HTTP registry and a false alarm for GHCR, which is HTTPS and pulls
   anonymously: on VM day it would have failed all four nodes at S3, before any of them joined the
   swarm.

## What changed

- `image-publish.sh`: the probe now uses the registry **host** (`${registry%%/*}`), and its message
  names the host and the two cases (private registry vs GHCR). Ref building, `--env-registry` and digest
  resolution are untouched — they were already correct for an owner path.
- `vm-bootstrap.sh`: `check_daemon_json` **moved, not deleted**. A missing `daemon.json` or an absent
  `insecure-registries` list is now `[INFO]` when no `--registry` is given (nothing to declare for an
  HTTPS registry), while `--registry HOST:PORT` keeps the original fail-closed rule, and invalid JSON
  stays a failure in both cases.
- Tests: one new test in `test_14_image_publish.py` pins the whole GHCR landing path (fake `docker` on
  `PATH`, a stdlib registry that answers **401 only on `/v2/`** and 404 everywhere else, push target
  `<host>/<owner>/<image>:prod`, env rewritten to `ghcr.io/<owner>/…:prod@sha256:…`); three tests in
  `test_12_vm_bootstrap.py` pin the moved guard.
- Docs: the runbook's registry rows, S4 steps 5–6, firewall table, acceptance check and deploy notes
  now describe GHCR and R2; the plan document carries the dated decision.

## Measured while verifying

- The rehearsal that found the bug: `--registry localhost:5000/saurabh17111994` → `http 404`, exit 2,
  zero pushes. With the fix: `localhost:5000/v2/` answers 200 and the seven images push under the owner
  path.
- **The publish rehearsal end to end:** `--registry localhost:5000/saurabh17111994 --tag prod` →
  exit 0, seven pushes, and seven deploy values of the form
  `ghcr.io/saurabh17111994/<image>:prod@sha256:…` (one per `${X_IMAGE:?}` the stack demands). The local
  registry serves them under the owner path — `GET /v2/saurabh17111994/trading-flink-runtime/tags/list`
  → `{"name":"saurabh17111994/trading-flink-runtime","tags":["prod"]}`. The ingestion digest this run
  resolved is byte-identical to the one `~/.p6v/reh/rehearsal.env` already pins (`sha256:d41329f4…`):
  that is the content-addressing property the whole digest pin depends on — the address changes, the
  digest does not.
- `test_14_image_publish.py`: **11 passed**. Mutation — probe the owner path again: the new test fails
  (`no registry answered at http://127.0.0.1:<port>/v2/`), because the fake registry is path-strict; an
  earlier version of the fake that challenged *every* path passed the broken script too.
- `test_12_vm_bootstrap.py`: **24 passed**. Mutation A — make the missing-file branch fail
  unconditionally: caught. Mutation B — downgrade the declared-plain-HTTP `does not list` branch to
  `info`: caught by the pre-existing `test_daemon_json_must_declare_the_registry`, which is how the
  guard was shown still live. Restore verified byte-identical (`cmp`), then re-run green.
- `bash -n` clean on both changed scripts.

## Not verified

- **A real push to GHCR.** No PAT exists yet, so the seven images have only been pushed to a local
  `registry:2` under a GHCR-shaped owner path. The first real publish is the step that proves it.
- **An anonymous pull by a node.** `docker manifest inspect ghcr.io/…` without credentials is what the
  VMs depend on; it is recorded as the S4 exit check and cannot be run before the packages exist.
- **A private package.** Not chosen, and untested: the token-on-every-node path described in the
  runbook is reasoning, not measurement.
