# CHG-189 — the Flink jobmanager can create its checkpoint directories (wave 36)

- **Status:** recorded — fixes a pre-existing deployment defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** found while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`. It is the layer immediately
  behind CHG-185/186/187/188: with those fixed, the run reached job submission
  for the first time and failed there.

## What happened

Submitting `SignalJob` failed at the checkpoint coordinator:

```text
java.io.IOException: Failed to create directory for shared state:
file:/checkpoints/59a848d3dabbe17f7ad875fa17f66c6b/shared
  -> org.apache.flink.util.FlinkRuntimeException: Failed to create checkpoint storage at checkpoint coordinator side.
```

The image `flink:2.2.1-scala_2.12-java17` ships **no** `/checkpoints`
directory, so Docker creates the `flink-checkpoints` volume's mount point as
`root:root` (mode 755) the first time it is mounted. The image's default user is
`flink` (uid 9999), which then cannot create the per-job `shared` directory:

```console
$ docker exec -u 9999 01_docker-flink-jobmanager-1 mkdir -p /checkpoints/x
mkdir: cannot create directory '/checkpoints/x': Permission denied
$ docker exec -u 0    01_docker-flink-jobmanager-1 mkdir -p /checkpoints/x
(created)
```

**This is a repo defect, not stale local state.** Mounting a brand-new named
volume at `/checkpoints` on the same image reproduces it exactly
(`/checkpoints` comes up `root root`), while a path the image *does* own comes up
correctly (`/opt/flink` -> `flink flink`): Docker copies image ownership only
for mount points that exist in the image. So every `make up` against a fresh
`flink-checkpoints` volume hits this.

**Why it had never been seen.** No run in the repository's `logs/` history has
ever recorded a checkpoint, and none had ever reached job submission — the four
defects fixed by CHG-185 through CHG-188 all failed earlier, so this layer was
unreachable. The `flink-jobmanager` and `flink-taskmanager` services both mount
the same volume, but only the taskmanager carried a `user: "root"` line — added,
per its own comment, for the same class of failure on a different path
("/tmp/fluss ... the image default user flink:flink gets AccessDeniedException").
The jobmanager, which is the process that actually creates checkpoint storage,
did not.

## The fix

Give `flink-jobmanager` the same `user: "root"` the taskmanager already uses,
with the same dev-only rationale:

```yaml
    user: "root"
    volumes:
      - flink-checkpoints:/checkpoints
```

The `compute` service also mounts this volume but only submits jobs; it does not
create checkpoint directories, so it is deliberately left unchanged.

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*Deployment topology*. This changes the identity a deployment service runs as,
and it is the enabler for the checkpoint storage that the durability contract
(T9/G4) depends on.

## Verification

* Root cause proven by direct experiment on the live containers: uid 9999 cannot
  create `/checkpoints/x` (Permission denied), uid 0 can.
* Reproduced on a **brand-new** named volume on the same image, so the defect is
  a repo/docker interaction rather than stale volume state; the image has no
  `/checkpoints` directory (`ls: cannot access '/checkpoints'`) while `/opt/flink`
  is `flink flink`.
* Established the defect had never been reached: no `logs/**/checkpoints.jsonl`
  in the repository is non-empty, and no harness run recorded a job id.
* `docker compose config` exits 0 and renders `flink-jobmanager: user='root'`
  (taskmanager unchanged at root, compute unchanged at None).
* Live: the recreated jobmanager reports `uid=0(root)` and
  `mkdir -p /checkpoints/probe-fix/shared` succeeds.
* `python3 code/01_platform/04_scripts/change_control_check.py` exits 0.
