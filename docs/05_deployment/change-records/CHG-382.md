# CHG-382 — M4-3: bounded-queue backpressure reaches readiness

- **Status:** complete — every bounded queue's 80%/100% listener is wired: WARNING/CRITICAL mark
  that queue blocked in `HealthProbe` (readiness false + readiness-marker sync), RESUMED clears it
  after the drain. Before this, `BoundedQueue.setListener` had no production caller, so a queue at
  the warning band or a stalled writer behind a full queue left the service "ready" (audit I3).

## Notes

- **Why the listener is not the drop counter:** the CRITICAL event and the first rejected offer are
  the same instant; routing CRITICAL into `onWriterDrop` would count a phantom record loss on top
  of the offer site's real one. The listener owns readiness, the offer site owns the loss, and the
  handler's durable record + fail-fast stop stay once per process (CAS).
- **RESUMED on an empty queue:** `poll()` clears an active episode even when nothing was drained,
  so a single oversized-row rejection on an empty queue cannot latch readiness blocked forever.
- **Wiring proof:** `QueueBackpressureReadinessTest` invokes the listener the service actually
  stored on each queue (a default no-op would leave readiness untouched), which is deterministic —
  a behavioral test would race the live writer workers, and `WriterWorker.close()` closes the queue.
