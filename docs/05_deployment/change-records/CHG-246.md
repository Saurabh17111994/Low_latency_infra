# CHG-246 — the example inventory marks O1 as a joined worker, so its swarm checks actually run

## Why

`prod_vms.example.json` is the template an operator copies to `prod_vms.json` before the `D1.3`
acceptance gate. Its O1 entry declared `"swarm": false` with `"role": "observability"`, matching a
topology note that placed O1 outside the swarm.

Two facts made that wrong, and each hides the other:

- The stack pins three observability services with `node.labels.observability == true` and thirteen
  workload services with `node.labels.role == worker`. A node label only exists on a joined node, so
  an O1 outside the swarm leaves those three services at `0/1` with no node to land on — forever,
  because nothing else carries the label.
- `prod_node_check.py` skips its swarm check entirely when `swarm` is false, so the gate reported
  PASS for a node whose labels and role were never verified. The template's own bug was invisible to
  the gate that reads it.

Flipping the flag alone would have made the gate FAIL: the checker compares the inventory's `role`
against the role the swarm actually reports (`manager` / `worker`, case-insensitive), and no swarm
node reports `observability`. The flag and the role therefore had to change together, which is what
the new test asserts.

## What changed

- `code/01_platform/04_scripts/prod_vms.example.json` — O1: `"swarm": false` → `true`,
  `"role": "observability"` → `"worker"`; the `observability=true` label is unchanged.
- `code/01_platform/04_scripts/tests/test_10_prod_node_check.py` — new
  `test_example_inventory_marks_o1_as_a_joined_worker`: every `swarm: true` node must declare
  `manager` or `worker`; O1 must be a joined worker carrying the observability label; and no other
  node may carry that label, which is the property that keeps the trading stack off the
  observability VM.
- `code/01_platform/04_scripts/prod_node_check.py` — its `--self-check` fixture keeps a non-swarm O1,
  because that fixture is the only cover for the "not joined" branch, but the fixture and the run now
  say so: the self-check prints `FAKE inventory — classification proof only, not the shipped
  topology` before its per-node lines, and the fixture entry carries a comment not to copy it.
- `docs/05_deployment/PROD_VM_PROVISIONING.md` — the documentation half of the same decision: §1 and
  §2 describe O1 as a joined worker outside the manager *quorum*, §5.1 records the registry choice,
  and §9 carries the executable `S4`/`S5`/`S6` steps plus the three-item security baseline.
- `docs/08_implementation/09-production-swarm.md` — v1 and v2 topology diagrams and prose describe
  O1 as a joined worker with no vote, and build-plan item 1 names the registry mechanism.

The checker's `swarm: false` path stays supported and tested (`test_observability_skips_swarm_checks`):
a genuinely non-swarm node remains a legal inventory entry. O1 simply is not one, because the stack
places work on it.

## Limitation

The template describes the v2 topology (3 managers + 3 workers + O1). The v1 baseline reuses those
entries with a different label set — VM1–VM3 carry `role=worker` and no `role=manager`, because a
node holds one value per label key — and that v1 label set is documented in the VM guide but not
asserted by a test. A future inventory that switches to v1 will not be caught by this test.
