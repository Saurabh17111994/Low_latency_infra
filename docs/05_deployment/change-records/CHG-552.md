# CHG-552 — the ingestion client's own Fluss writer metrics become observable (opt-in JMX bridge)

- **Status:** implemented (opt-in instrumentation; the client's configuration is byte-identical when
  the flag is off).
- **Filed:** 2026-10-06
- **Source:** Task 3b of `docs/plans/2026-10-06-p99-integrated-program.md`. The p99 ≤ 50 ms program's
  tail was traced to the ingestion client's accept→ack path (Task 3c/3d/3e), and the two instruments
  that exist on that path **disagree**: the client reports
  `append.latency.ms` p50 9–13 ms while the tablet counts only 22.4 `produceLog` requests/s carrying
  ~137 KB (≈ 217 rows) each. A batch that needs ~137 ms to accumulate cannot be acked in 10 ms, so one
  of them is not measuring what its name says, and nothing in any captured arm can adjudicate.

## What changed

1. **`FlussClientMetrics`** (new, package-private): reads the Fluss client's own MBeans out of the
   **platform** `MBeanServer` and returns `{domain-tail + "." + attribute -> value}` for beans under
   `org.apache.fluss.client.*`, numeric attributes only, capped at 64 gauges, empty map on any
   `JMException` (a metrics read must never break ingestion).
2. **`OtlpMetricsEmitter`**: `flushInternal` appends those as `fluss.client.<name>` gauges through the
   existing `appendGaugeDouble` helper. Nothing is emitted when the reporter is off, so fleet arms that
   do not set the flag are unchanged.
3. **`FlussClientAdapter.connect(...)`**: new 6-arg overload; when enabled it sets consumer-side
   `client.metrics.enabled=true` and `metrics.reporters=jmx` **with no port**, which registers the
   metrics in the platform MBean server (no RMI, no JVM flag, no extra dependency — the JMX reporter is
   bundled inside `fluss-client-1.0.0.jar`).
4. **Plumbing**: `FLUSS_CLIENT_METRICS_ENABLED` (declared in `ConfigKeys`, parsed in `IngestionConfig`
   with default `false`, mirrored to the config env map) and a `-e` passthrough in the deck start
   (`pipeline-lib.sh`) and both harness fleet starts (`stage-profile.sh`).

## Why JMX and not Prometheus

`client.metrics.enabled` defaults to **false**, which is why the client-side split is absent from every
arm: the `fluss_client_*` series that *do* appear in job arms belong to the Flink connector, which
enables its own registry. `fluss-metrics-jmx` is bundled with the client; `fluss-metrics-prometheus`
is not present in the local `.m2` and would add a dependency, which the platform's dependency rules
require asking about first.

Metric names: the Fluss reporter encodes the metric path in the **MBean domain** and exposes generic
attribute names, i.e. `org.apache.fluss.client.writer.batchQueueTimeMs` with attribute `Value`
(also `Count`, `Rate`, `99thPercentile`, `bufferWaitingThreads`, …). Verified by probing the jar:
leaving `metrics.reporter.jmx.port` unset registers 25 `org.apache.fluss.*` MBeans in the platform
MBean server with no JVM flag.

## Verification

* New unit test `FlussClientMetricsTest` (hermetic: no cluster, no Fluss connection) — see
  `test_updates` above.
* `mvn -q test -pl common,02_services/01_ingestion -Dtest=FlussClientMetricsTest`.
* The measurement arm that spends this instrument (`FLUSS_CLIENT_METRICS_ENABLED=true`) is recorded under
  `logs/tracker-14/` with its raw `fluss.client.*` series.

**Value contract (learned the hard way, 2026-10-06):** the flag goes through
`IngestionConfig.boolEnv`, which accepts **only `true` / `false`** — passing `1` aborts startup with
`Ingestion config validation failed (1 errors): FLUSS_CLIENT_METRICS_ENABLED must be true or false, got: 1`.
Both harness scripts therefore default it to `false` (the repo-wide convention for boolean env keys),
not `0`.

## What deliberately did NOT change

* **No client-side Prometheus reporter** (would need a new dependency).
* **No change to the writer's own tuning** — `client.writer.batch-timeout=1ms`, `batch-size=64KiB`,
  dynamic batch sizing off, `buffer.wait-timeout=30s` stay exactly as the O-2 / Exp 4 / R-297
  decisions left them.
* **No `make gate` step** and no new always-on metric: the bridge is opt-in per arm.
