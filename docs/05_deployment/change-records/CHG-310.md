## What changed

1. **`pipeline_purge_table`** no longer re-creates the current day's partition after dropping a
   partitioned table's partitions. The partitioned branch ends with the drops and prints
   `PURGED <table> (partitions=N)`.
2. **`writePathBlocked`** treats a partitioned table with zero partitions as *not blocked*: there
   is no bucket to probe, and the next append creates the day. Without this, every purge would
   have spun to the settle timeout and warned.
3. The unused imports and the `timeZone` helper (only the pre-create used them) are gone.

## Why it is safe

- Measured on 1.0 (dev stack): a brand-new client appending to a purged partitioned table logs
  `Dynamically creating partition ...` and succeeds in 258 ms; the partition is present right
  after and a second fresh client appends fine. The server-side `Register partition` line
  confirms the client drove the create (no "Auto partitioning created" sibling).
- Every purge caller purges BEFORE it starts a writer (`pipeline_purge_raw_table`: "Raw must be
  purged BEFORE pipeline_start_ingestion"; `stage-soak-e2e.sh` / `holistic-measure.sh`: purge
  then bring-up), so the append always comes from a fresh client - the measured case.
- Any transient churn on the newly created bucket is retryable in the ingestion
  (`RetryClassifier`: NotLeaderOrFollower / PartitionNotExist / UnknownTableOrBucket -> RETRYABLE),
  so a first append cannot be lost to it.
- The 1.0 out-of-date rejection (writes to out-of-retention partitions) is already handled by
  CHG-309 (drop + count, never halt).
