## Problems found

The first C2 attempts exposed independent pre-kill failures rather than proving
TaskManager recovery:

1. Raw-table purge/recreate lost `PARTITIONED BY (event_day)` because the DDL
   parser discarded partition keys. Fluss then rejected the table's auto-
   partition configuration.
2. A pre-existing tiering job had no restart backoff and remained failed after a
   TaskManager shutdown. The drill could also submit a second tiering job while
   an older one was still restarting.
3. Concurrent drill processes consumed the local TaskManager's ten slots and
   made SignalJob submission fail with `NoResourceAvailableException`.
4. The shaded compute artifact bundled roughly 9,000 Fluss classes while the
   Flink image supplied the Fluss runtime. ServiceLoader then loaded the HDFS
   token receiver against a duplicate interface and failed with `not a subtype`.
5. G7 counter analysis treated a reset as data loss, and a single global first-
   candle window caused false loss reports for tokens that started later.
6. After the partition fix, the compute job still used v2 raw-row indexes while
   the recreated v3 table put `event_day` at index 0. The watermark then read
   the `symbol` string column as a long and restarted before the kill point.
7. The live Flink vertex summary exposed zero read/write counters while a
   running SignalJob was processing records; the accumulated counters only
   became populated after cancellation. The warm-up guard therefore rejected
   a healthy feed and needed the live aggregate metrics endpoint.
8. Compose short bind syntax had created directory-shaped sources when plugin
   jars or `alert-consumer.py` were absent. Later container starts failed with
   OCI exit 127 (`not a directory`) instead of identifying the missing source.
9. The default Compose stack starts one read-only `Babysitter Positions
   observer`. Treating every non-tiering job as a conflict made a valid C2
   stack fail before submission; duplicate Babysitter instances still remain
   forbidden because they consume slots.
10. After the live metric endpoint was adopted, its counters reset when the
    recovered task attempt was installed. Comparing the pre-recovery absolute
    value with the post-recovery final value falsely reported `120048 -> 73793`
    as no progress even though the post-kill samples increased continuously.
11. The coordinator container could be running while the tablet was still
    crash-looping on a truncated log segment. The drill reached the first
    destructive purge and received `Alive tablet server is empty`; coordinator
    liveness alone was not a safe Fluss readiness contract.
12. After the v3 daily-partition migration, the G7 reader still used the
    non-partitioned LogScanner overload and v2 raw-column indexes. Fluss then
    rejected subscription with `please use subscribe(partitionId,bucket,offset)`;
    after that was corrected, the stale indexes raised `BinaryString cannot be
    cast to Long`. The streamed reader also suppressed stderr and opened its
    evidence file in `w` mode, hiding the root cause and risking prior-evidence
    truncation. The reader now enumerates partitions, validates the exact v3
    schema, uses v3 indexes, preserves evidence via a temporary file, and
    records non-zero exits/timeouts in a per-table stderr artifact.
13. The non-streaming preview, final-candle, and signal readers had the same
    fail-open shape: a non-zero Java reader exit was ignored and an old
    evidence file could make the analyzer continue with an empty in-memory
    result. They now record stderr, preserve prior evidence, return a failure
    sentinel, and make the owning G6/G7/F4 guard fail closed.
14. The 2026-09-01 full-load attempts (3/4) and the clean A/B probe
    (`1ea4e699`, 60s checkpoints, live feed) all emitted ZERO
    candles/previews/signals despite a healthy source (~485k-1.4M records
    consumed). Root cause is a three-factor interaction, none fatal alone:
    (a) the v3 daily-partition table always carries permanently-empty
    partitions — `num-precreate=2` creates tomorrow, and Fluss's
    `AutoPartitionManager` assigns each DAY table a random 0-23h creation
    delay (`ThreadLocalRandom.nextInt(60*23)` minutes) that also back-creates
    yesterday after a purge (p37=20260831, created 5 min post-recreate,
    empty forever); (b) Flink 2.2's `withIdleness` measures split silence on
    a per-split `PausableRelativeClock` that is PAUSED while the task is
    backpressured — under drill load (bp≈850-999ms/s) the 15s idle timeout
    degenerates to 15s/(1-bp) ≈ hours while the drill runs ~7 min, so the
    empty splits stay active at watermark `Long.MIN_VALUE` and the combined
    watermark (min over active splits) never advances; (c) the pipeline
    carries real backpressure at load (candle-15s/preview operators busy
    ~400ms/s at 8-10k records/s). Live-proven 2026-09-01 on job `e4b4c19f`
    (exact drill env, 10k/s feed): zero output at 50-80s with p36/p37
    `accumulatedIdleTimeMs=0` and all 8 source subtasks at wm=MIN; the splits
    went idle once backpressure eased (~100s), the watermark jumped to
    lag≈100s on all subtasks, and 4096 candles + 73k previews fired
    immediately. The pre-08-31 runs passed only because the v2 table was
    unpartitioned (every split carried data).

## Changes and guards

- `tm-kill-full-load.sh` performs a serialized, full-load local drill: strict
  preflight, fresh TaskManager restart, checkpoint freshness before and after
  `SIGKILL`, observed job recovery, post-recovery source/output progress, and
  parity-only G7 analysis. It fails closed on missing jobs, duplicate active
  tiering, missing recovery transitions, stale checkpoints, or no progress.
  `C2_MODE=smoke SMOKE_S=180` runs the same setup and telemetry for a
  three-minute no-kill gate first; it requires a running job, at least two
  completed checkpoints, and reset-aware source/output progress before the
  destructive main mode is allowed to start.
- `pipeline_validate_compute_jar` rejects corrupt jars, bundled Fluss classes,
  and Fluss ServiceLoader descriptors before any cluster-mutating preflight
  step. `test-pipeline-lib.sh` proves both rejection and acceptance paths.
- `pipeline_validate_compose_bind_sources` and the C2 G-TMK-0 guard reject
  missing or directory-shaped file mounts before a drill can touch tables;
  G16 proves both failure shapes and the repository's valid sources.
- `flink_metric_dump` queries live `0.numRecordsIn`/`0.numRecordsOut`
  aggregate metrics for running jobs and uses job-summary counters only as a
  terminal fallback. Its fixture test proves stale live summaries cannot hide
  source progress.
- `c2_progress.py` summarizes the post-kill phase with reset-aware deltas and
  requires a later upward sample after a reset; its tests prove both recovery
  progress and reset-only failure paths.
- `tiering-start.sh` submits fixed-delay restart settings and rejects a running
  tiering job whose REST configuration does not expose that strategy.
- `pipeline-lib.sh` passes explicit restart attempts/delay to SignalJob and
  makes raw-table purge strict for C2, including the `PURGED` marker.
- `pipeline_wait_for_fluss_ready` requires both Fluss containers to be running
  and both client listeners (`:9123` and `:9124`) to accept connections before
  any table mutation. A crash-looping/truncated tablet now fails closed with a
  repair-tool pointer instead of reaching `TablePurge`.
- `DdlText` parses and reapplies partition keys; unit and compatibility tests
  pin the behavior.
- `holistic-analyze.py` uses reset-aware counters and per-token G7c windows;
  parity is always checked while exact counter reconciliation remains gated on
  deliberate injection evidence. Its G7 raw reader now handles the v3 daily
  partitions, checks the live column contract before positional reads, and
  fails closed with visible reader diagnostics. The smaller table readers use
  the same non-zero-exit, timeout, stderr, and evidence-preservation contract;
  a zero-row read cannot silently pass latency or settlement analysis. Unit
  tests pin clean-feed, injected-feed, partition-subscription, schema-index,
  reader-failure, and evidence-preservation behavior.
- The compute POM marks both Fluss connector and client dependencies as
  `provided`, leaving the Flink image as the single runtime classpath owner.
- `RawTableColumns` now mirrors the shared v3 `RawTableSchema` (21 columns),
  and a static initializer fails fast if the local index/name contract drifts;
  regression tests exercise the event-time index and schema ordering.
- `SourceIdleWatchdogGenerator` (compute) now marks a source split idle after
  `SOURCE_IDLE_MS` of WALL-CLOCK silence, in addition to its observability
  role: `output.markIdle()` from `onPeriodicEmit` sets the split's
  `PartialWatermark` idle flag, and `WatermarkOutputMultiplexer` excludes
  idle splits from the combined minimum at the same periodic tick — so the
  operator watermark advances past the empty future-day partitions even while
  `withIdleness`'s pausable clock is frozen by backpressure. The first record
  afterwards reactivates the split (the bounded delegate's advancing
  watermark clears the idle flag; explicit `markActive()` covers a
  non-advancing first record). Edge-triggered per split episode, mirroring
  `WatermarksWithIdleness.isIdleNow`; idempotent with the wrapper's own
  markIdle on the same `PartialWatermark`. The generator stays inside the
  FLIP-27 source operator (zero graph nodes — StreamGraphHasherV2 operator
  IDs unchanged, P10 archived-checkpoint restore unaffected). Trade-off,
  deliberate: wall-clock marking can mark a backpressured split with buffered
  records idle, letting the watermark run ahead of it (late-drop path);
  `SOURCE_IDLE_MS` silence is already the production definition of an idle
  split, G7c late-drop counters monitor the cost, and the alternative is a
  total pipeline stall under load. Pinned by `SourceIdleWatchdogGeneratorTest`
  (12 tests — 5 new wall-clock-marking legs: threshold marking, no marking
  while flowing, edge-triggered episodes, first-record reactivation incl. the
  non-advancing record, idle-from-open for never-data splits).

- 2026-09-01 post-watermark-fix drills exposed a separate throughput ceiling
  (~3.7-4.1k ticks/s regardless of 4Hz/10Hz feed): attempt 5
  (`tm-kill-full-load-20260901-154753`, 10Hz) emitted candles/previews/signals
  correctly but consumed only ~24% of the feed; attempts at 4Hz
  (`...-162646`, `...-163755`) failed pre-kill on checkpoint expiry
  (durations growing 3.1s -> 25.9s -> expired at a stable ~15MB state size).
  JFR profiling of the loaded TaskManager (60s, /tmp/prof2.jfr) closed the
  root cause: task threads spent their entire sampled native time inside
  `org.rocksdb.RocksDB.put`/`delete`/`Checkpoint.createCheckpoint` with
  near-zero user CPU — and `/tmp/flink-rocksdb` (the configured
  `state.backend.rocksdb.localdir`) sat on the container overlay filesystem
  because no volume was mounted at that path. Every state op paid overlayfs
  I/O (~0.5-1ms vs ~5-20us expected). Fix: named volume `flink-rocksdb`
  mounted at exactly `/tmp/flink-rocksdb` in docker-compose.yml (zero other
  config changes; verified post-recreate via `mount`/`df` inside the TM).
  The "absurd 4k/s ceiling" was an environment defect, not a machine limit.
- 2026-09-01 follow-up (layered root cause, closed the remaining gap): the
  volume fix was necessary but NOT sufficient. Clean-profile evidence
  (`/tmp/prof4.jfr`, 10Hz, degraded steady state): WAL disabled (0-byte
  .log files — not the cause); Fluss fetch healthy (5-11ms latency,
  requestsInFlight=0 — the source is not fetch-bound); ingestion delivers the
  full 10,240/s into Fluss; GC clean; disk not saturated (w_await ~0.7ms);
  14 of 16 cores idle. The residual cap: ~80 RocksDB instances (every keyed
  operator x 8 subtasks) share the 2.2GB managed memory and one disk; TTL
  dedup garbage + window-state churn drives constant memtable flushes
  (586 SST files / 335MB live state in ~6 min, vs 15-19MB per incremental
  checkpoint) and unending compaction, so state puts intermittently stall
  and each checkpoint costs a fixed 7-10s (Checkpoint.createCheckpoint x 80
  DBs + SST upload on the same disk). At 10s checkpoint interval the job is
  checkpointing ~100% of the time: throughput degrades from a measured
  12k/s (fresh state, before the first checkpoint) to ~3k/s, checkpoints
  exceed the 30s timeout, and the job restarts (drill FAIL at 10Hz and,
  with longer exposure, at 4Hz too). With a 120s checkpoint interval the
  pipeline sustains ~10k/s until the first checkpoint, then degrades the
  same way — the per-checkpoint stall, not the frequency alone, is the
  poison. Network memory 512m was tested and ruled out (no effect; default
  reverted to 256m, parameterization kept). Not yet fixed: RocksDB
  write-buffer/compaction tuning or checkpoint-contract changes (options
  recorded below); C2 main-mode PASS still blocked on this.

## Known limitations

- The local compose environment has one TaskManager, so this is a checkpoint
  recovery proof, not a four-VM or multi-TaskManager availability proof.
- The C2 drill deliberately does not claim a live 60k rows/s capacity result;
  the existing ingestion contract records the synthetic/emitter ceilings.
