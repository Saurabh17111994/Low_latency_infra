## Why

Plan item 4 (`09-production-swarm.md`): `stack_selfcheck.sh` refused any swarm with more than one node
("refusing to label — single-host mimic, not a cluster"), so **nothing validated a real cluster's stack
before `docker stack deploy`**. The refusal was correct about labelling — `docker node update --label-add`
on a cluster mutates a peer (P6-207) — but it threw away the useful half: the manifest compiles the same
way on four nodes, and the constraints the deploy depends on can be checked without writing anything.

## What changed

- `stack_selfcheck.sh` gains `CLUSTER=1`, validation-only against an existing swarm:
  - never `docker swarm init` (a node that was meant to join a cluster must not become a one-node swarm
    of its own — it schedules nothing and looks healthy while it does it) and never `docker node update`;
  - every node must be `Ready`+`Active` and at least one manager `Leader`/`Reachable`;
  - every `node.labels.… == …` constraint of the **rendered** stack (`docker stack config` output, so
    anchors and per-service overrides are included) must be satisfied by some node's labels;
  - `CLUSTER=1 DEPLOY=1` is refused (exit 2): `DOWN=1` is the default, so a deploy from a validator would
    remove the production stack as a side effect of a check (P6-019, one level up).
- The default mode is unchanged, except that its multi-node refusal now names the new mode.
- `tests/test_stack_selfcheck.py`: the stub `docker` answers `docker node ls --format`,
  `node inspect --format '{{json .Spec.Labels}}'` and a rendered `stack config`; seven new tests cover the
  green path and each failure mode.

## Verification

| Check | Result |
| --- | --- |
| `test_stack_selfcheck.py` | 23 passed (16 pre-existing + 7 new) |
| Mutations of the new checks | 5/5 caught: drop Ready+Active, treat every constraint as satisfied, write a label in cluster mode, drop the live-manager check, allow a deploy |
| Real Swarm on this host, `CLUSTER=1` | rc=0 — `swarm active`, `1 node(s) — labels are verified, never written`, `stack config: OK`, `nodes Ready+Active; live managers: 1`, `placement constraints satisfied: 2` |
| Same run's docker calls | no `swarm init`, no `node update` (asserted in the stub test; observed in the real run's output) |
| `CLUSTER=1 DEPLOY=1` on the real host | rc=2, refused before any docker call |
| Constraints measured from the real render | `node.labels.role == worker` ×16, `node.labels.observability == true` ×3 — the two the validator checks |

## Not verified

- **A real multi-node swarm.** The rehearsal is a single-node swarm on this laptop (the only one
  available); the four-node run is S7. What is proven is the check logic and its failure modes, not a
  four-node topology.
- **A node that is `Drain`** (valid but not schedulable) is caught by the `Availability` half of the
  Ready+Active check, but only via the stub — no drained node exists here to reproduce against.
- The compile-only path needs `O2_PASSWORD` in the environment: the stack declares 16 `:?` variables and
  the script's placeholder set covers 15, so a bare shell fails at `docker stack config` before reaching
  the cluster checks. Pre-existing, and separate from this change — the smoke run supplied the value.
