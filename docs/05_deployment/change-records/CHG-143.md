# CHG-143 — Master keys and the envelope are checked, not assumed

- **Status:** recorded — all eleven wave-6 findings verified and fixed in two commits
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 6 ("Key and envelope crypto"):
  P6-281, P6-282, P6-283, P6-284, P6-285, P6-286, P6-674, P6-675, P6-676, P6-677, P6-678

## What happened

Every finding was re-verified against the current code before editing. Unlike the previous waves
these classes have a real consumer — `EncryptedExportEodOffloadExecutor` (the encrypted export
offload path) and its test — so every call site was checked first: all keys passed are 32 bytes, the
AAD is always the record id and never empty, and every `MasterKeyStore.of(...)` call passes a
non-empty map. Nothing in this change breaks a caller.

**The class contract said AES-256; the code would run AES-128 (`P6-283`, `P6-284`, `P6-281`).**
The JDK happily accepts 16- and 24-byte AES keys, and neither `seal()`/`open()` (nor `wrap()`/
`unwrap()`, which delegate to them) checked the length, so a caller-supplied short data key or
master key produced AES-128/192-GCM under a javadoc promising AES-256-GCM with a 256-bit data key.
`EnvMasterKeyStore.decode()` had the same hole at the front door: it validated Base64 syntax while
its javadoc promised a 32-byte key, so a truncated env key was accepted at startup and only
surfaced later as a wrap/unwrap failure. All three now require exactly 32 bytes
(`EnvelopeCrypto.AES_KEY_BYTES` is the single source for the number) and name the length they got.

**The key stores did not own their key material (`P6-282`, `P6-285`, `P6-286`).** `MasterKeyStore.of`
kept the caller's mutable map *and* the caller's arrays, and computed `current` once — so a later
`put`/`remove` changed what `keyFor()` saw while `currentVersion()` stayed as first computed, which
is precisely the disagreement decrypt-old/write-new rotation cannot survive. `keyFor()` also handed
out the stored array itself, in both stores, so any caller could zero master key material in place
for every other user. `of` now snapshots the map into an unmodifiable one with cloned values, and
both `keyFor` implementations return a copy. (In `EnvMasterKeyStore` the arrays come from `decode()`
and are never aliased on the way in, so only the return path needed a clone there.)

**A retried or retired version could hide a higher key (`P6-674`).** The rotation probe stopped at
the first missing version: a store holding v1 and v3 but not v2 (a version that has been retired
after its bundles were re-wrapped) never loaded v3, kept wrapping new bundles with v1, and reported
no error while the operator believed v3 was current. The probe now continues past gaps up to a named
bound, and `current` is the highest version actually loaded.

**A store with no key advertised one (`P6-678`).** `MasterKeyStore.of(Map.of())` produced
`currentVersion() == 0` via `orElse(0)` with no v0 behind it, so a bundle wrapped with the advertised
current version could never be unwrapped. An empty map is now rejected; in `EnvMasterKeyStore` the
same placeholder was unreachable (v1 is required) but is now impossible — `current` comes from the
version map's last key.

**Tamper findings and programming errors were indistinguishable (`P6-675`, `P6-676`, `P6-677`).**
`catch (Exception)` in `seal`/`open` rewrapped null keys, null payloads, an empty AAD and a
too-short payload as "AES-GCM open failed (wrong key, tamper, or AAD)" — so an operator reading the
log could not tell a null pointer from a detected attack. `open()` also rejected only `<= 12` bytes,
so the 13..27-byte range (below `iv(12)+tag(16)`) reached the cipher and came back as tamper instead
of as truncation. Inputs are now validated before the cipher runs, the catch is narrowed to
`GeneralSecurityException`, and the length floor is 28 with the received length in the message.

## Judgement calls (review these)

1. **An empty AAD is now a hard error, not a warning.** The finding asked for null *and* empty to be
   refused; they are. The class contract defines AAD as the record identity, and GCM without AAD does
   not bind the bundle to its record at all, so accepting an empty AAD would let a caller silently
   drop the binding this class exists to provide. No caller does this today.
2. **The rotation probe is bounded at 64 versions, and I chose "continue past gaps" over "fail fast
   on a gap".** Both halves were offered by the finding. Failing on a gap would break a legitimate
   documented workflow — retiring a version after its bundles are re-wrapped is exactly what
   "old versions are retained so previously wrapped data keys stay decryptable" implies, and gaps
   are normal after retirement. Continuing past gaps removes the silent-stale-current bug without
   forbidding retirement. The bound exists because an env accessor can only be asked for a name,
   never enumerated: an unbounded probe spins forever on an accessor that answers every name. The
   ceiling (a version above 64 is invisible to the store) is documented on the constant, pinned by a
   test, and is the one behaviour here that is bounded rather than checked.
3. **`EnvMasterKeyStore`'s store side is not cloned, only its return path.** Its arrays are minted by
   `decode()` inside `fromEnv` and never aliased by a caller, so there is nothing to defend against
   going in. Cloning there would be cargo-culting the fix rather than applying it.
4. **`AES_KEY_BYTES` is now public on `EnvelopeCrypto`.** The 32-byte rule is one rule with two
   entry points (the cipher and the env key store); a private constant in each would be two literals
   free to drift apart. This is the only public surface added by the wave.
5. **The existing env-required message is unchanged** (`EOD_EXPORT_MASTER_KEY_B64 is required ...`),
   because `EncryptedExportEodOffloadExecutorTest` asserts on its text; the new length error is a
   separate message, so no existing assertion changes.
