# CHG-227 — the gate's cap must outlast every scenario it wraps

- **Status:** recorded — fixed (2026-09-19)
- **Filed:** 2026-09-19
- **Source:** the step-11 screen run that preceded the W39 certificate attempt
  (`logs/soak/monday-gates-20260919-024248/`).

## What happened

Measured 2026-09-19 on a cluster that had just been restarted clean (catalog 27/27, tablet logging
no errors):

| scenario | result | wall |
|---|---|---|
| 1 `[skip-smoke]` | PASS (exit 0), `apply.json` written, `matrix.status=PASS` | ~30 s |
| 2 `[no-ack]` | PASS (exit 0), `apply.json` written, `matrix.status=PASS` | ~960 s |
| 4 `[container bad-ownership]` | **killed mid-apply by the runner's cap** | 840 s of its entitled 1800 s |

The two PASSes are the point. They include the COMPAT-FLUSS-005 matrix cell that had refused in the
gate attempt minutes earlier, so the cluster was healthy and the applies themselves were fine. What
failed was the **outer** cap: CHG-226 raised each scenario's budget to 1800 s and left the gate's
`DDL_SMOKE_TIMEOUT_SEC` at 1800 s — the budget of ONE scenario while the cap wraps THREE. S1+S2
consumed ~990 s, so S4 was handed 840 s of the 1800 s it is entitled to and was killed at the cap.

CHG-226 introduced this deliberately and wrote its reasoning down: it records 1800 as *"equal to the
gate's own `DDL_SMOKE_TIMEOUT_SEC` default"* and notes *"the worst case for step 11 grows
(3 × 1800 s)"*. Equal-to-one-scenario is precisely wrong when the cap wraps all three, and the worst
case it named was never given a cap to run inside. This record corrects that reasoning.

A second defect made the failure undiagnosable: `ddl-smoke.log` came back **empty**. The runner
redirects the smoke's stdout into that file and the cap SIGKILLs it, which discards a pipe-buffered
stdout — so a cap kill produces a FAIL carrying no evidence at all. The verdict above had to be
recovered from the tool's own `apply.json` files rather than from the step's own log.

## The change

- `run-monday-gates.sh`: `DDL_SMOKE_TIMEOUT_SEC` 1800 → **6000** (3 × 1800 s + 600 s slack for the
  classpath build and the per-scenario cleanups), and the smoke now runs as `python3 -u` so its log
  survives a kill.
- `ddl_apply_smoke.py`: `SCENARIO_COUNT = 3` — the number the cap is sized from.

The cap only ever bounds the *outer* wait, so it cannot mask a failure: a scenario that genuinely
deviates still fails, just later. The measured healthy case remains run 6's 17 m 16 s; only a
pathologically slow cluster can approach 6000 s, and step 11 is the step entitled to wait.

## Verification

- New `GateCapTest`, test-first: red with two `AttributeError`s (`SCENARIO_COUNT` absent) and one
  failure (`python3` where `python3 -u` is required), then green after the change —
  `Ran 12 tests … OK`.
- Three legs: the cap must exceed `SCENARIO_COUNT × SCENARIO_TIMEOUT_S`; the declared count must
  equal the `ok &= scenario` invocations in `main()`, so a new scenario cannot silently re-break the
  cap; and the smoke must be invoked with `-u`.
- `bash -n` clean on the runner; the 67 `test_gate_*.py` tests and the 146 `test_08_local_compose*`
  tests still pass with the changed line, and so does the full suite:
  `Ran 1539 tests in 318.908s` → `OK (skipped=11)` (1536 + the 3 new legs).
- The unbuffered invocation is confirmed live: the raised-cap run's log carries
  `--- scenario 1 [skip-smoke] … PASS (exit 0)` while scenario 2 is still running — the mid-run
  content the killed run lacked.
- The raised-cap run finished: `SMOKE_EXIT=0`, all three scenarios PASS — S1 29 s, S2 829 s, S4 911 s
  (`exit 1` in-band: the ownership gate catching the seeded record) — 1769 s total, against the old
  1800 s cap's 31 s of headroom on a healthy cluster. The screen's kill landed ~70 s before S4 would
  have finished. The killed run left its temp dir behind; the passing run removed its own.
