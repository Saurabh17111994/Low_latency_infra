## What changed

**1. `run-meta.txt` records the arm, not just the job** (`code/01_platform/04_scripts/stage-capture.sh`,
the metadata block written before the capture window):

| field | source | why it is load-bearing |
|---|---|---|
| `feed_type` | `FEED_TYPE`, set by `stage-profile.sh` from `FEED` | the ms fake broker vs the production feed decides whether `tick_to_strategy` (event-time anchored) is a valid KPI at all |
| `unaligned_checkpoints` | caller env | dev submits unaligned while the certified production profile is aligned-only (CHG-543) |
| `changelog_state_backend` | caller env | the certified production profile runs the changelog backend (CHG-541); off changes checkpoint cost |
| `scanner_fetch_wait_max_time_ms` | caller env | lever F1 |
| `buffer_timeout_ms` | caller env | lever F2 |
| `deck_ingestion_state` | `docker ps -a --filter name=01_docker-ingestion-1` | a live deck writer shares `raw_table_1` with the fleet; the 2026-10-06 F1+F2 arm ran with it up and its measured growth went 179 → 405 MB/min |
| `tablet_kv_snapshot_interval` | `docker exec <tablet> grep '^kv.snapshot.interval' /opt/fluss/conf/server.yaml` | dev runs 1m while the certified production default is 0s, so the same arm name means different server behaviour |

`code/01_platform/06_stage_profiler/stage-profile.sh` now passes `FEED_TYPE="$FEED"` into
`stage-capture.sh` (the checkpoint and F1/F2 vars already arrive as exported prefix-env on the
harness process).

**2. The prom-staleness budget is derived from the run it is judging.** The old leg used
`max(CAPTURE_INTERVAL_S × 5, 25s)`, i.e. the *configured* cadence. The *observed* spacing is
probe-bound (the same tick also runs the Fluss and ingestion probes): measured 17 s median / 24 s max
in the 2026-10-06 Task 1 arms and 16–23 s in C0e — so C0e's 25 s budget sat inside one trailing
iteration's noise and the phase exited 1 with the message
`!! FAIL: last prom scrape was 26s ago (budget 25s at interval 5s; TM prom endpoint died before capture end)`
even though its capture was complete (900 s, 48 snapshots, presence gate PASS).

The new budget is `2 × the run's own worst observed snapshot gap`, floor 25 s. A genuinely dead
endpoint produces no further snapshots, so its gap grows without bound and still trips the check.
Four fields are appended to `run-meta.txt` before the verdict (`prom_snapshots`,
`prom_observed_max_gap_s`, `prom_staleness_budget_s`, `prom_final_gap_s`), and a trip now marks the
run `partial=yes` with `partial_reason=prom-stale:<gap>s>budget<N>s` — a truncated leg and a leg that
was never measured must not look alike to a later reader.

## What deliberately did NOT change

* The **start gate** still owns a prom endpoint that is dead from the beginning: it fails hard with
  rc 1 before the timed window (`test_prom_endpoint_dead_at_capture_start_fails_before_capturing`).
  Making the tail's softer posture apply there would let a dead endpoint burn a full capture.
* No `make gate` step, no job, no config, no DDL. `run-meta.txt` gains lines only; nothing parses it
  by exact content.
