## What landed and why

The user asked for an audit of the signal-job design against the **official
integration surface** — Flink DataStream API + the Fluss connector — with the
rule: "use what they natively provide; do not engineer there." The audit ran
against the actual sources: Flink checkout (`release-2.2.1` tag) and Fluss
checkout (0.9-SNAPSHOT, the 0.9.1-incubating base).

**Every claim below was verified in source, not assumed:**

| Verification | Source evidence |
| --- | --- |
| Flink 2.2.1 ships a native OTLP metric reporter | `flink-metrics/flink-metrics-otel/` present at the `release-2.2.1` tag (FLINK-33696, `OpenTelemetryMetricReporter` + factory; config `exporter.endpoint` / `exporter.protocol` / `exporter.timeout` / `service.name` / `service.version`) |
| Flink has no event-time state TTL (ProcessingTime only) | `StateTtlConfig.java` — enum has only `ProcessingTime` |
| Fluss has no per-key TTL (log TTL only) | `ConfigOptions.java` — only `TABLE_LOG_TTL`; no key-level TTL in the server |
| Fluss lookup client retries forever by default | `ConfigOptions.java` — `client.lookup.max-retries` default `Integer.MAX_VALUE`; `ServerConnection.java` inflight-limit TODO |
| Fluss sink natively batches + flushes on the checkpoint barrier | `FlinkSinkWriter.flush` / `UpsertSinkWriter` via the connector Sink API |
| Connector open-time validation is minimal | `FlinkSinkWriter.initialize` — table exists + PK-presence match only; `FlinkSourceEnumerator.start` — table exists only |
| Fluss DataStream source/sink are the official API | `FlussSourceBuilder`/`FlussSource`, `FlussSinkBuilder` |

**Decision (user, 2026-08-17): adopt the native-integration profile — replace
the five pieces of custom machinery below with what Flink/Fluss natively
provide.** `TableContractValidator` is explicitly **kept** (see below) — the
connector's open-time checks are only existence + PK-presence, so the validator
is a live-cluster drift guard, not duplication.

**Kept as-is — `TableContractValidator` (drift guard, not over-engineering):**
the connector's open-time validation was traced end-to-end:
`FlinkSinkWriter.initialize` checks table existence (`getTable`) + PK *presence*
(`sanityCheck`), and *tolerates* column-count mismatch (schema-evolution
`ProjectedRow` mapping); `FlinkSourceEnumerator.start` checks table existence
only. It does **not** check exact PK column set, bucket count, `bucket.key`,
strict column count, or `kv.format-version` — all of which the validator checks,
and all of which have caught real live drift (the id-7 LOG-era forming_bar
table, the id-90 LOG→KV candle conversion, the id-693→697 TTL recreate). The
validator stays; only the table-existence leg is arguably redundant, and it is
retained as intentional pre-submit fail-fast.

## Trade-offs (recorded, not hidden)

- **Expiry semantics change (item 2):** native TTL is wall-clock
  (ProcessingTime), not watermark-based. For a 5-minute real-time dedup rule
  this is the *correct* semantics; the event-time machinery was both non-native
  and unnecessary. If a future requirement genuinely needs watermark-aligned
  expiry, the native fallback is event-time timers *without* the index (one
  timer per key, direct delete) — recorded, not built.
- **Metric series change (item 1):** OpenObserve dashboards/alerts keyed on the
  custom emitter's series must retarget to the native reporter's series in the
  same change (openobserve.md + runbooks list the affected rows). Semantics
  note: the native reporter exports counters as **monotonic DELTA** sums (the
  standard OTel counter shape); the custom emitter emitted `isMonotonic=false`
  — dashboards on those series must be re-created with the monotonic flag.
- **Checkpoint size (item 2):** removing the expiry index shrinks the
  checkpoint further — the Design-B envelope (~628 MB at 20 480 t/s) already
  proved acceptable; this only improves it.
