## Why

CHG-283 moved both infra scrape jobs from `static_configs` to `dns_sd_configs`. `test_09_stack.py` asserts that the
collector addresses the **per-task** DNS name (`tasks.node-exporter:9100`), which is still the right thing to
assert — the bare name resolves to the VIP and would sample one random node per scrape — but it collected its
target set from `static_configs` only, so the change made it fail:

```
AssertionError: the collector must scrape tasks.node-exporter:9100; the bare name resolves to
the VIP and would sample one random node per scrape
assert 'tasks.node-exporter:9100' in {'flink-jobmanager:9249', 'zookeeper-1:7000', ...}
```

CHG-283's record lists only `test_16` in `test_updates`, and that is all that was re-run. The canonical pytest
run was not run again until 2026-09-21, which is when this surfaced — **one green test had gone red and nothing
said so**. The fix keeps the signal (the per-task name, never the bare name) and stops depending on which
mechanism expresses it.

## What changed

- The target set is the union of `static_configs` targets and `dns_sd_configs` names with their ports.
- The anti-VIP clause became a real assertion instead of only prose inside a message: the bare
  `node-exporter:9100` / `cadvisor:8080` must **not** appear as a scraped target. That is the shape a
  `dns_sd_configs` job would produce if someone wrote the bare service name, and no test caught it before.

## Not verified

Nothing about the running system — this is a test-only change, and CHG-283's in-situ evidence (the same
OpenObserve stream holding `tasks.node-exporter:9100` before and `10.0.1.27:9100` after) stands unchanged.
