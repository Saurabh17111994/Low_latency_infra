# CHG-223 — the dedup commit borrows from the handle pool, and the pool's close is honest

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** the wave-36/38 evidence report §5.7 and §5.8 (deferred there as "each wants its own
  change, not a bundled one").

## What happened

**§5.7 — a writer abandoned per retry.** `FlussIntentDedupStore.record()` (the durable dedup
commit for `Execution_Intent_Processed`) created a writer per attempt:
`table.newUpsert().createWriter()`. Fluss 0.9.1 gives a `TableWriter` no `close()` — only
`flush()` — so a timed-out attempt abandoned its writer, and with it an RPC Sender still holding
the pending record. That is the run-4b storm shape (an unclosable writer plus a resolved-then-
dropped table) sitting on the handoff path. The drill never reaches it — run 1's storm names
`Execution_Intent`, not `Execution_Intent_Processed` — which is exactly why it survived the gate.
The report's prescribed fix was the `FlussHandlePool` pattern the four sibling stores already use.

**§5.8 — `clear()` used as a close.** Every pool-owning store dropped its retained handles with
`pool.clear()` (or by clearing its pool map) on close. That reads as a lifecycle but is not one:
it cannot recall a borrowed handle, and it silently says nothing about a record already in
flight. The report's conclusion stands — no production close can fix that, so the test-side
keep-guard remains the load-bearing protection — but the pretend-close is worth removing.

## The change

- `FlussHandlePool` gains `close()`: it drops retained handles, refuses to **retain** a handle
  returned after close (so a later borrower can never be handed a closed store's handle), and
  makes `borrow()` fail fast instead of manufacturing handles during shutdown. `clear()` stays,
  now documented as "drop retained handles; a borrowed one is not recalled".
- `FlussIntentDedupStore`: `record()` runs `writerPool.with(writer -> …)` inside the existing
  `RequestBudget.run`, and `close()` closes the pool before the table and connection. A failed
  attempt's writer is dropped rather than pooled — the pool's own rule, which is what the old
  comment claimed per-attempt creation was doing — so a retry still gets a fresh writer, but the
  abandoned one no longer leaks.
- `FlussProjectionWriter`, `FlussProjectionLedgerStore`, `FlussControlStateStore`
  (gateway) and `FlussPostbackQuarantineStore` (common): their `close()` calls `pool.close()`
  instead of `clear()`/map-clearing.

Deliberately **not** changed: nothing tries to cancel or await a record that is already in
flight. That is unreachable in Fluss 0.9.1 and is why the run-4b guard is "do not drop a table
under an unresolved write" rather than "close the writer".

## Verification

- `FlussHandlePoolTest`: `Tests run: 8, Failures: 0, Errors: 0, Skipped: 0` — the 6 existing legs
  plus `closeDrainsRetainedHandlesAndRefusesNewBorrows` and
  `aHandleReturnedAfterCloseIsDroppedInsteadOfPooled`.
- New `FlussIntentDedupStorePoolingTest`: `Tests run: 2, Failures: 0` — two successful writes
  create **one** writer (reuse); after a timed-out attempt the next write creates a **new**
  writer (the poisoned handle was not pooled). Negative control: restoring the per-attempt
  creation makes that leg fail (`Tests run: 2, Failures: 1`), so the test discriminates.
- Module suites, both modules built from this tree: gateway `Tests run: 155, Failures: 0,
  Errors: 0, Skipped: 7`; common `Tests run: 735, Failures: 0, Errors: 0, Skipped: 2`; reactor
  `BUILD SUCCESS`.
- Targeted live run of the two drill classes that exercise the changed pools:
  `FlussProjectionWriterIntegrationTest` `Tests run: 1, Failures: 0` (9.5 s).
- `GatewayFlussIntegrationTest` failed on its **first** live attempt: raw-client matrix cell 3
  ("v2 + single-field subset bucket key") reported *write unresolved (batch may still be
  pending)* after 93.5 s, then passed on a rerun in 4.0 s. That verifier
  (`CompositeKeyMatrixVerifier`) references none of the classes changed here, and the symptom is
  the §2.2 replica-placement/remote-log-teardown delay on a cluster that `make up` had just
  restarted. Recorded as observed, not attributed to this change — and not hidden.
