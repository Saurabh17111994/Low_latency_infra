## Why

`cluster_check.py` asks the live swarm whether every service has a node it can land on, and
`stack_selfcheck.sh CLUSTER=1` asks the same question while validating a machine — but both need the
machines to exist. The failure this project has already produced once is exactly the one that
arrives before a machine exists: a node inventory whose labels leave fourteen services with no
eligible node, while `docker stack deploy` still reports success and the services sit at `0/N`.

With the first deploy changing shape to two machines (one trading, one observability), that risk
grows rather than shrinks: two machines that each carry the *wrong* single label look exactly like a
correct pair until deploy day.

## What it does

Reads the stack deck and the node inventory and reports, per service, whether **at least one** node
satisfies **every** one of that service's placement constraints, then exits with the number of
services that have nowhere to land — the convention `cluster_check.py` already uses, so it can gate
a deploy.

Three design decisions worth their sentence:

- **It reuses `cluster_check._matches` instead of re-implementing constraint evaluation.** The
  offline and live verdicts therefore cannot drift apart; if the deck ever grows a constraint form
  the helper cannot read, both report "cannot evaluate" rather than guessing. A test pins that the
  deck only uses forms the helper understands, so the offline gate cannot quietly become useless.
- **Unknown constraint forms FAIL, never pass.** `node.role == manager` and its relatives are
  reported as unevaluable, because a silent pass here is a false all-clear — worse than no check.
- **`mode: global` services are skipped, not failed.** They run on every node, so no constraint can
  be unsatisfiable for them; they print as `SKIP` so the counts stay explicable.

Deliberately out of scope: replica spread. A deck needing more eligible nodes than exist still
passes here — that shortfall is the `replicas-topology-limited` WARN `cluster_check.py` reports
live, which the runbook's measured verdict table documents for the two Flink services.

## Measured

Against the real `docker-stack.yml` (20 services) and a two-row inventory:

| Case | Result |
| --- | --- |
| Two rows — trading `role=worker`, observability `observability=true` | rc=0, **17 PASS, 3 SKIP**, "every service has a home" |
| Trading node labelled `role=manager` | rc=14, **14 FAILs** naming the workload services; the 3 observability services still PASS |
| Trading node with no label at all | rc=14 |
| Restored inventory | `cmp` byte-identical; baseline reproduced |

The second row is the trap this repository names: a node holds one value per label key, and no
service in the deck pins `role == manager`, so `role=manager` excludes a node from every workload.
