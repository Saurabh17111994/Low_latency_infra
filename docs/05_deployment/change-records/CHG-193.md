# CHG-193 — the raw-path liveness guard knows no operator names (wave 36)

- **Status:** recorded — fixes a pre-existing defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** found in run 10 (2026-09-17 10:44) of
  `code/01_platform/04_scripts/holistic-measure.sh`, during the first warm-up
  after CHG-191 wired the candle path.

## What happened

The warm-up guard failed a phase whose pipeline was demonstrably healthy:

```text
!! raw-path progress=0 after 45s warm-up — pipeline dead:
STATE RUNNING
Source: raw-table-1 -> raw-validation | 0 | 0
fingerprint-dedup -> ingest-latency-monitor | 0 | 0
multi-tf-aggregator | 458132 | 539648
candle-closed-first-write-wins | 5120 | 5120
candle-closed-sink: Writer | 5120 | 5120
candle-live-sink: Writer | 534528 | 534528
SMOKE FAIL — main measurement SKIPPED
```

`multi-tf-aggregator` had processed 458 132 records and the candle sinks
534 528 — the feed was traversing the job at full rate (45s × 10 240 t/s ≈
460 800, matching the aggregator exactly). The two vertices the guard actually
consulted both answered `0`.

Two known-and-accepted facts combined into a false negative:

1. **The `0|0` race is documented.** `pipeline_metric_input_progress`'s own
   comment records it ("the raw source's live aggregate can briefly report 0|0
   while downstream vertices are already processing records, observed in C2 on
   2026-09-01"), and the downstream fallback exists for exactly that.
2. **The fallback's operator set was stale.** It matched a hand-written list —
   `fingerprint-dedup | candle-15s | forming-bar-(builder|detection|writer)`.
   `0f3e5952` ("retire 15s candle path, forming stack, and position gate")
   deleted the 15s candle path and the forming-bar stack and touched **no file
   under `04_scripts/`**, so two of the three alternatives named operators that
   no longer exist; and the vertices the multi-tf cutover added
   (`multi-tf-aggregator`, `candle-closed-*`, `candle-live-sink`) were never
   added. With both `raw-table-1` and `fingerprint-dedup` answering `0`, the
   fallback had nothing left to match and returned `-1`.

This is the third defect in this wave with the same shape — hardcoded
`04_scripts` topology knowledge that a signal-topology change invalidated
(CHG-191: the candle path itself; CHG-193: the operator names).

## The fix

`pipeline_metric_input_progress` no longer names a single operator. The raw
counters keep their priority (they are the most informative value when
readable); otherwise it takes the largest counter seen on **any other vertex**.
That is sound rather than merely permissive: the graph is linear from the raw
source, so records cannot appear on a downstream vertex unless the feed is
traversing the job — a positive counter anywhere downstream *is* proof of
progress. An all-zero dump still returns `-1`, so callers keep failing closed on
a genuinely dead pipeline.

## Verification

* The function was extracted from the live library and run against the three
  real `smoke/metrics-warmup.txt` dumps on disk:
  * run 10 (the false negative): `-1` → **534528** (the guard now passes).
  * run 9: **458640** — unchanged (raw priority still wins, so healthy dumps
    report the same value as before).
  * run 8: **456616** — unchanged.
  * a dump with no downstream progress: still `-1`; an empty dump: still `-1`.
* Two new tests in `test_flink_metric_dump.py`: the run-10 dump verbatim (must
  return 534528, not `-1`), and a dump where the raw counters are readable (must
  still report the raw value, pinning the priority order).
* **Mutation-checked**: restricting the fallback back to the old stale name set
  fails the new test; removing the generic fallback fails both it and the
  pre-existing downstream-fallback test.
* `test-pipeline-lib.sh`: 131 guards, 0 failed.
* Blast radius checked: the only callers are `holistic-measure.sh` L219 and
  `tm-kill-full-load.sh` L331. The change can only turn a `-1` into a real value
  when a downstream vertex has progress; every path that previously returned a
  positive value is unchanged.
