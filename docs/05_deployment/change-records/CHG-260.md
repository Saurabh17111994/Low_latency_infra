# CHG-260 — the dashboard is reachable from the workstation, and the firewall is the control

## Why

OpenObserve **is** the single pane of truth for this platform (user decision, 2026-08-22), which
makes it the one service an operator must be able to open. It had no published port: the stack file
deliberately published nothing, and a test banned the `ports:` key outright, so reaching the UI meant
hand-editing a running service with `docker service update --publish-add` — an edit that the next
`docker stack deploy` silently undoes.

The first implementation was the obvious one: publish on the loopback only.

```text
$ docker stack deploy ... 
services.openobserve.ports.0 Additional property host_ip is not allowed
```

`host_ip` is *not* part of the stack schema — that is the engine's schema, not Compose's — so a
loopback-only publish is not expressible in a stack file at all. `docker service update
--publish-add` does not offer it either (its grammar is `mode`, `target`, `published`, `protocol`).
The port therefore binds `0.0.0.0` on the node that runs the task, and the layer that restricts who
can reach it is the firewall.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** — `openobserve` gains
  `ports: [{mode: host, published: 5080, target: 5080}]`, with a comment that records both measured
  constraints: `host_ip` is rejected at deploy time, and the S4 firewall rule is consequently the
  control. `mode: host` keeps the port on the node that actually runs the task instead of meshing it
  across the swarm.
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — `ports` left the
  `TestNoComposeOnlyKeys.FORBIDDEN` list (it *is* valid stack schema; the blanket ban was policy, not
  a technical limit) and became an explicit policy instead: `TestPublishedPorts.ALLOWED` names
  `openobserve: {5080}` as the only service allowed to publish, and
  `test_the_ui_port_is_host_mode_and_cannot_be_loopback` asserts host mode, the agreed port, and that
  `host_ip` is **absent** — so nobody re-adds the key the engine rejects.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — S4 step 4 grows a two-row table of the only
  ports that are not Swarm-internal (`5000` registry on VM1, `5080` on the OpenObserve node), each
  limited to the workstation's address; S8 explains both ways in (tunnel or direct) and the
  one-at-a-time constraint against the development compose stack; the readiness table and the CloudPe
  security-group row name both ports.

## Measured

```text
$ docker service inspect prod_openobserve --format '{{json .Spec.EndpointSpec.Ports}}'
[{"Protocol":"tcp","TargetPort":5080,"PublishedPort":5080,"PublishMode":"host"}]

$ ss -ltn | awk '$4 ~ /:5080$/'
0.0.0.0:5080

$ docker service ps prod_openobserve --format '{{.CurrentState}}'
Running 2 minutes ago            # the publish did not block placement

# exactly one of the 18 services publishes anything
$ for s in $(docker service ls --format '{{.Name}}'); do ... len .Spec.EndpointSpec.Ports ...; done
1
```

The failed deploy is the evidence for the shape of the change, and it is quoted above: the stack
file cannot ask for a loopback-only bind, so the firewall rule in S4 step 4 is what keeps `5080`
private to the operator. The rehearsal also measured the collision with the development stack, which
publishes the same port: with the compose OpenObserve running, the Swarm task cannot bind `5080` and
stays `Pending`. One at a time, and the runbook says so.

## Limitation

Until the S4 rule is applied on VM4, anyone able to reach the VM's private address can open the
dashboard. The CloudPe security group is the outer layer and the host firewall the inner one; both
rows are now written down, and neither is something a stack file can enforce. The rehearsal proves
the binding and the publish count — it cannot prove a firewall rule that lives outside the stack.
