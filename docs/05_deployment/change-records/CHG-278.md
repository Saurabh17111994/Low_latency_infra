## Why

The runbook's §1 "v1 baseline" paragraph already said M1–M3 are Manager+Worker, carrying the label
`role=worker`. `prod_vms.example.json` — the template an operator copies to `prod_vms.json` before
the node gate — labelled the same three nodes `role=manager`. Both cannot be right, and the
template was the wrong one:

- Nothing in `docker-stack.yml` pins `node.labels.role == manager`; **fourteen** services pin
  `role == worker` (parsed from the YAML, not grepped).
- A node holds exactly **one value per label key**, so `role=manager` does not merely fail to help
  — it excludes that node from every workload service. On a v1 deck, where those three managers
  *are* the workload nodes, that is 14 services stuck at 0/N, with `docker stack deploy` reporting
  success. This is decision D5 of the plan, and it is the reason the template and the runbook had
  to be reconciled before a VM exists.
- The same rows declared `expect_availability: drained` and `disk_min_gb: 10`. Drained nodes take
  no new tasks — contradictory for a workload node — and the manager disk figure belongs to the v2
  shape, where managers are drained and run nothing; v1's workload VMs take the 500 GB floor from
  §1.

The change is confined to the template and the truth it must tell; no deployed artifact moves.

## What changed

- `code/01_platform/04_scripts/prod_vms.example.json` — M1, M2, M3: label `role=worker` (the swarm
  role stays in the `role` field, which is what the swarm itself reports), `expect_availability`
  removed, `disk_min_gb` 500. The `$comment` — which still pointed at a retired D1.3/D2 sequence —
  now states the rule: the number of rows *is* the topology (1 row = this single-node profile, 4 =
  v1, 7 = v2 with the managers drained), and a workload node is labelled `role=worker`, never
  `role=manager`. W1–W3 and O1 are untouched: O1 carries `observability=true` only, which is the
  invariant that keeps the trading services off the observability node.
- `code/01_platform/04_scripts/tests/test_10_prod_node_check.py` — the new test pins both rules
  against the template. Without it, the same trap can be reintroduced by editing one JSON string.
- `docs/05_deployment/PROD_VM_PROVISIONING.md` — new §1b, the single-node profile: the both-labels
  command sequence, the one-row inventory recipe, the **measured** verdict from a live single-node
  cluster, where each service lands, sizing, what one VM cannot prove, and nine exit criteria that
  turn the 2–3 day watch into a test. It also records that the production stack file adds
  `otel-collector-logs` (absent from the rehearsal deck by design), so VM-1 is that agent's first
  real start.
- `docs/plans/2026-09-21-ci-publish-and-single-node-rollout.md` — a dated note correcting this
  plan's own Stage-3 acceptance: it promised FAIL=0, and the measurement says two FAILs are the
  honest expectation on a single node.

## Measured

- Live single-node acceptance run (`cluster_check.py --expect prod_vms.json` against this
  workstation's swarm, 2026-09-21): **7 PASS, 2 FAIL, 1 WARN**, exit code 2. The two FAILs are
  `replicas-complete` (`prod_ingestion 0/1` — the known `ARROW_*` credential gap) and
  `no-stuck-tasks` (the same ingestion task with `task: non-zero exit (1)`, plus a
  `No such container` history line on each Flink service, whose running replicas are healthy while
  their extra replicas are `Pending` for the topology reasons the WARN names). The WARN is
  `replicas-topology-limited` for `prod_flink-jobmanager 1/2` and `prod_flink-taskmanager 1/3`.
- The recipe itself is verified end-to-end, not assumed: the one-row inventory was generated from
  the live node and the checker's two inventory checks — `expect-node-count` and
  `expect-observability-labels` — both PASS, so a node carrying `role=worker` *and*
  `observability=true` is recognised as the deck the inventory describes.
- `docker stack config -c docker-stack.yml` with all 16 required variables exported: rc=0, 1271
  lines of resolved stack. (Nothing in the stack file changed here; this is the profile's
  structural check.)
- Tests: `test_10_prod_node_check.py` + `test_11_cluster_check.py` → 48 passed (pytest), OK
  (unittest discover), before and after. Both mutations caught, file restored byte-identically.
- Counts were taken by parsing `docker-stack.yml` with `yaml.safe_load`: 14 `role == worker`, 3
  `observability == true`, 3 `mode: global` — 20 services in the production file, 19 in the
  rehearsal deck.

## Not verified

- No VM exists: the section's command sequence, sizing advice and the nine exit criteria have not
  been executed on a real single-node VM, only measured against the workstation's single-node
  swarm, which is a different machine with the same shape.
- The expectation that the two Flink `no-stuck-tasks` lines disappear on the v1 deck follows from
  the checker's own rule (a dead task is counted only while its service is short of replicas) and
  from three eligible nodes existing there; it is not measured, because there is no four-VM deck.
- The `prod_ingestion` FAIL is expected to clear with real `ARROW_*` credentials; the rebuilt
  ingestion image has still never run, so that too is VM-day evidence.
