# CHG-222 — step 19 runs with FLUSS_BOOTSTRAP unset, and every post-export suite is guarded

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** the wave-36/38 evidence report, §7 item 4 — "generalize the step-14/16 guard".

## What happened

Step 11 (the DDL apply smoke) runs `: "${FLUSS_BOOTSTRAP:=localhost:9123}"; export FLUSS_BOOTSTRAP`.
The export is deliberate — the smoke needs it — but it outlives step 11, so **every later step
executes with the bootstrap in its environment**. Any test class that self-gates on
`FLUSS_BOOTSTRAP` therefore runs against the live cluster in whatever module suite comes after
step 11. That is the shape that failed run 4b: a second live run on top of the drill's own table
churn waited 420 s on the coordinator's deletion backlog, timed out, and dropped a scratch DB
under a pending write (628,185 storm lines).

Steps 14 and 16 are covered by the drill-ownership exclusions (CHG-215), and steps 12/13 name
their classes with `-Dtest=`. **Step 19 (mock-arrow) did neither**: plain `mvn -o test` with the
inherited bootstrap. Nothing in that suite gates on it today, so no run was wrong — the exposure
was a class added later, which would have gone live inside a suite whose whole purpose is to be
offline.

## The change

- `run-monday-gates.sh`, step 19: `… env -u FLUSS_BOOTSTRAP mvn -o test`, with the reason in a
  comment. Nothing else about the step changes — same goal, same log, same
  `BUILD SUCCESS` + `require_tests_run` checks.
- `tests/test_gate_drill_exclusions.py` (the CHG-215 guard) gains three legs and two helpers:
  1. the export site is asserted as an anchor, so the checks below cannot quietly go vacuous;
  2. **every** `mvn … test` after that anchor must either unset the bootstrap or name what it runs
     (`-Dtest=`, including `surefire_exclude`) — this is the generalisation: the rule now belongs
     to the position in the script, not to a hand-maintained list of two steps;
  3. the mock-arrow suite must not reference `FLUSS_BOOTSTRAP`, so step 19's unset can never hide
     a live leg.
- The parser reads each mvn command from the enclosing subshell / `&&` rather than from `mvn`
  onwards, because the guard flags sit on both sides of it (`env -u …` before, `-Dtest=` after).
  The first version of this guard mis-parsed exactly that and called a guarded step unguarded —
  the comment in `_mvn_commands` records it.

## Verification

- Guard suite: `Ran 7 tests in 0.012s` → `OK` (the 4 pre-existing legs plus the 3 new ones).
- Negative control: with `env -u FLUSS_BOOTSTRAP` removed from step 19 the guard fails, naming it —
  `step 19 (mock-arrow broker suite …) runs a module suite with FLUSS_BOOTSTRAP exported from
  step 11 and no guard`; restoring the fix returns it to `OK`.
- Coverage is provably unchanged, measured on the live tree: the mock-arrow suite reports
  `Tests run: 7, Failures: 0, Errors: 0, Skipped: 0` and `BUILD SUCCESS` **both** with
  `FLUSS_BOOTSTRAP=localhost:9123` (what step 19 inherited before) and with
  `env -u FLUSS_BOOTSTRAP` (what it does now).
- `bash -n` and `shellcheck -S warning -x` clean on the changed script.
