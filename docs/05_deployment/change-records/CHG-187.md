# CHG-187 — the jobmanager starts with STATE_RECOVERY_PATH unset, not blank (wave 36)

- **Status:** recorded — fixes a pre-existing bring-up defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** discovered while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`, after CHG-185 and CHG-186
  unblocked the earlier bring-up failures. Not one of the wave's 18 findings —
  the live run surfaced it once the harness could finally submit a job.

## What happened

`docker-compose.yml` put this on the `flink-common-env` anchor, which the
`compute`, `flink-jobmanager` and `flink-taskmanager` services all inherit:

```yaml
# No default: unset stays unset.
STATE_RECOVERY_PATH: ${STATE_RECOVERY_PATH:-}
```

The comment states the intent; the syntax does the opposite. `${VAR:-}`
substitutes an **empty string**, so when nothing sets the variable the container
receives it **present and blank**. A bare `KEY:` (YAML null) is what omits it.

`SignalJobConfig.validateStartupMode` fails closed on a blank restore path:

```text
[F005] Config STATE_RECOVERY_PATH is present but blank — a restore path must be
a real path (CANDLE-KV-REPLAY-001 A3.3)
```

`pipeline_submit_job` submits with `docker compose exec -T … flink run`, and
`compose exec` inherits the service's environment. The submitted JVM therefore
read a blank restore path and refused to start, so `SMOKE FAIL — main
measurement SKIPPED`. Every caller of `pipeline_submit_job` was affected:
`holistic-measure.sh`, `stage-a2-baseline.sh`, `stage-soak-e2e.sh`,
`eod-controller-test.sh`, `tm-kill-full-load.sh`.

**The trap is recent.** The line arrived in `7da45c6b` (*fix(compute): Part G
packaging & deploy hardening*, 2026-09-10), which added it so the job JVM — not
just the `submit-jobs.sh` launcher — could see the restore path. The last
successful harness run was 2026-09-03, before that commit. This is why the
defect presented as "the harness has never worked" while the harness code itself
was sound.

**Two neighbouring fields show the intended shape.** `SAVEPOINT_DIR` hit the same
trap and was resolved on 2026-08-22 by treating blank as unset *in Java*
(`T9-errata`) — but the compose line there is still `${SAVEPOINT_DIR:-}`, so the
two fields now use opposite remedies. And `.env.example` shipped
`STATE_RECOVERY_PATH=` (empty) directly beneath a comment reading *"Unset = clean
LATEST start"* — the documented "copy `.env.example` to `.env`" flow reproduced
the same blank.

## The fix

Two lines, so that "no restore" means *unset* on every path rather than blank on
the two paths that happened to be exercised:

```yaml
STATE_RECOVERY_PATH:      # YAML null: omitted when unset, forwarded when set
```

and, in `.env.example`, the empty assignment is replaced by a commented example
of a real value, so the documented setup flow leaves the key out.

**Why not relax the Java gate.** `[F005]`'s blank-rejection is deliberate and
tested: `SignalJobStrictGateT7Test.blankRestorePathFailsWithF005` asserts it as a
**T7 / G1 Safety** gate, and `CANDLE-KV-REPLAY-001 A3.3` is the decision it
enforces. Accepting a blank env value as "no restore" would weaken a fail-closed
safety gate to accommodate a configuration defect — the wrong direction. The
gate stays strict; the environment must stop manufacturing a blank.

**Why not fix it in the harness.** `docker compose exec` has no flag that
*removes* an inherited variable, so the caller cannot express "unset". The fix
has to be where the variable is defined.

```text
change_record_id: CHG-187
scope: deployment, gate-behavior
owner: platform-ops
date: 2026-09-17
affected_artifacts: code/01_platform/01_docker/docker-compose.yml, code/01_platform/01_docker/.env.example
compatibility_class: COMPATIBLE
savepoint_impact: none — no Flink state, checkpoint, table schema, DDL or connector changes. The change alters only whether an unset variable is present-and-blank or absent in the container environment; a real STATE_RECOVERY_PATH value is forwarded unchanged, so RESTORE mode behaves exactly as before.
test_updates: no new test files. The fix is verified against the live gate: with host STATE_RECOVERY_PATH unset the jobmanager now reports the variable ABSENT (F005 passes, LATEST mode), and an exported value interpolates into the rendered compose config (RESTORE mode). The end-to-end proof is the live harness run recorded in the wave-36 plan.
rollback_behavior: restore `${STATE_RECOVERY_PATH:-}` on the anchor and the empty assignment in .env.example. Bring-up then fails again for every pipeline_submit_job caller — the submitted JVM exits at [F005] "present but blank" and the harness reports SMOKE FAIL with no data-plane impact, since the job never starts and no container reaches the point of writing to Fluss.
plan_tasks: docs/plans/2026-09-16-wave36-holistic-measure-repair.md
```

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*Deployment topology or secret scope* and *Execution gate or approval behavior*.
This changes the runtime environment of the Flink job containers, and it
interacts directly with the `[F005]` gate that decides whether a job may start in
LATEST, RESTORE or FULL_REPLAY mode. This record carries both scopes rather than
only `deployment`, because the defect is in the container environment and the
gate it trips lives on the other side of that boundary.

## Verification

* Reproduced live before the fix: the wave-36 harness reaches
  `deploying SignalJob` and exits at `[F005] … present but blank`, then
  `SMOKE FAIL — main measurement SKIPPED`.
* Proved the mechanism with throwaway compose files run against the real image —
  a table of `{anchor form} × {host unset | host set | .env ships an empty key}`
  confirmed `${VAR:-}` yields `PRESENT=[]` and a bare null yields `ABSENT` when
  unset, with both forwarding a real value.
* Verified on the recreated stack: the jobmanager container reports
  `STATE_RECOVERY_PATH` **absent**, and `compose exec -T -e
  ALLOW_FULL_REPLAY=false` into it sees the same (this is the exact shape
  `pipeline_submit_job` uses).
* Verified RESTORE mode still works: exporting `STATE_RECOVERY_PATH` before
  `docker compose config` renders the value onto the anchor.
* `docker compose config` exits 0 with the anchor rendering
  `STATE_RECOVERY_PATH: null`.
* `python3 code/01_platform/04_scripts/change_control_check.py` exits 0.
* The wave-36 harness is re-run end-to-end after this change lands; the result is
  recorded in the plan's Task 7 checklist.
