## What changed

- New `jar-freshness.sh`: the single implementation (`JAR_FRESHNESS_ROOTS` +
  `jar_freshness_check`). It prints the reason and returns 0 fresh/overridden,
  1 stale, 2 unreadable; it never changes shell options and never exits.
- `rollout-savepoint.sh` sources it via the `JAR_FRESHNESS_LIB` seam and keeps
  its preflight wrapper (`die`/`warn`/`log`); the embedded copy is gone.
- `pipeline-lib.sh` sources the same lib and `pipeline_submit_job` calls it
  before any cluster interaction, failing through `pipeline_fail`.

## Why

- The fresh-submit path serves `stage-a2-baseline.sh`, `stage-soak-e2e.sh`,
  `holistic-measure.sh`, `tm-kill-full-load.sh`, `eod-controller-test.sh` and
  the day-start fresh mode (`COMPUTE_SUBMIT_SIGNAL=1`). A stale jar there
  silently corrupts measurements/drills with old code — the same failure class
  measured on the restore path on 2026-10-02.
- One implementation means the two paths cannot drift.

  rollout wiring/pins 1 failure + 1 error; G30 3 failures
  (`guards: 136 passed, 3 failed`). After the change: **6/6**, **26/26**,
  `guards: 139 passed, 0 failed`.
- Mutations (5, each reverted): neutralize `-newer` → both stale tests fail;

  appears in the `JAR_FRESHNESS_LIB` default; strengthened to the exact
  `. "$JAR_FRESHNESS_LIB"` line, mutation re-run caught); move the rollout call
  into deploy → the wiring test fails.
- `bash -n` + `shellcheck -S warning` clean on all three scripts.
- Smokes: rollout DRY_RUN fresh → freshness line + plan; stale → `FATAL` with
  no `JobManager reachable` (no cluster contact). Fresh-submit harness: fresh
  jar → freshness line then `REACHED-COMPOSE`; stale jar → `pipeline FATAL`
  stale and the compose step is never reached.
- Full certifying gate to follow.
