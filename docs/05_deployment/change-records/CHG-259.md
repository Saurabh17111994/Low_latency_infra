# CHG-259 — ZooKeeper ensemble health reaches the single pane

## Why

The observability scope covers the ZooKeeper ensemble (quorum, leader, latency, JVM), and the
dossier claims it as delivered. Measured on this cluster, nothing scraped ZooKeeper at all: the
collector's `prometheus` receiver had three jobs (`flink`, `infra-host`, `infra-containers`) and
none of them pointed at a ZooKeeper. The ensemble that decides whether Fluss and Flink HA can make
progress was invisible, so an operator would learn about a degraded quorum from application
failures rather than from the pane.

The remaining question was whether this needs a new component. It does not — the provider ships in
the image that is already pinned:

```text
$ docker exec <zk> ls /apache-zookeeper-3.9.2-bin/lib/
... zookeeper-prometheus-metrics-3.9.2.jar ...
$ unzip -l zookeeper-prometheus-metrics-3.9.2.jar | grep PrometheusMetricsProvider
org/apache/zookeeper/metrics/prometheus/PrometheusMetricsProvider.class
```

`ZOO_CFG_EXTRA` in the entrypoint writes each whitespace-separated token as its own `zoo.cfg` line
(`for cfg_extra_entry in $ZOO_CFG_EXTRA; do echo "$cfg_extra_entry" >> "$CONFIG"; done`), so the
provider is switched on with two more tokens and no new service, image or daemon.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** — the three ZooKeeper services add
  `metricsProvider.className=org.apache.zookeeper.metrics.prometheus.PrometheusMetricsProvider` and
  `metricsProvider.httpPort=7000` to `ZOO_CFG_EXTRA`. `otel-collector` gains the scrape job
  `infra-zookeeper` targeting `zookeeper-1:7000`, `zookeeper-2:7000`, `zookeeper-3:7000` at the same
  15 s interval as the other jobs.
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — `TestCollectorScrapeTargets.
  test_zookeeper_metrics_port_matches_what_the_collector_scrapes` ties the two halves together: the
  port in `ZOO_CFG_EXTRA` and the port in the scrape targets must agree, and every ZooKeeper service
  must appear as a target. A new `_hosts_with_ports()` helper harvests `host:port` pairs from the
  targets, so the assertion compares numbers rather than prose.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — S8 records what the ZK families are and what
  their names look like (see the label warning below).

## Measured

Endpoint, from inside the first member's network namespace:

```text
$ docker exec <zookeeper-1> grep -c metricsProvider.className /conf/zoo.cfg      # fresh volume, first boot
1
$ docker run --rm --entrypoint python3 --network container:<zookeeper-1> ... -c "...urlopen('/metrics')"
# HELP lines: 182
```

End to end in OpenObserve, queried through its own network namespace:

```text

up{job="infra-zookeeper"}:       3 series   value=1 for all three
```

Six failures in the first 37 seconds — targets that had not finished starting — then zero for the
remaining 38 minutes of the task's life. `zookeeper-1:7000` and `zookeeper-2:7000` never failed at
all. The rehearsal check now settles for 45 s and then requires a clean trailing window, so a
*persistent* scrape failure still fails the run while a starting target does not.

## Limitation

**The provider only appears on an ensemble whose data volume is created after this change.**
`ZOO_CFG_EXTRA` is consumed by the entrypoint when it initialises `zoo.cfg`; an existing volume keeps
the file it already has. That is correct for the production VMs, which have never run ZooKeeper
yet — this change lands in their first boot — but it means applying the same change to an
already-running ensemble requires recreating the member's volume, which is a quorum operation and
not something this change does by itself.

**ZooKeeper's metric names collide with Flink's.** The provider publishes unprefixed names
(`znode_count`, `avg_latency`, `jvm_threads_current`, ...), and Flink's scrape job publishes `jvm_*`
of its own. The series are only distinguishable by their labels — `job="infra-zookeeper"` and
`instance="zookeeper-N:7000"` — so any dashboard or alert over a shared name must carry one of those
labels. Recorded in S8 rather than renamed, because the provider offers no prefix option.

## Note

Rolling this onto the live ensemble exposed a placement trap worth recording, because it applies to
every `start-first` service with `max_replicas_per_node: 1`: on a node whose only eligible slot is
occupied by the task being replaced, the new task waits as `Pending — no suitable node (max replicas
per node)` and the update never completes. The three ZooKeeper members are now `stop-first` in the
stack file (CHG-262); on the single rehearsal node the roll needed the same switch applied live
before the members would move at all.
