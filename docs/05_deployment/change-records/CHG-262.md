# CHG-262 — a quorum member rolls stop-first, because start-first needs a free node

## Why

Adding the ZooKeeper metrics setting (CHG-259) looked like it had no effect. The service spec had it,
the rendered file had it, and the running container was two hours old:

```text
$ docker service ps prod_zookeeper-1
prod_zookeeper-1.1  Pending 10 minutes ago  "no suitable node (max replica…"
prod_zookeeper-1.1  Running 2 hours ago
$ docker service inspect prod_zookeeper-1 --format '{{.UpdateStatus.State}} {{.UpdateStatus.Message}}'
updating update in progress
```

The three members pin `max_replicas_per_node: 1`. With `order: start-first` the replacement task waits
for a **second** eligible node, and on a cluster where the only eligible node already runs the replica
— a one-worker rehearsal, or production with two of its three workers down — that node never appears.
The old container keeps serving the old `zoo.cfg`, `docker stack deploy` exits 0, and nothing in the
output says the change never landed. Only `docker service ps` shows `Pending`.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** — `zookeeper-1/2/3` use
  `update_config: {order: stop-first, failure_action: rollback}`. Stopping one member of three keeps
  quorum, which is the rolling-restart order ZooKeeper's own operations guidance assumes, and a
  replacement then needs no spare node at all. Everything else stays `start-first`: overlapping old and
  new task is the point there, and those services are not pinned to one replica per node.
- The policy block at the top of the file now states the rule and its reason, next to the existing
  note about shallow YAML merge keys.
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — `TestQuorumRolloutOrder` requires every
  `zookeeper-*` service to roll `stop-first` and requires at least twelve other services to keep
  `start-first`, so neither half of the decision can be dropped quietly.


## Note

The general trap is in the runbook: after any deploy whose effect you expect to see, check
`docker service ps` for `Pending`. `docker stack deploy`'s exit code describes the API call, not the
rollout.
