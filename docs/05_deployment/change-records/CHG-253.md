# CHG-253 — Flink binds the RPC port it advertises, in both directions

## Why

Run8f's production stack came up 22/22 with the jobmanager Running 1/2 and leadership
granted — and **no TaskManager ever joined it**. The taskmanager log repeated `Could not
resolve ResourceManager address pekko.tcp://flink@flink-jobmanager:6123/user/rpc/
resourcemanager_*` until `RegistrationTimeoutException: Could not register at the
ResourceManager within the specified maximum registration duration PT5M` killed the task,
so the service restarted forever at 0/3 while every component reported itself healthy.

Probing the running task explained it: nothing listened on 6123 at all. Pekko had bound a
random port and published that one —
`Remoting started; listening on addresses :[pekko.tcp://flink@flink-jobmanager:42353]`
(`/proc/net/tcp` inside the container showed 6124, 8081, 9249, 35349, 44777 and no `17EB`).

An isolated A/B on the deployed image isolated the trigger, because the first guess — "the
advertised port and the bound port are two settings and the bind side defaults to `0`" — did
not survive measurement:

| configuration | main Pekko listener |
| --- | --- |
| `jobmanager.rpc.port` 6123, no HA | `pekko.tcp://flink@flink-jobmanager:6123` |
| same, plus `jobmanager.rpc.bind-port: 6123` | 6123 (unchanged) |
| same, address `127.0.0.1` instead of a name | 6123 (unchanged) |
| **`high-availability.type: zookeeper` added** | **`…:35821` / `…:42955` — ephemeral** |
| HA plus `jobmanager.rpc.port: 6123` and `jobmanager.rpc.bind-port: 6123` | `pekko.tcp://flink@flink-jobmanager:6123` |
| `taskmanager` role, no bind port | `33255` / `33801` / `46237` — ephemeral |
| `taskmanager` role with `taskmanager.rpc.bind-port: 6123` | `6123` |

So the split is real, but the defaults differ per role: a standalone jobmanager binds
`jobmanager.rpc.port`; **the jobmanager in ZooKeeper HA mode binds an ephemeral port unless
`jobmanager.rpc.bind-port` pins it** (consistent with HA meaning "the address is discovered
through ZooKeeper rather than dialled"); and a taskmanager binds ephemeral unless
`taskmanager.rpc.bind-port` pins it. Production is the HA shape with a statically addressed
taskmanager, i.e. the one combination that cannot work: the taskmanager dials the advertised
6123 that nothing is listening on, and with HA the jobmanager's own ZooKeeper registration
points at its ephemeral port instead.

The failure is symmetric: the ResourceManager dials a registered TaskManager's advertised RPC
address, so an ephemeral bind port on the worker side leaves it unreachable in exactly the same
silent way. Both sides are pinned, the jobmanager's address is back to
`pekko.tcp://flink@flink-jobmanager:6123` — the address the taskmanager dials — and a test fails
the build when one half is pinned without the other.

The class of defect is the one rules 6 and 7 already describe (a service that cannot become
reachable because of *how* it publishes itself) with a new twist: here nothing fails to start,
so only a runtime probe of the listening socket shows it.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** (4 lines + prose above both properties
  blocks) — the jobmanager block pins `jobmanager.rpc.port: 6123` and
  `jobmanager.rpc.bind-port: 6123`; the taskmanager block pins `taskmanager.rpc.port: 6123`
  and `taskmanager.rpc.bind-port: 6123`. The rationale sits above the block keys, because a
  `#` inside `FLINK_PROPERTIES` reaches Flink verbatim (rule 8).
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — new
  `test_flink_rpc_binds_the_port_peers_dial`. It finds the Flink services by their declared
  `command` (`jobmanager` / `taskmanager`), then requires the advertised port to be pinned,
  requires a `bind-port` for it, requires the two to be equal and refuses `0`. Green
  unmutated; fails all five drift mutations (bind line removed; bind mismatched to 6124; bind
  `0`; port and bind both `0`; taskmanager bind line removed). File 43/43.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — rule 10 states the trap and the remedy;
  the S6 OpenObserve paragraph now also states the password policy that container enforces
  (8–128 characters with lower, upper, digit and special), which is what a rehearsal run hit
  when the root password was too weak: `ZO_ROOT_USER_PASSWORD is too weak` followed by
  `backend job init failed: channel closed`.
- Rehearsal scaffolding (local, not committed): `run9.sh` adds the fresh-create proof — the JM
  must show a listener on 6123 and the JM's own REST `/taskmanagers` must be non-empty — plus a
  refresh of the two rehearsal-only OpenObserve secrets so the stronger dummy password and
  `o2_auth_basic` cannot drift.

## Limitation

The rehearsal proves the jobmanager side end to end (listener plus a registered
TaskManager) and pins the worker side statically. A full job deployment would be the
strongest proof that the ResourceManager can reach the TaskManager it registered; the
rehearsal has no job submission step, so the TaskManager's advertised address is verified by
value and by the listener probe rather than by a running job.

Also engine-specific in one respect: the pinned ports assume nothing else inside the
container claims 6123. The image's own defaults (blob 6124, REST 8081, metrics 9249) do not.
