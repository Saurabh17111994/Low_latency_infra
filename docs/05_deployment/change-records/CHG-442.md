## What was wrong

`B4SignalIntentE2ETest.scanLog` stopped at the first `LogScanner.poll` that reported no
progress. In the Fluss client, an empty poll means *"no fetch completed within the poll
timeout"*, not *"end of log"* — fetches for later buckets can still be in flight. On the
lived-in cluster (16 buckets; `raw_table_1` ≈ 2.4 GB, `Signal_Candidates` ≈ 47 MB after the
CT-2 900 s run) the scan consistently truncated before the later buckets.

Symptom: the first test run (intent enabled) failed with
`smoke: no Signal_Candidates row for the crafted series in 90 s (candles=8)` while the second
test (intent disabled) passed in the same job environment. Tokens are clock-derived, so the
failing token's row sat in a late bucket (`log-14`) and the passing token's row in an early
bucket (`log-2`) — same code, different bucket position.

Proof the production pipeline was correct all along:

- The rule fired in both tests (`n7diag FIRE tf=FIFTEEN_S side=BUY price=10071` at
  21:41:16.551 and 21:43:44.299 — instrumentation since reverted).
- The failing token's row is on the tablet:
  `Signal_Candidates-19236/log-14/00000000000000000000.log`, mtime `2026-09-29 16:11:16.674197941 +0000`
  (= 21:41:16.674 IST, 0.12 s after the fire), containing the run's setup marker
  `1790698260000`; it is also present in the `Signal_Candidates_current` KV projection
  (`kv-14`).
- Controlled comparison on the same live rows: old scan `old=[0,0,0,0,0]`, drained scan
  `new=1` for the failing token; control token `old=1 new=1`.

Attribution: not a CHG-441 regression (flag absent in the drill env → changelog block
skipped; failing leg is the N7 detector, untouched). The failure window opened when the CT-2
run grew the tables enough that a fetch response could exceed one poll timeout.

## What changed

`scanLog` now drains to a target instead of guessing the end:

1. `Admin.listOffsets(..., new OffsetSpec.LatestSpec())` captures each bucket's log end at
   scan start (the same pattern as `RawSampleReader.latestOffsets`).
2. The scan subscribes all buckets at offset 0 and polls until every non-empty bucket's
   `ScanRecords.consumedUpToOffset` (exclusive upper bound) reaches its target, or a 20 s
   deadline. Empty polls no longer terminate the scan.

Imports added: `org.apache.fluss.client.admin.OffsetSpec.LatestSpec`,
`org.apache.fluss.client.table.scanner.ScanRecord`, `org.apache.fluss.metadata.TableBucket`.
No production code, config, DDL, or job behavior changed.
