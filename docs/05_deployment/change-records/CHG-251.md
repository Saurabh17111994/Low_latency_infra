# CHG-251 — Ingestion reads Swarm secrets from files like every other service

## Why

The run7 watch left `prod_ingestion` at 0/1, exit 1: `ARROW_APP_SECRET is required
but not set` plus the TOTP trio missing — while the stack (CHG-249) mounts all three
Swarm secrets and the deployed-spec assertions confirmed the mounts. Root cause: a
missing reader, not a missing mount. `IngestionConfig.java` consulted only the plain
variables while the gateway, the Go execution bridge and nautilus all implement the
`_FILE` contract — DEC-048 (mounted implies consumed) was violated for this one
service, and it hits production identically.

## What changed

- **`code/02_services/01_ingestion/src/main/java/com/trading/ingestion/config/IngestionConfig.java`**
  — `secretFromFile` plus `requiredSecret` and `optionalSecret`, mirroring
  `GatewayConfig.gatewaySecret` exactly: the file wins when both forms are set, a
  named-but-unreadable or empty file fails loud, an absent file falls through to the
  plain variable, and the missing-case message is unchanged
  (`ARROW_APP_SECRET is required but not set`). `ARROW_APP_SECRET` reads through
  `requiredSecret`; `ARROW_PASSWORD` and `ARROW_TOTP_KEY` through `optionalSecret`.
- **`code/02_services/01_ingestion/src/test/java/com/trading/ingestion/config/IngestionConfigFileTest.java`**
  (new) — 4 tests mirroring the gateway contract: all three secrets from files (with
  the secret guard ON, proving guard and file form coexist), file wins over plain,
  plain still works, unreadable/empty fails loud. Plain JUnit assertions: this module
  has no AssertJ, so the first draft's AssertJ imports were rewritten with zero pom
  change. The valid base map also carries the two required `ARROW_MAX_*` keys.
- Rebuilt `01_docker-ingestion` and republished; the rehearsal deploys the new digest
  pin. No stack change (the mounts were already correct), no SecretGuard change
  (`_FILE` keys are not policed keys), no new dependency.

## Limitation

The rehearsal proves the file *reading* (resolution, precedence, loud failure), not
credential *validity*: rehearsal secrets are dummy values, so a real Arrow login is
still untested and stays a first-boot-with-real-secrets risk. The Go bridge path was
already covered by CHG-249; this record closes the Java path.

## Rehearsal result (run8c)

Deploy rc=0 on a fresh create; the ingestion secret-file assertion passes against the
deployed spec. Runtime watch: the service logs `ingestion-config: validated 41 keys`
and `config validated (41 keys, fluss=fluss-coordinator:9123)` with the secret guard
ON - the file reader provably resolves all three secrets past validation. It then
exits fail-closed on `Fluss schema verification failed (allowRuntimeDdl=false)` /
`No resolvable bootstrap urls`: no DDL has ever been applied to this fresh cluster,
so there is nothing to verify against. That is sequencing, not a defect: the DDL-apply
step must precede ingestion on first boot. The runbook did **not** record it when this
record was written — that gap is closed by CHG-256 (runbook step S7b) and the apply is
now measured on the rehearsal cluster.

re-run9 (fresh create, after CHG-253/255) passes the same assertion — `ingestion secret file
wired` — and `no placeholder leak`; ingestion still exits fail-closed on the missing schema
until the DDL-apply step runs. That link is measured as of CHG-256 (2026-09-20): after the
catalog was applied, the schema failure disappeared and ingestion reached the Arrow vendor,
which rejected the placeholder credentials (`user not found`). The vendor feed — not the
schema — is what ingestion still needs to reach `1/1`.
