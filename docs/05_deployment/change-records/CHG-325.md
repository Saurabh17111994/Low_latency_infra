# CHG-325 -- Fresh JobManager restore: create the jar directory before `compose cp`

- **Status:** landed 2026-09-26 -- failing-first red (test harness:
  `ensure_jar_dir: command not found`, rc 127) -> green (21/21 rollout tests);
  real `make day stop` -> `start` restore demo PASSED.
- **Filed:** 2026-09-26
- **Source:** the 2026-09-26 daily-runner dry run (plan P4-3). After a real
  `make day ARGS="stop"` + `start`, the native restore died at the deploy step:
  `rollout-savepoint.sh` runs `docker compose cp <jar>
  flink-jobmanager:/opt/flink/jobs/compute.jar`, but a **freshly created**
  JobManager has no `/opt/flink/jobs` -- it existed in long-lived containers
  only because earlier submits had created it (`pipeline-lib.sh`
  `pipeline_submit_job` does `docker exec ... mkdir -p /opt/flink/jobs` before
  its own copy). The SignalJob was never deployed and the runner reported RED.
  This is the exact Monday-morning path: any day that starts after a stop (or
  any JM recreate) would fail to restore.

## What changed

| Piece | Change |
|---|---|
| `rollout-savepoint.sh` | New `ensure_jar_dir <service> <jar path>` helper: `compose exec -T <service> mkdir -p $(dirname <jar>)`, called immediately before `compose cp`; failure dies with the directory and service named |
| `test_rollout_savepoint.py` | `test_ensure_jar_dir_mkdirs_before_copy` pins the mkdir-before-copy contract |

This mirrors the existing `pipeline_submit_job` behavior; no new mechanism.
