## Why

Item 1 of the build plan (`docs/08_implementation/09-production-swarm.md`) is to publish every
project-built image and make every deploy reference immutable. Today no image has been pushed to a
real registry and the deploy env carries bare tags for three of the seven, so a deploy pulls whatever
`:prod` or `:latest` happens to be, and no digest can be verified against the deployed artefact.

The plan decision of 2026-09-21 settled *how*: GHCR plus the runner's built-in `GITHUB_TOKEN` — not a
classic personal access token and not a push from a laptop. A manual push keeps a workstation in the
production artifact path and needs a long-lived credential, and a PAT created for it would then live
on the machine that must not be in the loop. Public packages pull anonymously, so no registry
credential ends up on a VM either.

The second half of the item is that the deploy env stops being hand-edited: `--merge-env` renders it
from a tracked fragment, so "which digest is deployed" becomes a git fact rather than an operator's
typing.

## What changed

- `.github/workflows/publish-images.yml` (new) — `workflow_dispatch` only; `permissions:
  contents: write` (to commit the fragment) and `packages: write` (to push); a concurrency group
  with `cancel-in-progress: false`, because a half-published release is worse than a slow one; a
  disk-reclaim step (two runtime images plus eight service images do not fit a runner's default free
  space); `docker login ghcr.io` with `github.actor` + `secrets.GITHUB_TOKEN`; a step that creates
  the two env files `make images` insists on (`.env` holding the six placeholder values, plus an
  empty `secrets.env`); the build in the order the tree requires (`make flink-image`,
  `make fluss-image`, `make images`); then
  `image-publish.sh --registry https://ghcr.io/<owner> --env-registry ghcr.io/<owner> --tag prod
  --write-env code/01_platform/01_docker/images.published.env`; then it stamps the fragment with the
  source commit and run id, prints it, and commits it back to the default branch.
- `code/01_platform/01_docker/images.published.env` (new) — tracked, env-shaped, secret-free: package
  names and digests only. Deliberately empty until the first publish, because an image that was never
  pushed has no manifest digest — the same reason CHG-218 commented the four local-build pins out of
  `runtime.lock`. It exists as a file because `--write-env` refuses to create one (`FAIL: env file
  not found`, exit 3).
- No value in the workflow is a secret, and none is real: `docker-compose.yml` refuses to interpolate
  without six `${VAR:?}` values, so the job supplies parseable placeholders, and no build pulls them.
  The only credential the workflow touches is the token GitHub issues that job.
- An owner path is lowercased before it is used for a push or written into the fragment. GHCR requires
  a lowercase repository name, GitHub's `github.repository_owner` keeps the account's display casing
  (`Saurabh17111994`), and Docker refuses the reference outright — so the first CI run would have
  failed at the first push. The workflow lowercases the owner once, where both registry arguments are
  built, so the pushed ref and the value that lands in the deploy env are both lowercase. The runbook's
  manual publish step now states the same requirement for an operator pushing by hand.
- Deviation from the plan's Phase 1 text, recorded as a dated note in the plan itself: the digest
  carrier is the fragment rather than `runtime.lock`, and the `v*` tag trigger is deferred until the
  commit-back path is proven by a dispatch run.

## Not verified

- The workflow has never run, and cannot until it exists on the default branch. Unmeasured: total
  build time on a GitHub runner; whether the disk-reclaim step is enough for ten images; whether
  `stack-lock.sh`'s flock behaves on a runner (`flock` present, `/tmp` writable, lock uncontended);
  whether Docker Hub's anonymous pull limits bite while the build pulls its base images; and whether
  the first publish's digests satisfy `pin-check`.
- The two one-time GitHub actions remain open and are the operator's: check the repository's Actions
  workflow-permission setting, and flip the seven packages from private to public **after** the first
  successful push (visibility is a one-way change; new packages are private by default).
- Anonymous pull is a plan acceptance criterion, not a measurement here: with nothing pushed,
  `docker logout ghcr.io` followed by `docker manifest inspect` has nothing to prove.
- The dated correction note in `docs/08_implementation/09-production-swarm.md` — build-plan item 1's
  "Not verified: a real push to GHCR" line — is deliberately not part of this change, because it
  would assert a push that has not happened. It follows the first green run, with that run's digests.
