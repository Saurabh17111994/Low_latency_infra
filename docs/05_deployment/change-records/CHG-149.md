# CHG-149 — The catalog and lake guards check what they claim to check

- **Status:** recorded — all 22 wave-12 findings fixed
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 12 ("Catalog and lake guards"):
  P6-034, P6-035, P6-317, P6-318, P6-319, P6-320, P6-321, P6-714, P6-715 (catalog-guard.sh);
  P6-121, P6-122, P6-436, P6-437, P6-438, P6-439, P6-440, P6-755, P6-756 (lake-guard.sh);
  P6-573, P6-574, P6-793, P6-794 (stale_table_kind_scan.py)

## What happened

Both guards answer an operational question with a verdict, and in every one of these findings the
verdict was reachable without the fact behind it.

**`catalog-guard` could repair on a phantom empty catalog (`P6-034`).** `count_tables` printed `0`
whenever the zkCli output contained no `[...]` line — which happens both when the ZK path is absent
(the state this guard exists to repair) and when the probe failed outright: a dead connection, a
renamed container, a changed zkCli path. The caller could not tell them apart and the next step is a
DDL apply, so an unreachable ZooKeeper looked exactly like a lost catalog. The probe now
distinguishes "the node does not exist" (repairable `0`) from anything else it cannot parse, which
fails closed with the raw zkCli output in the message (exit 5). The probe also had to move its state
out of a command substitution — a reason string set inside `$( )` never reaches the caller, a defect
the new test caught during this wave's own build.

**A failed apply was masked by a complete-looking count (`P6-035`).** The verify step exited 0
whenever the post-apply count matched, logging the apply's non-zero exit as a "smoke flake". The
count proves the *tables* exist; the apply's exit code is the only evidence about everything else in
that contract, and swallowing it is how a broken apply looks healthy. A complete catalog with a
failed apply is now exit 5 with what to re-run, and the smoke-flake explanation stays in the message
rather than in the exit code.

**An over-count was called healthy (`P6-320`).** The header documents `count == EXPECTED` as healthy
and `0 < count < EXPECTED` as PARTIAL, but the test was `-ge`, so a catalog with *extra* tables — a
rolled-back DDL, a manual experiment — was reported healthy. Equality is now required in both
directions: fewer tables is PARTIAL (exit 3), more tables is drift (exit 3, different message).

**The rest of the catalog findings.** `EXPECTED_TABLES` is validated as a whole number before it is
compared arithmetically (`P6-317`: a typo used to surface as a bash "integer expression expected"
error and an undocumented exit); the compose inputs and the docker daemon are preflighted before any
compose call (`P6-318`: a missing `.env` was reported by compose, which reads like a guard bug); the
zookeeper container is resolved through this compose project and re-checked as running, and the
zkCli path is discovered inside the image instead of assumed (`P6-319`: `docker ps --filter
name=zookeeper` can match another project's container or a sibling service); two guards can no longer
repair at once (`P6-321`: `flock` on a per-uid lock file, second run exits 6); `fail "msg" 3` no
longer prints the exit code into the message (`P6-714`); and a whitespace-only table list counts as
empty instead of one table (`P6-715`).

**`lake-guard` counted markers as data (`P6-121`, `P6-122`).** The day checks were
`grep -c '^<table>/data/event_day=<day>/'`, so `_SUCCESS`, a `.crc` sidecar or a zero-byte directory
marker satisfied "≥ 1 object" while the table held no data at all — on the *yesterday* check and on
the after-18:30 *today* check alike. `r2_list_lake` already emitted the object size next to the key
and nothing read it. Both checks now count non-empty `.parquet` objects only.

**Old manifests passed for a live table (`P6-439`).** "At least two `.avro` under `metadata/`" is
satisfied by orphaned files from a commit that failed months ago, and by zero-byte markers. The
listing now carries `LastModified` through (an additive change to `r2-list.sh`), the count ignores
empty files, and the newest manifest must be younger than `LAKE_GUARD_MAX_MANIFEST_AGE_H` (default
48) — an old newest-manifest is exactly the "yesterday's commit never landed" signal the guard
exists to raise.

**One snapshot, one giant listing (`P6-437`, `P6-440`, `P6-438`).** The guard paginated the entire
warehouse once at startup, held it in a shell variable, grepped it two or three times, and reused it
for a check that runs hours later — so an object written while the guard was running was invisible,
and a listing failure exited non-zero under `set -e` with no `!! lake-guard FAIL` line for alerting
to match on. Each check now lists only its own prefix, at the moment it runs, and a failed listing
is a FAIL with the r2-list reason in it.

**The rest of the lake findings.** `LAKE_GUARD_CHECK_DAY` is validated as `yyyyMMdd` before it
reaches a listing prefix (`P6-436`: `.*` matched every key and forced a PASS); the manifest floor is
a documented knob instead of a magic `2` (`P6-755`); the table prefix is derived from
`S3_WAREHOUSE_PATH`/`R2_PREFIX` with an override, instead of three hard-coded copies of
`lake/default/raw_table_1/` (`P6-756`).

**The scan's four.** A missing or malformed `schema_manifest.json` is reported as a finding with a
non-zero exit instead of a `FileNotFoundError` traceback from a CI gate (`P6-573`); a DDL file whose
`CREATE TABLE` cannot be found is now an explicit problem and fails the "every DDL file has a
manifest entry" check, instead of being dropped from `parsed` while that check printed a PASS over
the remaining files (`P6-574`); the reversed test-count form carries the same `(?!\s+tables?)`
exclusion as the forward one, so "24 common tables" is no longer read as a stale test count
(`P6-793`); and the table-kind/phase-status dedup key includes the classification tier, like the
numeric loops already did (`P6-794`).

## Judgement calls

1. **"Real data object" = a non-empty `.parquet`.** That is the shape the tiering writer produces
   (`r2-restore.sh` globs `**/*.parquet` under the same prefixes), and it is the fix the finding
   suggests. It is an assumption about the writer: if the lake ever stores data under another
   extension, the guard would report "no data" for a day that has some.
2. **`r2-list.sh` changed in wave 12 (two additive changes).** The wave rule assigns *findings*, not
   files; P6-437's fix needs the optional prefix argument and P6-439's needs the timestamp, and the
   alternative was a per-object HEAD request. Both are additive: no argument still lists the whole
   warehouse prefix, and the third TSV field is an extension of `key<TAB>size`.
3. **The third TSV field changes the CLI/TSV shape**, so wave-10's own tests were updated with it
   (two assertions, the ListObjectsV2 stub now emits `LastModified`, one new test for the prefix
   argument). That is a test-pin update, not a reassignment of a wave-10 finding.
4. **A listing failure is a FAIL line; bad input is not.** lake-guard prints `!! lake-guard FAIL:
   …` and exits 1 when R2 cannot be listed (the alerting contract), but an unusable knob prints
   `!! lake-guard INPUT: …` and exits 2 — a misconfigured cron job is not "the lake is unhealthy".
5. **catalog-guard gains exit codes 5 and 6 and an exact-count rule.** The only in-tree caller is the
   Makefile target, which already treats any non-zero exit as "catalog NOT healthy"; the header and
   the exit-code table in the script were rewritten to match.
6. **`LAKE_GUARD_AFTER` and the `CATALOG_GUARD_*_WAIT` knobs are test seams** (same class as
   `LAKE_GUARD_CHECK_DAY`): documented in the script headers, unset in production, where the
   defaults (18:30 IST, 30 × 2 s) apply.
7. **The P6-794 fixture had to be constructed deliberately.** With the claim regex capped at 60
   characters and `KIND_WINDOW` at 80, two same-type hits on one line only receive different tiers
   when the marker sits beyond `m1 + 80` and inside `m2 - 25`; below that both hits get the same
   tier and the key change is invisible. The test uses exactly that shape and asserts both tiers are
   reported.
8. **The compose-form registry row is part of this change, not a later wave's finding.**
   `test_compose_form_contract.py` is the test that made one compose form mandatory after the
   2026-09-13 drift incident; it refuses any invocation site that is not in its registry, so
   resolving the zookeeper container through `"${COMPOSE[@]}" ps -q` (P6-319) cannot land without a
   row. The row is kind `VAR`, whose definition is the already-registered `COMPOSE=(docker compose`
   in the same file, so the env-file assertion still applies to the new site.
9. **No live call was made to R2, Cloudflare or ZooKeeper.** Every new path is exercised against
   stubs (a stub `docker` on PATH, a stub `r2-list.sh` beside the script). The paginated listing and
   the `LastModified` field have never talked to the real bucket; the next scheduled run of
   `lake-guard.sh` (or a manual `r2-list.sh lake`) is the first live exercise of both.
