## Why

The first CI publish run (`35563082177`, 2026-09-21) failed in step 6, "Build the two runtime
images", after 121 seconds with exit code 2 — `make`'s own error code, so a recipe command failed
rather than a compile. Steps 1–5 were green (disk reclaim, GHCR login, env files), so the failure was
a fast prerequisite, not a build.

It reproduced on the workstation, and the variable turned out to be the locale:

| Locale | `hadoop-mapreduce-compat-2.8.5.jar` | Verdict against the old pin |
| --- | --- | --- |
| `en_IN.UTF-8` — this workstation, where the pin was made | `14c5a8e5…` | matched |
| `C` — a GitHub runner's locale | `c19c414b…` | MISMATCH → `die` → `make` exits 2 |

`fetch-jars.sh` derives that jar with `find org -type f | sort | zip -q -X` and verifies the *whole
file's* SHA256. The file mtime was pinned (CHG-… of 2026-09-16 made that explicit and tested); the
**collation was not**. `sort` follows the caller's `LC_ALL`/`LANG`, so the entry order — and with it
the zip bytes — depended on whose machine ran the derivation. The pin was therefore measuring the
developer's environment rather than the content it was supposed to guard.

Nothing about the image was ever wrong. Both orderings carry the same 499 entries: the sorted
entry-listing hash is `efb55cbefbf82a2c5b07bde61d608a126496edb29c6fb84c93b26bc5de9df4ed` for both.
That measurement is what makes re-pinning honest here instead of a loosened guard: the change moves
the pin from "the bytes one workstation produced" to "the bytes any machine produces", and the
content check that matters — every installed artifact must match a pin — is untouched.

## What changed

- `code/01_platform/01_docker/flink-runtime/fetch-jars.sh` — the derivation pipeline is now
  `find org -type f | LC_ALL=C sort | zip -q -X -@ "$dir/$COMPAT_JAR"`, and `COMPAT_SHA256` holds the
  C-collation bytes (`c19c414b…`). The comments above both lines state why, and the pin comment keeps
  the previous value for archaeology. This file is the only place the hash appears (verified by a
  repository-wide grep for the old value: one hit, the pin itself).
- `code/01_platform/04_scripts/tests/test_flink_runtime_image.py` — `test_derivation_pins_the_collation`
  asserts the pipeline pins the collation, exactly as the neighbouring test asserts it pins the mtime.
  Without the `LC_ALL=C`, a future edit silently reintroduces an environment-dependent pin.
- `code/01_platform/01_docker/flink-runtime/README.md` — the paragraph explaining why the jar is
  derived now lists the collation beside the mtime and records the measured pair. It previously said
  "two independent runs on 2026-09-16 produced byte-identical output" — true, and the reason the trap
  survived: both runs happened on one machine under one locale.
- `docs/plans/2026-09-21-ci-publish-and-single-node-rollout.md` — dated note: this fix consumes
  CHG-277, so the plan's Stage 3 single-node profile is CHG-278.

## Measured

- Pre-fix, same content, four runs: `LC_ALL=C` → `c19c414b…` (MISMATCH against the old pin, rc=1);
  `en_IN.UTF-8` → `14c5a8e5…` (match, rc=0). That is the CI failure reproduced on the workstation.
- Entry count 499 and sorted-entry hash `efb55cbe…` identical in every run, pre- and post-fix: the
  two jars differ in order only.
- Post-fix, `LC_ALL=C` **and** `LC_ALL=en_IN.UTF-8` → both **rc=0** with file sha256
  `c19c414bc07b610b6d42c1806a511526113036dc5b6bb0bf0c3c730a7ae989df`, i.e. byte-identical output from
  two different locales. This is the property the fix buys.
- Mutation 1 — `LC_ALL=C ` removed from the pipeline → `test_derivation_pins_the_collation` fails
  (rc=1); file restored byte-identically (`cmp`).
- Mutation 2 — final hex digit of the pin changed in a throwaway copy → the script fails with
  `MISMATCH`, rc=1, so the runtime guard still bites after the re-pin.
- `python3 -m pytest test_flink_runtime_image.py test_fluss_runtime_image.py -q` → **61 passed, 6
  subtests** (60 before), and `python3 docs_audit.py` → rc=0.
