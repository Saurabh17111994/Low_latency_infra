## Result: no storage gain (negative result, recorded)

- **Fluss already compressed.** Both 0.9.1 and 1.0.0 default to
  `table.log.format=ARROW` + `table.log.arrow.compression.type=ZSTD` +
  `zstd.level=3` (`fluss-common` `ConfigOptions` source). The legacy table had no
  materialized property but ran the default -- it was already zstd.
- **Live measurement, property verified materialized** (TableInfo before: 11
  properties, no compression entry; after: 12, `= zstd`):
  smoke `logs/chg487-smoke-20261001-120429` -> `fluss.tablet.bytes` raw_table_1
  **+146.90 MB/min vs +148.42 MB/min** in the CHG-484 900 s baseline (unchanged);
  physical ~508 B/row vs ~542 B/row before (row-count/du check).
- **Why the probe misled:** it replayed 200 k rows as fast as the scanner
  delivered (multi-row per-bucket batches) and compared against an explicit
  `compression=none` control (926 B/row), not against the live default. At the
  live rate (~1 600 rows/s over 16 buckets ~= 100 rows/s/bucket) and the
  ingestion `client.writer.batch-timeout=1 ms`, each stored batch is ~1 row, so
  per-batch Arrow overhead leaves compression almost nothing to work with.
  Correction filed at
  `logs/soak/raw-compression-probe-linger1ms-20261001-114821/findings-correction.md`.

## What the recreate did fix

- **Retention drift (real bug):** `RawTableSchema.LOG_TTL/PARTITION_RETENTION`
  were still 9d/9 while the DDL has said 3d/3 since 2026-09-30 (A2). The
  bootstrap/repair recreate path (`DropRawTable ensure`, `RawTableAdmin`) would
  have produced a 9-day-retention table. Now 3d/3 with the two guard tests above.
- The recreated live table now carries the property explicitly (operator decision
  2026-10-01: keep the pin -- harmless and makes the metadata deterministic).
- Recreate sequence: `DropRawTable drop localhost:9123` ->
  `DropRawTable ensure localhost:9123` (dev only; synthetic replay data).
