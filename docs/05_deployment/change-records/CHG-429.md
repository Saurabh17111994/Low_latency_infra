## Notes

- **The name was the bug:** nothing failed while the class existed — it compiled, it closed its handles, its
  tests passed. What it did was teach every reader that a durable ledger lived in `common`, when the only
  durable ledger is the gateway's. Deleting it removes the false affordance; the guard keeps it gone.
- **Why the guard scans imports, not just names:** a future class could be named `FlussLedgerStore` or
  `FlussPostbackLedgerStore`; the invariant is "a ledger store that talks to Fluss lives in the gateway",
  so the scan keys on the Fluss import plus a `*LedgerStore*` file name.
- **Observed residual (not fixed — outside L5-4's scope):** `FlussCorrelationIndex` and
  `FlussLifecycleStore` in the same package are the same dead fake-durable pattern (Connection/Table
  opened, every call delegated to an in-memory counterpart, zero usages; honesty notes P4-009/P4-154).
  They are candidates for the same treatment in a follow-up finding; the guard stays ledger-scoped per
  the plan. `FlussPostbackQuarantineStore` is different — it really writes through an AppendWriter and
  stays.
- **The in-memory oracle stays:** `InMemoryProjectionLedgerStore` is what the offline drivers and drills
  use, and the plan keeps it. The port javadoc now says so instead of promising durability.
