# CHG-142 — The tamper-evident trail stops accepting forged or silent evidence

- **Status:** recorded — seventeen of eighteen wave-5 findings fixed in two commits; one half of one
  finding deliberately left open with the reason below
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 5 ("Audit chain and deletion control"):
  P6-259, P6-260, P6-261, P6-262, P6-263, P6-646, P6-647, P6-648, P6-649, P6-650, P6-651, P6-652,
  P6-653, P6-654, P6-655, P6-848, P6-849, P6-850

## What happened

Every finding was re-verified against the current code before editing. `AuditHashChain` and
`AuditDeletionControl` are the two classes the retention and deletion rules are judged by, and they
had never been validated against hostile input — the canonical byte strings they hash were built by
unchecked string concatenation, and the reconstruction paths assumed their inputs were well formed.

**The canonical bytes could be forged (`P6-262`, `P6-263`, `P6-651`).** Both classes hashed
`key=value` lines assembled without any escaping or validation. In the chain, a newline in `table`
(or a `:` inside an `eventId`) could forge extra lines, so two logically different manifests could
produce one canonical string, one manifest hash and one root hash. In deletion evidence the same
injection let two different requests collide — a test now builds the pair that collided before this
change (`"r1"`/`"a\nscope=b"` versus `"r1\nscope=a"`/`"b"`). The chain validates its fields and
rejects line breaks plus the `:`/`=` delimiters; deletion evidence escapes values instead. Both
classes also accepted arbitrary strings as "SHA-256"; `HASH_HEX_LENGTH` was declared in
`AuditHashChain` and used nowhere, so `"x"` was a valid content hash that still produced a
valid-looking chain. It now must be 64-character hex.

**Malformed input crashed instead of being recorded (`P6-259`, `P6-260`, `P6-652`, `P6-653`,
`P6-655`, `P6-850`).** `Set.copyOf`/`List.copyOf` throw on a null element, so a deserialized
context or authorizer list failed at construction — before `evaluate()` could emit the immutable
deletion-evidence event the class promises for *every* attempt; a null element is now judged as an
unauthorized attempt. On the reconstruction side, a null manifest or a null observed event threw an
implicit NPE out of the verifier: `verifyChain` now returns `BROKEN_LINK`, `verifyManifestAgainstSource`
returns `MISSING_EVENT`, and the chain builders use a named `requireNonNull`. A null event list is an
`IllegalArgumentException` rather than a bare NPE from `List.copyOf`.

**Rejected attempts lost the one thing they exist to record (`P6-646`, `P6-647`, `P6-648`).** Every
rejection branch passed `null, null` for the authorizers, so the hash-chained evidence could not say
who attempted a deletion — worst for `REJECTED_UNAUTHORIZED_OPERATOR`, where the intruder's identity
is the entire point, and indistinguishable from an empty-authorizer attempt. Rejections now record
the attempted operator: the validated single operator for policy/hold rejections, the intruder for an
unauthorized one, the first two for an over-authorized pair.

**Stored hashes were trusted (`P6-261`).** `classify()` compared only the stored `eventId` and
`contentHash`, so an attacker who altered a field (scope, approved, authorizer) while preserving the
stored hashes was classified `DUPLICATE` — accepted as idempotent replay. It now recomputes
`canonicalHash(incoming.canonical())` and returns `VIOLATION` when the record does not match itself.

**The date check ordered strings, not dates (`P6-654`, partial).** `Manifest` accepted any non-blank
`tradingDate` and `verifyChain` compared them lexicographically, so `"2025-1-2"` sorted after
`"2025-10-01"` and any malformed value silently participated in `BROKEN_LINK` logic. The date must
now be ISO-8601 `yyyy-MM-dd` (checked for shape *and* parsed), which makes lexicographic order
chronological order.

## Judgement calls (review these)

1. **`P6-654` is only half done, and I left it unticked.** The finding also notes that the strictly
   increasing rule rejects legitimate same-day multi-table chains (a `Manifest` is one day for one
   table). That rule is mirrored **line for line** by the byte-exact Python port
   (`01_platform/04_scripts/r2_legal_hold_check.py::verify_chain`, pinned by golden Java-parity
   constants in `tests/test_11_r2_legal_hold.py`), so changing it in Java alone would make the two
   verifiers disagree about the same chain — a worse defect than the one being fixed. It must change
   in both files at once, in the wave that owns the Python port. Nothing is exposed meanwhile: no
   producer builds manifests yet (`01-foundation.md`: real per-day manifests still need the EOD
   controller, SCH-23). The map item stays open rather than being ticked with half a fix.
2. **`P6-650`'s suggested fix was rejected.** The finding asked for a timestamp-free `eventId` so a
   retry dedupes. With the timestamp excluded from identity but still inside the content hash, a
   retry that re-stamps the clock yields the *same* id with a *different* hash — which `classify`
   maps to `VIOLATION`, the quarantine-and-halt path, on the most routine operation there is. It
   would also collapse genuinely distinct attempts (same `requestId`, later time) into one id.
   Identity is therefore unchanged (the whole canonical record, timestamp included) and the contract
   is documented on the record and pinned by a test: reuse the same `timestampMs` for idempotent
   replay; a re-stamped attempt is a new, separately recorded attempt.
3. **`P6-263` is validation-only, on purpose.** The finding offered length-prefixed encoding as an
   alternative. That would change the canonical bytes of valid input and break both the golden
   Java-parity hashes and the Python port's byte-exactness, for no gain over rejecting the
   characters that make the format ambiguous (`P6-262`'s repo-wide "silent format breaks"
   discipline from CHG-083). A new test pins the bytes of valid input as unchanged.
4. **The deletion canonical form is versioned `v1` → `v2`.** Escaping changes the preimage, so
   `contentHash`/`eventId` differ from what the pre-fix code produced for the same logical request.
   No corpus needed migrating — the class has no producer yet, and the event record carries no format
   marker, so a `v1` hash can only be recognised by its own bytes. The version token is a code-level
   statement of when the preimage changed, not something a stored record reveals.
5. **`P6-848` resolves by being used, not by deletion.** The finding called `ArrayList`/`Collections`
   dead imports; the null-tolerant copies for `P6-259`/`P6-260` are exactly what they carry now.
   `P6-849` is a comment: `authorizerTwo` stays in the record and the canonical form as
   legacy-reserved schema (DEC-044), always null for new evidence, documented so a future
   two-authorizer check cannot misread it as a live field.
6. **`P6-649` follows the class's own convention.** The finding allowed either a governed outcome or
   `requireNonNull`; `evaluate()` already `requireNonNull`s its two top-level inputs, so `classify`
   now does the same. Note the honest limit: before and after, a null argument throws NPE, so that
   test documents the contract rather than proving a behaviour change.
