# CHG-269 — a named service owns the EOD trigger, so the daily manifest lifecycle actually starts

## Why

The stack requirement is a named service or scheduled job owning the EOD manifest lifecycle
(`docs/02_requirements/06-operational.md` §6.8, SCH-23). `eod_controller.py` implements that lifecycle
and has since W45, but **nothing invoked it**: no cron entry, no systemd timer, no stack service. The
runbook recorded the gap as a row in §6.1 and a `[NOT BUILT]` marker in S11 — and a schedule that
exists only as a runbook line is not a schedule. In production the manifest lifecycle would never have
started, and nothing would have said so.

Three constraints shaped the design:

- **Timing is not durability.** The controller already owns durability (state table, lease, TTL
  extension, retry/backoff). The trigger must own only *when* — so a trigger restart cannot corrupt or
  duplicate a day, and a missed fire is recoverable by re-running the controller.
- **Rule 6 (DEC-047): a healthcheck may not depend on another service.** A scheduler whose liveness is
  "Fluss answers" restarts during someone else's outage, which is exactly when the manifest is least
  safe to lose track of. The scheduler therefore healthchecks **its own heartbeat file**.
- **Fail closed on the money path.** `EOD_OFFLOAD` defaults to `none` and `EOD_TABLES` has no default,
  so the service cannot offload anything, or guess which tables it covers, until an operator says so.

## What changed

- **`code/01_platform/04_scripts/eod_schedule.py`** (new) — the trigger. Owns a strictly-after,
  DST-correct clock (`zoneinfo`, `--at`/`--zone`, default 23:30 `Asia/Kolkata`), recomputes the next
  fire after every fire and after every sleep chunk (a suspended laptop or a clock jump does not shift
  the schedule), writes a heartbeat before it starts the controller (a long run must not look dead to
  its own healthcheck), retries a crashed controller with exponential backoff, and returns the
  controller's exit code for `--once`. `--dry-run`, `--days`, `--check-heartbeat`, `--max-age`,
  `--controller-arg` for the rest.
- **`code/01_platform/04_scripts/tests/test_15_eod_schedule.py`** (new) — 15 hermetic tests with a fake
  controller that records its invocations and returns scripted exit codes: the clock (leap day, DST in
  two zones, strictly-after, monthly boundary), heartbeat freshness, retry/backoff, and exit-code
  propagation. Seven mutations were injected and each was caught.
- **`code/01_platform/01_docker/docker-stack.yml`** — the `eod-scheduler` service: one replica,
  `<<: *deploy_workload` placement (`node.labels.role == worker`), **unbounded restart**
  (`restart_policy: {condition: any}`, CHG-258's reasoning applied to a schedule), the image's
  `entrypoint`/`command` overridden to run the trigger, and a healthcheck that runs
  `--check-heartbeat --max-age 2700` (its own file only; 2700s covers the controller's 30-minute lease).
- **`code/01_platform/01_docker/ddl-apply/Dockerfile`** — the image now carries `eod_schedule.py`
  beside the controller it already shipped (java, `common/target/classes`, the five pinned jars, the
  M2 repository at `/opt/ddl-apply/m2/repository`), so no new image is published.
- **`code/01_platform/04_scripts/eod_controller.py`** — `M2_REPO` now falls back
  `EOD_M2_REPO` → `DDL_APPLY_M2_REPO` → `~/.m2/repository`, so the launcher resolves its jars inside
  that image as well as on a workstation.
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** (+5) — the owner contract (one replica,
  fail-closed lake and tables, unbounded restart), that the healthcheck depends on nothing but itself,
  and that the scheduler and the Java tool agree on the zone (a wrong-day EOD is a real defect class).
- **`code/01_platform/04_scripts/stack_selfcheck.sh`**, **`tests/test_stack_selfcheck.py`**,
  **`code/01_platform/01_docker/.env.example`** — the deploy validator's required list grew 13 → 15
  (`DDL_APPLY_IMAGE`, `EOD_TABLES`) with compile-only placeholders exported, and the template documents
  both. Measured before the fix: compile-only mode died at interpolation on the new `:?` values, and
  `DEPLOY=1` reported 7 of 15 missing instead of the documented 5.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`**, **`docs/08_implementation/09-production-swarm.md`**
  — the EOD-trigger gap row becomes a lake-offload gap (the trigger exists), S11 tells the operator what
  the service does and which two values are their decision, and plan item 5 is now `Built (CHG-269)`.

Two defects were found by running things rather than by tests, and both are fixed here:

- **`docker stack config` corrupts `${VAR:?message}` when the message contains a hyphen.** Measured:
  `"${EOD_TABLES:?name the EOD-eligible tables}"` renders the *value* as `eligible tables` whenever the
  variable is set, and truncates the message when it is not. The service would have received prose as
  its table list. The message is reworded, and `test_09_stack.py` now rejects any hyphenated
  interpolation message in the stack (it was the only one of 42).
- **The validator would have failed closed on a correct deploy.** Covered above.

## Not verified

**A manifest reaching `VERIFIED` in the rehearsal.** The fire above failed at
`Table 'default.eod_offload_state' does not exist`: the rehearsal cluster's catalog is empty because the
last successful DDL apply (`~/.p6v/reh/ddl-apply.log`) predates the current stack, and re-applying is
gated — `ddl_apply.py --apply-verified` refuses without `--matrix-evidence` (COMPAT-FLUSS-005 capability
artifact, runtime-only, not on disk). On the real VMs the catalog step (S4/S7) runs the DDL apply before
the stack, so this is the rehearsal's own sequencing, not a property of this change. What the live fire
does prove is the trigger path end to end and that a failure is **loud and fail-closed** rather than a
silent unverified day.

Also unproven here: the production clock (the service has never fired on a real 23:30), the lake offload
path (`EOD_OFFLOAD=lake` needs the R2 bucket and keys), and the 4-VM deploy.

**The scheduler holds no lease.** Two replicas would both fire; the controller's lease makes the second
a no-op, which is why `replicas: 1` is the contract and `test_09_stack.py` pins it. A single-node
rehearsal cannot exercise the two-replica race.
