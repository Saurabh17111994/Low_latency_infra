# CHG-124 — Content-addressed image freshness (build stamps)

## Why

`make check-image-stale` (CHG-101) decided freshness by comparing an image's
`Created` epoch against the last commit touching its source paths. Two live
failures on 2026-09-12 proved that proxy unsound:

* **`compute` reported STALE for a current image.** The image contained exactly
  the committed `submit-jobs.sh` (`sha256 96b5bb3f…` both inside the image and
  in the tree), but it was built 13 minutes *before* the commit that touched
  that path — so it predates the commit while containing its content. No
  rebuild could clear it: BuildKit correctly cache-hits and reuses the image,
  so `Created` never moves. Gate step 8 could not pass.
* **`loadgen` reported MISSING for a freshly built image**, because the checker
  derived `<project>-<service>` instead of reading compose's declared
  `image:`. Fixed in the same session as part of step-8 restoration.

The repository already had the right mechanism: G27b's content stamp on the
loadgen image (`pipeline-lib.sh`, 2026-09-02 — *"the mtime first draft
false-positived on git checkout/touch … and a fully-cached rebuild never bumps
the image Created time, so it could never clear again"*). This record
generalises that stamp to every `build:` service rather than inventing a
second mechanism.

## What changed

* **`make images`** — computes each service's stamp, exports it, builds every
  `build:` service, then re-runs the checker. Fail-closed: no stamps computed
  ⇒ nothing is built.
* **compose** — every `build:` service carries
  `labels: {com.trading.build-stamp: ${<SERVICE>_BUILD_STAMP:-none}}`. This is
  compose's native image-label feature, so no Dockerfile is edited and no
  layer is invalidated (measured: a labels-only rebuild of the 13-layer
  compute image takes 0.26 s; layer count unchanged).
* **`image_staleness_check.py`** — `input_stamp()` (sha256 over the service's
  `SERVICE_SOURCES` contents plus its Dockerfile; content-only, so `touch`,
  `git checkout` and cache hits are invisible to it), label read-back, and
  `--print-services` / `--print-stamps-env` for the builder side. The stamp
  decides FRESH/STALE; the timestamp comparison survives only as the fallback
  for images built before this change, and its verdict text says so.

Not changed: loadgen's `/app/build-stamp` file and its two readers
(`pipeline-lib.sh` G27b, `stage-soak-e2e.sh`). The label is additive, so no
existing freshness mechanism is disturbed.

## Follow-up — the first cut silently no-op'ed (measured, same day)

The first build after this change produced eight images carrying **no** label:
`docker image inspect` returned `none` for every service, and the checker fell
back to the timestamp proxy — the mechanism was inert while the gate stayed
green. Cause: `make images` ran `eval "$stamps"`, which sets *shell* variables;
`docker compose` is a child process and never saw them, so every
`${<SVC>_BUILD_STAMP:-none}` interpolated to `none`. The compose declaration and
the stamp arithmetic were both correct — only the transport was broken, and
nothing asserted that the value reached the build command.

Caught by reading the checker's verdict text (`(timestamp proxy: no build stamp)`)
and the raw labels, *not* by the exit code: `make check-image-stale` said PASS
throughout, because a fallback that is allowed to be wrong always can be.

Fixed by handing the stamps to the build command's own environment
(`env $(... --print-stamps-env) docker compose build`) and by adding
`--require-stamps`, which `make images` now passes: an image without a label is
`NO-STAMP` and fails the run, so this failure mode is loud instead of silent.

Falsified evidence (each guard fails when its behaviour is removed):

- `env INGESTION_BUILD_STAMP=probe123 docker compose … build ingestion` → the
  image carries `probe123`: the compose mechanism itself works.
- the `eval` path → eight unlabelled images, checker still PASS.
- after the fix → labels present, checker PASS *by stamp* (`stamp <sha>… matches
  the sources`), not by clock.

Considered and rejected — *let BuildKit answer* (rebuild each service and compare
image IDs: an unchanged ID means unchanged inputs): more native still, and it
would delete the stamps, the labels and `SERVICE_SOURCES` entirely. Rejected for
this gate because it **repairs** staleness instead of reporting it — a forgotten
rebuild would silently happen at gate time and nobody would learn the process
failed — and it needs the network on any real miss (nautilus fetches its crate
graph). For a pre-market gate the honest signal is worth more than the deleted
bookkeeping. Also rejected: hashing inside the Dockerfile (`RUN … > build-stamp`,
read back with `docker cp`) — it removes the env transport but keeps the curated
host-side input list, so it trades real maintenance for cosmetic self-containment.
