# CHG-265 — the agents monitored the node they ran on, and they ran on one node

## Why

`node-exporter` and `cadvisor` are per-host agents: they report the host they run on. Both were
`mode: global` **and** pinned to `node.labels.observability == true`, which in this topology is VM4
alone. On the four production VMs that means VM1–VM3 contributed no host metrics and no container
metrics at all — the trading nodes were the unobserved ones.

Two more things were wrong underneath it, and neither is visible from the stack file:

```text
# the collector's scrape targets, before
- targets: ["node-exporter:9100"]     # the service name resolves to the VIP, not to every task
$ docker run --rm --network container:<collector> python:3.12-alpine python3 -c "...gethostbyname_ex..."
tasks.node-exporter -> ['10.0.1.18']   # the task itself
node-exporter       -> ['10.0.1.17']   # the load-balanced VIP

# what the agent reported as "which node am I", before
node_uname_info{... nodename="f77f64fd95c1"}   # the container id — identical shape on every node
```

With the agents on every node, the bare service name would have been worse than useless: each
scrape would hit one arbitrary task, so four nodes' series would arrive under one instance label and
silently sample at random. And a `nodename` of container-id makes four nodes indistinguishable even
when the numbers do arrive.

The stack also could not express the correct placement: `test_09_stack.py` required a label
constraint on *every* service, and the runbook's rule 1 said the same. A per-host agent's correct
placement is "every node" — that is what `mode: global` means — so the rule itself was the obstacle.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** — `node-exporter` and `cadvisor` lose their
  placement block (they keep `mode: global`), and gain `hostname: "{{.Node.Hostname}}"`. The comment
  carries the measured cost of running them everywhere and the reason the hostname is not cosmetic.
- **`code/01_platform/01_docker/otel-collector-config.swarm.yaml`** — the two per-host jobs scrape
  `tasks.node-exporter:9100` and `tasks.cadvisor:8080`, so one central collector covers every node
  without duplicating a series.
- **`code/01_platform/01_docker/otel-collector-config.yaml`** (dev compose) — targets stay bare, with
  a comment saying why: `tasks.` is Swarm DNS and does not resolve under plain compose. This is the
  one place the two configs must differ.
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** — the blanket rule becomes a policy with a
  named exception: `PER_HOST_AGENTS` must be `global` with **no** constraint, every other service
  still places by label, and nothing may pin a hostname. The two agents leave `OBSERVABILITY`. The
  new test pins the node template and the `tasks.` targets; the scrape-host test learns that
  `tasks.<svc>` names the same service.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — rule 1 gains the per-host-agent exception, "5
  observability services" becomes 3, the S8 paragraph stops saying the agents pin, and S8b records
  what a `configs:` change costs on an already-running stack.

## Measured

Cost of running both agents on every node — measured with `docker stats --no-stream` on the running
task, this being the only node available for the measurement:

```text
prod_node-exporter  0.00%  9.906MiB / 512MiB     # trivial
prod_cadvisor       2.58%  99.65MiB / 1GiB       # the one with real cost; re-measure on the VMs
```

The mechanisms, each probed on a throwaway service before being written into the stack:

```text
$ docker service create --hostname '{{.Node.Hostname}}' --name hostname-probe ... python:3.12-alpine sleep 60
$ docker inspect <container> --format '{{.Config.Hostname}}'   -> saurabh-MS-7D90
$ docker exec <container> hostname                             -> saurabh-MS-7D90   # UTS namespace
$ docker run --rm --network container:<collector> python:3.12-alpine python3 -c "...gethostbyname_ex..."
tasks.node-exporter -> ['10.0.1.18']        # the task  (rehearsal)
node-exporter       -> ['10.0.1.17']        # the VIP   (rehearsal)
```

Then, after a **fresh create** of the rehearsal stack (a changed `configs:` entry cannot be applied
to a running stack, see Limitation):

```text
$ docker inspect prod_node-exporter task -> Config.Hostname=saurabh-MS-7D90
$ docker inspect prod_cadvisor     task -> Config.Hostname=saurabh-MS-7D90
$ docker run --rm --network container:<collector> python:3.12-alpine python3 -c "urlopen('http://'+gethostbyname('tasks.node-exporter')+':9100/metrics')"
node_uname_info{...nodename="saurabh-MS-7D90", machine="x86_64", release="6.8.0-110-generic"}
$ OpenObserve PromQL
up{instance="tasks.node-exporter:9100", job="infra-host"}         = 1
up{instance="tasks.cadvisor:8080",      job="infra-containers"}   = 1
```

So the template survives `docker stack deploy`, the collector reaches every task by the `tasks.`
form, and the node's own name is what ends up in the series.

## Limitation

**Host logs are still VM4-only, and this change does not touch that.** Metrics are now collected from
every node, but the collector still runs on VM4 with a read-only `/var/log` mount, so VM1–VM3 host
logs are not in the pane. Closing that means a per-node filelog agent — a separate change with its
own measurement (log volume, collector cost per node), not a constraint to delete.

**The old series stay in OpenObserve until retention expires.** After the change the same metric
arrives under two instance labels: the superseded `node-exporter:9100` with
`nodename="f77f64fd95c1"`, and the new `tasks.node-exporter:9100` with the VM's name. Dashboards and
alerts must filter on the new instance (or on a real `nodename`) or they will read a frozen copy of
the past.

**cAdvisor is the only component here with meaningful cost**, measured at 99.7 MiB / 2.58% CPU on
this laptop. That is a single measurement on one machine: re-measure it on a trading VM with
`docker stats --no-stream` before assuming it is free, and if it is not, the fallback is a lower
scrape resolution or pinning it to a subset of nodes — not silently accepting it.

**A changed `configs:` entry cannot be applied to a running stack.** Measured, and worth knowing
before any future config edit:

```text
$ docker stack deploy -c docker-stack.rehearsal.yml prod
failed to update config prod_otel-collector-config: Error response from daemon:
rpc error: code = InvalidArgument desc = only updates to Labels are allowed
```

Configs are immutable in Swarm. Applying a changed collector config therefore means
`docker stack rm` followed by `docker stack deploy` (which is what the rehearsal does), or giving the
config a new name. A plain redeploy is not enough, and the deploy reports a failure rather than
quietly keeping the old contents.

**Verified on one node.** That the agents run on every node is what `mode: global` means and what the
validator's `global-coverage` check now verifies against the real node labels at S8b; the four-VM
arrival of four sets of series has not been observed yet, because there are no VMs.
