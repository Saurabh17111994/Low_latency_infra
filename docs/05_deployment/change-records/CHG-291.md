## Why

The executor proved a day's snapshot by looking for `event_day=<day>` inside the manifest's key. Real
Iceberg names manifest lists `metadata/snap-<id>-….avro`, and every other artifact in this repository
scopes manifests by the table's `metadata/` prefix with no day component: `lake-guard.sh`
(`META_PREFIX=…/metadata/`), `tiering-smoke.sh` (`metadata/.*\.avro`) and `test_lake_guard.py`'s stated
TSV contract. Measured on a real-shaped listing with two `.avro` objects present, the count was 0 — a
fully tiered day reported "no iceberg manifests — snapshot not committed".

The day marker was not arbitrary. It was trying to answer "is this *today's* snapshot, or an old one?" —
there is a test named `staleManifestFromPriorDayDoesNotSatisfyNewDay`. So dropping it would have thrown
that property away, and replacing it with a fixed age window would have meant arguing about a window.

## What changed

A manifest now counts when it was written **after the day's newest data object**. That is the property
the day marker was reaching for, expressed in what the storage actually provides, and it is the rule
`lake-guard.sh` already applies (P6-439: "a manifest count alone passes on arbitrarily old files, so the
newest one must be recent"). It is also the honest question: the copy happened, then a snapshot was
committed.

The timestamps were already in the contract — `r2-list.sh` emits `key<TAB>size<TAB>LastModified` — and
the parser was discarding them. Comparing two stamps from the same listing needs no clock and no
timezone reasoning, so no window policy had to be invented. A manifest with a missing or unparseable
stamp is not evidence, and a day whose data carries no stamp cannot be ordered against a manifest at all:
all three fail closed.

## Evidence

`~/.p6v/evidence/c2-lake-20260921/` — the same throwaway TLS MinIO listing, now run through the parser
with the rule in place: `dataObjects=2 dataBytes=300 manifestFiles=2`, "offload() proceeds — a snapshot
was committed after the data". In that listing the data objects are stamped `…:40.385Z` and `…:40.392Z`
and the two manifests `…:40.407Z` and `…:40.415Z`, which is what a real commit looks like. The stale
case is pinned by unit test rather than by a second endpoint.

## Known limit

A later commit for a *different* day satisfies the rule as well: the listing proves that a snapshot was
committed after this day's data, not that this exact day is inside it. Proving which snapshot holds the
day needs the manifest's contents — `r2-query.sh`/DuckDB territory, and part of D1's restore work. The
canonical DuckDB count query for a day already exists in the lake runbook.
