## What landed

The broker's real per-instrument peak is **1 tick per 50 ms = 20 ticks/s**
(user-confirmed 2026-08-27), not the documented 30/s. The theoretical cap
ceiling is therefore **3,000 × 20 = 60,000 ticks/s**, and the acceptance gate
is **re-raised from 50k (DEC-036) to 60k sustained (DEC-045)**.

## Code changes

- `FixedScope.MAX_TICKS_PER_INSTRUMENT_PER_SEC` 30 → **20**
- `FixedScope.PEAK_TICKS_PER_SEC` 90_000 → **60_000**
- Mock `SyntheticWorkload` PEAK profile: 34/35 ms → **51–54 ms** (worst case
  ≤19.6/s, same ~2% margin the 34 ms mean gave the old 30/s cap)
- `PerfBaselineTest`: target 50k → **60k**, floor 48k → **57.6k** (96%),
  socket floor 47.5k → **57k** (95%)
- `PlatformConfigTest` / `SyntheticWorkloadTest` assertions 30 → 20

## Doc reconciliation

Every forward-looking doc row referencing 30 ticks/s → 20, 90,000 → 60,000
(peak), and the 50k gate → 60k gate (DEC-045). The 50,000 ticks/s **average
baseline profile** (≈16.7/instrument) is unchanged — it is the normal load
shape, not the gate. Historical records (DEC-036, CHG-001, P7 evidence,
`PERF-*90000*` retired IDs) stay locked as written, annotated with the
DEC-045 supersede.

## Evidence

- 2026-08-27 user confirmation of the 20/s per-instrument broker peak
- `FixedScope` + tests build green; ingestion suite 285/0; mock_arrow 3/0
- The 60k gate sits at the measured tablet ceiling (~59k, 2026-08-13) with
  zero margin — sustained 60k acceptance requires a live full-envelope bench
  (Test D / multi-writer may be required). Risk is documented in DEC-045,
  not hidden.
