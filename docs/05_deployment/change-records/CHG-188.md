# CHG-188 — purging a partitioned table no longer churns its identity (wave 36)

- **Status:** recorded — fixes a pre-existing purge defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** found while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`. Not one of the wave's 18
  findings — the live run reached the ingestion append step only after CHG-185,
  CHG-186 and CHG-187 cleared the three failures in front of it.

## What happened

`pipeline_purge_table` cleared a table by dropping and recreating it:

```java
admin.dropTable(tp, false).get(60, TimeUnit.SECONDS);
admin.createTable(tp, DdlText.toDescriptor(parsed), false).get(60, TimeUnit.SECONDS);
```

For a **partitioned** table this leaves the table unusable for about a minute.
The recreate hands the table a new id and the tablet must re-establish
leadership for that table's buckets; while that settles, a client connecting
cold fails every append:

```text
IllegalArgumentException: table path not found for tableId <old> in cluster
  -> FlussRuntimeException: Failed to update metadata
  -> Failed to send record to table default.raw_table_1(p=20260917). Writer state: running
```

`RawTickWriter` classifies a stale handle as FATAL and `signal_ingestion`'s
FAIL-FAST path correctly refuses to continue, so ingestion exits 1 and
`pipeline_start_ingestion` times out waiting for a readiness marker that can
never appear.

**Measured on the live cluster**, one purge at a time on a quiet node so that
prior test traffic could not distort the result:

| purge method | append immediately after |
| --- | --- |
| drop + recreate | fails at t+0s, t+5s … t+50s; first success **t+55s** (reproduced twice, 3/3 fails at t+3s) |
| drop every partition | **succeeds at t+0s**, 6/6 back-to-back |

Only a partitioned table shows the window. Among the tables the harnesses purge,
only `raw_table_1` is partitioned (`code/01_platform/02_sql/ddl/02_raw_table_1.sql`,
`PARTITIONED BY (event_day)`) — which is why the defect surfaced there and
nowhere else. An early probe run of this investigation reported the opposite
result; it was measuring against a cluster still draining several test purges of
its own, and the measurement was repeated on a quiesced cluster before this
record was filed.

Historical runs appear to contradict the table above (Sep-3/4/5 runs recorded
`fatalAppend=0`). Those runs purged and then spent ~9s on bring-up before
ingestion connected, and the window is a race it is possible to lose rather than
one that always bites. It is also self-masking: the run-#3 attempt never reached
the append, because the manifest defect that CHG-186 fixes stopped it earlier —
CHG-186 *unmasked* this defect rather than causing it.

## The fix

`TablePurge` now clears a partitioned table by dropping its partitions and
keeping the table's identity:

```java
if (live != null && live.isPartitioned() && schemaCurrent) {
    for (PartitionInfo part : admin.listPartitionInfos(tp).get(30, TimeUnit.SECONDS)) {
        admin.dropPartition(tp, part.getPartitionSpec(), false).get(60, TimeUnit.SECONDS);
    }
    System.out.println("PURGED " + tp + " (partitions=" + dropped + ")");
} else {
    // unchanged drop + recreate
}
```

The table is emptied just as completely — dropping a partition takes its log
segments with it — and the DDL sets `table.auto-partition.enabled=true`, so the
next write re-creates the current day's partition (verified live: after purging
both partitions, an append re-created `20260917` and succeeded).

**The current day's partition is then re-created at purge time**, and that
step is load-bearing rather than tidiness. Fluss's auto-partitioning does not
create a partition on the write that needs it — it runs on the coordinator's
periodic sweep — so a purged table left with zero partitions answers the next
append with:

```text
PartitionNotExistException: Table partition 'default.raw_table_1(p=20260917)' does not exist.
```

This was found the hard way: the first version of this fix dropped the
partitions and relied on auto-partitioning to bring the day back. A live
acceptance run then failed with exactly that exception. Measured afterwards with
the harness's own timing (purge, wait ~50s of bring-up, append): without the
pre-create the append failed and the partition was *still* absent afterwards;
with the current IST day pre-created first, the same append succeeded. The day
is named in the DDL's own `table.auto-partition.time-zone`, so it matches the
partitions the coordinator would create, and a repeat purge in the same day
(partition already there) is not an error.

**The drop + recreate path stays**Rejected alternatives: *waiting for the window to clear* (fragile, and it pays a
minute per purge, per harness), and *retrying the append in the ingestion client*
(would weaken the FATAL classification that deliberately refuses to retry a
stale handle).

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*DDL/schema* and *Deployment topology*. This changes how a schema's data is
cleared and it is a shared bring-up library change affecting every harness that
sources `pipeline-lib.sh`. The `measurement-gate` axis also applies: a purge that
leaves the table unwritable turns a measurement run into a failed run.

## Verification

* Compile check: the extracted `TablePurge.java` compiles against the ingestion
  classpath (`javac` clean).
* Live, on the reverted (pre-fix) helper on a quiet cluster: one drop + recreate,
  then a cold-client append 3s later failed 3/3 with the production signature
  ("Failed to send record to table … Failed to update metadata"), and a single
  purge left appends failing through t+50s with the first success at t+55s.
* An interim version of this fix (drop partitions, no pre-create) was run through the
  full acceptance harness and FAILED live at the append with
  `PartitionNotExistException: Table partition 'default.raw_table_1(p=20260917)'
  does not exist` — recorded here because it is the evidence that the
  pre-create step is required, not optional.
* Live, with the final fix: partitioned table + matching schema -> `PURGED
  default.raw_table_1 (partitions=2, day=20260917)`, 1 partition present
  immediately after, and an append after the harness's ~50s bring-up gap
  succeeded. A second purge in the same day also succeeded (the pre-create is
  idempotent), and six consecutive drop-all-partitions purges each appended
  successfully at t+0s.
* Live, schema-drift guard: a DDL with one extra column took the drop + recreate
  branch (`PURGED default.raw_table_1`, no partition count) and the extra column
  was present on the recreated table — the schema change still applies.
* Live, non-partitioned table: `PURGED default.Signal_Candidates` via drop +
  recreate, unchanged.
* `test_pipeline_lib_hardening.py`: 46 passed. The new test fails against the
  pre-fix library, so it pins the fix rather than the implementation's spelling.
* `python3 code/01_platform/04_scripts/change_control_check.py` exits 0.
