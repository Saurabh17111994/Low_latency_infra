# CHG-138 — The config surface stops carrying declarations nothing reads

- **Status:** recorded — five findings fixed, two reframed as documentation, one closed as verified-clean, two declarations deleted
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 1 ("The rest of the config surface"):
  P6-270, P6-271, P6-659, P6-662, P6-663, P6-664, P6-665, P6-851, P6-852, P6-853

## What happened

All eleven findings were re-verified against the code before anything was edited. Nine were real;
two were not what the audit said:

* **P6-270/P6-662** — `FixedScope.BASELINE_TICKS_PER_SEC` was still `50_000L` after DEC-045
  (2026-08-27) re-raised the sustained gate to 60,000 and cut the per-instrument cap 30 → 20. The
  decision record lists this exact edit, and `PerfBaselineTest`'s floors already used the DEC-045
  numbers, but the constant was never changed and **nothing read it**, so no test could notice.
  The stale javadoc around `PEAK_TICKS_PER_SEC` still cited DEC-036's 50k gate.
* **P6-851** — `ConfigKeys.APPEND_TIMEOUT` was never read. The only occurrence of the name was the
  `"APPEND_TIMEOUT"` *label* in `IngestionConfig.toMap()`; the live input is
  `APPEND_TIMEOUT_SECONDS`. This is exactly the shape the wave-0 guard fix cannot catch: a string
  literal that looks like a read.
* **P6-664** — `INGESTION_MAX_BATCH_RECORDS`/`_WAIT_MS` were declared in `PlatformConfig` (and
  pinned by the mandatory-order gate) while `IngestionConfig` repeated the same values as literals.
  The live values were already correct; there were simply two statements of one policy.
* **P6-665** — `MAX_ACTIVE_CANDIDATES_PER_INSTRUMENT` had no reader after CHG-005 removed the
  ranking/reservation arm (01-foundation.md row 4 is struck). Only the repo gate's needle kept it
  alive — a check pinning a declaration instead of a behaviour.
* **P6-852** — `PlatformConfig.maxPendingAppendBytes(long)` implemented
  `min(201326592, floor(limit * 0.10))` with an R-199 fail-fast, and **had no production caller**:
  the shipped byte ceiling is `IngestionConfig`'s flat, validated default
  (`MAX_PENDING_BYTES = 201_326_592`, floor 1 MiB, env-overridable). The live path never had the
  non-positive-limit hazard R-199 describes.
* **P6-854** — `SecretGuard.assertNoSecrets(null)` threw `NullPointerException` although its
  javadoc promised `IllegalStateException`.
* **P6-271** — real mechanism, wrong remedy: the guard reads `SECRETS_VIA_ENV_FILE` from the same
  env map it is guarding with, and the javadoc claimed host scripts do not set it. Four harnesses
  (`loadtest-run.sh`, `pipeline-lib.sh`, `tiering-smoke.sh`, `stage-soak-e2e.sh`) and
  `docker-compose.yml` do set it, in the same block as their fake secrets. Splitting the marker
  into an explicit boolean parameter moves the same in-band value one call frame; it adds no
  security, because anything that can set the process environment owns the process either way.
* **P6-659** — premise stale. Ingestion already prefers `DEPLOYMENT_ENV` and falls back to
  `DEPLOY_ENV` (P1-077), log4j2 resolves the same order, and compute *requires* `DEPLOYMENT_ENV`
  loudly. The described silent divergence cannot happen.
* **P6-853** — no defect: `Long` vs primitive `long` unboxes before the numeric comparison.

## What changed

* `FixedScope.BASELINE_TICKS_PER_SEC` → `60_000L`, javadoc rewritten to cite DEC-045 as the
  authority and the `PEAK_TICKS_PER_SEC` comment now says the ceiling and the generator's stress
  bound coincide today but are not derived from each other (P6-663: a comment, not the proposed
  equality assert, which would couple two independent quantities).
* New `FixedScopeTest` pins the DEC-045 numbers (60k gate, 20/instrument cap, derived ceiling)
  and the R-263 delegation from `PlatformConfig`, so the drift cannot recur silently.
* `SecretGuard` fails closed on a null map with `IllegalStateException`, and its class comment now
  states what the marker is (a deployment declaration) and is not (a trust boundary).
* `ConfigKeys.APPEND_TIMEOUT` deleted; `IngestionConfig.toMap()` reports
  `APPEND_TIMEOUT_SECONDS`; `DEPLOYMENT_ENV`/`DEPLOY_ENV` document the alias precedence.
* `IngestionConfig` reads the two batch defaults from `PlatformConfig`.
* `PlatformConfig.MAX_ACTIVE_CANDIDATES_PER_INSTRUMENT` and `maxPendingAppendBytes(long)` deleted,
  replaced by a note naming what enforces each rule now (the KV primary key; the validated flat
  default). `PlatformConfigTest` was removed with them — its R-263 pin moved into `FixedScopeTest`,
  its two R-199 tests tested only the deleted helper.
* `implementation_gate.py` seq 4 keeps its slot but pins
  `PRIMARY KEY (instrument_token)` in `code/01_platform/02_sql/ddl/23_signal_candidates_current.sql`
  instead of a declaration nothing read.
* Doc rows reconciled: the four candidate-bound rows name the KV enforcer, the test-truth line in
  `01-foundation.md` moves 644 → 664 with the delta recorded, and its checklist row 54 loses
  DEC-036's 50k/30-per-instrument numbers.

## What this does and does not mean

* No runtime behaviour changes. Both deletions removed code with zero production callers, and the
  batch defaults are numerically identical.
* `P6-271` is **not** claimed as fixed in the security sense: the marker remains in-band by
  construction. Hardening it onto an out-of-band channel (e.g. `/.dockerenv`) was rejected because
  it would reject the local harnesses' fake secrets too.
* `P6-853` is closed with no code change — the audit itself proposed none.

## Rollback

`git revert` of the four commits. Nothing is enabled, written or migrated: every change is a
declaration, a default or a comment. The one ordering constraint is the CHG-112 annotation, which
names the commit that deleted `PlatformConfigTest.java` — reverting that commit before the
annotation would make the annotation unverifiable.
