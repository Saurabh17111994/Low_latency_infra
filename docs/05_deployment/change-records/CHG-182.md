## What was wrong

Four independent defects in the same four services. Each is fatal on its own.
CHG-181 recorded the first and named the other three without fixing them.

| # | Defect | What the operator saw |
| --- | --- | --- |
| 1 | No `command:` on any of the four services | The image's `Cmd` is `help`, so each container printed usage and **exited 0**. Swarm reported the task as started while no server ran. |
| 2 | The probe was `CMD-SHELL` with `/dev/tcp` | `/bin/sh` in this image is **dash**, which has no `/dev/tcp`, so the probe failed for a healthy server. A second defect hid underneath: Fluss binds the container **hostname**, not loopback, so the planned `127.0.0.1:<port>` target was refused even under bash — measured on a live tablet, `rc=1` for loopback against `rc=0` for `$HOSTNAME:9124`. |
| 3 | The R2 credentials arrived as Swarm **files** that nothing read | `/run/secrets/aws_access_key_id` was mounted while `FLUSS_PROPERTIES` held `${env.AWS_ACCESS_KEY_ID}`. The stock image has no `*_FILE` handling, so the placeholders never expanded and R2 was unreachable. |
| 4 | `remote.data.dir` was `/tmp/fluss/remote-data` on a driver-less, unpinned volume | Fluss tiers by default (`remote.log.task-interval-duration` is 1 minute). Tiered bytes landed on one node's volume; a reader on another node found nothing — and **does not error**, it under-counts. |

Defects 3 and 4 are a pair: credentials without a shared location still lose the
data, and a shared location without credentials cannot write. Both had to move.

## What changed

`docker-stack.yml`:

- `command: ["coordinatorServer"]` on `fluss-coordinator`;
  `command: ["tabletServer"]` on `fluss-tablet-1/2/3`.
- Each probe is now
  `["CMD","bash","-c","(echo > /dev/tcp/$$HOSTNAME/<port> || echo > /dev/tcp/127.0.0.1/<port>) >/dev/null 2>&1"]`.
  `$$HOSTNAME` because compose interpolation rejects a bare `$(...)`; the render
  delivers `$HOSTNAME`. The same interpreter defect was fixed on
  `flink-jobmanager:8081` (Flink also listens on loopback, so the fallback
  covers it).
- New `configs:` entry `fluss-r2-secrets-bridge` sourced from
  `code/01_platform/01_docker/fluss-r2-secrets-from-file.sh`; all four services
  run `entrypoint: ["/bin/sh","/opt/fluss/bin/r2-secrets-from-file.sh"]` and
  name `AWS_ACCESS_KEY_ID_FILE` / `AWS_SECRET_ACCESS_KEY_FILE`. Credentials
  never enter `environment:`; `/run/secrets` stays the only source.
- `remote.data.dir: s3://${R2_BUCKET}/remote-data` plus the six `s3.*` keys on
  all four services; the `fluss-remote-data` volume and its four mounts are
  deleted.

`stack_selfcheck.sh`: `R2_BUCKET` joins `required_vars` (13 now). The stack's
own `:?` guard does **not** fire inside the `FLUSS_PROPERTIES` block scalar —
verified: an unset `R2_BUCKET` renders `s3:///remote-data` with rc=0, the same
behaviour as the dev twin. The fail-closed behaviour therefore lives in the
`DEPLOY=1` gate, which refuses an unset or empty `R2_BUCKET` and names it before
any deploy.

**On the healthcheck scope.** The openobserve probe was deleted rather than
repaired: that image is a static binary with no shell, `curl` or `wget`
(`exit=-1`, `exec: "/bin/sh": stat /bin/sh: no such file or directory`, container
`unhealthy`), so no probe can run there at all. It carries an `x-healthcheck`
marker and joins the shell-less allowlist alongside `otel-collector` — a
documented exception, not a silent drop.

Docker network carried the production shape: the bridge entrypoint, the real
`s3.*` keys, `remote.data.dir` on the bucket, its own ZooKeeper chroot
(`/trial-chroot`) and a separate `tablet-server.id`. An oversized row batch was
written through the Flink SQL client:

- `Starting Coordinator Server` and `Starting Tablet Server`; the tablet
  registered (`Registered tablet server 99 at path /tabletservers/ids/99`).
- `Copied 00000000000000000000.log of table trialdb4.readtest bucket
  TableBucket{tableId=3, bucket=0} to remote storage as remote log segment:
  51fba597-ab67-4ee3-9599-9fdf3c01a67f.` — 142 such copies stand in the
  surviving tablet log, and the bucket holds the objects they name.
- The tiering task then **committed the manifest**. ZooKeeper
  `.../tables/2/buckets/0/remote_logs` held

**Not verified — with the specific reason:**

- **No `docker stack deploy`.** This host is a Swarm worker
  (`ControlAvailable=false`, `NodeID=""`), so `make stack-selfcheck` exits 1 at
  "cannot determine this node's swarm NodeID" **before** reaching the stack. The
  equivalent check available here is the manual `docker stack config` above; it
  was run and passed.
- **A read served from R2 — closed 2026-09-16, after this record was first
  written.** The write path, the manifest commit and the client-side read path
  are all now proven. The earlier version of this bullet said no `SELECT` row had
  been shown to come from the bucket; the trial below closes that gap, and the
  two experiments it names are kept because both are still true and both are
  traps. The client-side downloader is real, and the read that reaches the
  bucket is an ordinary default-settings `SELECT`.

  **How it was closed.** The first attempts failed for one reason: the trial
  configured `table.log.tiered.local-segments` as `0`, and `LogTablet` rejects
  that (`log segments to retain in local must be greater than 0`), so **cleanup
  never ran** and every row stayed on local disk. With the value set to `1` and a
  1,020,000-row write, the tablet copied 17 closed segments to R2, committed the
  manifest, and then actually deleted its local copies — the local directory held
  one segment (base offset **981794**, confirmed by reading the number out of the
  segment header) while the manifest covered offsets **0–981794**. Offsets below
  981794 existed *only* in the bucket.

  **What the reader did.** A Flink SQL `SELECT` against the trial table returned
  the row `id = 500000, v = '50000042042'`. That value decodes: the write's
  formula was `id || (a+1)(b+3)(c+7)(d+9)(e+11)(f+13)`, and for the digits of
  `000500` the product is `1*3*7*14*11*13 = 42042`, which is exactly what the
  returned `v` carries. The row is therefore a write3 row, and the write3 rows
  begin at log offset 20000. **The row's exact offset is bounded between 20005
  and 520000**, not pinned: `id = 500000` is the digits `(0,0,0,5,0,0)`, so its
  position depends on the cross-join's enumeration order — the single non-zero
  digit carries weight 1e5 in the id but 1e2 in the output order, and across all
  720 digit orderings the position lands somewhere in that range. (An earlier
  version of this bullet stated offset 520000 as a fact and named the segment
  covering it. That number is the **upper bound** of the range, not a measured
  position — corrected here rather than by amending the commit.) The conclusion
  does not depend on which position it is: **every candidate offset lies below
  the local base of 981794**, so the row's bytes were in the bucket and nowhere
  else. The task manager log shows the client downloading **17 distinct remote
  segments**, every one of them present in the R2 manifest and every one
  starting below 981794
  (`Successfully downloaded remote log segment file <uuid>_<offset>.log`), on
  every read including reads with no startup option set. This is a client-to-R2
  read, not a tablet-to-R2 read.

  Two controls worth naming, because both nearly produced a false negative:
  passing the S3 settings on the *job manager* changed nothing — the read runs on
  the task manager, which already carries the committed `core-site.xml` mount and
  the R2 environment, so a "control" that withholds them from the job manager
  proves nothing. And `scan.startup.mode` is not the lever here: a dynamic
  `/*+ OPTIONS(...) */` hint is silently ignored (a future timestamp still
  returned rows), and while `ALTER TABLE ... SET ('scan.startup.mode'='earliest')`
  does persist — it is visible in `SHOW CREATE TABLE` — reads returned the same
  rows before and after, and after `RESET` as well. The read that reaches
  the bucket needs no startup option at all.

  **Still true, and still worth keeping (the two experiments the earlier bullet
  named):**
  (a) a tablet started against a **fresh, empty** local data directory did
  **not** re-read from R2 — ZooKeeper still held the manifest path and
  `remote_log_end_offset: 9923850`, but the tiering task logged
  `Local end offset should be greater than remote end offset, but the offset of
  bucket ... is local: 0 and remote: 9923850. Reset remote end offset to local
  end offset.` and `SELECT COUNT(*)` then returned **0**. Note what this does and
  does not model: production gives each tablet its own named data volume
  (`fluss-tablet-data-1/2/3:/tmp/fluss/data`), so an ordinary restart or a
  reschedule onto another node keeps its local log. This experiment models a
  **lost volume on a node that comes back** — the case the new tier directory
  does *not* rescue either, since the bytes it needs are the ones that used to be
  there. In this version R2 is not a recovery source for a tablet that lost its
  local log, and the change does not claim it is;
  (b) `fluss-flink-2.2-0.9.1-incubating.jar` ships a client-side remote-read
  path (`RemoteLogDownloader`, `remote_log_fetch_info`, a remote-log prefetch
  knob) — this is the path the read above exercised.

- **What Swarm does with an unhealthy task** stays unverified; it needs a manager
  node. The fix stands on the false-signal argument alone.
- **Lake tiering (`datalake.*`)** is unwired in production: the keys are present
  but no plugin jars are mounted, unlike dev, which bind-mounts `fluss-fs-s3`,
  `fluss-fs-hdfs` and `fluss-fs-hadoop-shaded` into `plugins/iceberg/`. Carried
  as a residual risk in `docs/08_implementation/09-production-swarm.md`.
- **The 4-VM Swarm** was not exercised. This is offline plus single-host
  container evidence, consistent with the M2/M3 split.

## A measurement trap worth keeping

The first trial attempt looked like it disproved tiering: the tablet logged
`Created a new remote log task`, a restart closed nothing, and the bucket
listing showed **0 keys**. Concluding "tiering does not work" would have been
wrong. Tiering copies only **closed** segments, the default
`log.segment.file-size` is large, and three small rows never rolled the active
segment — so nothing was eligible to copy. Repeating with an explicit small
`log.segment.file-size` and a large write produced the copies above. *A 0-key
listing after a small write says nothing about tiering.*

A second trap sits next to it. Wiping a tablet's local data directory and
restarting it looks like a clean way to prove reads come from R2. It is not: the
tablet reset its remote end offset to 0 and `SELECT COUNT(*)` returned 0 while
the tiered objects sat intact in the bucket. That result shows the *restore*
path behaving as designed in this version, not a broken tiering write — reading
it as "R2 has no data" would invert the truth, since the same prefix held 833
verified objects at the time. (That trap is about a tablet **losing** its local
log. The read path that *is* served from the bucket is the client-side
`RemoteLogDownloader`, proven above; the two are different paths.)

A third trap cost the most time on the read proof, and it is the one to remember:
`table.log.tiered.local-segments` is validated as **greater than 0**. Setting it
to `0` — the obvious way to say "keep nothing local" — makes `LogTablet` throw
`log segments to retain in local must be greater than 0`, and the trial's config
never applied at all. Tiering still copied segments and still committed the
manifest, so the bucket filled correctly and everything looked like it worked;
what never happened was the **delete**, because cleanup had no valid retention
setting to act on. Every row therefore stayed readable from local disk, and each
of the first several "proof" reads returned tail rows for a reason that had
nothing to do with the reader. `1` is the value that expresses the intent.
