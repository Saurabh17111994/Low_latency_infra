# CHG-137 — The two Java guards stop answering "fine" when they cannot tell

- **Status:** recorded — both classes are fail-loud on a fault and quiet on a healthy config
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 0 ("The two Java guards (both CRITICAL)"):
  P6-025, P6-026, P6-264, P6-265, P6-266, P6-267, P6-268, P6-269, P6-656, P6-657, P6-658, P6-660, P6-661

## What happened

Both guards were shaped like gates but could not fail:

* `ConfigGuard.assertAllKeysRead()` scans every `.java` file under `code/` for each declared key —
  including `ConfigKeys.java`, which declares them. Every key therefore matched its own declaration
  and the guard passed unconditionally (P6-025). Reachability was confirmed before the fix: 613
  `.java` files against the `.limit(2000)` cap, so the declarations file is always inside the
  scanned window. The inventory happens to be honest today (all 124 keys are read outside the
  declaration file), which is exactly why the defect was invisible.
* The same scan treated a key named in javadoc or a comment as a read (P6-657), followed the
  process working directory instead of the code it was inspecting (P6-658), re-walked the corpus
  once per key, and reported "verified" when no source tree existed at all (P6-264) or when the
  scan threw an `IOException` (P6-265) — the container case, where the jar is mounted without
  sources, so the guard silently did nothing in the environment that ships misconfiguration.
* `ContainerMemoryGuard` read the cgroup v1 memory limit, whose "unbounded" spelling is a huge
  near-`Long.MAX_VALUE` sentinel rather than the v2 string `max`. Treated as a real limit, it made
  `utilizedPercent` ≈ 0 — and that value feeds `IngestionService`'s scheduled memory monitor and
  `JvmHeapReadinessGate`, so on a cgroup v1 host the readiness block could never trigger and a
  mis-sized JVM would be OOM-killed instead of gracefully taken out of rotation (P6-026).
* The percent arithmetic overflowed for large limits (`limit * pct` → negative budget, P6-268;
  `used * 100` → an alert threshold that is never reached, P6-660), a corrupt cgroup value was
  reported as "unbounded" (P6-269), the heap and reserve knobs were not required to sum to 100
  (P6-267), and the violation message printed the *allowed minimum* reserve instead of the one
  actually left (P6-661).

## What changed

**`code/common/src/main/java/com/trading/common/config/ConfigGuard.java`** — the scan is now one
pass and honest about its own coverage:

```text
ConfigKeys.java          excluded from the corpus — a declaration is not a read (P6-025)
comments                 block comments and whole-line // stripped before matching (P6-657)
source root              -Dconfigguard.sources, else the class code-source anchor walked up to
                         code/, else the CWD — never the CWD first (P6-658)
corpus                   read once for all keys; the 2000-file cap is gone (P6-266)
inventory                static final String constants only; null/blank skipped (P6-656)
no source tree           loud stderr warning naming the search path, verification SKIPPED (P6-264)
unreadable tree          IllegalStateException — a reachable tree that cannot be read is a fault,
                         not a licence to skip (P6-265)
```

Fail-open is kept for the packaged case on purpose: the compute image ships the job jar with no
source tree, so failing closed there would refuse to start a deployment that cannot be checked
rather than the configuration that is wrong. The skip is now printed on every affected start and
the javadoc no longer claims a guarantee the guard cannot make.

**`code/common/src/main/java/com/trading/common/config/ContainerMemoryGuard.java`** — the limit is
read through one place that knows what "unbounded" looks like in both cgroup spellings, and the
arithmetic is overflow-safe:

```text
limitFromRaw              >= 1<<60, "max", <= 0 or absent  -> NO_LIMIT  (P6-026)
usedFromRaw / readFirstLine  absent -> null/-1; present but corrupt or unreadable -> throw (P6-269)
percentOf / ratioPercent  floor arithmetic that cannot overflow; BigInteger only where the
                          product would (P6-268, P6-660)
assertPercentagesComplementary  heap% + reserve% must be 100 where the contract is asserted (P6-267)
contractViolationMessage  reports the reserve actually left (limit - currentMaxHeap) (P6-661)
```

`percentOf` and `ratioPercent` are proven equal to exact `BigInteger` arithmetic over the range the
guard can see (a property test over realistic limits and all percent values), so the callers —
`IngestionService.startMemoryMonitor` (armed at `IngestionService.java:589`) and
`JvmHeapReadinessGate.observe` — need no change and no behaviour of theirs changes.

## What this does and does not mean

Compatibility is `COMPATIBLE`: no signature changed, and every behaviour that changes does so only
in a state the old code answered incorrectly — a cgroup reporting unbounded, a corrupt cgroup file,
a source tree that cannot be read, or a knob pair that cannot both hold.

It means both guards can now fail. It does not mean they are complete:

* `PlatformConfig.validateStartup()` — which calls `assertContainerMemoryContract`, `maxHeapBudget`
  and the violation message — has no caller in the repository, so the contract half of
  `ContainerMemoryGuard` is still unenforced at startup; only the ingestion monitor and readiness
  gate use this class live.
* The cgroup v1 sentinel path is dormant on this host (kernel 6.8, Docker "Cgroup Version: 2"); it
  is a documented fallback (`docs/08_implementation/11-testing-and-release.md`), not dead code.
* `ConfigGuard` still matches a quoted literal anywhere outside comments. Requiring a specific read
  expression would have to enumerate every helper (`getenv`, `getProperty`, `envLong`, …) and would
  start failing on real reads — the false-positive direction that refuses a healthy start.

## Rollback

`git revert` of the two commits. Nothing is enabled, written or migrated by this change: the guards
read the environment and the source tree and nothing else.
