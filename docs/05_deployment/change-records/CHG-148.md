# CHG-148 — The audit walker and the hash-chain verifier tell the truth about what they checked

- **Status:** recorded — all nine wave-11 findings fixed plus the P6-654 remainder deferred from wave 5
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 11 ("r2 audit walk and legal hold"):
  P6-307, P6-308, P6-709, P6-710 (audit_r2.py) and P6-499, P6-500, P6-769, P6-770, P6-771
  (r2_legal_hold_check.py), plus **P6-654's second half** (AuditHashChain.java, deferred from
  wave 5 because the Java rule and its Python port had to change together — recorded in CHG-142)

## What happened

Both files exist to produce evidence a human will trust, so the defects that matter are the ones
where a *claim* was stronger than the check behind it.

**The legal-hold verifier could not see most of the objects it was verifying.**
`list_objects` read keys by iterating the root's children and matching a tag ending in `Key`. R2's
ListObjectsV2 (like S3's) nests `<Key>` inside `<Contents>`, and R2 replies with no namespace, so
that expression matched *nothing*: on a populated prefix the checker raised "no .manifest objects
under prefix … nothing to spot-check" and recorded the prefix as empty. Found while writing
the pagination test for P6-499 — the listing had to be fixed first for the finding to be testable at
all. Tag matching is now depth- and namespace-agnostic (`_tags`).

**A truncated listing was reported as a complete one (`P6-499`).** `max-keys=1000` with no
continuation handling meant everything past the first page was dropped — including, by design of the
sample, the newest manifests. The listing now follows `NextContinuationToken` until `IsTruncated` is
false, and *refuses* to continue when a page does not say whether it is complete or is truncated
without a usable token (the same reasoning as `r2-list.sh` in wave 10): a verifier that silently
omits objects is worse than one that stops. There is a 1000-page cap behind it.

**`keys[-sample:]` sampled one table (`P6-771`).** Keys are `<table>/<YYYY-MM-DD>.manifest`, so
lexicographic order is dominated by the table name: with several audit tables under the prefix the
last keys are the lexicographically-last table's newest manifests and the newest manifests of every
other table were never checked. The sample now takes the newest manifests of *every* table
(`sample // n_tables` each, at least one) and links them in `(date, table)` order. That order is an
assumption about the writer shared by both sides — it is not recorded in any object — so a
multi-table sample carries a `sample_order_note` and the evidence `limitations` says a root mismatch
there can also mean a different order rather than tampering. No new verdict state was invented.

**Same-day manifests were called a broken chain (`P6-654`, second half).** The object contract is
one manifest per table per day, so a day legitimately holds several links, and the rule
`compareTo(...) >= 0` — written to make lexicographic date order safe — rejected exactly those real
chains. Both the Java `AuditHashChain.verifyChain` and its Python port now require dates to be
non-decreasing (`> 0`) rather than strictly increasing, and the duplicate-event check still runs
afterwards, so a chain cannot silently accept a re-linked manifest. This closes the item left open in
CHG-142 and unblocks the `AuditHashChain.java` line that has been 🟨 6/7 since wave 5.

**Each sampled manifest was downloaded twice (`P6-500`).** Once to hash it for the evidence and
again to build the chain text, which doubles egress and leaves a window where the hashed bytes and
the verified bytes are different reads. Each object is now fetched once, hashed and decoded from the
same body. The function also returned an `(evidence, objects)` tuple whose second element the only
caller ignored; it returns the evidence record alone.

**The probe's cleanup claim was a constant (`P6-307`).** `checks["probe_cleanup"] = "PASS"` was
hardcoded right after a broad `except R2Error`, so a failed `delete_object` — the failure that
leaves an object behind — was attested as a clean round-trip. Cleanup is now always attempted (it
moved out of the same `try`) and the claim reflects the outcome: `PASS`, or `FAIL` with a note naming
the key, and `NoSuchKey` counts as clean because nothing is left behind.

**Two of the five config keys were the only ones the environment could override (`P6-308`).** The
documented contract says real environment variables win over the file, but the overlay filtered
`os.environ` to `REQUIRED_KEYS`, so `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` exported in the
shell were ignored: `validate` recorded `bucket_lock=NOT_CHECKED` and `provision --set-lock` refused
with "missing credentials" while both were set. One `merge_env` helper now merges the file under the
environment for every key, and the legal-hold checker uses it too — its own `_env_or_file` had the
opposite precedence (file over environment), which is the same defect written the other way round.

**A network failure aborted the audit (`P6-709`), and a signed header was never sent (`P6-710`).**
The Cloudflare lock helpers only caught `HTTPError`, so a DNS/TLS/connect/timeout failure escaped as
a traceback instead of being recorded as `ERROR` in the evidence; they now also convert `URLError`
and `TimeoutError` into `UnsupportedFeature`, which `validate` already records per check. And
`R2Client._request` merged `extra_headers` into the *signed* header set without ever adding them to
the request — a request signing headers the server never receives is a guaranteed
`SignatureDoesNotMatch`, in the one helper where that is hardest to debug. No caller passed it, so
the parameter is gone rather than half-wired.

**Dead code and unused imports (`P6-769`, `P6-770`).** `urllib.request` / `urllib.error` are no
longer imported by the legal-hold checker (all HTTP goes through `audit_r2`). The unreachable
`if int(value) != 0 and not lines` branch in `parse_manifest` is gone and replaced by the check it
pretended to be: `count` must be an integer, must be present, and must equal the number of `event=`
lines — a clearer message than the round-trip's "corrupt object" for the one field that was never
compared.

## Judgement calls (review these)

1. **P6-654 is fixed in Java and Python in one commit**, with the golden Java-parity constants in
   `test_11_r2_legal_hold.py` untouched: only the comparison operator and the two docstrings change,
   so the canonical format, the links and the root are unaffected. The Java test pins both sides —
   same-day different tables is `VALID`, going backwards is still `BROKEN_LINK`.
2. **The nested-`<Key>` fix is wider than P6-499's wording.** It is the same function and the same
   question ("did the listing see the objects?"), and without it the pagination fix would have been
   untestable and the checker would have reported a populated audit prefix as empty. Recorded here
   because it is a defect nobody had reported, found by the new test rather than by the audit.
3. **Equal dates are now `VALID`; the duplicate protection moved, it did not disappear.** Two links
   for the same day are legitimate (different tables). Re-linking an identical manifest repeats its
   event ids, which the `DUPLICATE_EVENT` check still catches.
4. **Per-table sampling can exceed `sample` GETs** when the prefix holds more tables than `sample`
   (each table gets at least one). Bounded by the table count, and the alternative — silently
   dropping tables again — is the defect.
5. **The within-day cross-table link order is `(date, table)`**, an assumption shared with the
   writer, stated in the module docstring, in `sample_order_note` and in the evidence `limitations`.
   I did not add an "UNVERIFIED-ORDER" verdict: a root mismatch is still `TAMPERED`, now with a note
   saying what else it could mean.
6. **A failed probe cleanup is reported, not escalated.** `_audit_probe/` is the scratch prefix this
   tool's own lifecycle rule expires (the audit prefix never is), so a leftover is a real state to
   record but not a reason to fail the whole validation record. The finding asked for a truthful
   claim, which is what `FAIL` + `probe_cleanup_note` now is.
7. **`merge_env` overlays every key, not a curated list.** That is the documented contract, it keeps
   the overlay in one place, and the merged dict is only read through named keys
   (`config_from`, `cloudflare_lock_config`), never dumped into evidence.
8. **The Python return shape changed** (`check_retrieval_and_chain` returns the evidence record, not
   `(record, objects)`). The only caller is in the same file and ignored the second element, but an
   out-of-repo importer doing `record, objects = …` would break — hence
   `COMPATIBLE_WITH_LIMITATION` rather than `COMPATIBLE`.
9. **Red runs use a `*_SOURCE` seam** (`AUDIT_R2_SOURCE`, `R2_LEGAL_HOLD_SOURCE`) that points the
   suite at a pre-fix copy; unset in production and unread unless the suite asks. It matches the
   `RAW_TABLE_ADMIN_SOURCE` seam from wave 9.
