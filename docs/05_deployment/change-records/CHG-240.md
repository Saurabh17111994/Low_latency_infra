## New guard module

`tests/test_compose_ladder_guards_wave50.py` (22 tests): AST detectors that (a) prove each flagged
shape is absent from the real modules and (b) prove the same detector fires when handed that shape,
so a reintroduction fails. It also drives the new helpers against synthetic fixtures — a third Arrow
carrier, a compose that pins `-Xmx`, a doc section with its number changed, a failing harness — and
checks the dead/duplicate-import rule across all six modules. Not wired into the per-layer Makefile
targets; it runs in the whole-tree sweep (gate step 3's `unittest discover` command).

## Deviations from the audit's fix text

1. **P6-601** — the audit suggested asserting `mem_limit` / `deploy.resources.limits.memory`. The
   compose declares **no** memory limits at all, so that remedy is unwritable. Verified real wiring:
   `ContainerMemoryGuard.maxHeapBudget()` (guard L115) takes the container limit and derives the
   budget from `PlatformConfig.JVM_HEAP_PERCENT_OF_CONTAINER_LIMIT` (guard L52), env-overridable.
   RES-001 therefore asserts the pin, the consumer, and that no live (non-comment) `-Xmx` /
   `MaxRAMPercentage` appears in the compose — the only way the 65% policy could be bypassed.
2. **P6-611** — "only bridge/ingestion may mention ARROW_*" is false as a text check and true as a
   config check. The rendered config hands ARROW_* to **eight** services because every service
   carries `env_file: secrets.env` (the false-fire L2's NETWORK-008 already documents and works
   around by checking the source). Source carriers today: `ingestion` (14 keys) and
   `execution-bridge` (5). The fix uses the same source-level walk, plus a positive assertion so the
   guard cannot pass by finding nothing.
3. **P6-600** — nothing executes the harness directly: all five call sites in the Makefile use
   `python3 <path>`. The exec bit is therefore not a contract (it happens to be set). Option A, per
   the wave owner's decision: importability + Makefile wiring replace it.
4. **P6-811** — "exactly two jobs" is not assertable from source: `safetyhalt/SafetyHaltJob.java` is
   a third main job class, documented at `docker-compose.yml:86` as the slot-scoped safety consumer.
   `JOB-001` therefore pins the spec sentence (`installs exactly Signal and Babysitter jobs`) plus
   those two classes, and the third class is recorded here as an observation.

## Observations recorded, not fixed

- `SafetyHaltJob` is a third `*Job.java` under `02_compute`; JOB-001's spec language covers only the
  two submitter jobs. Not a defect on today's evidence, but the docstring now says so.
- Rendering ARROW_* onto eight services is by design of the shared `env_file` (decision 2026-08-29 A),
  yet it is a broad credential hand-out. Out of scope for a test wave; worth a deliberate review.
- The compose declares no `mem_limit` for any service, so "memory limit enforced" (RES-001) is
  enforced by the guard's budget check, not by the runtime.

## Self-caught during the wave (five detector bugs, found by the new module)

`or_short_circuit` was too broad (it flagged legitimate `A or B` either-is-acceptable checks) and
only looked at argument 0, so it missed `assertIn(needle, x or y)`; the double-negative detector
looked for `UnaryOp(Not)` where `not in` is `ast.NotIn` inside the `Compare`; the ternary detector
flagged the legitimate `else ""` idiom; and one fixture assumed a token appeared elsewhere in the
doc when it did not. All five are fixed and each now has a mutant that fires.

## Follow-up (post-commit, found while verifying wave 51)

This record said the new guard module carries **30** tests. It carries **22**. The
number was written from a combined run (six wave-50 modules + the contract module +

`22 passed`; AST count → 22 test methods, all inside `TestCase` subclasses. The
whole-tree sweep after the wave-50 commit agrees: `Ran 1712 tests` = 1690 (wave-49
baseline) + 22. No test is missing or uncollected; only this record's number was wrong.

The functional claims in this record are unaffected — the 22 tests are the mutants
