# CHG-147 — The R2 tools report "no objects" only when the lake really is empty

- **Status:** recorded — all seventeen wave-10 findings verified and fixed in one commit
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 10 ("r2 listing and query"):
  P6-154, P6-155, P6-156, P6-157, P6-485, P6-486, P6-487, P6-488, P6-489, P6-765,
  P6-766, P6-767 (r2-list.sh) and P6-162, P6-163, P6-494, P6-495, P6-496 (r2-query.sh)

## What happened

`r2-list.sh` answers one question for the tiering smoke and the daily lake guard — "are there
objects under this prefix?" — and `r2-query.sh` answers the same question in rows. In both scripts
*every* defect had the same shape: a problem was reported as the empty answer instead of as a
problem. On a lake check that is the one wrong answer, because "no objects" is also the alarm
condition.

**A listing could not tell "empty" from "unreadable".** An HTTP 403, an unreachable host, a
truncated body and an S3 `<Error>` document returned with HTTP 200 all crashed with a python
traceback (`P6-155`, `P6-156`); `findall("s3:Contents", ns)` read a namespace-less page as an empty
bucket (`P6-488`); and a page whose `IsTruncated` was missing had no completion flag at all. Each of
those now ends the run with the S3 `Code`/`Message` or the parse error, and a page without
`IsTruncated` is refused rather than assumed complete. A truncated page with no usable
`NextContinuationToken` used to re-request page 1 forever (`P6-157`); it now fails on the first
page, with a 1000-page cap behind it.

**The config was read in a way that produced empty strings instead of errors.** `grep … | cut -d= -f2-`
kept quotes, `\r`, whitespace and inline comments, ignored `export`/spaced forms, and returned an
empty value for a missing key or file — so the failure surfaced as a `SignatureDoesNotMatch`
(`P6-485`, `P6-162`). Both scripts now read values through a shared `r2-env.sh` (`r2_var`) that
de-quotes, strips CR, drops an unquoted trailing comment, and reports `missing <KEY> in <FILE>` or
`cannot read <FILE>`. The endpoint must be an `https://` URL, and its host is taken from the URL
rather than by splitting on `//` — so `https://host/` no longer produces a double slash and a
mismatched `Host` header (`P6-487`). `S3_WAREHOUSE_PATH` must now be `s3://<bucket>/<prefix>` with the
bucket equal to `R2_BUCKET`: a bucket-only path used to list `lake-bucket/` as a key prefix, quietly
scanning the wrong scope (`P6-486`), and `r2_list_lake` expanded the prefix *before* loading it, so a
fresh shell listed `/` (`P6-489`).

**Sourcing the file changed the caller's shell (`P6-765`, `P6-766`, `P6-767`).** `set -euo pipefail`
plus an eager config load ran inside `source`, so `lake-guard.sh` (and any interactive shell) could
die at source time with grep's `No such file` instead of a reason, and the flags leaked into the
caller. Executing the script did nothing at all — a silent `exit 0` that reads as "the lake is
empty". The file now sets no options and loads nothing at source time (`r2_load` is lazy and called
by the functions), and it has a real CLI: `r2-list.sh lake|all`, with usage and exit 2 on a bad
argument.

**The credentials and the query were in argv.** `r2-list.sh` passed the access key and secret to
`python3 - … "$AK" "$SK"`, and `r2-query.sh` interpolated the secrets and the caller's SQL into
`duckdb -c "…"` — both world-readable in `/proc/<pid>/cmdline` for the life of the process, and the
SQL subject to `ARG_MAX` (`P6-154`, `P6-163`, `P6-496`). The listing now passes them in the
environment; the query writes its `SET` statements and the caller's SQL to a `0600` temp file that
DuckDB reads on stdin and that is removed on exit, with single quotes in values escaped.
`r2-query.sh` also no longer assumes `$HOME/bin/duckdb` exists (`DUCKDB_BIN`, then `$HOME/bin`, then
`PATH`, each with a named error) and no longer runs `INSTALL` on every invocation: it tries `LOAD`
first and only installs when the cached extensions are missing (`P6-495`). Its endpoint is validated
and normalised, so a trailing slash no longer reaches `s3_endpoint` (`P6-494`).

## Judgement calls (review these)

1. **A new shared file, `r2-env.sh`.** P6-485 and P6-162 are the same defect written twice, so the
   parser is one `r2_var` function sourced by both scripts instead of two copies. It sets no shell
   options and never calls `exit`, which is what makes it safe to source — that property is asserted
   by a test.
2. **`r2-list.sh` became executable and grew a CLI.** It was mode 644 and a no-op when executed, so
   no caller can have depended on running it; `source` usage is unchanged. Callers were checked:
   `lake-guard.sh` and `tiering-smoke.sh` source it (and keep their own `set -e`), and the operator
   docs now use the CLI.
3. **A page without `IsTruncated` is an error, not an empty page.** That is stricter than "handle
   errors" and it is the point: a page that does not say whether it is complete cannot prove that a
   listing is complete. The same reasoning is why a namespace-less response is now *parsed* rather
   than refused — the tags are unambiguous, only the namespace was.
4. **`r2-query.sh` stays an unsandboxed operator tool, and now says so.** The caller's SQL can
   `COPY TO`, read local files and reach the network with the operator's credentials; the finding's
   argv half is fixed, the sandbox half is not built (DuckDB has no such mode), and the header plus
   `COMMANDS.md` state the risk instead of implying a boundary that does not exist.
5. **Secrets go to a 0600 temp file rather than DuckDB's credential chain.** It keeps the documented
   `SET s3_*` behaviour that the proof query in `07-lake-archive-ops.md` depends on, and adds no
   dependency.
6. **Two documented seams are new, one is now stale.** `R2_ENV_FILE` / `R2_SECRETS_FILE` match the
   names the mover and restore scripts already use, and `DUCKDB_BIN` matches `r2-restore.sh`.
   `R2_LIST_SCRIPT` — used in one documented EOD command — is not read anywhere in the tree
   (pre-existing doc drift, left alone; the test file uses the same name as a path seam).
7. **The price of `LOAD`-before-`INSTALL`:** on a host where the extensions are missing, the first
   invocation fails once and is retried; both stderr streams are shown only when the retry also
   fails, so a successful retry does not pollute the caller's stderr (which the smoke captures).

## Verification

1. **Red before green.** The new suite was run against the pre-fix scripts (`git show HEAD:…`,
   sha256 `0f4e69ce…` for r2-list, `10998d17…` for r2-query) in a fixture tree that supplies the
   `01_docker/.env` + `secrets.env` those versions read: **30 failing checks**. Two further containers
   are reported as `PASSED` only because every one of their cases failed as a subtest (the summary
   counts those as failures, the container line does not). **Exactly one test genuinely passes on the
   pre-fix code** — `test_sourcing_the_script_does_not_abort_a_clean_shell` — because the fixture tree
   has a valid `.env` beside the script, which is not the situation P6-765 is about; the same source
   with the config absent aborts the caller's shell pre-fix (that is the defect, and the green suite
   covers it with absent files).
2. **Green.** `test_r2_scripts.py`: **30 tests, 15 subtests, 0 failures** — a TLS stub endpoint on
   127.0.0.1 drives the real SigV4 client (success and TSV, prefix encoding, namespace-less page,
   HTTP 403 with `Code=AccessDenied`, an error document at HTTP 200, a non-XML body, a missing
   `IsTruncated`, a truncated page with no token that must not re-request, two-page pagination with
   the continuation token, a trailing slash, and an unreachable host); `duckdb` is a stub that proves
   the secrets and the SQL never reach argv, that the stdin script is `0600` and removed afterwards,
   that `LOAD` precedes the `INSTALL` retry, and that a missing binary is named. No test reads
   `01_docker/.env`; no test can reach Cloudflare.
3. **Callers checked, not assumed.** `tiering-smoke.sh` pipes r2-query's stdout through
   `grep -oE '[0-9]+' | head -1`; verified locally on duckdb v1.3.2 that `-c` and stdin produce
   byte-identical output for the same query, so the parse is unaffected. `lake-guard.sh` sources the
   file and keeps its own `set -euo pipefail`.
4. **The helper suite: 554 tests, OK** (524 before the wave; +30).
5. **`full_audit.sh`: exit 0, 201 `[PASS]` / 0 `[FAIL]`**, including the change-control check
   that reads this record.
6. **Not run in this wave:** the Monday gate (a certificate re-run needs its own decision), and no
   query against the real R2 bucket — every endpoint in the suite is either `127.0.0.1` or a fixture
   string that is never dialled. The scripts' real-world use (tiering smoke, lake guard, EOD lake
   verification) was not executed.
