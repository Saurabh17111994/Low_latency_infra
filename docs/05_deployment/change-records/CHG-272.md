## Why

Plan item 3 — "host bootstrap and a real clock source" — had three pieces missing. The sysctl list was
undefined, so `vm-bootstrap.sh --check` **always** reported a failure and no host could ever be declared
ready (`S4` was unreachable by construction). `prod_node_check.py` recorded `clock: UTC` as a label but
measured no offset, so a node with a drifting clock passed the pre-deploy gate. And the executor's
`DriftMonitor` — armed since CHG-107 — sampled `FixedOffsetSource(0)`, a hardcoded zero, so the
enforcement could never fire in production.

## What changed

**The sysctl decision (runbook §6.1).** Four rules, each with the failure it prevents, applied by
`vm-bootstrap.sh --apply` to `/etc/sysctl.d/99-arrow-infra.conf` (rewritten only when the content
changes) and verified by `--check`:

| Knob | Rule | Prevents |
| --- | --- | --- |
| `vm.swappiness` | ≤ 1 | paging out JVM heaps and RocksDB caches — a p99 spike becomes a stall |
| `net.core.somaxconn` | ≥ 32768 | the accept queue overflowing at the 4096 default |
| `net.ipv4.tcp_max_syn_backlog` | ≥ 16384 | the same, one step earlier |
| `vm.max_map_count` | ≥ 262144 | the RocksDB state backend failing to open state at the 65530 default |

Rules are **comparisons**, not equalities: a host already beyond a floor passes, and writing an exact
value would have *lowered* this laptop (which reports `max_map_count = 1048576`). Deliberately not set,
with the measurement that justifies each skip: `fs.file-max` (effectively unlimited), the Docker daemon's
`LimitNOFILE` (package default already 524287), `vm.overcommit_memory` (masks real memory exhaustion).
A parity test keeps the script's list and the runbook's table equal.

**The node gate measures the clock.** `prod_node_check.py` now runs one extra SSH probe per node
(`timedatectl` synchronization plus the `System time` field of `chronyc tracking` — the same field S4's
bootstrap reads) and fails on an unsynchronized clock, an unreadable probe, or an offset beyond the limit
(default 200 ms, the executor's own `CLOCK_OFFSET_LIMIT_MS`; `--max-offset-ms` overrides). Exactly at the
limit is *within*, matching the Rust contract.

**The live `OffsetSource`.** `ChronycOffsetSource` spawns `chronyc tracking` (stdlib only, no new crate)
and parses field 4 of the `System time` line; every failure mode is an `Err`, so the existing monitor
classifies it `Unmeasurable` and halts. `main.rs` selects it with `CLOCK_OFFSET_SOURCE=chronyc`; the
default stays the fixed source so a dev box without a disciplined clock keeps working, and the armed
source is named in the boot log.

## Not verified

- **A four-node run.** `prod_node_check.py --inventory prod_vms.json` has never run against real VMs;
  what is proven is the classification logic against a fake runner and the probe's field choice.
- **The executor's live source inside a container.** The runtime image is `debian:bookworm-slim`, which
  ships no `chronyc`, and chrony's socket is root-owned on the host. Wiring that (image package, socket
  mount, ownership decision) is recorded as a gap in the runbook and cannot be proved without a VM, which
  is why `CLOCK_OFFSET_SOURCE` is not set by the stack in this change.
- **The sysctl values on a real CloudPe VM.** They are applied by the script and verified by `--check`,
  but no VM exists to run it on; the values themselves come from the mechanisms named above, not from a
  measurement on that hardware.
