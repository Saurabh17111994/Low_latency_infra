## Why

T13 asks whether the secrets the deploy demands are the secrets the rotation log tells
the operator to rotate. The row's criterion says the union of `secrets:` plus `${VAR:?}`
equals the set named in the rotation log and the bootstrap script. Measured before the
check was written, that is not literally true and never was:

| artifact | measured 2026-09-21 |
| --- | --- |
| deck `secrets:` block | 9 names |
| `secrets-bootstrap.sh --print-names` | the same 9 names — equal in both directions |
| `04-secrets-rotation.md` | names all 9, each in a table row |
| deck `${VAR:?}` | 16 names, 15 of them image tags, paths and identifiers; only `O2_PASSWORD` names a secret |

So C20 holds the two sets that can honestly be equal — the deck's declared secrets
against the bootstrap's names, in both directions, since a secret declared but never
rotatable and a secret rotatable but never declared are both drift — requires every
bootstrap name to be named by a row of the rotation log, and requires a required
variable that is a secret to also be declared as one. The 15 remaining required
variables are counted in the check's message rather than classified: deciding which of
them "look like" a secret is guesswork, and a check that guesses is worse than a count
that is honest. `ARROW_APP_ID` and `ARROW_USER_ID` are two of those 15; the rotation
log's known-exception bullet covers them.

The must-fail control the row asks for is in the suite: a fixture deck carrying a fake
declared secret fails the check, and so does a fixture rotation log that drops a name.
