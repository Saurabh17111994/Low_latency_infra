# CHG-247 — publish and digest-pin the six project-built images (image-publish.sh)

## Why

Build-plan item 1 of `docs/08_implementation/09-production-swarm.md` and gap row 1 of
`docs/05_deployment/PROD_VM_PROVISIONING.md` §6.1 recorded the same blocker: the six images the
production stack runs are built locally, were never pushed, and therefore have no registry manifest
digest. Four of them were retired as pins in CHG-218 for exactly that reason, and the deploy
environment still carried bare tags for the three it did name. A `docker stack deploy` therefore had
no immutable reference to deploy, and `make pin-check` step `[5/6]` — which only reads
`runtime.lock` — could not see the problem.

Two facts had to be settled before the fix could be written, and both were settled by measurement
on 2026-09-19 against a local `registry:2` over plain HTTP:

1. **`digest-pin.sh` does not need special handling for a plain-HTTP registry.** `buildx imagetools`
   resolved every pushed image with no extra flags, and the value matched the digest `docker push`
   printed. The suspicion recorded in the VM guide ("`buildx imagetools` may refuse") is disproven for
   a local registry; a *remote* one still needs `insecure-registries` in `daemon.json`, which is a
   daemon setting rather than a resolver limitation. The speculative fallback written for that
   suspicion was removed rather than kept as untested code.
2. **A pushed reference actually resolves.** `docker pull <repo>@sha256:<digest>` succeeded for a
   pushed image, while the same pull with an altered digest failed with "manifest unknown" — so a pin
   produced by this path is real, not decorative. This is precisely what an un-pushed image could not
   do.

A third fact was found while writing the runbook pointer, and it is a trap: the push address and the
deploy address are not the same. Pushing through an SSH tunnel uses `localhost:5000`, but every node
resolves `localhost` as itself, so the deploy environment must carry `<vm1-ip>:5000`. The digest is
content-addressed and identical either way; the address is not.

## What changed

- **`code/01_platform/04_scripts/image-publish.sh` (new)** — tags, pushes and digest-resolves the six
  project-built images in one pass and rewrites the six deploy-environment lines. Modes:
  `--registry HOST:PORT [--tag TAG] [--env-registry HOST:PORT] [--write-env FILE]`, plus `--print-map`,
  `--merge-env FILE` and `--self-check`. It refuses before any push if the registry does not answer
  (`curl /v2/`, accepting 200 or the 401 of an auth-enabled registry), exits 4 rather than writing a
  partial env when an image is missing or a digest cannot be resolved, and never writes anything
  unless asked.
- **`code/01_platform/04_scripts/tests/test_14_image_publish.py` (new)** — 9 offline tests: the env
  rewrite preserves unrelated lines and comments, appends variables that are absent (four of the six
  are), is idempotent, and refuses a missing file with exit 3; the push map covers every `${X_IMAGE:?}`
  the stack demands; the map never names a stock upstream image; `--print-map` names the built runtime
  images; `--self-check` exits 0 and writes nothing; an unreachable registry is refused with exit 2.
- **`code/01_platform/01_docker/.env.example`** — the header told a production deploy to use
  `flink:2.2.1-scala_2.12-java17`, which cannot run the job (CHG-179). It now says the stock images are
  for Compose only, that production must use the built runtime images, and that the four application
  images are unset because Compose builds them. The values are unchanged, so Compose development is
  untouched.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — §9 S4 step 6 leads with the one-command path and
  explains the two-address trap; the fallback note is rewritten around the measurements above,
  including the fact that `docker image inspect`'s `RepoDigests` drops the tag.
- **`docs/08_implementation/09-production-swarm.md`** — build-plan item 1 names the script, its
  `--self-check`, and the test that now owns the parity claim.

## Limitation

The push path itself was rehearsed against a **local** `registry:2` reached as `localhost:5000` and
`127.0.0.1`; it has never run against the VM1 registry over the private network, where the daemon
must declare `insecure-registries` first. The three offline-tested behaviours (env rewrite, map
coverage, refusals) do not depend on a registry, but the tag/push/resolve loop has only the local
run behind it. `--env-registry` is covered by that rehearsal, not by an offline test, because the
envelope it affects (the pushed reference) only exists once a registry answers.
