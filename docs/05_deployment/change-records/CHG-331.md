## Findings

1. **The hop is not yet config-only for the projection leg.** Compose maps
   `${EXECUTION_ENABLED:-false}` to both the gateway (master switch for
   `/v1/events`, `/control/approve`, intent forwarding) and nautilus (Rust boot
   guard: `must not be true at boot`). A sanctioned window therefore needs the
   gateway switch decoupled (`GATEWAY_EXECUTION_ENABLED`, default false) or a
   targeted single-service recreate.
2. **The harness's required tables were wrong for this topology.** The
   direct-to-nautilus route writes nautilus's file attempt store, not the Fluss
   `Execution_Attempts`; `Order_Lifecycle` is the correct required table
   (projection of the emitted lifecycle event).
3. **Gateway enablement has a replay consideration.** `IntentReader` subscribes
   `Execution_Intent` from offset zero with durable dedup; enabling the gateway
   while the executor gate is ENABLED can forward pending intents (fake orders in
   paper mode — harmless; a release-gate concern for the live sandbox).

## Attempt 2 (2026-09-27 ~15:20 IST) — blocked by a real cross-service contract break

H2-3 landed (CHG-332) and the gateway was enabled with `GATEWAY_EXECUTION_ENABLED=true`
(bridge `fake`, gate still `HALTED`). The gateway then failed closed on the live
`Execution_Intent` table and refused to serve:

```text
execution-intent-reader ERROR execution intent halted; gateway HALTED until restart:
invalid Execution_Intent at offset 0: invalid instruction_id
/readyz → 503 {"healthy":false,"flussReady":false,"protocolReady":false,
"durableWriteReady":false,"reason":"invalid Execution_Intent at offset 0: invalid instruction_id"}
```

Root cause (verified in the tree): the compute builder mints
`instruction_id = "ei-v1-" + sha256(...)` = **70 chars**
(`ExecutionIntentBuilder.instructionId`; its test pins the `ei-v1-` prefix), while the
gateway validator allows `^[A-Za-z0-9_-]{1,64}$` (`IntentValidator`, P3-094). The b4 tests
never caught it: the compute e2e writes canonical rows into the live table without
validating them against the gateway, and the gateway e2e uses a hand-crafted short id
(`halt-instr-0001`). All 9 live `Execution_Intent` rows are unreadable by the gateway — the
compute→gateway intent path has never actually run end to end.

Reverted immediately: gateway back to the fail-closed default, bridge `disabled`, nautilus
`HALTED` (epoch 3). No order was placed in this attempt.

## Attempt 3 (2026-09-27, after CHG-333) — fix proven, blocked by the gate-row gap (H2-5)

The gateway was recreated on the rebuilt image (`make images`, stamp `eb074cf377b2`) with
`GATEWAY_EXECUTION_ENABLED=true`. `/readyz` came up **503** with
`{"healthy":true,"flussReady":false,"protocolReady":true,"durableWriteReady":true,
"reason":"key not found"}`: the 9 live intents passed `IntentValidator` (no halt) and the
reader reached `NautilusIntentClient.forward` — the only `controls.lookup` caller in main —
so the `instruction_id` fix is proven live (attempt 2's `invalid instruction_id` reason is
gone).

The remaining blocker is H2-5: `Execution_Gate` has no writer in the deployed topology, so
the gateway's gate lookup returns NOT_FOUND, which flips `readiness.fluss(false)` and keeps
`/v1/events` refused while pending intents exist. The executor owns the table
(`07-executor.md` line 29, `ExecutionGateColumnOwnership`), but its deployed store is the
file-backed `FileGateStore`; the Fluss-backed swaps (Workstream D) are designed but unbuilt
(`durable.rs`), and the gateway wires the non-authoritative placeholder. The B4 halted E2E
pins the missing-row DEFERRED outcome. Reverted immediately: gateway → default (locked),
bridge stayed `disabled`, nautilus stayed `HALTED` (epoch 3). No order placed, no control
action taken.
