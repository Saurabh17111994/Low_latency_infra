# CHG-252 — Stack uses only interpolation forms the deploy engine renders correctly

## Why

Run8b deployed rc=0 with 16/19 assertions, but `CHECKPOINT_DIR` deployed as
` prod requires s3://<bucket>/...` (a fragment of its own `:?` error text),
`state.savepoints.dir` and `SAVEPOINT_DIR` deployed as literal `${CHECKPOINT_DIR}`,
and `FLUSS_BOOTSTRAP_SERVERS` deployed empty. The root cause is the toolchain, proven
with a 5-line probe file on the same engine that deploys the stack: nested defaults
`${A:-${B}}` render the inner reference literal; a `:?` error text containing ` - `
renders the tail as the VALUE; and `${SIBLING}` reads the deploy environment, never a
sibling key, so it renders empty. The safe subset — plain `${VAR}`, `${VAR:-plain}`
without a colon, empty `${VAR:-}`, short `:?` without ` - ` — all render correctly in
the same probe.

This re-explains the run7 jobmanager death (24 s, exit 239, attempts exhausted): Flink
received garbage checkpoint paths at startup, so the `s3://` placeholder was at most a
second killer. It hits production identically (same engine), hence a repo fix rather
than a rehearsal override.

## What changed

- **`code/01_platform/01_docker/docker-stack.yml`** (10 lines) — the two
  `CHECKPOINT_DIR` `:?` texts shortened to the proven form (prod guidance kept as a
  comment); the two `SAVEPOINT_DIR` env lines and the two `state.savepoints.dir` lines
  use that form directly (savepoints = checkpoints, as the nesting intended);
  `S3_ENDPOINT` collapses to `${R2_ENDPOINT:-}` (the override knob was never set
  independently); `FLUSS_BOOTSTRAP_SERVERS` is a literal kept in sync with the
  hardcoded `FLUSS_BOOTSTRAP` two lines up (a sibling reference can never work).
- **`code/01_platform/04_scripts/tests/test_09_stack.py`** —
  `test_interpolation_uses_only_the_portable_subset` bans the nested form and the
  ` - ` message form file-statically (comment lines excluded) and pins
  `FLUSS_BOOTSTRAP_SERVERS` to a value `FLUSS_BOOTSTRAP` actually takes. Green
  unmutated; fails all three drift mutations (nested, desync, dash-text). A
  `docker stack config` render gate confirmed 6/6 lines correct before deploy.
- Out of scope, noted: the `${env.AWS_*}` lines still render literal (the
  `fluss-r2-secrets-from-file.sh` companion's domain, untested until real R2); the
  probe file and run scripts stay local until the rehearsal-scaffold decision.
- Scope extension from the watch: prose comments inside `FLINK_PROPERTIES` blocks
  are consumed by the Flink entrypoint as config keys (run8c: a `# CHG-252 ...`
  line loaded as a property). Benign today (unknown keys are ignored) but one
  strict parser away from fatal, so all in-block prose (this change's two lines
  plus the pre-existing REQ-FC-008, T3/G3 and G4/T9 notes) moved above the block
  keys with zero content change. Rule now pinned in the file: no prose comments
  inside the block.
- Second scope extension, same root: run8d proved an inline `#` is not merely inert
  — a rehearsal note appended to a path value survived into the value
  (`high-availability.storageDir` became
  `file:/checkpoints/flink-ha#REHEARSAL-ONLY(production:s3:/)`, a URI with a
  fragment), and the jobmanager died in `FileSystemJobResultStore` at 24 s with a
  message that reads like a storage outage. `#` is now banned inside every
  properties block, including the 25 lines of Fluss listener rationale this change
  set added, which moved above their `FLUSS_PROPERTIES` keys. A repo test pins the
  rule for all six blocks (4 FLUSS + 2 FLINK); a mutation that puts a comment back
  inside fails it.

## Limitation

Engine-specific: the finding holds for this machine's compose parser, and the safe
subset is conservative by design (it renders correctly everywhere, including newer
engines). If the VMs ship a parser that handles nesting, the restriction is still
harmless. Empty `${VAR:-}` and colon-free `${VAR:-default}` were probe-verified safe
and are intentionally NOT banned.

## Rehearsal result (run8c)

Deploy rc=0 on a fresh create; 19/19 ALL_PASS with zero placeholder leaks. Runtime
watch: the jobmanager still died at ~24 s exit 239 WITH correct paths, which isolated
the third cause (D-F): `FileSystemJobResultStore ... base directory isn't accessible`
for `file:///data/flink-ha` - the Flink services mount no `/data` (their volume is
`flink-checkpoints:/checkpoints`). Rehearsal-only fix, no repo change: the generator
and rehearsal env now place all Flink file:// storage under `/checkpoints`, and the
teardown wipes data volumes (D-G). Replayed as run8d.

Run8d: deploy rc=0, 20/20 assertions. The jobmanager still exited 239, and the log
gave the decisive line - `Creating highly available job result storage directory at
file:/checkpoints/flink-ha#REHEARSAL-ONLY(production:s3:/)/job-result-store/prod`,
i.e. the value carried the rehearsal note as a URI **fragment**, so the store's base
directory was never the directory it checked. That is D-H: the two fixes (D-F
placement and D-H marker hygiene, both rehearsal-side) plus this change's repo-side
comment ban. Replayed as run8e.

Run8e: deploy rc=0, 21/21 assertions, storage paths clean (`file:/checkpoints/flink-ha/
job-result-store/prod`), and the jobmanager *still* exited 239 with the same message -
which killed the D-H explanation as complete and found D-I. Decompiling the class from
the deployed image (`javap` on `flink-dist-2.2.1.jar`) shows
`FileSystemJobResultStore.createBasePathIfNeeded()` calling `mkdirs` and then
**discarding its result** before logging `Created …`; the failing condition is
`listStatus(basePath) == null`, i.e. the directory was never created. Cause: a fresh
named volume is `root:root 755`, the Flink image runs as uid 9999, so `mkdirs` is
denied (`PROBE_FAIL`, `Permission denied`) and Flink reports it as an inaccessible
directory. Production is unaffected by construction - HA, checkpoint and Fluss remote
storage are all `s3://` there - so this is rehearsal scaffolding plus runbook rule 9,
which also warns that the same silence can hide a rejected object-store write.

re-run9 (fresh create, after CHG-253/255) re-proves both halves of this change against the
deployed stack: `savepoints interpolated`, `HA storageDir deployed`, `CHECKPOINT_DIR value`,
`no inline comment on storage property lines` and `no placeholder leak` all pass, so the
rendered values are the intended filesystem paths rather than a leaked `${…}` reference or a
prose line read as a config key.
