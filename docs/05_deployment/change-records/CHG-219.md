# CHG-219 — gate step 3 also runs the pytest-style files the certificate never collected

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** certificate run 6 (`GATE RESULT: PASS — 19/19 verified, 0 skipped`) plus the
  post-gate `make gate-fast` pass, which showed the suite reporting `Ran 1477 tests`.

## What happened

`python3 -m unittest discover -s code/01_platform/04_scripts/tests -p "test_*.py"` — gate step
3, and `make test-audit-r2` — collects only `unittest`-based modules. 18 files in that
directory are written in pytest style (bare `def test_*()` plus `assert`) and unittest never
collected them, so an unknown share of the helper suite's coverage was outside the
certificate. Measured 2026-09-18: `1754 tests collected` in total against `1477` by unittest,
and `pytest … -p no:unittest` selects `278` of them (`278 tests collected in 0.33s`, `278
passed in 203.82s`).

## The change

Step 3 runs a second invoker after the unittest one, with its own failure check and its own
`PASS:` line so the existing evidence stays intact:

```
timeout -k 60 "$PYTEST_TIMEOUT_SEC" python3 -m pytest "$SCRIPT_DIR/tests" -q \
    -p no:cacheprovider -p no:unittest >"$PYTEST_LOG" 2>&1
```

- `-p no:unittest` disables pytest's unittest collector, so the selection is exactly the
  pytest-only files — no file list to maintain and no silent hole when a file is added.
- `PYTEST_TIMEOUT_SEC=420` is ~2x the measured 204s (the same rule as `PY_TIMEOUT_SEC`).
- A green zero is impossible: pytest exits 5 when it collects nothing, and the rc check
  refuses it; the `^[0-9]+ passed` / `^[0-9]+ (failed|error)` patterns are anchored so test
  chatter cannot fake either verdict (the CHG-201 lesson).
- The certificate's verdict counts step banners, not `PASS` lines, so a second `PASS:` inside
  step 3 does not move `19/19`.
