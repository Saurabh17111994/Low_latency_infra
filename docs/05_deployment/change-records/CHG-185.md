# CHG-185 — ingestion containers receive DEPLOYMENT_ENV explicitly (wave 36)

- **Status:** recorded — fixes a pre-existing bring-up defect found during wave 36
- **Filed:** 2026-09-17
- **Source:** discovered while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`. Not one of the wave's 18
  findings — the live run surfaced it after the harness could finally start.

## What happened

`pipeline_start_ingestion` launches the ingestion container with `docker run` and
an explicit `java … com.trading.ingestion.IngestionService` command, but never
passed `DEPLOYMENT_ENV`. `IngestionConfig` fails closed without it:

```text
ERROR com.trading.ingestion.config.IngestionConfig - Ingestion config validation failed (1 errors):
  DEPLOYMENT_ENV/DEPLOY_ENV is required but not set (must be 'dev' or 'prod'/'production')
Exception in thread "main" java.lang.IllegalStateException: Ingestion config validation failed
```

The container exits immediately, `pipeline_start_ingestion` times out after 120s
waiting for a readiness marker that can never appear, and every harness that
calls it dies during bring-up.

**Neither of the two usual paths covers this call:**

1. `docker-entrypoint.sh` (L23) defaults it — `export DEPLOYMENT_ENV="${DEPLOYMENT_ENV:-dev}"`
   — but `Dockerfile.loadgen` has *no* `ENTRYPOINT` by design ("the run script
   selects the binary"), so for this image the entrypoint never runs.
2. `docker run` does **not** forward the caller's exported environment. Verified
   live: `DEPLOYMENT_ENV=dev docker run … -c 'echo ${DEPLOYMENT_ENV:-UNSET}'`
   printed `UNSET`; only an explicit `-e DEPLOYMENT_ENV=dev` printed `dev`. So
   even an operator who exports the variable before invoking the harness is not
   covered — this is why the fix belongs in the library rather than in the
   caller's environment.

**Blast radius.** Every harness that calls `pipeline_start_ingestion`:
`holistic-measure.sh`, `stage-a2-baseline.sh`, `eod-controller-test.sh`,
`tm-kill-full-load.sh`. `test-pipeline-lib.sh` cannot catch this: its
ingestion-related guards are text checks (`grep` for `pipeline_require_preflight`),
and it never starts a real container.

**Date of the defect.** Pre-existing, not wave 36. `git log -L 655,662` traces
the `docker run` env block to `4065140c` (*wave 17 — pipeline helpers fail closed
instead of measuring garbage*), which added the `--env-file "$LIB_SECRETS_FILE"`
line and the secrets file check while adding the neighbouring `-e` flags. The
secrets file (`code/01_platform/01_docker/secrets.env`, git-ignored) carries
`ARROW_*`/`O2_*`/`AWS_*` credentials only — no `DEPLOYMENT_ENV`.

## The fix

One line beside the existing `-e LOG_DIR=/logs`, defaulting to the same value the
entrypoint would have used for an ad-hoc run, with an operator's explicit value
winning:

```bash
-e DEPLOYMENT_ENV="${DEPLOYMENT_ENV:-dev}" \
```

`dev` is the correct default here: these harnesses are ad-hoc measurement runs on
a local compose stack, which is exactly the case the entrypoint's own
`${DEPLOYMENT_ENV:-dev}` default was written for. A production invocation sets
`DEPLOYMENT_ENV=production` explicitly and that value is passed through
unchanged, so the production-only gates in `PlatformConfig`
(`DEPLOYMENT_ENV=production` requires an S3 checkpoint URI) still see the value
they were designed to see.

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*Deployment topology or runtime environment of a deployed component*. This
changes the runtime environment a deployed component is started with, in the
shared bring-up library used by several harnesses. The precedent is the same
axis: `CHG-138` carries `scope: deployment` for `DEPLOYMENT_ENV`/`DEPLOY_ENV`
alias precedence, and `CHG-154` for the neighbouring fail-closed ingestion
config behaviour.

## Verification

* Reproduced live before the fix: the wave-36 harness run exits with the
  `IngestionService` validation error and `SMOKE FAIL — main measurement SKIPPED`.
* Proved the mechanism with two throwaway containers (exported value does not
  reach the container; an explicit `-e` does).
* `python3 code/01_platform/04_scripts/change_control_check.py` exits 0, and the
  same check runs as C14 of `docs-audit`.
* The wave-36 harness is re-run end-to-end after this change lands; the result is
  recorded in the plan's Task 7 checklist.
