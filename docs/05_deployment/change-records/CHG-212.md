# CHG-212 — DDL apply: never drop a table with an unresolved write; drain the scratch teardown before returning

- **Status:** recorded — fixed and guarded (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** gate step 9 (`make drill-live`) red on two live classes
  (`DdlSmokeTwinSweepTest`, `FlussPostbackQuarantineStoreIntegrationTest`);
  root-caused from the coordinator/tablet logs and three probes (see below).

## What happened

Two independent failures, one shared head.

1. **Storm head.** When a table is dropped while its writer still has a batch
   pending, Fluss 0.9.1's client `Sender.sendWriteData` busy-loops re-resolving
   metadata for a table that no longer exists: 81,386 `NONODE` metadata WARNs in
   3 s from the coordinator, and the tablet's request channel went past its
   backpressure threshold (queue 70 vs limit 62). The old DDL smoke dropped its
   twin in a `finally` regardless of whether the smoke write had resolved, and
   the sweep test's cleanup did the same.
2. **Placement head.** A dropped table's buckets are torn down one at a time,
   ~1.5 s each, of which only ~65 ms is local work — the rest is
   `RemoteLogManager.stopReplica` deleting remote log segments from the
   configured remote store (Cloudflare R2 here; `server.yaml`
   `remote.data.dir: s3://...`, ~100 ms per round trip). One apply drops 54
   scratch tables (~540 buckets), so the queue runs for 7-8 minutes, and the
   coordinator does not bring up new replicas while it drains: a table created
   at 05:41:57 only had its replica attempted at 05:49:48, by which time the
   caller had given up and dropped it (`SchemaNotExistException`). Every phase
   after the apply inherited the backlog — the postback store's append burned
   its full 412 s retry budget on the same delay.

## What changed

- `code/common/src/main/java/com/trading/common/schema/fluss/WriteAwait.java`
  (new) — one bounded extra wait on the SAME append future (never re-issued,
  so no duplicate row), RESOLVED/UNRESOLVED reported to the caller.
- `DdlApplyTool.java` — the smoke twin is KEPT (loud log) when its write never
  resolved instead of being dropped under a pending batch; `closeBounded`
  (daemon executor, 30 s, WARN-only) replaces the unbounded
  `WriterClient.close`/`awaitTermination` at all three close sites; and the
  apply now ends with `drainScratchTeardown`, which waits (bounded, logged every
  30 s, canary kept on timeout) until the cluster can place a fresh replica
  again — the same create → append → drop operation the next phase needs.
- `CompositeKeyMatrixVerifier.java` — a timeout-only retry (one attempt,
  idempotent re-upsert, always logged) so a placement stall inside the matrix
  is not reported as a composite-PK failure.
- `DdlSmokeTwinSweepTest.java` — every cluster await is bounded, the unbounded
  `finally { flush() }` is gone (the acked write IS the visibility guarantee;
  the flush only masked timeouts for ~435 s), and a table whose write never
  resolved is KEPT rather than dropped.
- `docs/08_implementation/01-foundation.md` — plain-suite pin 729→733 for the
  four `WriteAwaitTest` cases.

## Verification

- Targeted drill-profile run (`DdlSmokeTwinSweepTest`,
  `FlussPostbackQuarantineStoreIntegrationTest`): 3/3 green, BUILD SUCCESS.
  Apply `RESULT=PASS EXIT=0 TABLES=27`, 54 scratch tables dropped, `scratch
  teardown drained after 454s`, sweep 2/2 in 906 s, postback 1/1 in 5.1 s
  (was 412 s and a timeout).
- `WriteAwaitTest` 4/4 green; `bash -n`/test-compile clean.
- Probes: burst probe (canary writes ~103 ms during churn → placement-only, not
  global starvation), drain probe (fresh-replica placement recovers 28 s after a
  batched burst), metadata probe (server-side list/create/drop 0-16 ms → the
  30 s stalls are client-side/queueing).
