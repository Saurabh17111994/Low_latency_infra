## What happened

`pin-check.sh` check 5 requires every `*_IMAGE=` ref to end in a full `@sha256:<64 hex>`.
Four refs could not satisfy it: they name images this repo **builds locally** and never
pushes, so no registry manifest digest exists for them. They carried the 12-hex prefixes
of buildx config digests from the 2026-08-28 build (visible in
`logs/gate/rebuild-images-20260828.log` as `writing image sha256:<64 hex> done`), which
is exactly the truncation P6-140 exists to reject — a 12-hex prefix is ambiguous and
mutable, a full digest identifies one image.

Two defects, not one. The values were also **stale**: the images on this host were
rebuilt on 2026-09-13/14, so the four recorded IDs matched no image on the machine at
all. Both are fixed by taking the value from the daemon instead of the log:

```text
INGESTION_IMAGE          = 01_docker-ingestion          @sha256:5e363c21e76a16b29670482939129fd0bc2010b4a67c7f4eee84e0a082de4e7c
NAUTILUS_IMAGE           = 01_docker-nautilus           @sha256:3e893cd8491e5ce32584330ec7523ced47a65f36fa057d306488423df1ce7135
EXECUTION_BRIDGE_IMAGE   = 01_docker-execution-bridge   @sha256:84c758d2c6ae302ae3f720d5d3b4d973f34d64cd48000fd5d66f83524203683d
EXECUTION_GATEWAY_IMAGE  = 01_docker-execution-gateway  @sha256:21b2fd9b22b0bb44fae95d7dbdfc4b89d459abcd22047f9a6fb00efb840c8ffb
```

## Judgement calls

1. **The image ID, not a manifest digest.** There is no manifest digest to pin: the four
   images have empty `RepoDigests` (never pushed). The image ID is the only digest that
   exists, and it is verifiable on the build host. Check 5 validates shape only — it
   cannot tell a manifest digest from a config digest — so the *meaning* is recorded in
   the lock instead.
2. **The lock now says what these four lines are.** `docker run <repo>@sha256:<image-id>`
   does **not** resolve (verified: `Error response from daemon: No such image` — digest
   resolution goes through `RepoDigests`/manifests, not the config digest). Before this
   change the lines were equally unpullable, just also ambiguous. The note above
   `INGESTION_IMAGE` states they are provenance ("which image was tested"), points at
   `digest-pin.sh` for the pushed-manifest path, and names the test that fails when a
   rebuild makes them stale.
3. **Freshness stays a separate check.** `image_staleness_check.py` compares a content
   stamp, not a digest; it does not read `runtime.lock`. It currently reports six stale
   images (see Risks) — pre-existing, and untouched by this change.
4. **The old trailing comment was rewritten, not dropped.** Each line still ends with a
   human note (`# local build — image ID (config digest), not a registry manifest`) so a
   reader is not left thinking the value is a registry digest.
5. **`test_short_digests_fail` was decoupled from the shipping lock.** It used to assert
   that the *real* lock fails check 5 — true only while the four values were wrong. It now
   builds its own 12-hex and 63-hex fixtures, so P6-140's boundary stays pinned after the
   re-pin and the test cannot pass or fail for the wrong reason.
6. **The live leg is docker-gated, and deliberately fails on drift.** A rebuild changes
   the image ID, so `test_local_build_pins_match_the_local_images` goes red until the lock
   is re-pinned. That is the point of a pin; it skips cleanly when docker or the image is
   absent.

## Risks

`image_staleness_check.py` (a gate step, `run-monday-gates.sh` L657) reports **3 of these
4 images STALE against the current sources** and 3 others stale as well:

```text
image-stale: [FAIL] execution-gateway STALE: stamp 2b2000fe6b8d... != sources 1d1e03cf5c38...
image-stale: [FAIL] ingestion         STALE: stamp 74c16c8917d2... != sources 74180c2105ff...
image-stale: [FAIL] nautilus          STALE: stamp e7cdd6399dc0... != sources 7ee3318010f7...
image-stale: [FAIL] ddl-apply, eod-controller, loadgen STALE (same shape)
image-stale: FAIL — 6 stale/missing/unstamped (rebuild: make images)
```

So these pins identify images whose *content* predates the tree (the ingestion image was
built 2026-09-14T11:56; its sources last changed 18:54 the same day). The pin is honest
about which image is on this host; it is not a claim that the image is current. Pre-existing
and independent of this change (the checker reads neither the lock nor the pins).
Remedy, in order: `make images`, re-run the new test to get the fresh IDs, re-pin.
