# CHG-256 — the DDL-apply tool image is published, and the first-boot catalog step is documented

## Why

A production cluster boots with an **empty Fluss catalog**, and nothing in the deploy fills it.
`ingestion` starts with `allowRuntimeDdl=false` and exits fail-closed:

```text
Fluss schema verification failed (allowRuntimeDdl=false)
```

That is the state where no data loop can start, and the runbook had no step that changes it. Two
separate gaps produced it, and the rehearsal closed both:

1. **The image was never published.** `image-publish.sh` pushes the six images the stack demands, all
   named as `${X_IMAGE:?}` in `docker-stack.yml`. The DDL-apply tool is not a stack service, so it was
   absent from that map — on VM1 there was nothing to run the catalog step *with*.
2. **No step documented it.** `catalog-guard.sh` applies the catalog in the development stack only: it
   hard-codes `docker compose --env-file … -f docker-compose.yml` and finds ZooKeeper by its compose
   project name. It has no Swarm path, and the production runbook (`docs/05_deployment/PROD_VM_PROVISIONING.md`)
   named no DDL step at all. A fresh production cluster therefore reached S8 with ingestion `0/1` and no
   documented recovery.

The command itself was measured on the rehearsal cluster before it was written down, because the two
obvious forms of it do not work: the stack's overlay networks are deliberately **not** `attachable` (a
standalone container cannot join them), and the dispatcher refuses `--apply-verified`/`--matrix-evidence`
as command-line flags (exit 2, duplicated state).

## What changed

- **`code/01_platform/04_scripts/image-publish.sh`** — `IMAGE_MAP` gains
  `DDL_APPLY_IMAGE=01_docker-ddl-apply:latest` (seven project-built images, not six), with the reason
  above the map: the tool image runs outside the stack, so nothing else pins it.
- **`code/01_platform/04_scripts/tests/test_14_image_publish.py`** — the push-map test asserts the new
  variable, and `test_the_first_boot_catalog_step_runs_a_published_tool_image` ties the two files
  together: the runbook's `S7b` must invoke `"$DDL_APPLY_IMAGE" apply`, name the tool's own sentinel
  (`DDL-APPLY-RESULT: PASS`), say why the step exists (`allowRuntimeDdl=false`), and the variable must
  be the one `--print-map` publishes. Removing the map entry fails both tests.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — new step **S7b — Apply the DDL catalog (first boot
  only)** between S7 and S8, with the measured command, the empty-catalog precondition, the expected
  sentinel and record, the ingestion restart that follows, the three measured traps, and the explicit
  statement that this step does not replace the vendor feed. Also updated: the sequence table (new row,
  S8 now depends on S7b), S1 builds `make ddl-image` and expects nine images, S4/S6 publish and write
  seven image lines, and the stage-evidence table gains an S7b row.
- **`docs/08_implementation/09-production-swarm.md`** — item 1 of the build plan names the tool image
  and the new count.

## Limitation

The command in the runbook was measured on a single-node rehearsal cluster with the
`docker run --network container:` form. The native Swarm one-shot form
(`docker service create --mode replicated-job` on the overlay) is not measured yet, and the 4-VM first
boot has never been run — both are recorded as open items rather than claimed. Publishing the tool
image to a real registry has been proven for the other six images (CHG-247 rehearsal) but not for
this one; the push path is identical, the digest-pin step is the same code, and `--self-check` now
requires the image to exist locally.
