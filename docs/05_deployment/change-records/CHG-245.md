# CHG-245 — host-stray detection recognises every container cgroup form (P6-144)

## Why

P6-144 (HIGH) from the ops/scripts/tests/chaos audit was re-verified independently against the code
on disk on 2026-09-19 and was still exactly as audited, while the audit row was already ticked.

`pipeline_lib_preflight` decides whether a data-path JVM spotted through the host `/proc` belongs to a
container or to the host:

```sh
if ! grep -qs 'docker-' "/proc/$p/cgroup" 2>/dev/null; then
```

`docker-` only matches the cgroup v1 / systemd-scope spelling (`docker-<id>.scope`). On a cgroup v2 host
using the cgroupfs driver the path is `0::/docker/<id>`, and containerd/k8s hosts use `containerd` or
`kubepods` paths, so a container's own JVM is classified as a host stray and trips G26 — the exact false
positive that blocked the run after the 2026-09-02 reboot, only on a different host layout.

## What changed

- `code/01_platform/04_scripts/pipeline-lib.sh` — the predicate is now
  `grep -qsE 'docker[-/]|containerd|kubepods' "/proc/$p/cgroup"`, and the comment records the three path
  spellings and the finding id.
- `code/01_platform/04_scripts/tests/test_pipeline_lib_hardening.py` — new
  `StrayCgroupClassificationTest`: it reads the pattern out of the script (so it cannot drift away from
  what is tested), then feeds five real container cgroup shapes and three real host shapes to `grep -E`
  and asserts the classification. It fails if the predicate goes back to a bare `docker-`.

Evidence that the guard can ring: with the same cgroup-v2 line, the new pattern exits 0 (container) and
the old `docker-` exits 1 (host stray); both still exit 1 for `0::/system.slice/ssh.service`.

## Compatibility

The gate becomes less likely to accuse: a host process on these hosts is by definition not inside a
container cgroup, so widening the container test does not mask a real stray. No interface, no data, and
no deployment surface changes.

## Limitation

The classification still relies on the container runtime putting a recognisable segment in the cgroup
path. A runtime that does not (for example a rootless podman layout such as
`user.slice/.../libpod-<id>`) is still classified as a host process; add its segment to the same
predicate if that host is ever used.
