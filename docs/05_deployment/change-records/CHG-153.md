# CHG-153 — The self-checks stop tearing down and start reading

- **Status:** recorded — all 10 wave-16 findings fixed
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 16 ("Self-checks that must not destroy
  or mis-resolve"): P6-019 (critical), P6-206, P6-207, P6-208, P6-209 (high), P6-550, P6-551
  (medium) in `stack_selfcheck.sh`; P6-012 (critical), P6-484 (medium), P6-762 (low) in
  `pom-snapshot-scan.py`

## What happened

Two scripts whose whole job is to tell the truth about a deploy. One could delete a stack it
never deployed; the other had been reporting "clean" on a directory it never looked in.

**A validate-only run removed `prod` (`P6-019`).** Teardown was `if [[ "${DOWN:-1}" == "1" ]]`,
with no reference to `DEPLOY`, so `make stack-selfcheck` — documented as compile-only — ran
`docker stack rm prod` against whatever stack was on the host, and its `|| true` plus an
unconditional echo reported success when the removal failed. Teardown is now gated on
`DEPLOY=1` *and* on the stack actually being listed, `|| true` is gone, and the message says
"requested removal" only after `docker stack rm` exits 0.

**The gate had never scanned a pom (`P6-012`).** `pom-snapshot-scan.py` sits three directories
below `code`, so three `dirname` calls resolved the root to `<repo>/code` and the glob became
`<repo>/code/code/**/pom.xml` — a directory that does not exist. The gate printed "no external
SNAPSHOT dependencies" and exited 0 on every run, as check [3/6] of `pin-check.sh`. The root is
now four levels up (6 pom.xml found, verified), and a scan that finds no pom at all exits 2
instead of passing.

**The swarm checks mutated things they did not understand (`P6-206`, `P6-207`).** A failing
`docker node ls` (which can mean "no permission") triggered an unconditional
`docker swarm init --advertise-addr 127.0.0.1`; the node to label came from
`docker node ls -q | head -1`, whose ordering is undefined and which on a joined swarm labels
an arbitrary *peer*. The script now asks `docker info --format
'{{.Swarm.LocalNodeState}}'`, takes the id from `{{.Swarm.NodeID}}`, and refuses to label when
the swarm has more than one node.

**Placeholder defaults defeated the stack's own fail-closed checks (`P6-208`).** `FLUSS_IMAGE`
and eleven others were defaulted to `*:unset`/`s3://placeholder/*`, which is what made a
`DEPLOY=1` run look successful while deploying unpullable images; and `CHECKPOINT_DIR` — one of
the twelve `:?` vars in `docker-stack.yml` — was never set at all, so offline validation failed
for a reason the script did not explain. A deploy now requires real values for all twelve (exit
2, nothing deployed); a validate-only run keeps placeholders, states that it is compile-only,
and works offline.

**The documented invocations were no-ops (`P6-209`).** The header documents
`./stack_selfcheck.sh DEPLOY=1`, and `make stack-config` passes exactly that — but only
environment variables were read, so "deploy" silently ran validate-only with default teardown.
Key=value arguments are now parsed (and unknown arguments exit 2).

**The scan reported plugins as dependencies (`P6-484`), skipped unreadable poms (`P6-762`),
and the header described an impossible label (`P6-551`, `P6-550`).** The regex matched any
`groupId`/`artifactId`/`version` sequence, so `<plugin>`/`<pluginManagement>` pins were
reported as dependency violations; unreadable pom files were dropped with a bare `continue`; the
header claimed one label key held both `role=worker` and `role=observability`; and the repo root
came from `$0` plus a bare `cd`, which breaks when sourced or run from the script's directory.

## Judgement calls

1. **No `eval` for the positional overrides.** The finding's sketch was
   `eval "$arg"` after a case pattern; a `DEPLOY=1` argument would then be a shell injection
   point. The same behaviour comes from `${arg#DEPLOY=}`, so that is what is used.
2. **Teardown also checks that the stack is listed.** `DEPLOY=1` alone would still fire
   `stack rm` at a stack this host never deployed. The read is
   `$(docker stack ls … | grep -x … || true)` rather than a bare pipeline: under
   `set -o pipefail` a `grep -q` that exits early can make the pipeline return 141 from a
   SIGPIPE'd `docker`, which would read as "absent".
3. **`DEPLOY=1` needs real values; validate-only keeps placeholders.** The finding's sketch
   removed placeholders in both paths, which would have made `docker stack config` fail on any
   host without `.env` — the offline-prep use this script exists for. Fail-closed is applied
   where it matters (the deploy) and the validate path says out loud that it is compile-only.
4. **`CHECKPOINT_DIR` was the only genuinely missing required var.** The finding also named
   `SAVEPOINT_DIR`, but that one is `:-`-defaulted in `docker-stack.yml`; the `:?` set is
   exactly the twelve now covered. Adding `CHECKPOINT_DIR` makes offline validation work where
   it previously failed.
5. **The peer-swarm refusal is expressed as a multi-node refusal.** A leftover single-node
   swarm from a previous run still proceeds — that is the mimic's own normal state — while
   anything with peers is refused.
6. **Exit 2 for an unverifiable scan.** `pin-check.sh` treats any non-zero as a failure, so
   "no pom found" and "a pom could not be read" now fail the gate instead of passing it; 2
   matches the unusable-input convention used by the other operator CLIs in this tree.
7. **The dependency regex keeps `<parent>` and drops `<plugin>`.** The finding offered
   dependency-only or documented coverage; a `<parent>` version is a build-time artifact pin
   that the old loose regex did catch, so it is kept, and only the plugin false positives the
   finding named are removed. Today the result is identical (0 hits either way).
8. **`POM_SCAN_ROOT` is a test-only seam**, documented in the module docstring and unset in
   production.
9. **Two test bugs of mine, found by running the tests before committing.** (a) The deploy
   tests assumed `DEPLOY=1` deploys with placeholders, which P6-208 now refuses — they supply
   the twelve values; (b) the docker stub's `case` keys had a trailing space
   (`"node ls "` never matches `node ls -q`), so `docker node ls` and `docker stack ls` silently
   answered nothing and the "stack present" / "multi-node" paths took the wrong branch. Same
   class as the wave-15 compose-registry substring error.
10. **No Makefile or doc change was needed.** `make stack-config` already passes
    `DEPLOY=1` / `DOWN=…` positionally, so parsing them fixes that target as-is, and
    `09-production-swarm.md` already calls the script "compile-only" — which was wrong before
    and is accurate now.
