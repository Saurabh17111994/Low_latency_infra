# CHG-239 — the compose-ladder layer 0–2 asserts now fail when the property they name breaks (wave 49)

- **Status:** recorded — fixed; verification by per-step evidence (no gate run, see below)
- **Filed:** 2026-09-20
- **Source:** audit map wave 49 (`test_08_local_compose_l0.py` P6-597/598/802, `test_08_local_compose_l1_l3.py` P6-603/804/805, `test_08_local_compose_l2.py` P6-604/605/806/807).

## What was found

Ten MEDIUM/LOW findings in the first three rungs of the compose ladder (10 ids, no
draft/saved twins). **No finding was stale** — every one reproduces in the
2026-09-20 source — but four carry a wrong supporting claim or an unfixable fix
text; those are listed under *Deviations*. The theme is uniform: each assertion
passed on both the healthy and the broken configuration, so it could not fail for
the reason its name claims.

1. **P6-597 — CONFIG-004 asserted the wrong thing.** The comment claimed
   `O2_PASSWORD` is wired with `${VAR:?}` (fail-closed) "and that this is
   asserted"; the compose interpolates it plainly (`docker-compose.yml:1178`,
   `ZO_ROOT_USER_PASSWORD: ${O2_PASSWORD}`), and the test only grepped for the name.
2. **P6-598 — CONFIG-005's leak scan was inert.** It searched
   `docker compose config` output for `ARROW_TOKEN=`, but that output is YAML
   (`KEY: value`) — the string could never appear. `ARROW_TOKEN` was removed on
   2026-08-24 (TOTP only), so the check was vacuous twice over.
3. **P6-802 — the l0 module imported `os` and never used it.**
4. **P6-603 — START-003 asserted a tautology.** `assertIn("flink-jobmanager",
   tm_set | jm_set | {"flink-jobmanager"})` contains its own needle, so the
   intended "TM depends on JM" property was never checked.
5. **P6-804 — the l1_l3 module imported `re` unused**, and re-imported
   `json`/`subprocess` inside `compose_json()` although both are module-level.
6. **P6-805 — HEALTH-001 promised a healthcheck/readiness proof per service** and
   asserted only that the four service names exist.
7. **P6-604 — SEC-006 never looked at Fluss' published ports**, although its
   docstring claims the RPC/tablet ports stay inside the allowlist
   (fluss-coordinator `9123:9123`, fluss-tablet `9124:9124`).
8. **P6-605 — SEC-008 never looked at Flink's published ports** (JM `8081:8081` +
   `9249:9249`, TM `9250:9249`).
9. **P6-806 — NETWORK-001/SEC-003/SEC-009 only denied arrow-egress to others** and
   never asserted that `execution-bridge` **is** attached, so removing the order
   path's only egress network broke nothing.
10. **P6-807 — NETWORK-004/SEC-005 used `cfg["services"].get(name, {})`**, so a
    service removed from the profile silently matched "no published ports".

## Deviations from the audit's fix text

1. **P6-807 — SEC-006 and SEC-008 do not use the silent `.get(name, {})` shape.**
   Only NETWORK-004 (L45) and SEC-005 (L171) did; both already subscript the
   service (L178-179, L204-205). Fixed in the two real sites only.
2. **P6-604/605 — `ports == ["9123:9123"]` cannot work.** `docker compose config
   --format json` renders ports as objects (`{"published": "9123", "target":
   9123, "mode": "ingress", "protocol": "tcp"}`), verified against the real file,
   so the assertion compares `(published, target)` pairs — which also catches the
   `9250 -> 9249` remapping and a re-published port, neither of which a
   string-equality check on `ports` would catch.
3. **P6-805 — the docstring's universal claim cannot be encoded without changing
   the compose.** Only `ingestion`, `minio` (and `execution-bridge` in the
   execution-t3 profile) declare a healthcheck; `flink-*` and `fluss-*` declare
   none. The test now asserts the proof each service actually owns instead of
   pretending a healthcheck exists, and a new entry in the table without a proof
   fails loudly.
4. **P6-597 — Option A, test-only (wave owner's choice).** The dev compose keeps
   plain `${O2_PASSWORD}` on purpose: the rationale at `docker-compose.yml:50-60`
   records that hard `:?` pins broke `compose config` for the documented "copy
   .env.example to .env" flow (`.env.example` ships this key empty). Making the
   compose fail-closed would flip that documented flow, so instead the test now
   requires the value in `secrets.env`/`.env` and fails with the file name when it
   is missing. **Residual, recorded:** the compose itself still resolves an empty
   `ZO_ROOT_USER_PASSWORD` if the key disappears from both env files; the new
   assertion is what catches that, and the Java-side `SecretGuard` covers the
   Arrow keys, not this OpenObserve password.
5. **Scope:** the three ladder modules plus the approved one-line script default.
   The upper rungs (wave 50-51 modules) contain similar host-published-port and
   healthcheck checks and are **not** audited by this wave.

## Follow-up (post-commit)

The whole-tree sweep run after this wave's commit found two failures in
`test_compose_form_contract` — both caused by this wave, both test-only:

1. That contract scans every non-comment line for `docker compose <verb>` and
   requires each hit to be a registered invocation site. Two prose additions of
   this wave — the `literal_secret_settings` docstring in
   `test_08_local_compose_l0.py` and the new guard module's header — matched the
   pattern and were reported as unregistered sites. Both now say "compose config"
   without naming the CLI.
2. Rewriting CONFIG-005's docstring removed the prose site that the registry row
   `'config must not leak secret values'` classified, leaving that row dead. The
   row is deleted; the CONFIG-001 row stays and still matches.

Fix: 3 files, +2/−3. Evidence: `test_compose_form_contract` `Ran 5 tests ... OK`
(gate runner) and `5 passed` (pytest); the four wave-49 modules unchanged at
`74 passed`.

Recorded rather than just fixed, because it is a trap for any new test module: a
docstring, comment-continuation or message line naming the compose CLI is
indistinguishable from an invocation to that contract. Write "compose config", or
add a `TEXT` row to `SITES` — never add compose-talking prose and leave the
registry unaware of it.
