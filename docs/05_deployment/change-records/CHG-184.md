# CHG-184 — a failed table purge stops the measurement run (wave 36)

- **Status:** recorded — removes the limitation filed in CHG-154
- **Filed:** 2026-09-16
- **Source:** P6-102 (wave 36, ops/scripts/tests/chaos audit) against
  `code/01_platform/04_scripts/holistic-measure.sh`. The record reconciles the
  `ALLOW_STALE_TABLE` limitation that **CHG-154** filed as gate behaviour:
  *"a failed purge refuses without ALLOW_STALE_TABLE (holistic-measure.sh opts
  in explicitly; the smoke gate catches a failed CREATE)"*.

## What happened

`pipeline_purge_table` fails closed by default: when the purge does not report
`PURGED` and `ALLOW_STALE_TABLE` is not `true`, it calls `pipeline_fail` and
returns 1 (P6-148, CHG-154). `holistic-measure.sh` **opted out of that
protection unconditionally** — `export ALLOW_STALE_TABLE=true` at line 53 —
because the smoke gate was expected to catch a failed CREATE.

The opt-out was recorded in CHG-154 as a deliberate caller decision, with
`compatibility_class: COMPATIBLE_WITH_LIMITATION`. That limitation is now
removed, because it defeats the postcondition it relies on:

* the raw table is what the freshly submitted job replays **from EARLIEST**, so
  an unpurged table injects every previous run's rows into this run's window;
* the numbers that come out are plausible and wrong — a *measurement* failure,
  which the smoke gate does not detect: a pipeline can create the table and
  stream previews happily while replaying stale rows;
* the recorded mitigation ("the smoke gate catches a failed CREATE") therefore
  does not cover the failure mode the opt-in admits.

Because the caller had opted in, the library fell off the end of
`pipeline_purge_table` and returned **0** on a failed purge, so the caller's own
`pipeline_purge_raw_table || true` was unreachable code. Both halves had to
change together: removing either one alone leaves behaviour identical
(verified — restoring either alone is caught by the wave-36 suite as a
regression).

**Gate effect.** The run now refuses to measure on a stale table instead of
proceeding, and the refusal reaches the phase result (`return 1`) rather than
being swallowed. An operator who deliberately accepts stale data can still opt
in by setting `ALLOW_STALE_TABLE=true` in their own environment — the line is
**deleted** rather than set to `false`, precisely so that opt-in keeps working
(an explicit `export ...=false` here would override it).

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) is led
by *Execution gate or approval behavior*. `ALLOW_STALE_TABLE` is an
approval-to-continue-when-the-precondition-failed switch sitting in front of a
measurement phase: removing it changes whether the system may proceed. The
precedent is the same axis — `CHG-174` (the `bench-throughput.sh` gate, the
sibling harness) carries `scope: gate-behavior`, and `CHG-176` uses
`measurement-gate`.

The *Active decision* trigger does **not** fire: the opt-in was never recorded
in `docs/01_project/04-decisions.md` (`grep ALLOW_STALE` is empty there), so
there is no active decision to reconcile.
