# CHG-195 — dead compute identifiers removed from the capture list and the seeded dashboards (Task 3)

- **Status:** recorded — Task 3 of `docs/plans/2026-09-17-compute-identifier-parity.md`
- **Filed:** 2026-09-17
- **Source:** found by `code/01_platform/04_scripts/tests/test_compute_identifier_parity.py`
  (the new static parity suite): leg 1 ("no script names a dead identifier") failed with
  39 findings, and the by-hand sweep it prompted found a fourth site the scanner does not
  cover — the seeded dashboard corpus.

## What happened

The class is CHG-191/193/194: a topology cutover retires an operator or a metric, touches
no file under `code/01_platform/04_scripts/` (or the dashboard corpus), and every
downstream gate keeps asking for a name that no longer exists. Nothing errors. A gate
compares `0` with `0` and passes, a dashboard tile renders empty, an alert binds to a
stream that is never written.

Reproduced statically, without a live run:

| Site | Dead references | Evidence |
|---|---|---|
| `stage-capture.sh` requested-name list | 22 | 15 s candle window, forming-bar, 1 s preview, old signal LOG/KV sinks — all retired by the 2026-09-05 cutover; none of the names appears in any `.counter()/.gauge()/.histogram()` in `02_compute/src/main/java` |
| `o2-provision.py` dashboard tiles | 8 lines (7 panels) | `compute_candles_late_updates` ×2, `compute_signals_detected`, `compute_dedup_state_count` ×2, `compute_dedup_state_bytes_estimate`, `compute_kv_filtered_noncanonical` ×2 |
| `openobserve/dashboards/*.json` (seeded corpus) | 3 | `dedup-state.json` (2), `compute-decision.json` (1) — same two dedup gauges |

The third row is the one worth noting: `seed_dashboards.py` pushes that corpus into O2, so
those panels were live, and the parity suite never looked there — its scan root is
`04_scripts`. The 39 the suite reported were therefore an undercount of the class, not the
whole of it.

Two of the findings are *not* drift and were deliberately left alone (below).

  - Deleted with no successor: `Signals detected`, `Dedup state count` (×2),

- `code/01_platform/01_docker/openobserve/dashboards/dedup-state.json` — the two empty

- `code/01_platform/01_docker/openobserve/dashboards/compute-decision.json` — the dead

## Why delete rather than repoint, per name

Java source is the authority: `FingerprintDedupFunction` registers exactly
`compute.dedup.first` and `compute.dedup.duplicates`, and its live-entry count
(`totalEntries`, the G-DEDUP-2 guard) is an internal field, not an exported gauge. So
`compute.dedup.state.count` / `…bytes.estimate` have no producer and no successor, and
repointing the "Live dedup entries" gauge at a cumulative firsts counter would have been a
false claim. The same check removed `Signals detected` (its live successor is the dynamic
per-rule `strategy_host_emitted_<rule>` family, which is not a single stream).

Each deletion was confirmed against the source that would have to produce it before it was
made — an unverified "dead" verdict pointed the other way deletes a working panel.

## Deliberately NOT changed

1. `compute-decision.json` panel **C04** (`Decision p99 — trigger tick → immutable
   decision`, stream `compute.decision.latency.p99`). It has no producer anywhere in the
   repo, but that is design, not drift: `SIG-PERF-001`'s p99 decision-latency half is
   `NOT_IMPLEMENTED` (`docs/02_requirements/09-acceptance-matrix.md` AC-NFR-002). It is a
   labelled placeholder for a pending emitter, so it stays — with that status now recorded
   in the panel description and in the manifest `measurement_boundary`.
2. `openobserve/dashboards/position-state.json` — the scan flags 5 more stream names
   (`compute_signal_passed`, `…dropped_active_exists`, `…active_count`,
   `…cleared_closed`, `…cleared_admin`, in 4 panels) that belong to the retired
   active-signal lifecycle. Whether the lifecycle itself is retired or merely renamed is
   **not** established, and unlike the dedup gauges these panels may be the only
   observability for a live subsystem. Reported, not deleted — see Remaining.

## Residual limitation

The parity suite still scans only `code/01_platform/04_scripts`, so the seeded dashboard
corpus and `openobserve/` are outside its reach — the 4 `position-state.json` findings above
were found by hand, not by the suite. Extending the scan root (or adding the corpus to the
suite's reference set) is the follow-up that closes the class rather than this instance.

Two counts to keep honest: `stage-capture.sh` still requests the 9 cross-job names
(`babysitter.positions.*`, `rows.*`, `transitions.applied`) that belong to the
BabysitterJob/SafetyHaltJob graphs and can never appear in a SignalJob capture; they are
retained deliberately and now recorded per-sample as `present=no` in the capture's
`metric-availability.tsv`, so the absence is stated rather than implied.
