## Why

CHG-331 attempt 2 enabled the gateway projection intake and it failed closed at offset 0:
`invalid Execution_Intent at offset 0: invalid instruction_id`, `/readyz` 503. The producer
(`ExecutionIntentBuilder`) mints `ei-v1-` + sha256 hex (70 chars, content-addressed) while the
gateway `IntentValidator` (P3-094) allowed `[A-Za-z0-9_-]{1,64}` — so every real
compute-written intent was unreadable and the first live row halted the gateway. No test
crossed the service boundary: compute's B4 e2e writes rows without validating, and the
gateway's own e2e hand-crafts short ids (`halt-instr-0001`), so both suites stayed green
while the deployed path was dead. Operator picked option A (widen the validator), keeping
the canonical content-addressed id and the existing live rows.

## What changed

| Piece | Change |
|---|---|
| `IntentValidator.java` | `INSTRUCTION_ID` = `^(?:ei-v1-[0-9a-f]{64}\|[A-Za-z0-9_-]{1,64})$` — canonical form OR bounded client id; used for `instruction_id` and `supersedes_instruction_id` |
| `IntentValidatorTest` | +3: canonical id accepted, canonical `supersedes_instruction_id` accepted, non-canonical (65-char client id / 63-hex / uppercase-hex) rejected |
| `ExecutionIntentBuilderTest` | +1: emitted id is 70 chars and matches `ei-v1-[0-9a-f]{64}` |
| `test_instruction_id_contract.py` (new) | extracts the builder prefix and the validator regex from the production sources and asserts compatibility (canonical accepted, client ids accepted, non-canonical rejected) |
| `05-execution-core.md` | §Flink/Fluss to Nautilus documents the grammar and the cross-service pin |

## Safety

- Fail-closed is unchanged for everything non-canonical: the client bound stays 64, uppercase
  hex is rejected (the minted form is lowercase), and `supersedes_instruction_id` uses the
  same pattern.
- The live `Execution_Intent` rows (9 compute-minted `ei-v1-` ids) become readable. The
  gateway's HALTED gate still defers them — no order — until a signed approve; in the paper
  drill the approve turns them into fake orders, exactly the replay behavior CHG-332
  documented. No data migration, no DDL change.
- The executor side imposes no id length cap (only non-empty), and the Arrow `remarks`
  bound applies to the derived 14-hex `client_order_ref`, not to `instruction_id`.
