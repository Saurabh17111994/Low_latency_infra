# CHG-135 — The durable attempt and gate stores exist, and the flags select them

- **Status:** recorded — the Rust executor gains the durable clients D1/D2 promised (default OFF)
- **Filed:** 2026-09-14
- **Source:** workstream D items D1 (atomic `try_claim` + key layout) and D2 (a HALT must create the
  gate row), carried as deferred in `WAVE3-IMPLEMENTATION-HANDOFF.md`

## What happened

Three claims in the code were true and disagreed with each other:

1. `config.rs` parsed `DURABLE_GATE_ENABLED` / `DURABLE_ATTEMPTS_ENABLED` /
   `DURABLE_JOURNAL_ENABLED` / `DURABLE_AUDIT_ENABLED` strictly, with the comment that an operator's
   failed attempt to enable one "must not pass unnoticed" (P3-434);
2. `durable.rs` recorded that the flags were "read by nothing" (P3-192) — an all-ON bundle was
   behaviour-identical to an all-OFF one by construction;
3. `executiongate.rs` stated the atomicity contract (P3-201) and the gate-row rule (D2) as
   *requirements on a store that did not exist*, with `durable.rs`'s test module recording the gap
   (P3-438): no in-memory test can model a process restart.

So an operator could set every durable flag and get in-memory stores, and a HALT on a partition with
no gate row wrote nothing and returned `Ok(())`.

## What changed

**D1 — the atomic claim, as an entry point, not a comment.**

`AttemptStore::try_claim(attempt_id, instruction_id, request_hash, client_order_ref)` —
classify + claim in one call, returning `Claimed(Attempt)` / `Existing(Attempt)` / `Duplicate` /
`ContractViolation`. It replaces the `get` → `has_duplicate`/`has_instruction` → `put` sequence in
`ExecutionGate::execute`, and the key layout it fixes is stated on the trait: `attempt_id` primary,
`(instruction_id, request_hash)` unique, a different hash under an existing `instruction_id` is a
contract violation. A durable implementation must perform classification and insert as one durable
operation.

Behaviour preserved, which is the point of the refactor: the four classifications are the same four
outcomes `execute` produced before, including "duplicate beats contract violation" when both apply.
The pre-existing 307-test suite passes unchanged, and the crash-exactly-once integration decorator
(`tests/crash_exactly_once.rs`) records the claim from `try_claim` as well as `put`, so its
one-record-per-instruction assertion still measures what it names.

**D2 — a deliberate halt creates the row; an incidental halt still does not.**

`GateStateStore::init(row)` — create-if-absent, existing row returned untouched (Java
`GateStateStore.init` parity, P3-151). It is *not* wired into `ExecutionGate::halt`, deliberately:
the halts inside the gate are raised **because** no row vouches for the partition
(missing/corrupt/unreadable), and inventing a row there would give a state that nothing established
an epoch and a fence token — which is exactly what the gated contract
`exe_fail_003_missing_corrupt_blocks_calls` asserts must not happen. The create belongs to the boot
path: with the gate flag on, the executor creates its partition's row HALTED and unbound, and never
clobbers a fenced row on restart.

**The store: file-backed, no new dependency.**

`src/durable_file.rs` — `FileAttemptStore` (`attempts.jsonl`) and `FileGateStore` (`gate.jsonl`),
one JSON record per line, `write_all` + `sync_data` before any call returns, replay on open, latest
record per key wins. Two failure shapes are read differently on purpose: a torn **final** line (the
process died inside its own append, so no caller proceeded on it) is dropped with a warning, while a
corrupt line anywhere else, or an unreadable file, is a hard error — reading "unavailable" as
"absent" is the fail-open shape the Java store documents. Each store takes a pid lock file and
refuses a log whose lock names a live `/proc` entry (one actor per log, P3-201); a lock whose process
is gone is taken over so a `kill -9` cannot make the service unstartable.

**The plumbing.** `DurableClients::open_for_service(dir, flags, partition)` builds the flag-selected
stores and is called by `main` before the health server starts; `DURABLE_DIR` (new, default
`data/durable`) names the directory, `EXECUTION_PARTITION_ID` (already in compose) names the owned
partition and is required exactly when the gate client is durable. `DURABLE_JOURNAL_ENABLED` and
`DURABLE_AUDIT_ENABLED` are **refused** at boot: those two clients have no durable implementation
yet, and a quiet in-memory stand-in is what this change exists to end.

## What this does and does not mean

Compatibility is `COMPATIBLE`: every durable flag defaults OFF, flag-OFF behaviour is pinned by tests
(no store file is created) and the live order path is unchanged.


An enabled flag now means the matching store is the file-backed one, opened and validated at boot,
with the boot failing loudly if it cannot be. It does **not** mean the live order path is durable:
`ExecutionGate` is still constructed only by tests, so the attempt store's live caller remains the
Workstream-D swap. That boundary is stated on the module header and in the boot log line rather than
left to inference.

## Defect found by the live smoke, not by the tests

The first live run of the flag path failed: the pid lock was written before the log created its
directory, so every first start with a fresh `DURABLE_DIR` died with
`writing lock …: No such file or directory`. The unit tests missed it because every test created its
scratch directory first. Fixed by creating the parent directory in both paths, with a test that opens
a store under a path that does not exist yet.

## Rollback

No flag is enabled anywhere by this change, so the default deployment is unaffected: rollback is
`git revert` of the commit, which restores the flags to inert. If a future operator has enabled the
flags, the durable directory is plain JSONL and can be inspected or removed without a migration.
