# CHG-547 — `Signal_Candidates_current` orders writes in the tablet (versioned merge engine)

- **Status:** implemented (DDL + ingestion bootstrap + job startup contract + dev
  table recreated and probed). Production/replicated tablets apply it by
  recreating the table in their own window — the option is create-only.
- **Filed:** 2026-10-04
- **Source:** the KV current-row table carried **no ordering guard** by design
  (`23_signal_candidates_current.sql` header, P4-070/224: "last-writer-wins on
  `instrument_token` with NO ordering guard in the sink"). A delayed or retried
  write therefore replaced a newer row. Keying the table by `candidate_id` was
  tried and reverted on 2026-08-13 (DEC-035) because readers need one current row
  per instrument. That left two options: a Flink deduplicate / row-number stage
  (job state, checkpoint cost, per-writer discipline) or enforcing the order
  where the row is stored. Fluss 1.0 ships the second one.

## What changed

One table, one option pair, kept in agreement in three places:

```sql
'table.merge-engine' = 'versioned',
'table.merge-engine.versioned.ver-column' = 'evaluation_ts',
```

- `code/01_platform/02_sql/ddl/23_signal_candidates_current.sql` — the two options in
  the `WITH` block, plus the `-- Staleness (P4-070/224)` header paragraph rewritten:
  the tablet now drops a strictly older version, an equal version keeps the newer
  write, and the two timestamp columns must be non-null on every write. The rest of
  that paragraph (the P4-224 timestamp-unit contract) is unchanged.
- `code/02_services/01_ingestion/src/main/java/com/trading/ingestion/DdlBootstrap.java`
  — the same two values as `.property(...)` on the `Signal_Candidates_current`
  descriptor, so the dev table is created with the ordering guard (DDL and bootstrap
  were already pinned equal by `DdlBootstrapSchemaAgreementTest`).
- `code/02_services/02_compute/src/main/java/com/trading/compute/signaljob/TableContractValidator.java`
  — `validateSignalCurrentKvTable` now also calls `validateVersionedMergeEngine`: the
  job refuses to start when the live table is not versioned on `evaluation_ts`,
  instead of silently writing into a table that can clobber a newer row.

## Semantics (read from the server's own bytecode, not from docs)

`org/apache/fluss/server/kv/rowmerger/VersionedRowMerger.merge(oldValue, newValue)`
decompiles to:

```java
if (oldValue == null) return newValue;
return versionComparator.compare(oldValue.row, newValue.row) > 0 ? oldValue : newValue;
```

so: older incoming version -> **ignored, no exception raised** (nothing new for a
writer to handle); equal version -> the incoming row wins; newer -> the incoming row
wins. The version column must be `INT`, `BIGINT`, `TIMESTAMP` or `TIMESTAMP_LTZ`
(`evaluation_ts` is `BIGINT NOT NULL`). The engine rejects `DELETE` and partial
updates; this table's writers do neither (full-row upserts only, and the current row
is never deleted — staleness is superseded by the next signal).

This is not a new pattern here: `Execution_Gate` already runs the versioned engine
(`code/01_platform/02_sql/ddl/11_execution_gate.sql`, version column `fence_token`,
CHG-122) with a live drill in `GateMergeEngineDrillIntegrationTest`. The repair tool
`code/01_platform/04_scripts/fluss-repair/GateTableAdmin.java` was generalized from
"pinned to `fence_token`" to "any versioned table" so it can recreate this table too;
the `fence_token` pin stays covered by the gate DDL and the gate drill.

`Admin.getTableInfo` before the recreate:

```text
DROP OK: default.Signal_Candidates_current
CREATE OK: default.Signal_Candidates_current (VERSIONED on evaluation_ts)
+ table.delete.behavior=IGNORE   + table.kv.value-layout-version=1
+ table.merge-engine=versioned   + table.merge-engine.versioned.ver-column=evaluation_ts
```

The recreate ran while no `signal-job-compute` job was RUNNING (checked with
`/jobs/overview`). It also answers the precondition the plan held open: the catalog
**does** surface these properties on `TableInfo`, so the startup contract cannot fail
spuriously against a correctly created table.

## Not changed

- **Schema, types, bucket count and `table.log.ttl=7d`** — untouched; only merge
  behaviour changes. `raw_table_1`, `candle_features`, `Signal_Candidates` (the LOG
  twin) and every other table keep their current engines.
- **No Flink dedup state.** `StrategyHostFunction.emittedIds` keeps its bounded
  per-ledger suppression; the tablet guarantee is additive and holds for any future
  writer.
- **`Position_State` and the gateway projections are deliberately out of scope:**
  they are written with partial updates, which the versioned engine rejects. They
  need full-row upserts first — a separate change, listed in
  `docs/plans/2026-10-04-signal-candidates-current-versioned-merge.md` §3.

## Open

Q1 (**answered 2026-10-04 by measurement**): a *rejected* stale write **does** still
append one changelog record — it reaches the log and is dropped at apply time. An accepted
update appends two (`UPDATE_BEFORE` + `UPDATE_AFTER`), so the guard halves the changelog
cost of the out-of-order/retried writes it rejects rather than removing it. Method and
numbers: `logs/tracker-14/20261004-chg547-versioned-merge-apply.md` and §10 Q1 of
`docs/plans/2026-10-04-signal-candidates-current-versioned-merge.md`.

Planned separately (not this change): production and the second tablet are untouched — the
option is create-only, so each needs its own recreate window (runbook section added) — and
the same engine for `Position_State` and the gateway projections is blocked until those
writers move from partial updates to full-row upserts.
