# CHG-197 — O2 alert thresholds tied to their constants; checkpoint-slow fired at 10× the relation

- **Status:** recorded — fixed, guarded, live rule re-provisioned, and fire-proven end-to-end (2026-09-17)
- **Filed:** 2026-09-17
- **Source:** the Post-Completion note of `docs/plans/2026-09-17-compute-identifier-parity.md`
  predicted the identifier-drift class recurs one level up in the *values*: nothing tied
  O2 alert setpoints to the constants they assume. Building the guard found the drift
  before the guard even landed.

## What happened

`o2-provision.py` hand-copies the numbers behind its 47 alert rules from constants that
live in Java (`AlertThresholds`, `PlatformConfig`), the compose pin, the ingestion alert
contract (`02-ingestion-alerting.md`), the runbook table and the observability doc. No
mechanism joined the sets, so a constant change in Java touches no file under
`04_scripts/` and every consumer keeps firing at the stale setpoint. An alert that fires
at the wrong level is the same failure class as an alert that never fires (CHG-191):
silent, and only visible as a wrong verdict in an incident.

Found by the first run of the new suite:

| Rule | Fires at | Authority says | Verdict |
|---|---|---|---|
| `SIGNAL-error-checkpoint-slow` | **240 000 ms** | 80% of `PlatformConfig.CHECKPOINT_TIMEOUT_MS` = 30 000 ms (compose pins `"30000"`); runbook quotes **24 000 ms** twice (L372, L519); the rule's own desc claimed "= 80% of pinned CHECKPOINT_TIMEOUT_MS=300000" — a value that exists nowhere in the repo | **drift, fixed** → 24 000 |
| `SIGNAL-warn-dedup-state` (runbook row) | "> 6.5M entries on `compute_dedup_state_count`" | The rule was repointed 2026-08-28 to `flink_jobmanager_job_lastcheckpointsize` > 1.5 GB (in-rule comment); the dead series name is gone from the live rule | **doc-side drift, fixed** |

## What changed

- `code/01_platform/04_scripts/o2-provision.py` — `SIGNAL-error-checkpoint-slow`
  threshold 240000 → **24000**, desc restated against
  `PlatformConfig.CHECKPOINT_TIMEOUT_MS=30000`.
- `code/01_platform/04_scripts/tests/test_alert_threshold_parity.py` — **new suite,
  15 tests, 0.17 s, fully static**. Same design as the identifier suite (stage 1):
  hand-maintained expected rows with provenance anchors re-read at test time; actual
  setpoints extracted from the `ALERTS` list via `ast` (fail-closed on non-evaluable
  expressions); a completeness leg requiring every rule to be pinned or explicitly
  exempted (absence-triggers with no tunable setpoint), and pruning exemptions whose
  rule disappears. Coverage: Java-constant relations (checkpoint-slow = 80% of the
  pin; JM heap 900 MB ≈ 0.85 × 1 GiB; container-memory 85 shared with the JVM gate;
  60 s breach window), the 9 INFRA rows vs `10-observability.md`, the 8 contract-quoted
  ING setpoints **including evaluation periods**, the runbook-quoted SIGNAL setpoints,
  the 2026-08-28 dedup repoint, and the position-state JSON corpus.
- `docs/06_operations/01-runbooks.md` — `SIGNAL-warn-dedup-state` row corrected to the
  repointed series and threshold (the old row still advertised `compute_dedup_state_count`
  > 6.5M — the series CHG-195 established has no producer).

## Residual limitation

The fire-proof above proves the corrected setpoint fires and stays silent on the right
side of the boundary, through the real delivery chain (collector → O2 rule → dev-webhook
→ durable consumer record). It was a synthetic gauge, not a real slow checkpoint; the
JVM-side value source is the Flink JobManager metric, which only exists while a job runs.

Two operational notes discovered during the fire-proof, kept for the next operator:

* O2 metric-stream search requires `GET /api/default/_search?type=metrics`; the same
  query without `type=metrics` answers 400 "Search stream not found" even for streams
  that exist and hold rows (`perf_evidence_parse.py` already does this correctly).
* Test artifacts left in O2: one injected row in `flink_jobmanager_job_lastcheckpointduration`
  (50000.0) and a `fireproof_probe_gauge_xyz` stream — harmless, age out with the
  90-day metrics retention, but they can be deleted by hand if a clean pane is wanted.
