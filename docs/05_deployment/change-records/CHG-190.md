# CHG-190 — the purge waits for the write path, and the fingerprint cross-check compares like with like (wave 36)

- **Status:** recorded — fixes two pre-existing defects found during wave 36
- **Filed:** 2026-09-17
- **Source:** found while running the wave-36 acceptance run of
  `code/01_platform/04_scripts/holistic-measure.sh`. These are the layers behind
  CHG-185/186/187/188/189: with those fixed the harness reached ingestion and job
  submission, and failed at each in turn.

## Defect 1 — a purge returned before the table's write path served (P6-485)

### What happened

`pipeline_purge_table` cleared the table and returned. The harness then spent
~35s starting faketool + the ingestion container, and ingestion's *first append*
died:

```text
22:01:13.520 fluss: connecting (bootstrap=fluss-coordinator:9123, table=raw_table_1)
22:01:43.528 WARN MetadataUpdater - tabletServer fluss-tablet:9124 (id: ts-0) is unavailable for updating metadata for retriable exception
22:01:43.528 WARN MetadataUpdater java.util.concurrent.TimeoutException
22:01:50.917 fluss: connected
22:01:51.355 ERROR RawTickWriter - raw-writer: FATAL append error (table=raw_table_1, class=FlussRuntimeException)
22:01:51.356 ERROR IngestionService - ingestion: FATAL append: FATAL: Failed to update metadata
```

The server side shows why: the purge at 22:01:07 dropped the day's partition, and
the tablet was still deleting that partition's buckets for the next ~43 seconds
(`Deleted table assignment for partition ... 22:01:29` and `... 22:01:50`, 32
"Deleted log bucket" lines, 2 "Drop empty partition dir"). During that window the
bucket leaders are gone, so any client asking the leader anything gets
`NotLeaderOrFollowerException` / `Failed to update metadata`. The preflight
readiness probe cannot see it: it calls `getTableInfo`, which the coordinator
serves **without** a bucket leader, so the table reads as ready the whole time.

### The fix

The purge no longer returns until the write path answers for the table it just
cleared. `TablePurge` polls `listOffsets` (served by the bucket leader) for every
bucket of every partition — the cheapest read-only way to ask "would an append
work right now?" — backing off 2s, bounded by `PURGE_SETTLE_TIMEOUT_S`
(default 120s). It prints `SETTLED <table>`, or
`WARN: write path still not serving ...` when the budget runs out, and the shell
side reports which of the two happened.

### Verification

* **A/B on the live cluster, 400-row seed, one purge each:**
  * gate disabled (0s): `WARN: write path still not serving ... (NotLeaderOrFollowerException: server 0 is not leader or follower for TableBucket{tableId=7063, partitionId=395, bucket=1})` and the immediate append → `APPEND_FAIL java.util.concurrent.TimeoutException`.
  * gate enabled: `SETTLED`, purge took 32s, the same immediate append → `APPEND_OK`.
* Matches the earlier timeline measurement (purge → `listOffsets` failing t+0s…t+40s, recovered t+44s) and the window that killed the run above (purge → append at t+44s).
* An empty table still settles immediately (2s purge), so the gate is semantic, not a fixed sleep.

## Defect 2 — the bridge fingerprint cross-check compared two different schemes (P6-486)

### What happened

`IngestionService` compares each bridge event's `manifest_fingerprint` against
Java's `InstrumentManifestLoader.computeFingerprint` — a digest over token **and**
tradingSymbol/exchange/segment/lotSize. The bridge never sees those four fields:
the G3 handoff (`IngestionService.startBridge`) passes it
`ARROW_INSTRUMENT_TOKENS`, i.e. tokens only, so its `manifest_fingerprint` is
`tokenSetHash(allTokens)` — the same token-only scheme as
`assigned_token_set_hash`. The two were therefore never equal, on any run, on
identical token sets:

```text
ingestion: bridge manifest_fingerprint mismatch (slot=hft-0, epoch=1):
  got=4914b8f19735648e95e41264ead23e95a7edfa7d65920475e1fc52b0ad9f1adf
  want=c68f50f7f716b1d453a13cbce1bf5fa3e565f40eacaa30ff13496547f8ae146d
```

Reproduced from the run's own 1024-token slice: Go's `got=` and Java's
`computeAssignedTokenHash` both equal `4914b8f1…` (exact match), while
`computeFingerprint`'s `c68f50f7…` covers fields the bridge is never given. Every
subscribing run logged exactly 4 such lines (one per slot event) and the G8 gate
in `holistic-measure.sh` fails the run for them.

### The fix

`IngestionService` now compares the bridge's `manifest_fingerprint` against
`assignedTokenSetHash` — the digest both sides can actually compute over the
tokens the bridge was handed. The manifest-level drift check is unchanged and
still fail-closed, one level up, in
`InstrumentManifestLoader.isManifestApproved` (version + count +
`computeFingerprint` against the approved manifest). The Go comment claiming
byte-identity with `computeFingerprint` is corrected.

### Verification

* Both hashes recomputed in Python from the failing run's own token slice: the
  values match the `got=`/`want=` in its log exactly, proving the divergence is
  the scheme, not the data.
* Shared cross-language vector: `tokenSetHash({3,1,2})` is asserted against
  `ca73761ddabfffcbe51170be0b07f67bafcdbed202545c60707573d36dc935b4` in
  `go-bridge/subscription_plan_test.go` **and** in `SafetyHaltWriterTest`, so the
  two implementations can no longer drift apart silently.
* `mvn -pl 02_services/01_ingestion -am test`: 471 tests, 0 failures, 0 errors.
* `go test ./...` in `go-bridge`: passes.

## Why this is a change record

The trigger list in `docs/08_implementation/01-foundation.md` (L323-336) includes
*Deployment topology* — the settle gate changes how the harness sequences a purge
against ingestion start, and the cross-check changes the ingestion image's
behaviour. Both affect what a measurement run accepts as valid evidence.
