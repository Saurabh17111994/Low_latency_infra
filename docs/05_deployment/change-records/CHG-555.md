# CHG-555 — a second, independent in-flight/terminal pair in `RawTickWriter` (OQ9 localiser)

- **Status:** implemented (diagnostic instrumentation only; no behaviour change on any path).
- **Filed:** 2026-10-07
- **Source:** OQ9 of `docs/plans/2026-10-06-p99-integrated-program.md`. The 90 s single-JVM arm
  (`logs/tracker-14/20261007-oq9-identity/`) showed that `AppendTracker`'s own identity is **exact**
  (`accepted - appended - failed - pending == 0` at 9/9 flushes, and the shutdown journal drains
  594 → 0 with `total_failed` 0) while the *same* run's `append.latency.ms` histogram count equals
  `tick.throughput` exactly at every flush (145 169) and not the completion count (144 508). Two
  instruments on the same events differ by 661, and the deployed bytecode (`javap` of
  `pipeline-loadgen:1.0.0`'s `/app/ingestion.jar`) proves the sample counter can only be incremented
  by a terminal outcome — i.e. by the same code path that releases the tracker slot. The existing
  instruments therefore cannot adjudicate which one is wrong; a third, counted *inside the
  submit/completion funnel itself*, can.

## What changed

1. **`RawTickWriter`**: two `AtomicLong`s, `writesInFlight` and `writesCompleted`. In-flight is
   incremented in `submitAppend` **on the first attempt only** (`attempt == 1`) — a retry re-submits
   the same record and must not be counted twice. Both are updated once per record in
   `completeOutcome`, the single funnel every terminal outcome passes through, and **outside** its
   shutdown gate: a late completion after `close()` is correctly not delivered to the listener, but
   it must still release its slot or the two counters would drift apart from each other. Two
   read-only accessors were added next to `appendCount()`.
2. **`OtlpMetricsEmitter`**: two new gauges, `append.inflight.records` and
   `append.completed.records`, published beside the CHG-553 tracker counters, plus
   `setWriterCounters(long, long)`.
3. **`IngestionService`**: published from the same per-tick site as the other append counters (two
   `AtomicLong` gets; no new hot-path work beyond that).
4. **Parser**: `logs/tracker-14/20261007-oq9-identity/parse_identity.py` gained the two columns plus
   the histogram count and its deltas against `appended` and `ticks`, so one run shows all three
   instruments side by side.

## How the result is read

| reading | conclusion |
|---|---|
| writer in-flight **≈ 0–20** while `append.pending.records` stays ~600 | the tracker over-counts: its release path is not paired with its reservation |
| the two **agree** (~600) | the tracker is right, and the histogram's count (which tracks ticks) is the broken instrument |
| `append.completed.records` vs `append.appended.records` | isolates the tracker's release count from the histogram's sample count independently |

## What deliberately did NOT change

* **Not** `AppendTracker` itself — the identity it reports is exact, so its arithmetic is not the
  suspect; changing it would destroy the instrument that produced the finding.
* **Not** the latency histogram, its percentiles or the 1 024-sample ring (the ring is a separate,
  already-recorded defect: the percentiles are a ≈0.63 s snapshot, not a 10 s window).
* **No DAG, DDL, table, connector or client-configuration change**; no new always-on subsystem, no
  `make gate` step.
