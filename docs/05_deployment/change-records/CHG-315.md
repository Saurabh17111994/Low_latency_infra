# CHG-315 -- raw-source fetch/flush latency tuning (S5→S6)

- **Status:** recorded -- landed 2026-09-26 (smoke + 900 s full-universe run green)
- **Filed:** 2026-09-26
- **Source:** the stage profiler (CHG-314) measured S6
  (`raw_table_1 → Flink post-dedup`) at p50 316 ms against S5 (ingestion e2e)
  27 ms at 48.4k rows/s, while every Flink operator sat 88–95 % idle, backpressure
  ≈ 0 and the source held a 600–960-record standing backlog. The cost was
  cadence, not compute: Fluss's default scanner fetch chunk (16 MiB request /
  1 MiB per bucket / 500 ms wait) and Flink's default output-buffer flush
  timeout (100 ms) at every shuffle hop.

## What changed

| knob | old (default) | new | set in |
|---|---|---|---|
| `execution.buffer-timeout` | 100 ms (Flink) | **10 ms** | `SignalJob.applyRuntimeOptions` (typed `ExecutionOptions.BUFFER_TIMEOUT`) |
| `client.scanner.log.fetch.max-bytes` | 16 MiB (Fluss) | **512 KiB** | `SignalJob.flussSourceConfiguration` (typed `ConfigOptions` via `setFlussConfig`) |
| `client.scanner.log.fetch.max-bytes-for-bucket` | 1 MiB (Fluss) | **128 KiB** | same |
| `client.scanner.log.fetch.wait-max-time` | 500 ms (Fluss) | **20 ms** | same |

Env seam (declared in `ConfigKeys`): `BUFFER_TIMEOUT_MS`,
`FLUSS_SCANNER_FETCH_MAX_BYTES`, `FLUSS_SCANNER_FETCH_MAX_BYTES_FOR_BUCKET`,
`FLUSS_SCANNER_FETCH_WAIT_MAX_TIME_MS`. Defaults carry the tuned values (the
fix is the default, not a flag); `perBucket > maxBytes` fails closed.

## Measured effect (full 2 433-instrument universe @ 20 Hz)

- S6 p50 / p95 / p99: **316 / 543 / 599 → 27 / 43 / 55 ms** (×11.7 p50).
- Post-dedup throughput: 48 398 → **48 831 rows/s** (parity, not a trade).
- Source `pendingRecords` standing backlog: 1 673 → 0 steady state.
- Tracker hops p50 (dedup / aggregator / live sink / closed sink):
  37–45 / 76–94 / 116–148 / 172–198 → **4–5 / 9–10 / 13–16 / 18–21.5 ms** —
  each hop fell by ~40–50 ms, exactly the buffer timeout's average wait.
- The residual ~1.1 s p99 sink tail is checkpoint-dominated (15 checkpoints in
  900 s, p50 680 ms end-to-end, 60 s interval) — a separate lever, unchanged here.

Smoke evidence `logs/stage-profile-20260926-015049/` (presence gate PASS),
record run `logs/stage-profile-20260926-015722/` (900 s).

## Why it is safe

- Both levers change cadence only, never semantics: the scanner still fetches
  every record in order (just in smaller chunks), and the buffer timeout only
  bounds how long an output buffer may wait before flushing (Flink's documented
  `execution.buffer-timeout`).
- The job was measured > 85 % idle in every operator with zero backpressure and
  a Fluss tier appending at p50 11 ms — the extra fetch requests and flushes fit
  inside the idle budget, confirmed by throughput parity in both runs.
- No topology, UID, serializer, checkpoint or DDL change.
