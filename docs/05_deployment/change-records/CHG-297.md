## Why

The live Arrow app was found on this laptop on 2026-09-21 and classified live by the
operator: the four values in the home-dir env file are real, the local ingestion pipeline
uses them, and value-equality scanning found the same values in the gate's own
`compose-config.log` files, in agent transcripts outside the repository, and — for the
app id — in a tracked document that is therefore published. A copied secret cannot be
un-copied and a published identifier cannot be unpublished, so rotation is the remedy and
deletion is only the cleanup that follows it.

## The names, and the count the runbook got wrong

The runbook listed four values; there are **five** credentials, because `ARROW_USER_ID` —
present in the home-dir file, in the dev `.env`, and in the dev template — belongs to the
same login. The home-dir file also holds `ARROW_TOKEN` and `ARROW_REQUEST_TOKEN`, which are
session tokens the TOTP login mints, not credentials to rotate: they expire on their own,
and the validation step below re-checks that a token minted before the rotation stops
working.

| name | kind | where production takes it |
| --- | --- | --- |
| `ARROW_APP_ID` | identifier, rotates with its app | deck env, `${VAR:?}` |
| `ARROW_APP_SECRET` | secret | Swarm secret `arrow_app_secret`, mounted as `*_FILE` |
| `ARROW_USER_ID` | identifier | deck env, `${VAR:?}` |
| `ARROW_PASSWORD` | secret | Swarm secret `arrow_password`, mounted as `*_FILE` |
| `ARROW_TOTP_KEY` | secret (the login's second factor) | Swarm secret `arrow_totp_key`, mounted as `*_FILE` |

Measured 2026-09-22 while preparing this record: the deck (`docker-stack.yml:43-47`,
`:851-853`, `:870-872`) takes the three secrets through the Swarm secret mechanism and
needs only the two identifiers from the environment; the dev compose file
(`docker-compose.yml:772-776`, `:894-898`) substitutes all five plainly, which is exactly
how the values reached the gate log.

## Limitation

The operator's answer of 2026-09-22 is that this login has **one** consumer, so no second
update is expected before revocation. That is an intention, not yet a measurement, and the
difference lands at exactly one step: revoking the old password. The confirmation is cheap
and read-only — the portal's app list and its device/session list, read before the revoke —
and the class stays `COMPATIBLE_WITH_LIMITATION` until that list has been read. If a
binding turns up there it is a consumer for this purpose whether or not the operator
intends to use it, and it gets updated before the old credential is revoked.

The home-wide value scan (2026-09-22, root `/home/saurabh`, four values) returned **229 hits in
51 files** — 2 in-repo, both in the git-ignored `secrets.env`, 227 outside — over 524,267 files

Two of the measurements changed this record rather than merely illustrating it:

- **229 is a floor.** The run searched four values, and `ARROW_APP_SECRET` exists in two
  versions on this laptop — `~/.env.arrow` and `secrets.env`, both 64-character lowercase hex,
  no shared prefix, neither a placeholder. One string was therefore never searched, so the
  number of copies is not yet known; both strings are treated as live until the application is
  retired.
- **The app id is published** in this repository's history and in two sibling trees' committed
  documentation. It is an identifier, not a secret; the consequence is narrow and firm: step 1
  retires the application, because no file edit can recall a published id.

## Order of work

1. The operator reads the portal's app list and device/session list (read-only) and confirms
   the one-consumer assumption. Anything bound there is updated after the new credentials
   exist and before the old ones are revoked.
2. App credentials first — isolated, no login risk. Per B1 item 2 the market-data app is
   registered fresh with no order rights, and the exposed app is retired rather than its
   secret rotated in place, so the published app id dies with the app.
3. The trading login's password, verified by a fresh login, then TOTP re-enrollment with the
   old binding kept alive until the new one produces a working code.
4. Revocation of the old credentials, after which the validation below runs.
5. Cleanup: the local value file is rewritten with sandbox values (not emptied — the dev
   compose file still substitutes the three names), the two session tokens are cleared, and
   the rotation log's rows are dated.

## Validation

- A fresh portal login with the new password and a code from the new binding.
- Ingestion reconnects under the market-data app and its `ING-*` alerts clear.
- B1's four refusals are re-attempted against the new credentials and the refusals recorded.
- A session token minted before the rotation is rejected.
- C1's scanner in value mode, re-run with the old values: the old values must appear nowhere
  under the repository or the home directory, and the new values must appear nowhere either.
- The rotation log's rows carry the rotation date and the next quarterly date.
