# CHG-213 — Fresh-table replica placement: bounded fixture readiness, and never drop a table whose write is unresolved

- **Status:** recorded — fixed and guarded (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** gate step 9 (`make drill-live`) red again after CHG-212, in the gateway
  module; root-caused from the drill log (289 MB), the coordinator/tablet logs, and
  the repo's own `FlussHandlePool` javadoc.

## What happened

CHG-212 fixed the storm at the two drop sites the *common* module exercises. The
gateway module has the same hazard at two more sites, and its classes also paid
the placement delay CHG-212 measured:

1. **Third and fourth storm sites.** `B4HaltedIntentConsumeDeferE2ETest` wrote to a
   table whose replica was not placed yet (placement head, CHG-212), its write
   budget expired, the record stayed pending inside the writer's `Sender`, and the
   class dropped its scratch database anyway. Result: 115,251
   `TableNotExistException` / `Failed to update metadata` lines, the coordinator
   starved for ~16 minutes, and the next class
   (`FlussProjectionWriterIntegrationTest`) failing at its production 2 s budget —
   after which the class itself hung in `Connection.close()` and died on its own
   120 s preemptive guard.
2. **An unclosable writer.** The repo's `FlussHandlePool` javadoc already states the
   constraint: in Fluss 0.9.1 `Lookuper` exposes only `lookup()` and `TableWriter`
   only `flush()` — there is no `close()`. So an abandoned writer *cannot* be
   closed; the only ways to stop its `Sender` are to keep the table alive or to
   close the connection (which is precisely the hang above). "Never drop a table
   whose write is unresolved" is therefore not a convention but the only correct
   option — and it must hold at every drop site, not just the two CHG-212 fixed.
3. **Fixtures written milliseconds after creation.** `GatewayStartupPrewarmTest`,
   `GatewayFlussDurableReplayIntegrationTest` and
   `FlussProjectionWriterIntegrationTest` each created tables and immediately wrote
   to them, so the first write spent its budget on `NotLeaderOrFollowerException`
   while the coordinator was still placing the replica. That is a fixture-timing
   defect, not a defect in the step under test.

## What changed

- `FlussProjectionWriterIntegrationTest.java` — one shared bounded, logged
  `awaitReady(what, budgetMillis, step)` helper (240 s budget, 500 ms probe
  interval, asserts nothing, prints `[await] ... ready after N attempt(s)`), a
  readiness wait before the prewarm/ledger/projection steps, and a post-write
  "did it land" probe whose failure keeps the scratch DB instead of dropping it
  under a pending write.
- `GatewayStartupPrewarmTest.java`, `GatewayFlussDurableReplayIntegrationTest.java`
  — the same readiness wait before their fixtures are used; the ledger probe is a
  READ lookup on the same bucket, so it adds no rows. Their preemptive guards moved
  90 s → 360 s (a timeout on a bounded fixture wait; the assertions themselves are
  unchanged, and the production 2 s budget assertion is untouched).
- `B4HaltedIntentConsumeDeferE2ETest.java` — readiness wait, `WriteAwait`-guarded
  append, and the scratch DB is KEPT (loud log) when the append is UNRESOLVED.
- `CompatFlussIntegrationTest.java` — all 14 unbounded `finally { flush() }` sites
  replaced with a comment. The acked write IS the visibility guarantee, so the
  flush added nothing but ~10-14 minutes of drill wall-clock and masked timeouts
  (same finding CHG-212 recorded for `DdlSmokeTwinSweepTest`).
- `WriteAwaitTest.java` — the late-resolution case now resolves with real margin
  inside the second wait window (1000 ms against a 750 ms budget; it previously
  completed at exactly 2 x 80 ms, i.e. on the deadline, which failed once in the
  plain suite). One assertion was added, none weakened.
- `WriteAwait.java` — a `retry-exempt-file:` marker with its reason: the class
  exists to wait on an ALREADY-ISSUED future, so routing it through
  `BoundedRetry` would re-issue the write and duplicate the record.

## Verification

- Drill run 2 (`make drill-live`, 19:27 min, `/tmp/drillfull-fixed2.log`): **the storm
  is gone — 0 `TableNotExistException` lines against 115,251 in run 1.** The scratch
  drain completed in 451 s and the apply passed with the same manifest
  (`RESULT=PASS EXIT=0 TABLES=27 MANIFEST=664cd369...`). `GatewayStartupPrewarmTest`
  passes where the de-risk run failed it (`[await] ... ready after 11 attempt(s)`).
  The run stopped in the common module on one new red — the placement head at a fifth
  site: `CompatFlussIntegrationTest.schemaRec001CleanBreakReplay`, first upsert to a
  fresh table, 20.05 s TimeoutException with a clean coordinator log — so the gateway
  module never ran and the two gateway fixes above are verified only by their own
  classes, not yet by a full drill.
- That fifth site is now covered by the readiness probe inside `createTable`, verified
  in a targeted drill-profile run: `[await] compat table compat_test_kv_rec_... ready
  after 1 attempt(s)` (4 KV tables) and `skipped: no primary key to probe (LOG table)`
  (4 LOG tables), 8 tests / 0 failures / 0 errors / BUILD SUCCESS. The first version of
  that probe was a silent no-op (an equality check against `DataTypes.STRING()` matched
  no column), which the run exposed because the skip path logs — the probe now derives
  its value from the column's type root and prints the actual type when it cannot.
- The class's 14 unbounded flushes are gone: 90.6 s in the drill against ~10-14 min
  with them, the single largest non-apply cost of run 1.
- Plain suite: `WriteAwaitTest` 4/4 and `BoundedRetryGuardTest` 1/1 green
  (`mvn -o -pl common test -Dtest='WriteAwaitTest,BoundedRetryGuardTest'`), where
  `WriteAwaitTest` had been failing on its deadline-exact resolver.
- Not yet re-run: the full drill with these last fixes. Gate step 9 is that proof, so
  this record is filed with the drill still to be re-certified.
