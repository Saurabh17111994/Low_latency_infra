# CHG-150 — The Fluss probes report what they could and could not measure

- **Status:** recorded — all 19 wave-13 findings fixed
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 13 ("Fluss probes"):
  P6-080, P6-081, P6-082, P6-083, P6-084, P6-373, P6-374, P6-731 (FlussPrefixReader.java);
  P6-085, P6-086, P6-375 (FlussReadLagProbe.java);
  P6-079, P6-370, P6-371, P6-372, P6-730 (FlussKvProbe.java);
  P6-376, P6-377, P6-378 (FlussRuleCounter.java)

## What happened

All four probes feed the soak/capture evidence chain, and in every one of these findings a probe
could produce output that looked like a measurement while the thing it claimed to measure had not
happened: unfiltered rows read as a filtered sample, a failed connection read as "not reached yet"
by a caller blocking on a sentinel that never came, a truncated log scan read as a complete one, a
capped census read as a full one.

**The sentinel was the worst of them (`P6-080`).** `FlussPrefixReader` prints `__END__ <count>` and
its callers wait for it, but any failure after startup — a refused connection, an unknown table, a
lookup timeout — propagated out of `main` with no sentinel at all. The caller's only way to reach
its own timeout. The sentinel is now printed on every path, including the failure path, which also
carries `__ERROR__` on stderr and a non-zero exit, so "0 rows because nothing matched" and "0 rows
because the probe could not run" are finally different facts.

**Neither filter argument was ever applied (`P6-081`, `P6-084`).** `ws`/`we` were parsed and
discarded, and the LOG branch emitted every row of every bucket regardless of `tokens_csv`, so a
soak comparison of two runs with different windows or token lists compared the same unfiltered data
twice. Both paths now filter, through one `inWindow` helper, and the LOG branch requires an
`instrument_token` column to filter by (it refuses rather than scanning unfiltered).

**The KV key and the row layout were guessed (`P6-082`, `P6-371`).** `lookupBy("instrument_token")`
and `getLong(5)`/`getLong(12)` assumed a layout; the sibling probe already resolved names from the
live schema. Both probes now resolve every column by name and refuse a table whose shape they cannot
read, including the primary-key name check that P6-082's own suggested fix asked for.

**A slow partition or token took the whole sample with it (`P6-085`, `P6-079`).** One failing
partition ended the sample with no row; one slow token ended the tick with no rows at all, which is
indistinguishable from a total outage. Both probes now isolate the failure per partition/per token,
report it on stderr, exclude it, and keep the rest of the sample — with a distinct exit code (3)
for a partial one.

**The census capped itself and ended buckets on one empty poll (`P6-376`, `P6-377`).** The
`.limit(1_000_000_000)` contradicted the "full-bucket census" the tool prints, and a single
time-bounded empty `pollBatch` was treated as end-of-scan. The cap is gone and a bucket is now
drained after three consecutive empty polls — the same rule `TokenCountReconcile`'s log path already
uses.

## Judgement calls

1. **Exit-code convention: 0 = complete, 1 = nothing usable, 2 = unusable input, 3 = partial.** None
   of the probes distinguished these before. It is a new contract for in-tree callers, which is why
   the change is `COMPATIBLE_WITH_LIMITATION`: `stage-capture.sh` already treats any non-zero exit as
   a per-tick WARN, so a *partial* sample now warns where it previously passed silently.
2. **The sentinel is unconditional.** `__END__ <count>` is printed even for unusable input (with the
   count it managed to emit, usually 0) and even when the run fails. A caller that blocks on the
   sentinel must never be left waiting for a probe that already gave up.
3. **An empty token list means "no filter"; a non-empty list with no parseable token is an input
   error** (exit 2). This is where the class of the argument decides the behavior: `""` or `"*"` is
   an explicit request for everything (the LOG path needs it), while `"abc,def"` is a broken request
   whose silence would look like an empty table. P6-083's suggested fix leaned toward failing on the
   empty string; the wildcard reading is recorded here as the deviation, because the LOG branch has
   no other way to say "all tokens".
4. **A window bound on a table without a `window_start` column is an input error, not a no-op.**
   Honoring the filter is impossible, so the probe refuses instead of returning rows the caller
   believes were filtered.
5. **The primary-key name is validated, not just used.** P6-082 asked for `primaryKeys.get(0)` to
   replace the hard-coded `"instrument_token"`. The probe additionally requires that key to *be*
   `instrument_token` and refuses otherwise: a table whose first PK is `token` cannot be looked up
   with this probe's documented key order, and silently trying was the defect.
6. **P6-731 is not implementable as written.** The suggested fix is try-with-resources around the
   `Lookuper`, but in fluss-client 0.9.1 `Lookuper` is not `AutoCloseable` — verified with `javap`
   after the rewrite failed to compile. The in-code note now records that the leak is bounded by
   `System.exit`, and that embedding this logic would need the client's own close path.
7. **`formatValue` names every supported root and marks the rest.** Complex roots (ARRAY/MAP/ROW)
   are still not decoded field-by-field, but they now print `<unmapped:ARRAY>` instead of the `null`
   that silently corrupted soak diffs (P6-374).
8. **A truncated LOG scan is a WARN plus a non-zero exit, not a silent short count (P6-373).** The
   60 s deadline is now a knob (`PROBE_READ_DEADLINE_MS`) so the test and the operator can shorten
   it, and hitting it prints `WARN: LOG scan hit the …` on stderr.
9. **`FlussKvProbe` timestamps each emitted row, and a null `last_event_time` prints `-1`.** Reusing
   a startup clock under-reported the lag of every later token (P6-372); a null timestamp is "no
   event yet", and `now - 0` would have printed a 56-year staleness.
10. **The census drain uses three confirmations at 500 ms, not at the full 5 s timeout.** The
    soak gate's host-N7 leg runs this census per table; three 5 s confirmations per bucket would
    have added minutes to a gate that must stay quick. The first poll keeps the 5 s window because
    it is the one waiting for data.
11. **`stage-capture.sh`'s comment was stale, not its code.** It still documented the fixed
    15-column index layout that P6-371 removed; the comment now says the probe resolves by name and
    notes the exit-3 partial-sample path. The corresponding findings for that script belong to its
    own wave — this was an incidental correction required by the change (same precedent as wave 12's
    registry row).
12. **No live Fluss call was made.** The dev stack on localhost:9123 is not running, so the four
    live smoke tests in the new file skipped. Everything the hermetic layer covers — compile, the
    input-validation paths, the sentinel, the "no row on failure" paths — ran; the filtering,
    formatting and drain logic is covered by construction and by these tests only against a live
    cluster, which is the main limitation of this wave.
