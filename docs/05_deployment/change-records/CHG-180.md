## What was wrong

W35x (P6-380) moved `remote.data.dir` from the container-local path
`/tmp/fluss/remote-data` to an `s3://` URI. That fixed the census probe, which
had been reading a directory only its own container could see. It left the dev
task manager behind:

| The task manager had | Why it was not enough |
|---|---|
| AWS credentials (from the shared anchor) | Credentials without an endpoint resolve against Amazon's S3 |
| No `R2_ENDPOINT` | The R2 plugin takes the endpoint from the environment |
| No `AWS_REGION` | S3A answers `400 Bad Request` |
| No Hadoop config | Nothing turns those variables into `fs.s3a.*` |
| `fluss-remote-data:/tmp/fluss/remote-data` | Held bytes only while the path was local; now a permanently empty directory |

The last row is the dangerous one. Fluss does not raise on a missing tiered
segment — it under-counts, so the failure looks like a smaller table rather
than an error. That is the same class of silent wrong answer W35x set out to
remove.

## Why the config goes where it goes

`FLINK_PROPERTIES` cannot carry these settings. Hadoop reads `core-site.xml`
off the classpath, and Fluss forwards only `client.fs.`-prefixed keys, which
the shipped S3 plugin matches against `s3.`, `s3a.` and `fs.s3a.` and
therefore ignores — measured against `fluss-fs-s3-0.9.1-incubating.jar` while
closing P6-380.

The file is bind-mounted at `/etc/hadoop/conf/core-site.xml` because Flink's
own `bin/config.sh` auto-detects that directory when `HADOOP_CONF_DIR` is
unset (`config.sh:379-382`), and `flink-daemon.sh:139` puts the result on the
daemon classpath. So the container needs no `HADOOP_CONF_DIR` of its own and
the existing image stays as it is.

## Residual risk

The production stack (`docker-stack.yml`) still has the family of gaps this
record closes on the dev side, and they are **not** addressed here because
fixing them changes production topology and needs its own live verification:

1. No task manager receives S3 client configuration. The baked
   `/etc/hadoop/conf/core-site.xml` from CHG-179 supplies it in the image, but
   the compose-side settings this record adds have no production equivalent yet.
2. The production servers still name the container-local
   `remote.data.dir: /tmp/fluss/remote-data` and share it as a volume, so a
   tiered read from any other node still resolves nothing.

Both were reported by W35x as a separate record and remain open.
