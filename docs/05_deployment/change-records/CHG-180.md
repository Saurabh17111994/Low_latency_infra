## What was wrong

W35x (P6-380) moved `remote.data.dir` from the container-local path
`/tmp/fluss/remote-data` to an `s3://` URI. That fixed the census probe, which
had been reading a directory only its own container could see. It left the dev
task manager behind:

| The task manager had | Why it was not enough |
|---|---|
| AWS credentials (from the shared anchor) | Credentials without an endpoint resolve against Amazon's S3 |
| No `R2_ENDPOINT` | The R2 plugin takes the endpoint from the environment |
| No `AWS_REGION` | S3A answers `400 Bad Request` |
| No Hadoop config | Nothing turns those variables into `fs.s3a.*` |
| `fluss-remote-data:/tmp/fluss/remote-data` | Held bytes only while the path was local; now a permanently empty directory |

The last row is the dangerous one. Fluss does not raise on a missing tiered
segment — it under-counts, so the failure looks like a smaller table rather
than an error. That is the same class of silent wrong answer W35x set out to
remove.

## Why the config goes where it goes

`FLINK_PROPERTIES` cannot carry these settings. Hadoop reads `core-site.xml`
off the classpath, and Fluss forwards only `client.fs.`-prefixed keys, which
the shipped S3 plugin matches against `s3.`, `s3a.` and `fs.s3a.` and
therefore ignores — measured against `fluss-fs-s3-0.9.1-incubating.jar` while
closing P6-380.

The file is bind-mounted at `/etc/hadoop/conf/core-site.xml` because Flink's
own `bin/config.sh` auto-detects that directory when `HADOOP_CONF_DIR` is
unset (`config.sh:379-382`), and `flink-daemon.sh:139` puts the result on the
daemon classpath. So the container needs no `HADOOP_CONF_DIR` of its own and
the existing image stays as it is.

## Correction note (2026-09-16): overstated evidence, and one gap that is not real

Two claims in the first version of this record did not survive checking against
the artifacts. Both are corrected here rather than by amending the commits.

**1. The status overstated the live evidence.** It said the tiered read was
"wired and proven live against the real bucket". What was actually proven is that
a container with the task manager's exact new mounts and environment can reach the
bucket: it listed `s3a://<bucket>/remote-data/log/default` through S3A and read
real objects, and the same command failed `400 Bad Request` with `AWS_REGION`
removed. That is bucket access, not a tiered read. No segment download from R2 was
ever exercised, and it cannot be exercised on the current dev stack: every one of
the 45 segments present on R2 also exists on the tablet's local volume — verified
by comparing the two listings per file, `45 LOCAL / 0 REMOTE-ONLY` — so a read
served from local disk and a read served from R2 are indistinguishable here. A
later probe run with the endpoint black-holed (`R2_ENDPOINT=https://127.0.0.1:9`)
returned the same answer as the live-endpoint run, which confirms the reads were
local. An earlier "45 remote-only segments" reading was a measurement artifact of
a broken extraction (the local layout pads segment names and keys on bucket,
`log-<b>/<segment>.log`; the remote layout does not, `<b>/<uuid>/<segment>.log`)
and was wrong.

**2. Residual risk #1 was false.** No production gap closes here, because the
production task manager already receives S3 client configuration: `docker-stack.yml`
sets `S3_ENDPOINT`, `R2_ENDPOINT` and `AWS_REGION` on `flink-taskmanager` (L595,
L596, L601 — the first two since `f0b98334`, the region since CHG-179), and the
image carries the same baked `/etc/hadoop/conf/core-site.xml` that does the
`${env.NAME}` expansion. `test_flink_runtime_image.py` pins all three. The claim
"the compose-side settings this record adds have no production equivalent" is the
reverse of the truth: the dev compose changes were copied *from* the production
stack, and production was never missing them.

Also dropped: "Both were reported by W35x as a separate record." No such record
exists — `CHG-178` is unwritten and its number is cited by
`FlussRuleCounter.java:27` for unrelated work (the probe's row-count contract,
P6-376/377/378). The production `remote.data.dir` gap below is reported here for
the first time.

## Residual risk

The production stack (`docker-stack.yml`) is **not** changed by this record, and
one real gap remains. It is not addressed here because closing it changes
production storage topology and needs its own live verification:

1. The four production Fluss servers still name the container-local
   `remote.data.dir: /tmp/fluss/remote-data` (L270, L333, L384, L435) and share it
   as the `fluss-remote-data` volume (declared L132, mounted L283, L346, L397,
   L448). A named volume with no `driver:` is node-local, so every writer and
   reader of tiered segments must land on the node that holds that volume for the
   bytes to be visible. The tablet services allow any worker and are not pinned to
   one node (only `max_replicas_per_node: 1`), and the coordinator has no placement
   block at all, so in a multi-node Swarm the co-residency this depends on is not
   guaranteed. Fluss tiers by default (`remote.log.task-interval-duration`
   defaults to 1 minute), so this is not a dormant configuration.

Read behaviour on the production task manager is a separate question and is not
claimed here in either direction: no production job was submitted and no
production cluster was deployed, so nothing in this record proves or disproves
that a production task manager can read a segment that tiered out.
