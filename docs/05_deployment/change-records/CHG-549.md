# CHG-549 — `FlussVisibilityProbe`: an independent reader-visibility stopwatch for L7

- **Status:** implemented (harness only — no cluster, job, image, DDL or config change).
- **Filed:** 2026-10-06
- **Source:** Task 3a of `docs/plans/2026-10-06-p99-integrated-program.md`. L7 (the ~65–69 ms
  between a record's `ingest_ts` and its emission by the Flink source) had no instrument: Flink's
  native latency markers start their clock when the source *emits* a marker, and the Fluss scanner
  gauges only prove that the source polled, so neither can see a record waiting between the source's
  fetch and its emission. Attributing L7 needs a reader that is independent of Flink and whose clock
  starts at the record's own timestamp.

## What changed

New `code/01_platform/04_scripts/fluss-probes/FlussVisibilityProbe.java` (261 lines), written in the
style of the existing probes (single file, no package, hand-rolled argument parsing):

* tail-follows the newest partition of a LOG table, subscribing every sampled bucket **at the current
  log end** (`admin.listOffsets(..., LatestSpec)` then `scanner.subscribe(partition, bucket, end)`),
  so it can only ever see records written after it started — no backfill, no replay;
* pins `client.scanner.log.fetch.wait-max-time` to the value it is given (the arm used the job's
  2 ms) and `max-poll-records=200`, so it is not measuring its own batching;
* per poll prints `<epoch_ms> <records> <newest_age_ms> <stalest_age_ms> <buckets>`, where
  `newest_age_ms = pollWall − max(ingest_ts in that poll)`; both clocks are the ingestion host's, so
  no clock skew enters the number;
* prints `__END__ <records>` on every exit path plus a min/p50/p90/p99 summary on stderr; exit 0
  samples collected, 1 no records/read failure, 2 unusable input.

`code/01_platform/04_scripts/tests/test_fluss_probes.py`: one list entry (see `test_updates`).

`docs/plans/2026-10-06-p99-integrated-program.md`: Task 3a/3b bullets, the L7 budget row and OQ4
updated with the arm's result.

## What it measured (the reason it was built)

Fleet-only arm (`SKIP_JOB=1 SMOKE_S=420 RATE_HZ=2`, deck writer `01_docker-ingestion-1` stopped),
two probes back to back:

| Window | samples | records | newest visible record age: min / p50 / p90 / p99 | same-window ingestion accept→ack (p50/p90/p99) |
|---|---|---|---|---|
| 90 s | 1 678 | 108 720 | 2 / 9 / 22 / 38 ms | 11 / 16 / 20 ms |
| 60 s | 1 112 | 72 694 | 2 / 9 / 24 / 38 ms | 12 / 27 / 35 ms |

Read visibility after the ack therefore costs about nothing, which rules the Fluss side out as a
65 ms term (the Flink scanner's own gauges — 0 records lag, poll every 2.1 ms — and the native
markers — whole in-DAG chain ≤ 8 ms p99 — agree). The remaining candidate window is the Flink
source's poll→emit path, i.e. Task 3b.

## Not changed

* `code/01_platform/04_scripts/stage-capture.sh`'s probe compile/sampling list is deliberately

* No job, config, DDL, image, dependency or `make gate` step is touched; no pipeline behaviour
  changes.

## Launch rule (cost one empty run)

A Fluss **reader** probe must be started with
`--add-opens=java.base/java.nio=ALL-UNNAMED`. The Fluss client's shaded Arrow cannot initialise
`MemoryUtil` on JDK 17 without it, the failure appears only at the first record
(`ExceptionInInitializerError`), and the probe then exits 0 with zero samples — i.e. it looks like
"no data" rather than a crash. Metadata-only probes such as `FlussReadLagProbe` do not need the flag,
which is why the omission was invisible until now. The requirement is documented in the probe's own
usage docstring.
