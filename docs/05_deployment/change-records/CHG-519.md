## What changed

- `run-monday-gates.sh` grows a **parallel step pool** (`GATE-PARALLEL-BEGIN/END`
  block): the seven steps that neither touch the stack nor depend on each other
  — python suites (3), Go suite (5), E2E binaries (6), gateway suite (14), Rust
  suite (15), pin discipline (17), mock-arrow suite (19) — are launched as
  children of the same script right after step 2. Each child re-runs the script
  with `--steps N` and `GATE_POOL_CHILD=N`, writes into the parent's run
  directory, and writes its banner/PASS lines to a per-step summary fragment.
- The parent flushes fragments into `SUMMARY.txt` as it reaps children (so the
  final banner count still equals `SELECTED_COUNT`), checks for failures at
  serial-step boundaries, waits for step 6 before step 12 (steps 12/13 consume
  its binaries), and drains everything before the verdict.
- Concurrency is bounded by `GATE_PARALLEL_JOBS` (default **2** — the host has
  ~4 GB available during a gate; step 3 alone needs ~8.5 min) flock slot files
  the children claim themselves, so the parent never blocks launching them.
- Failure semantics: a pool child's non-zero exit is recorded, its fragment is
  flushed, and the parent prints one `FAIL: pooled step N — see .pool-stepN.log`
  plus the normal verdict. A pool child never prints a verdict itself
  (`gate_fail` exits 1 without one), never re-runs the lock/preflight, and never
  records the replay memo. The EXIT trap kills pool process groups so an early
  parent exit cannot orphan a suite outside the gate lock.
- `--steps`/`--sweep` runs stay serial by default (`GATE_PARALLEL=auto`);
  `GATE_PARALLEL=1` pools a scoped run (smoke tests), `GATE_PARALLEL=0` forces
  serial everywhere. `--sweep` never pools (its driver already runs one child
  per step).
- The pooled step 3 gets `PY_TIMEOUT_SEC=900` via an exported override (the
  literal default stays 600, pinned by `test_gate_runner_wave21`): 600 s was
  measured on a quiet tree (CHG-199), and the pool runs it under concurrent load.

## Why

- Timing profile of the 19/19 run `monday-gates-20261002-154848` (~22.5 min):
  drills ~6.8 min, python unittest ~5.4, pytest ~3.1, Java suite ~1.6, DDL
  smoke ~1.2, Go ~0.9, Rust ~0.9, images ~0.4. The two largest blocks (python
  suites ~8.5 min and the stack chain) are independent, so serial execution
  pays for both; the pool overlaps them.
- The seven pooled steps are stack-independent by construction: none starts a
  container, contacts Fluss, or reads another step's artifacts except step 6
  (whose binaries steps 12/13 need — hence the explicit sync). The live steps
  (9 drills, 11 DDL smoke, 16 compute/UID, 18 images) stay in the serial chain.

## Residuals

- Fail-fast granularity is now the serial-step boundary: a pooled failure is
  noticed at the next boundary check (worst case, during step 9's ~8 min drill
  block), not instantly. All serial steps still fail-fast individually.
- `GATE_PARALLEL_JOBS=2` is a memory-bound choice for this host (~4 GB
  available, swap in use). On a bigger host `GATE_PARALLEL_JOBS=3` shortens the
  pool; it is env-overridable without a code change.
- The first certifying run with the pool is also the load test for the raised
  step-3 budget; if step 3 still times out under concurrency, lower
  `GATE_PARALLEL_JOBS` to 1 (step 3 still overlaps the chain) before touching
  the suite.
