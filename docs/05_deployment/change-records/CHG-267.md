# CHG-267 — the deploy environment is checked before the deploy, not after it

## Why

Compose interpolates the deploy environment **silently**. A key that is missing becomes an empty
string, a tag where a digest belongs becomes "whatever the node happened to pull", and a
`CHECKPOINT_DIR` that is not a remote URI becomes a single point of failure that only announces
itself when the node holding it dies. None of that is visible in the stack file.

This repository already had four checks that would notice — and every one of them runs too late to
save a deploy: `stack_selfcheck.sh` after the deploy, `submit-jobs.sh` on the job-submit path,
`lake-guard.sh` on its own schedule, and the runbook's prose. Nothing asked the question the operator
needs answered *before* `docker stack deploy`: is this environment coherent at all?

One fact made the gap concrete while writing this: the stack interpolates 41 variables and **40 of
them carry a stack-side default**. Defaults are dev values. A production node that pulls one of them
is pulling something nobody chose, and nothing in the repository said so.

## What changed

- **`code/01_platform/04_scripts/deploy_preflight.py`** (new) — read-only, exit code = number of
  FAILs. It resolves every `${VAR}` the stack interpolates, judges the **effective** image for each
  image slot (the environment's value, else the stack's default), and checks the six values the
  platform cannot invent (`S3_WAREHOUSE_PATH`, `R2_ENDPOINT`, `R2_BUCKET`, `ARROW_APP_ID`,
  `ARROW_USER_ID`, `CHECKPOINT_DIR` — the same six `stack_selfcheck.sh` requires), `R2_ENDPOINT` being
  `https://`, `CHECKPOINT_DIR` being `s3://<bucket>/…`, and no image pointing at a loopback registry.
  `--check-lake` performs one real signed LIST through `r2-list.sh` with `R2_ENV_FILE`/
  `R2_SECRETS_FILE` pointed at the files being checked; `--secrets-check` runs
  `secrets-bootstrap.sh --check`. `--expect dev` demotes the production-only rules to `[INFO]`.
- **`code/01_platform/04_scripts/tests/test_13_deploy_preflight.py`** (new) — 17 hermetic tests.
- **`docs/05_deployment/PROD_VM_PROVISIONING.md`** — S4 gains the invocation, right after step 6
  rewrites the deploy environment.

## Measured

Against the real dev environment and the real `docker-stack.yml`:

```text
$ python3 code/01_platform/04_scripts/deploy_preflight.py            # --expect production
[PASS] deploy environment code/01_platform/01_docker/.env is readable
[PASS] all 41 variable(s) the stack interpolates resolve to a non-empty value
[FAIL] CHECKPOINT_DIR is empty — the platform cannot start without it (stack_selfcheck.sh requires it too)
[PASS] R2_ENDPOINT is an https:// endpoint
[PASS] every image a node would pull is pinned: 0 digest-pinned, 6 upstream image(s) left to their author (tag or digest)
[INFO] the lake is not contacted without --check-lake (a signed LIST needs the real credentials)
1 failure(s)

$ python3 code/01_platform/04_scripts/deploy_preflight.py --expect dev
0 failure(s)

# the stack file itself, measured:
stack interpolates: 41 | with a stack-side default: 40
image vars: 3 | of those defaulted: 3 | defaulted AND undefined in the env: ['CADVISOR_IMAGE', 'NODE_EXPORTER_IMAGE', 'ZOOKEEPER_IMAGE']
```

The one FAIL is correct and instructive: `CHECKPOINT_DIR` is deliberately *not* in the deploy
environment — the rehearsal generator injects a `file://` value — so a production deploy using this
file unchanged would start the coordinator with no checkpoint directory at all. Two iterations of
this check were wrong before they were right: the first flagged any defaulted image variable, which
would have failed `node-exporter`, `cadvisor` and ZooKeeper — all three pinned to digests in the
stack file, so pinned by default is finer than the rule assumed; the rule now judges the effective
value. The second iteration carried a loopback test for `CHECKPOINT_DIR` that no `s3://` URI can ever
match: dead code, removed.

## Limitation

**The lake has never actually been listed by this script.** R2 credentials do not exist in this
repository yet, so `--check-lake` is exercised only against stubs. Its value depends on `r2-list.sh`,
which is measured; its first real run is still unmeasured.

**It checks shape, not truth.** An `ARROW_APP_ID` that is present but wrong passes; so does a bucket
name that exists but is not the one tiering expects. Those surface at the vendor's answer or in the
lake, not here — this check only removes the failures that are decidable offline.

**`--secrets-check` reports the swarm's secrets, not their contents**, and only when asked; before S6
its failure is expected and reported as `[INFO]` in `--expect dev`.

Other checks remain the backstops they were: `stack_selfcheck.sh` (after the deploy),
`submit-jobs.sh` (the job path), `lake-guard.sh` (the lake), `cluster_check.py` (the deployed
cluster, CHG-264) and `vm-bootstrap.sh --check` (the host, CHG-266).
