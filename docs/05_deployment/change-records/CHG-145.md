# CHG-145 — The tiering proof can no longer pass on an empty run

- **Status:** recorded — all seventeen wave-8 findings verified and fixed in one commit
- **Filed:** 2026-09-14
- **Source:** P6 ops/scripts/tests/chaos audit, wave 8 ("Tiering: zero writes must not pass"):
  P6-021, P6-241, P6-242, P6-243, P6-244, P6-245, P6-246, P6-247, P6-248, P6-249, P6-250,
  P6-629, P6-630, P6-631, P6-632, P6-633, P6-634

## What happened

`tiering-smoke.sh` is the guarded end-to-end proof that log segments reach Iceberg in R2, and
`tiering-start.sh` is the idempotent submit for the long-lived tiering service. Both were re-read
line by line before anything was edited and all seventeen findings held.

**The proof passed when nothing had been tiered (`P6-021`, CRITICAL).** VERIFY-1's row check was
`if ROWS > 0 then require > 1000`, so a reader that returned nothing with an empty stderr — a
truncated read, a changed output format, a swallowed crash — skipped the check entirely and the run
went on to report success. Zero rows from the log reader is now a hard failure. The one legitimate
zero-row path, the partitioned-table fallback, records that it proved writes from the R2 day count
instead (`WRITE_PROOF=r2`) rather than being inferred from `ROWS`, and that path already fails on a
zero day count.

**The verifications after it did not verify (`P6-246`, `P6-629`, `P6-630`, `P6-631`).** VERIFY-2
counted tiering errors, printed them and gated nothing — a run with tablet tiering exceptions, or
with no tiering activity at all, still ended in PASS; both now fail, over a `--since` window bounded
to the run instead of two full container-log scans. GUARD-B's ZK read ran under `pipefail`, so a
docker or ZK failure aborted the script before its own diagnostic, and its `grep -q true` matched
any `true` anywhere in the payload; the property is now matched in the `...enabled` field, and an
empty payload fails first. The faketool probe fell through silently when the faketool never bound,
launching the JVM to fail confusingly two minutes later — the probe and a `kill -0` now fail fast.
Four `r2_list_lake` scans of a paginated listing became two, cached in `$OUT`, because a baseline
and a "current" count taken from different snapshots are not comparable.

**The run's own timing and state made a false pass reachable (`P6-241`, `P6-242`, `P6-244`).** The
inputs were unvalidated (`bash tiering-smoke.sh foo` reached `sleep foo` and died under `set -e`
with no message), and the default timing — 60s of writes plus a 120s wait — sat below the 5-minute
freshness window plus the 1-minute tier interval, so a default run could only pass on a *previous*
run's objects or fail VERIFY-3 spuriously. Input validation now runs first, before the script reads
any config, and exits 2; a total below 360s warns. Cleanup used `kill -9`, which truncated in-flight
log writes and destroyed the drained-write summary the script's own fallback depended on — it is now
TERM, up to 30s of grace, then KILL, idempotent and shared with the trap. The readiness marker was
one fixed path and the faketool port one fixed number, so a stale file from a crashed run reported
READY before this run's JVM started and two parallel runs could read each other; the marker is now
per-run (`READINESS_FILE_PATH`) and the port free-picked. The fallback query guards `R2_BUCKET`,
keeps DuckDB's stderr instead of discarding it, and takes the count as the first integer rather than
matching box-drawing characters. The faketool's test identity stays exactly as documented, now as
overridable defaults rather than literals in the middle of the launch line.

**The submit trusted its inputs and its outputs (`P6-247`, `P6-248`, `P6-249`, `P6-250`, `P6-632`,
`P6-633`, `P6-634`).** The config read was two greps: a missing or non-matching `.env` aborted under
`set -e` with no message, and an empty value was submitted as an empty `--datalake.iceberg.warehouse`
or endpoint, failing minutes later inside the job. It now reads `.env` the way compose does
(`export `, quotes, CRLF, blanks, last match wins) and refuses to submit when either value is empty.
`--status` matched the job name by substring and only counted `RUNNING`, so a restarting job or an
unrelated job whose name contained "tiering" decided the answer, and nothing serialised
check-then-submit; it now requires the exact pipeline name with any non-terminal state, under a lock.
The job id comes from a JobManager REST response and was interpolated straight into a `sh -c`
command line — a compromised JobManager could inject shell — so it must now be 32 hex characters
before any use. The restart-strategy check grepped the raw response body, so a description
mentioning "fixed delay" passed while a transient failure produced an empty body that was reported
as "no strategy"; it parses `execution-config` and reads the effective strategy field. `attempts=3`
turned a TaskManager loss into a *permanent* tiering outage after three restarts — the same outage
the strategy was added to remove, just delayed — so restarts are effectively unbounded
(`2147483647`, Flink's accepted maximum) with a 30s fixed delay, and `type=fixed-delay` is stated
explicitly so a cluster default cannot change it. `flink run`'s exit status is no longer discarded
and a truncated JobID no longer counts as a submit; the poll handles every terminal state, fetches
`/exceptions` and bounds each REST call with `curl -m 5`; `--status` returns 1 for "no running job"
and 2 for "running without fixed-delay restart" and prints the exact cancel command instead of just
`exit 1`.

## Judgement calls (review these)

1. **`P6-021`'s literal fix was rejected; the fix is one step narrower and one step stronger.** The
   finding asks for `ROWS > 1000` unconditionally. `ROWS` is legitimately 0 on the
   partitioned-table path, where the reader cannot express a partitioned subscribe and the write
   proof is the R2 day count instead — requiring it there would break the only working path for
   the current table. So the requirement is now: the log reader must show >1000 rows *on that
   path*, and the fallback must show a non-zero day count on its own. The hole being closed is the
   old one — a zero row count skipped the check — and `WRITE_PROOF` makes which proof applied an
   explicit, printed fact rather than a silent branch.
2. **The live half of the smoke is inspected, not executed.** `tiering-smoke.sh` needs a live Fluss
   cluster, R2 credentials and a real tiering round, so the new suite executes only its pre-flight
   validation (which runs before any config is read) and drives `tiering-start.sh` through a stub
   `docker`. The VERIFY-1/2/3 and GUARD A–E changes above are verified by reading the diff against
   the findings, not by a run. That gap is recorded rather than papered over. The smoke is not part
   of the Monday gate, so no gate silently depends on it.
3. **A short run warns, it does not refuse.** Refusing below the 360s floor would be defensible, but
   an operator deliberately reproducing a short-window bug would then have to edit the script. The
   warning names the floor and the reason; the documented invocations (`300` with `TIER_WAIT=420`)
   are already above it.
4. **Effectively-unbounded restarts are deliberate.** Making the tiering service give up is the
   failure mode `P6-250` reports, so the attempt count is `Integer.MAX_VALUE`. This trades one
   failure mode for another: a job that can never exhaust restarts must be watched, which is why
   `--status` exists and why the wrong-strategy case now exits 2 with the exact cancel command. The
   alternative (`failure-rate` or `exponential-delay`) was declined because it changes the pinned
   strategy tokens that `test_tiering_restart_guard.py` guards.
5. **`P6-654` is still open and this wave does not touch it.** Its remaining half — the
   strictly-increasing date rule rejecting legitimate same-day multi-table chains — must change in
   `AuditHashChain.java` *and* its byte-exact Python mirror together, which is the wave that owns
   `r2_legal_hold_check.py`. Recorded in CHG-142 judgement call 1; named here so this record is not
   read as closing it.
6. **A pin that encoded the defect was updated, not deleted.** `test_tiering_restart_guard.py`
   asserted `-Drestart-strategy.fixed-delay.attempts=3` — i.e. it pinned `P6-250`'s defect as the
   contract. It now asserts the new value with the reason, and checks that the strategy decision is
   made against the parsed `execution-config`.

## Verification

1. **Red before green, in a sandbox.** The new suite was run against the pre-fix revisions copied
   into a fixture tree (`code/01_platform/04_scripts/{tiering-start.sh,tiering-smoke.sh,r2-list.sh}`
   next to a fixture `01_docker/.env` whose endpoint is `https://127.0.0.1:9`, so no real endpoint
   can be reached) with the same stub `docker` on `PATH`. Every one of the 15 tests has at least one
   failing check — **23 failing checks, 4 "passed" being methods whose failures pytest itemises at
   subtest level** — including the injection case, where the pre-fix script used the hostile job id
   on a command line. The run was killed by the test budget rather than reaching the network; both
   repo scripts hashed identically before and after it (`a142d91adde3295d`,
   `e387ea994ece7910`; the first changed later by the `30 s` fix below).
2. **Green on the fixed code: 15 tests, 0 failures** (`test_tiering_guards.py`), 13 of them subtests.
   Together with the three tests in `test_tiering_restart_guard.py`: 20 tests, 0 failures.
3. **The helper suite: 503 tests, OK** (was 488 before the wave — exactly the 15 new tests).
4. **`full_audit.sh`: exit 0, 198 `[PASS]` / 0 `[FAIL]`.** An A/B on the same working tree — only
   this wave's files reverted to the previous revision — gives the identical 198/0, so the wave
   neither lost a check nor regressed one. A worktree at the pre-wave tip is *not* a valid baseline
   for that comparison: it reports 196/2 because the C6 doc-count checks read
   `target/surefire-reports`, which a fresh worktree does not have.
5. **This patch's own suite caught three defects in it.** A non-matching `grep` under `pipefail`
   aborted the submit path before its failure message (the same class as `P6-629`, in new code); the
   strategy parse initially matched any `restart-strategy*` key, so a description mentioning "fixed
   delay" still passed; and the pre-existing pin caught a dropped space in
   `-Drestart-strategy.fixed-delay.delay=30 s`, which is restored.
6. **Both scripts stay gate-clean:** `bash -n` plus `shellcheck -S warning` with no findings.
7. **Not run in this wave:** the Monday gate; the live smoke (needs Fluss + R2); no Java, DDL or
   container change. The one in-repo caller of `tiering-start.sh`
   (`tm-kill-full-load.sh`, its `TIER_KILL_REQUIRED` pre-flight) treats any non-zero exit as fatal,
   so the new 1-vs-2 split does not affect it; the exit codes are documentation-only otherwise.
