## Why

The plan's task C1 said "bind-mount the chrony socket and set `CLOCK_OFFSET_SOURCE`". Two independent facts
make that mechanism unusable, and the second makes it wrong even if it worked:

- **The directory is owner-only.** The Debian package's unit carries `RuntimeDirectory=chrony` with
  `RuntimeDirectoryMode=0700` and `User=_chrony` (read from the shipped
  `/usr/lib/systemd/system/chrony.service` in a throwaway `debian:bookworm-slim` container). A `0700`
  directory owned by `_chrony` cannot be traversed by this container's `nobody` user, and no `group_add`
  changes that — only loosening the directory for every local user would.
- **The socket is a control channel, not a sensor.** chronyd's command socket is unauthenticated: whoever
  can connect can run `makestep` and `add server`, i.e. move the very clock the gate exists to police.
  Mounting it into the container that parses untrusted market data and broker replies would hand clock
  control to the component being gated.

Separately, the measurement that started this: **the deck never selected a source.** The `nautilus`
service carried no `CLOCK_OFFSET_SOURCE`, so production would have run the default fixed-zero source and
the drift gate could never fire — the safety rule was implemented, tested, and unwired.

## What changed

- `clock_offset_fact.sh` (new): reads field 4 of `chronyc tracking`'s `System time` line — the same field
  `vm-bootstrap.sh --check` and `prod_node_check.py` read, so the three cannot disagree — and publishes
  `offset_ms`, `measured_epoch_s` and `source=chronyc-tracking-field4` into `/run/arrow-clock/offset`,
  replacing the file atomically. Any failure exits non-zero and **leaves the previous sample in place**: an
  old sample plus the consumer's age limit becomes a halt, not a comfortable lie. It also replaces a
  directory left behind by Docker when a bind-mount source was missing.
- `vm-bootstrap.sh`: installs the writer, writes `arrow-clock-offset.service` (root — it reads the socket
  only root and `_chrony` may use) and `arrow-clock-offset.timer` (10 s, first tick 15 s after boot),
  starts the timer if it is not already running, and publishes once immediately — best effort, because on a
  fresh node chronyd may still be starting, the timer retries every 10 s, and `--check` is the gate. That
  gate now fails when the fact is absent or stale beyond `CLOCK_MAX_AGE_S`. It reports the sample's age and
  nothing else: deliberately no `systemctl` in `--check` (the check path must only read), and an active
  timer whose last run failed leaves the file stale all the same. `cp`+`chmod` rather than `install -m`
  places the files, so the bootstrap's own harness runs this path for real.
- `docker-stack.yml`: `nautilus` gets `CLOCK_OFFSET_SOURCE=clockfile`,
  `CLOCK_OFFSET_FILE=/run/arrow-clock/offset`, `CLOCK_OFFSET_MAX_AGE_S=30`, and a **read-only directory**
  mount. The directory, not the file: a file bind-mount pins the inode, so an atomically replaced sample
  would never reach the container.
- `clockwatch.rs`: `ClockFileOffsetSource` (path + max age, `from_env`, pure `parse_fact`) behind the
  existing `OffsetSource` trait. Absent, unparseable, or older than the limit → `Err` → `Unmeasurable` →
  halt. `main.rs` selects it with `CLOCK_OFFSET_SOURCE=clockfile`; `chronyc` and the fixed source stay for a
  dev box and for CI.
- The runtime image is **unchanged**: no `chrony` package, no socket, no new capability.

## Not verified

- No VM exists yet, so the producer has never run against a real `chronyd`, and the deck has never started
  with these values. The VM half — `--check` reporting a fresh fact, the executor logging
  `source = node-published clock fact`, and the halt when the file is removed or aged past 30 s — is task
  C1's remaining checkbox, and T9 is its stated evidence.
- The container-based permission probe was inconclusive: `chronyd` cannot discipline the clock without
  `CAP_SYS_TIME`, so it exited and the socket never appeared, and every `chronyc` call returned
  "cannot talk to daemon" for every user. The load-bearing fact above is therefore the packaged
  `RuntimeDirectoryMode=0700`, read from the unit — not that probe.
- The executor binary changed, so the published `NAUTILUS_IMAGE` digest is now stale. The republish and the
  digest update are C1's other open checkbox and must land before the first deploy.
