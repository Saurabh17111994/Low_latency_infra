# CHG-511 — loadtest starts the current ingestion jar

- **Status:** implemented — unit tests green; live loadtest rc=0 without the export workaround
- **Filed:** 2026-10-02
- **Source:** found during the CHG-509 drill: `loadtest-run.sh` could not start
  a current ingestion jar. `resolve_arrow_credentials` sourced the 0600 secrets
  file without exporting, and the JVM env block omitted `DEPLOYMENT_ENV`; the
  rebuilt jar failed `IngestionConfig` validation (3 errors) and the feed never
  started. The drill ran with an inline `set -a; . secrets.env; set +a;
  DEPLOYMENT_ENV=dev` workaround.

## What changed

- `resolve_arrow_credentials` now exports `ARROW_APP_SECRET`,
  `ARROW_PASSWORD`, `ARROW_TOTP_KEY` after sourcing the file. Only those three
  leave the shell; the file's other secrets stay shell-local.
- The JVM env block pins `DEPLOYMENT_ENV="dev"`.

## Why

The script's own comment says the JVM inherits the credentials, and the JVM env
block already carries `SECRETS_VIA_ENV_FILE=1` — the marker `SecretGuard`
documents for exactly this harness pattern. But `source` without `export`
keeps the values shell-local, and the current `IngestionConfig` also requires
`DEPLOYMENT_ENV`. With the Sep-23 jar this was latent; a current jar fails
closed at startup.
