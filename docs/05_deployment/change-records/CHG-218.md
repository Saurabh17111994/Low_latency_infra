# CHG-218 — the four local-build image IDs are retired as pins; the content stamp owns image freshness

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** certificate run 6 (19/19 PASS), which rebuilt all eight images; `make gate-fast`
  afterwards went red on two of the four local pins.

## What happened

Gate step 18 rebuilds every image. Ingestion and execution-gateway changed in this batch, so
their IDs moved while `runtime.lock` still pinned the 2026-09-15 values; `test_pin_check.py`
failed on exactly those two (CHG-216 re-pinned them, ~10 minutes of hand work plus a
`gate-fast` cycle). That prompted the question this record answers: does the leg earn its
keep?

## Why it does not

1. **It cannot detect the risk it appears to cover.** Edit the source without rebuilding and
   the image ID still matches the lock — green on a stale image. Rebuild from identical
   sources and the ID changes — red on a correct image. The lock's own comment says it
   outright: "A pin can match this host and still be a stale build."
2. **The property is already owned, better.** `image_staleness_check.py` (CHG-101) compares a
   content stamp — sha256 over the Dockerfile's COPY inputs, baked in as
   `com.trading.build-stamp` by `make images` — against the stamp recomputed from the tree.
   It is content-addressed, so a rebuild cannot move it, and it fails in the direction that
   matters. Gate step 18 runs it *after* the build. CHG-162 judgement call 3 already said
   freshness "stays a separate check" that does not read `runtime.lock`.
3. **Nothing consumes the values at runtime.** `COMPOSE` takes `--env-file .env --env-file
   secrets.env` (`Makefile:6`); the four variables are absent from that file; the local
   services in `docker-compose.yml` declare `build:`. `docker-stack.yml` requires them from a
   *deployment* env, where a local config digest would be unusable anyway ("not a registry
   manifest").

## Why A2 (machine-write the IDs from the build) was rejected

Automating the write would make the host-comparison check self-fulfilling — it could never
fail, so it would be maintenance without signal. Choosing between "a check that is always
true" and "no check, with the real property owned elsewhere" leaves one answer.
