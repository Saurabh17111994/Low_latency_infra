# CHG-181 — the production Fluss services start nothing

- **Status:** recorded — the defect is **found and evidenced, not fixed**. No
  source file is changed by this record. It exists so the finding is on the
  record now rather than living only in a plan, because a production deploy of
  these four services cannot work today.
- **Filed:** 2026-09-16
- **Found during:** planning the follow-up to CHG-179 (moving the production
  `remote.data.dir` onto R2, as dev did in W35x/CHG-180). The storage question
  is moot until the servers run at all, which is why this finding outranks it.
- **Severity:** blocks any production deploy of Fluss. Nothing is corrupted and
  no data is at risk — there is no running server to hold any. The failure is
  that production has no Fluss cluster while the stack reports it as started.

## What was found

`apache/fluss:0.9.1-incubating` declares:

```text
Entrypoint=[/docker-entrypoint.sh]
Cmd=[help]
```

With no `command:` in the stack, each container therefore runs the entrypoint
with the argument `help`, prints a usage message, and **exits 0**. All four
production Fluss services are affected:

| Service | Stack line | Declares what to run? |
| :--- | :--- | :--- |
| `fluss-coordinator` | L236 | no — image default (`help`) |
| `fluss-tablet-1` | L299 | no — image default (`help`) |
| `fluss-tablet-2` | L350 | no — image default (`help`) |
| `fluss-tablet-3` | L401 | no — image default (`help`) |

The dev compose has the correct form (`command: ["coordinatorServer"]` at L321,
`command: ["tabletServer"]` at L437); the production stack never had it.
`git log -S coordinatorServer -- code/01_platform/01_docker/docker-stack.yml`
returns nothing, so no previous revision of the stack file ever named a Fluss
server type.

## How it was verified

Three independent checks, all run 2026-09-16:

1. **The image's default is the usage path.** `docker run --rm
   apache/fluss:0.9.1-incubating` prints
   `Usage: docker-entrypoint.sh (coordinatorServer|tabletServer)` followed by
   `Or docker-entrypoint.sh help`, and `echo $?` returns **0**. Exit 0 is what
   makes this quiet: Swarm sees a clean exit, not a crash.
2. **The command never arrives.** `docker stack config -c docker-stack.yml`
   (with the 12 placeholder values the stack's `:?` guards require) renders
   `command=None` for all four Fluss services, while the Flink services — fixed
   by CHG-179 — render `command: [jobmanager]` and `[taskmanager]`.
3. **The correct argument starts a real server.** `docker run --rm
   apache/fluss:0.9.1-incubating coordinatorServer` logs
   `Starting Coordinator Server` and
   `Starting coordinator-server as a console application on host <id>`, so the
   dispatch the stack omits is exactly the one that works.

## Why the offline gates could not catch it

Every gate the stack has validates **structure**, and the structure is complete:
replicas, placement constraints, distinct `tablet-server.id` values, secret
scope, volume declarations, healthchecks. None of them asks the one question
this defect fails — *does the container start the process it is supposed to*.

This is the same defect class CHG-179 fixed for the Flink services, where the
image's `CMD` was likewise only a usage fallback. That fix added
`ProductionStackTests.test_flink_services_declare_what_to_run` in
`test_flink_runtime_image.py`, which pins the Flink services only. The Fluss
half of the same stack was left unpinned, so the identical defect survived the
same wave that fixed it.

## What this record does not claim

- **It does not fix anything.** The four services still exit with the usage
  message. Acting on this record means executing the referenced plan.
- **It does not record three sibling findings** found in the same planning pass,
  which are also unfixed and are out of scope here: the four Fluss healthchecks
  cannot pass (`CMD-SHELL` runs under dash, which has no `/dev/tcp` — a healthy
  server reports unhealthy); the four services receive the R2 credentials as
  files that nothing reads; and their `remote.data.dir` is a node-local volume
  with no placement pin, so a tiered read that resolves to another node finds
  nothing. All three are covered by the referenced plan. They are named here only
  so they are not lost, not claimed as part of this record.
- **It has not been verified on a deployed cluster.** No production Swarm was
  available: the host used for verification is a Swarm *worker*
  (`ControlAvailable=false`), so no service could be created to watch the exit
  behaviour in a real service task. The evidence above is the image's own
  behaviour plus the stack's rendered configuration, both of which are
  deterministic and independent of the cluster.
- **It does not claim the healthchecks cause a restart loop.** What Swarm does
  with an unhealthy task is not settled by the sources consulted and could not be
  observed without a manager node; see the plan's Problem 2 for the conflicting
  evidence. That question is separate from this record.
