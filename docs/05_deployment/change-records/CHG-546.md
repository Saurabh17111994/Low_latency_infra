# CHG-546 — tablet `log.flush.offset.checkpoint-interval` is operator-settable

- **Status:** implemented (dev compose config surface only — the rendered value
  is unchanged until an operator sets `FLUSS_LOG_FLUSH_OFFSET_CHECKPOINT_INTERVAL`).
- **Filed:** 2026-10-04
- **Source:** `kv.snapshot.interval` was ruled out as the cause of the ~60 s
  append-p99 square wave (A/B, `logs/tracker-14/20261004-kv-snapshot-ab-verdict.md`),
  leaving the periodic log offset checkpoint — which flushes the log segment
  files + indices and fsyncs the directory once per interval on the same single
  writer thread that serves appends — as the last named candidate in the same
  60 s band (C2 follow-up, plan `docs/plans/2026-10-03-p99-50ms-combined-plan.md`).
  Its value is not runtime-settable (no config seam exists in the tablet's
  `FLUSS_PROPERTIES` today), so the A/B needs a parameterized key exactly like
  the `kv.snapshot.interval` knob added by A5.

```text
change_record_id: CHG-546
scope: dev-compose-config-surface
owner: platform
date: 2026-10-04
affected_artifacts: code/01_platform/01_docker/docker-compose.yml
compatibility_class: COMPATIBLE
savepoint_impact: none — the key only moves WHEN the persistent offset checkpoint is written (default `60s` = one minute = the upstream default's value). Raising it widens the recovery-point lag after a crash: the tablet replays from the last checkpoint. It does not change formats, APIs or state layout, and it is not set anywhere by default.
test_updates: `test_08_local_compose_f8_snapshots.py::test_duration_knob_defaults_are_parser_legal` (added 2026-10-04 after this key crash-looped the tablet) pins the `60s` default and fails on any `${VAR:-PT...}` default in the tablet block. `docker compose config` renders `log.flush.offset.checkpoint-interval: 60s` with the environment unchanged; the compose/snapshot pins plus the stage-capture gate tests pass (9 passed in 65.1 s + the new leg). The knob's *effect* is measured by the C2-follow-up arms, not asserted in a unit test.
rollback_behavior: remove the line (or leave it unset) — the tablet then uses the upstream default (one minute), which is the value the line renders today. No state, data or recovery-point artifact changes.
plan_tasks: docs/plans/2026-10-03-p99-50ms-combined-plan.md C2
```

## What changed

`code/01_platform/01_docker/docker-compose.yml`, tablet `FLUSS_PROPERTIES` block,
immediately after `kv.snapshot.interval`:

```yaml
log.flush.offset.checkpoint-interval: ${FLUSS_LOG_FLUSH_OFFSET_CHECKPOINT_INTERVAL:-60s}
```

The default is the upstream default's value (`ConfigOptions.LOG_FLUSH_OFFSET_CHECKPOINT_INTERVAL`
probed from `fluss-server-1.0.0.jar` = `PT1M` = one minute), so an unchanged environment
renders exactly as before. Compare `kv.snapshot.interval` and
`remote.log.task-interval-duration`: the same "parameterize for a scratch window,
keep the certified default" pattern, each with the reason in a comment.

## Revision 2026-10-04 — the ISO-8601 form crash-loops the tablet (found by its own A/B)

The first version of this line rendered `PT1M`, copied from the string
`ConfigOptions` prints as the option's own default. **`PT1M` is not a value the
server can parse.** The second arm of the C2 follow-up A/B recreated the tablet
and it never became ready (180 s timeout, `coordinator=running tablet=restarting`,
`FlussReadyProbe` → `StaleMetadataException: Alive tablet server is empty`); the
container reached 16 restarts at exit 2 and its log carried:

```text
ERROR org.apache.fluss.server.ServerBase - Could not start the TabletServer.
java.lang.IllegalArgumentException: Could not parse value 'PT1M' for key 'log.flush.offset.checkpoint-interval'.
  at org.apache.fluss.config.Configuration.getOptional(Configuration.java:610)
  at org.apache.fluss.server.log.LogManager.startup(LogManager.java:162)
Caused by: java.lang.NumberFormatException: text does not start with a number
  at org.apache.fluss.utils.TimeUtils.parseDuration(TimeUtils.java:80)
```

`TimeUtils.parseDuration` accepts only `<number><unit>` (`60s`, `1m`), not the
ISO-8601 `PT1M`. The same trap the repo already documented for
`remote.log.task-interval-duration` ("MUST be `'0s'`, not `'0'`") has a second
face: a *valid-looking* ISO-8601 default is equally fatal. The same run also
failed the queued changelog-profile arm (arm 1) at its preflight gate — one bad
default cost two arms, because the failure mode is a crash loop rather than a
config error at parse time of `docker compose config`.

Lesson kept as a test, not as prose: `test_08_local_compose_f8_snapshots.py`
now fails on any `${VAR:-PT...}` default in the tablet block.

## Not changed

- `code/01_platform/01_docker/.env` / `.env.example` — no default is pinned, so
  the A/B flips the value for one tablet recreate only and the tree keeps
  rendering the upstream default.
- `docker-stack.yml` / `docker-compose.tablet2.yml` — production and the second
  tablet keep the upstream default; a production A/B needs its own record.
- `log.flush.interval-messages` stays at its default (Long.MAX_VALUE: the
  per-message fsync path is dormant), so the offset checkpoint is the only
  periodic flush on the append path.
