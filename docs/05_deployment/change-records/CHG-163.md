## What happened

on 2026-09-13/14 while their sources changed afterwards. `make images` re-derived each
service's content stamp from the tree, rebuilt all 8 compose build services, and re-verified:

## Judgement calls

1. **Rebuild, not silence.** The alternative was to weaken or skip the staleness check. The
   check exists because a 2026-08-24 incident shipped 08-20 images with 08-24 sources
   (CHG-101); the stamps make "FRESH" a content claim, so the honest fix was to build.
2. **`execution-bridge` is not a missed re-pin.** It was rebuilt by the same command and its
   image ID is identical (`84c758d2…`): every layer was CACHED, so the content did not change.
   A pin is content-addressed — an unchanged ID is the correct value, not an omission.
3. **No test change.** `test_local_build_pins_match_the_local_images` (added by CHG-162) already
   fails exactly when a pin drifts from the host, which the red run demonstrated before the
   re-pin. Adding tests here would only pin the same property twice.
4. **The build ran in the background, with the tree frozen for writes.** `make images` reads the
   repository (image contexts include `code/`), so no file was edited while it ran — recon was
   read-only. A half-written source file could otherwise have been baked into an image.
5. **The rebuild also unblocks the gate's step 8.** That step checks `ddl-apply` only, with
   `--require-stamps`; the whole-set check now passes as well, so both the narrow gate step and
   `make check-image-stale` are satisfied by the same build.

## Limitations

- "FRESH" is freshness *relative to the tree at build time*. Any source edit after this build
  makes the corresponding image STALE again; that is the checker working, not a defect.
- The stamps certify the listed COPY inputs (`SERVICE_SOURCES` + the Dockerfile and
  `.dockerignore` resolved through the compose file), not the full build reproducibility: two
  builds of identical inputs can still differ if a base image is re-tagged. Base images remain
  pinned separately by `pin-check.sh`.
- The re-pin is host-local provenance. These images are still unpublished, so
  `docker run <repo>@sha256:<image-id>` does not resolve and a deploy path needs a pushed
  manifest digest (`digest-pin.sh`) — unchanged from CHG-162.
