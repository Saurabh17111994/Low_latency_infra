## 1. What was wrong

The production Swarm stack could not run a Flink job at all. Five independent
defects, each verified inside a container on 2026-09-16, each fatal on its own:

| # | Defect | What the operator saw |
| --- | --- | --- |
| 1 | `flink-jobmanager` / `flink-taskmanager` carried no `command:` | The image's default is the usage/help path, so the container printed usage and **exited 0**. Swarm reported the task as started while nothing ran — the worst kind of failure for a trading stack, because it looks healthy. |
| 2 | No `AWS_REGION` anywhere in the stack | S3A requests failed `400 Bad Request`. |
| 3 | No Fluss jars in `/opt/flink/lib` | The job could not load the connector. `compute.jar` contains **zero** `org/apache/fluss` classes — they are `provided` scope, supplied by the cluster. |
| 4 | `flink-s3-fs-hadoop` shipped in `/opt/flink/opt` but was not linked into `/opt/flink/plugins` | `state.checkpoints.dir: s3://…` had no filesystem at all. |
| 5 | No `/etc/hadoop/conf/core-site.xml` | The **endpoint** was lost. The credentials were still found by the default provider chain, so `s3://` silently resolved against Amazon's real S3 and failed `403 InvalidAccessKeyId` — a confusing failure that points at the credentials when the real problem is the missing config. |

Defects 2–5 are properties of the stock image. Defect 1 is a property of the
stack file. Both had to be fixed; neither fix is visible from the other.

## 2. Why the image is built by a script rather than from the working tree

The dev compose file mounts host-built jars from
`code/02_services/02_compute/target/`, which is gitignored and therefore
unversioned. A production image that copied from such a tree would be
reproducible only by accident. `fetch-jars.sh` instead downloads every jar from
Maven Central and verifies it against a pinned SHA256 **before the Dockerfile
can see it**, so a silently swapped upstream artifact fails the build instead of
shipping. `make flink-image` runs fetch, build and re-verify, and removes the
staging tree either way.

Two artifacts needed a judgement call, both recorded in the README:

- `fluss-fs-hadoop-shaded-0.9-SNAPSHOT.jar` is **unpublished** (HTTP 404 on
  Central; the similarly named published `fluss-fs-hadoop` is an unrelated 10 KB
  stub). A SNAPSHOT cannot be checksum-pinned, so it cannot be part of a
  reproducible image. All 12336 of its entries are already present in the
  published `fluss-fs-s3` + `fluss-fs-hdfs` pair, and it declares no Fluss
  `FileSystemPlugin` service of its own, so nothing loads it by name. It is
  dropped.
- The Hadoop MapReduce compat jar is **derived** in-script from the pinned
  `hadoop-mapreduce-client-core-2.8.5.jar`, keeping exactly the
  `org/apache/hadoop/mapreduce/**` package. Iceberg's shaded parquet write path
  lazily loads the un-shaded `FileInputFormat` (M-15/M-16), while the full jar's
  `org/apache/hadoop/mapred/**` would clash with the 3.3.x `Configuration`
  bundled in the Fluss filesystem jars (`NoSuchMethodError getTimeDuration`).
  File mtimes are pinned so the output is byte-reproducible; two independent
  runs produced identical bytes, and the result carries its own SHA256.

## 3. Why the Hadoop config is baked instead of bind-mounted

Flink's own `bin/config.sh` auto-detects `/etc/hadoop/conf` and appends it to
the JVM classpath with zero settings, so baking the file needs no environment
variable and no per-node bind mount. That matters here: `docker stack config`
resolves **relative** bind mounts to absolute paths at parse time, and Swarm
then resolves them **per node** — so a bind mount would need the same file at
the same absolute path on every worker, which the stack cannot express portably.
The config is client-side only; the Fluss *servers* read their object-store
settings from `FLUSS_PROPERTIES`, not from this file.

`core-site.xml` holds `${env.NAME}` placeholders and no credential value. The
entrypoint bridge `20-r2-secrets-from-file.sh` copies the Swarm `*_FILE` secret
mounts into the environment Hadoop expands, then execs the base image's
entrypoint with the container's own arguments. A `*_FILE` that is set but
unreadable **aborts startup** rather than booting a cluster that cannot write
its checkpoints; an unset variable is not an error, so local compose runs that
pass credentials directly are unaffected.

## 4. Two traps worth remembering

- **Setting `ENTRYPOINT` in a Dockerfile clears the base image's `CMD`.** A
  null command makes the Flink entrypoint print nothing and exit 0 — the same
  silent failure as defect 1, reintroduced by the fix for the secrets bridge.
  `CMD ["help"]` is re-declared, and
  `test_entrypoint_is_the_secret_bridge_with_a_fallback_cmd` guards it.
- **A non-root container cannot delete a root-owned baked file.** A negative
  control that "removes" the baked config to prove it is load-bearing silently
  fails and gives a false pass. The proof used a separately built no-config
  image variant instead.

## 5. Pinning: what is pinned, and what is not

| Layer | State |
| --- | --- |
| Base image | Digest-pinned: `flink:2.2.1-scala_2.12-java17@sha256:1934ab4b…` |
| Every jar | SHA256-pinned in `fetch-jars.sh`, verified at fetch and re-verified after the build |
| The built image itself | **Not pinned** — see below |

`runtime.lock`'s `FLINK_IMAGE` is deliberately **unchanged** and still names the
stock digest. A locally built image that was never pushed has no registry
manifest digest: `repo@sha256:<image-id>` does not resolve, because digest
resolution goes through `RepoDigests`/manifests and not the config blob.
Pinning the image id would produce a reference that cannot be pulled. The pin is
completed by pushing and then running
`code/01_platform/04_scripts/digest-pin.sh <repo>:<tag>` — do not invent a digest
here.

## 6. Not covered

- **No deploy was performed.** `docker-stack.yml` parses (`docker stack config`
  exit 0, four `command:` entries, two `AWS_REGION` entries) and the image runs,
  but the stack was never deployed to a Swarm and no job was ever submitted to
  it. Defect 3 — the connector actually loading inside a submitted job — is
  inferred from the jars being on the classpath, not proven by a running job.
- **The 4-VM Swarm was not exercised.** This is offline plus single-container
  evidence on a laptop, consistent with the M2/M3 split in
  `docs/08_implementation/09-production-swarm.md`.
- **Residual risk on the dropped SNAPSHOT jar.** 106 entries shared with the
  published pair differ in bytes (99 are Hadoop internals, 7 are metadata).
  Nothing loads that jar directly, but the only definitive test is a running
  tiering job — a live drill, out of scope here.
- **No live differential for the `AWS_REGION` default.** `auto` was chosen to
  match the compose file's `s3.endpoint.region`; it was verified to work
  against R2, not asserted as correct for every object store.
