## Why

- Every FlussSink builder set `client.request-timeout` + `client.writer.retries` but never
  the **linger** → the sinks inherited Fluss's **100 ms default**
  (`CLIENT_WRITER_BATCH_TIMEOUT`, ConfigOptions.java:971-974 per FlussWriteProfiles).
- D1 (`FlussWriteProfiles`) measured the mechanism on awaited writers: per-write latency =
  linger + ~2.5 ms; p50 **102.67 ms @ linger 100 → 2.29 ms @ linger 1**. For the Flink sink
  adapter the linger does batch — but CHG-444's residual and CHG-452's spikes both track the
  sink batch queue (`bq_cand` ≈ 101–110 ms).
- Scope: the two sinks chained to the strategy-host subtask (`strategy-host-candidates-sink`,
  `strategy-host-candidates-current-sink`). The feature sink (deliberately on its own
  operator) and the flag-gated intent/decision sinks are out of scope.

## What changed

- `SignalJob.java`: `.setOption("client.writer.batch-timeout", "1ms")` on both signal-sink
  builders (each with a CT-4B comment referencing D1/FlussWriteProfiles).
- Static pin `test_signal_sink_linger_is_pinned` — expects exactly **2** occurrences.
