# CHG-217 — certification hygiene: the two intents probe legs accept the documented refusal

- **Status:** recorded — fixed (2026-09-18)
- **Filed:** 2026-09-18
- **Source:** `make gate-fast` after the certificate: 4 failures inside the same
  1477-test discovery that gate step 3 ran green at 16:35.

## What happened

Two of the four were the `intents` legs of `test_fluss_probes`. They asserted the
probe exits 0 and prints a census, while the probe deliberately refuses that —
its header records the Fluss 0.9.1 measurement (25 rows by batch scan, 41 by
offset-paged read, 48 by the server's count) and the rule that a read which
disagrees with `Admin.getTableStats` fails loudly instead of printing a short
total. On this cluster it read 23 while the server reports 27, so it withheld
the census and exited 1.

The tests passed in run 6 only because `Execution_Intent` had not grown yet; the
drill then wrote to it. So the suite was data-dependent, and the next gate run
would have failed step 3 for a probe that behaved correctly.

The fix is the convention the file already applies to the sibling `orphans` leg:
both outcomes are accepted, and what stays forbidden is a census printed from a
read that disagreed. The refusal branch additionally requires stderr to name
both figures (`census read N rows but Fluss reports M`) and forbids any
`rows=`/`table=` line on stdout. Applied to both legs, plus the verification
tiers documented in `11-testing-and-release.md` and the two dated count
corrections in `01-foundation.md` that the same review surfaced.

## 2026-09-18 — follow-up: a refusal is reported as a skip, not a pass

The tolerance above was correct on the contract but silent on coverage. A refusal means the
leg verified nothing about the property it is named for, while the suite still said "OK" —
the same failure shape the legs exist to catch, one level up.

The three live census legs (`test_the_two_table_orphans_run_names_both_tables`,
`test_the_intents_run_agrees_with_the_server_row_count`,
`test_the_scanned_table_is_the_one_printed`) now call `skipTest()` **after** asserting the
refusal contract, quoting both counts in the reason. So the certificate's own
`Ran 1476 tests … OK (skipped=N)` line carries how many live properties went unverified this
run, and a *broken* refusal still fails — the assertions run before the skip. No tolerance
was widened; only the classification of an accepted refusal changed (pass → skip).

Consequence, as measured rather than predicted: while the census refuses (the current live
state — the probe reads 23 rows of `Execution_Intent` where the server reports 27), the
python suite reports `OK (skipped=11)` in the gate-fast run that closed this batch. Itemized
from that run's `-v` output: 5 × the `set DIGEST_PIN_LIVE=1` live-registry opt-outs, 2 × the
probe suite's by-design red legs, 1 × the bench's "stack is up" guard, and these 3 legs. The
baseline is therefore 8, all of it opt-in by design — **not** the 12 this record first
predicted from run 6's 9, and not "environment-dependent" either, which is what an earlier
revision of this paragraph guessed before the run was itemized.

Run 6's extra skip cannot be itemized at all: gate step 3 runs unittest without `-v`, so a
certificate records the skip *count* and never its membership. T0/T1 runs are the only ones
that can be audited that way — worth knowing when a future `skipped=N` moves.

The total is 1476, not the 1477 measured above: CHG-218 retired one leg the same day.
