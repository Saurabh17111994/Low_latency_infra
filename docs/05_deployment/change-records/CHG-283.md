## Why

CHG-273 collapsed the metric scrape into a single collector and pointed the two infra jobs at
`tasks.node-exporter:9100` / `tasks.cadvisor:8080` as **static** targets. Its comment and the test docstring both
state the reason: "`tasks.` returns EVERY task of the service, so this one collector scrapes all four nodes."

That is not what a static target does. Measured 2026-09-21 with a throwaway Prometheus against a name resolving
to 8 addresses:

| Form | Targets discovered | `instance` label |
|---|---|---|
| `static_configs: targets: ["<name>:443"]` | **1** | `<name>:443` — the name |
| `dns_sd_configs: names: ["<name>"], type: A, port: 443` | **8** | one address each |

So the collector scraped exactly one arbitrary agent per job and labelled it with a name that is identical on
every node. On two nodes that is not merely missing attribution: the node that was reached is indistinguishable
from the node that was not, so a panel shows one machine's numbers as if they were the platform's. Locally the
bug is invisible — one node, one agent, `1/1` either way.

The single-writer rule from CHG-273 is not weakened by this; it is strengthened. With discovery that actually
returns every agent, a collector on every node would scrape every agent from every node, storing each host
metric once per collector.

## What this changes

Both jobs move to `dns_sd_configs`, which yields one target per agent, each labelled with its own address. Adding
a node adds an agent, and DNS publishes it — no config change, no per-node list. `infra-zookeeper` stays static:
`zookeeper-1`/`-2`/`-3` are three single-task services, not one name with many addresses.

The compose collector config is deliberately untouched. It is single-host, and it already avoids `tasks.` for
the reason its own comment gives.

## Verification

- `test_16_otel_collector_split.py` → 7 passed; the static mutation fails it; restore byte-identical.
- Both jobs read back from the parsed YAML as `dns_sd_configs` with the expected name, type and port.
- The mechanism itself was measured, not assumed: the table above is a real Prometheus discovering real
  addresses. What remains unmeasured is whether a single static target sticks to one address or rotates between
  them per scrape — either way it cannot label them apart, and `dns_sd_configs` needs no answer to that question.
- In situ, after a fresh create of the deck (a swarm config is immutable, so only a fresh create applies it):
  the same OpenObserve stream now holds both labels, which shows the changeover in one query —
  `tasks.node-exporter:9100` (the static target, before) and `10.0.1.27:9100` (a discovered agent, after) — and
  `node_uname_info.nodename` names the node itself (`saurabh-MS-7D90`), so a panel can attribute by address or
  by name. On two nodes this is the acceptance test: the query must return one address per node.

## Correction (2026-09-21, CHG-287)

The `test_updates` field above names `test_16` only, and `test_16` is all that was re-run. This change also turned
`test_09_stack.py::test_per_host_agents_identify_their_node_and_one_collector_scrapes_them_all` red: that assertion
collected its target set from `static_configs` alone, and the infra jobs had just moved to `dns_sd_configs`.
Measured 2026-09-21, when the canonical pytest run was next run: `1 failed, 436 passed`. CHG-287 repoints the
assertion (both mechanisms, plus a real anti-VIP clause) and the run is green again (`437 passed`).

The in-situ proof in this record is unaffected — the same stream holding a name before and an address after still
shows the changeover, and the acceptance ("one address per node") is unchanged. What this correction adds is the
lesson: a mechanism change needs the *whole* suite re-run, not only the tests that were edited.
