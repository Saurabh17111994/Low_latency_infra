## Problem

raw_table_1 tiered to R2 iceberg as one unpartitioned iceberg table: lake
reads grew unbounded with table size, and per-day restore (Item 5) required
full-table scans. Retention/EOD also had no way to verify that a trading
day's copy exists in the lake.

## Change

- **Schema v3** (2026-08-31, live table id 76): `event_day STRING` (yyyyMMdd,
  Asia/Kolkata) added as first column (21 columns total, schema version 3);
  `PARTITIONED BY (event_day)` with auto-partition DAY (precreate 2,
  retention 7d); bucket key unchanged (`instrument_token`, 16 buckets);
  `table.datalake.enabled=true` at create (create-only option in Fluss 0.9.1).
- **Iceberg layout is now day-partitioned**:
  `lake/default/raw_table_1/data/event_day=<yyyyMMdd>/instrument_token_bucket=<N>/*.parquet`.
- **Migration**: old table dropped; pre-migration objects archived to
  `lake/_stale-20260831-v1/raw_table_1/` (62 objects, retained as history).
- **Tiering classpath fix** (was killing the tiering job under sustained
  write volume): minimal `hadoop-mapreduce-compat-2.8.5.jar` mounted into
  both flink containers — see
  `code/01_platform/01_docker/fluss-plugins/iceberg/README.md` for the
  rebuild recipe and the known-bad uber jar. `tiering-start.sh` guards both.
- **EOD lake verifier** (`--offload lake`): EOD verification now reads R2
  evidence (day-folder objects + iceberg manifests) instead of export
  bundles; raw_table_1 2026-08-31 verified live.
- **Ops tooling**: r2-list / r2-move-prefix / r2-query (DuckDB SQL over the
  lake) / r2-restore (one-day parquet pull) / lake-guard (cron health check)
  / tiering-smoke (guarded E2E proof) — documented in
  `docs/06_operations/07-lake-archive-ops.md`.

## Compatibility

INCOMPATIBLE for the table itself: the table was dropped and recreated
(readers pinned to the 20-column v2 shape or the old table id break).
Ingestion writers were upgraded in the same change set. Downstream
consumers read the lake via DuckDB/iceberg (`r2-query.sh`) — the day-folder
layout supersedes the flat layout.
