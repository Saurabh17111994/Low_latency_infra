  real R2 bucket: with the production `datalake.iceberg.*` config the **stock**
  image exits with `NoClassDefFoundError: org/apache/hadoop/conf/Configurable`
  while the **derived** image starts and loads the Iceberg HadoopCatalog. It is
  **not deployed**: the built image has no registry manifest digest yet, so
  `FLUSS_IMAGE` still names the stock digest.
- **Filed:** 2026-09-16
- **Closed:** 2026-09-16 — `make fluss-image` built a real image (image id
  `sha256:acfe030b…`). Against the same server.yaml, same network and same
  credentials, the stock image **exited** at startup and the derived image
  **ran**, logging `Successfully start Netty server` and
  `Loading custom FileIO implementation: org.apache.iceberg.hadoop.HadoopFileIO`.

  the isolated ZooKeeper chroot was removed afterwards.
- **Corrects:** CHG-181/CHG-182, whose `remote.data.dir` work covered **log/KV**
  tiering only. This record covers the **lake** tiering path, which needs a

## 1. What was wrong

The production stack sets the 36 `datalake.iceberg.*` keys on all four Fluss
services and 17 DDL tables declare `table.datalake.enabled = 'true'`, but the
image those services run cannot load an Iceberg catalog. Fluss loads
`/opt/fluss/plugins/<name>/` as **separate classloaders**, and the stock
`apache/fluss` image ships `fluss-fs-s3` and `fluss-fs-hdfs` in `plugins/s3/`
and `plugins/hdfs/` — directories the `iceberg` loader cannot see. Iceberg's
`HadoopCatalog` needs `org.apache.hadoop.conf.Configurable`, which lives in
those jars, so catalog construction dies.

| Image | Result with the identical `datalake.iceberg.*` config |
| --- | --- |
| **Stock** `apache/fluss` | container **exited** — `NoClassDefFoundError: org/apache/hadoop/conf/Configurable`, wrapped as `Cannot initialize Catalog implementation org.apache.iceberg.hadoop.HadoopCatalog` |
| **Derived** | container **running** — Iceberg `HadoopCatalog` constructed, `Successfully start Netty server` |

Class resolution in the iceberg plugin classloader, measured on 2026-09-16:

| Class | Stock | Derived |
| --- | --- | --- |
| `org.apache.hadoop.fs.s3a.S3AFileSystem` | MISSING | RESOLVED |
| `org.apache.hadoop.hdfs.HdfsConfiguration` | MISSING | RESOLVED |
| `org.apache.fluss.fs.s3.S3FileSystemPlugin` | MISSING | RESOLVED |
| `org.apache.fluss.fs.hdfs.HdfsPlugin` | MISSING | RESOLVED |

## 2. Why this only appears on a fresh clone

The dev compose **does** work, because it bind-mounts those two jars out of
`code/01_platform/01_docker/fluss-plugins/`. That tree is gitignored
(`.gitignore` line 6 is `*.jar`) — `git ls-files` on it returns exactly one
file, the README. So the jars exist only on a machine where someone downloaded
them by hand, and a Swarm stack cannot express a per-node bind mount portably
anyway. The image carries them instead, which is the same conclusion CHG-179
reached for Flink.

## 3. The two judgement calls

Both mirror CHG-179, for the same reasons:

- **`fluss-fs-hadoop-shaded-0.9-SNAPSHOT.jar` is dropped.** It is unpublished —
  HTTP 404 on Maven Central **and** on the Apache snapshots repository — so it
  cannot be checksum-pinned and cannot be part of a reproducible image. All
  12898 of its entries are already present in the published
  `fluss-fs-s3` + `fluss-fs-hdfs` pair (verified entry by entry: **0 missing**),
  and it declares no Fluss `FileSystemPlugin` service of its own, so nothing
  loads it by name.
- **No `hadoop-mapreduce-compat` jar here.** That jar exists for Iceberg's
  parquet *write* path, which runs in the Flink tiering job — not in the Fluss
  servers. Fluss 0.9 tiers from an external Flink job
  (`code/01_platform/04_scripts/tiering-start.sh`: the coordinator only
  coordinates). The dev tablet carries no compat jar and lake tiering works
  there, and the Flink image already ships one.

## 4. One measurement trap

An earlier attempt at this test used `remote.data.dir: s3://…` and appeared to
show the stock image resolving S3A — its stack trace named
`S3AFileSystem.bindAWSClient`. That is **log/KV** tiering, which loads
`plugins/s3/` and was already working (FACT-011). The lake path is a different
classloader entirely. To exercise lake tiering the config must carry
`datalake.*`, and it must include `datalake.iceberg.iceberg.hadoop.fs.s3.impl`
and `…fs.s3a.impl` — without those two, the classloader is fixed but startup
instead fails `No FileSystem for scheme "s3"`, which looks like the same bug and
is not.

## 5. Pinning: what is pinned, and what is not

| Layer | State |
| --- | --- |
| Base image | Digest-pinned, and asserted equal to `runtime.lock`'s `FLUSS_IMAGE` |
| Both jars | SHA256-pinned in `fetch-jars.sh`, verified at fetch and re-verified after the build |
| The built image itself | **Not pinned** — see below |

`runtime.lock`'s `FLUSS_IMAGE` is deliberately **unchanged** and still names the
stock digest. A locally built image that was never pushed has no registry
manifest digest: `repo@sha256:<image-id>` does not resolve. The pin is completed
by pushing and then running
`code/01_platform/04_scripts/digest-pin.sh <repo>:<tag>` — do not invent a digest
here.

## 6. Not covered

- **No deploy was performed.** This host is a Swarm worker, so no
  `docker stack deploy` ran and the 4-VM Swarm was not exercised.
- **No tiering job was run against the derived image.** The evidence is that the
  servers load the Iceberg catalog and start. That a tiering job then writes
  parquet to the lake prefix is NOT proven here — it needs the Flink tiering
  service plus a `table.datalake.enabled = true` table, and it remains the
  open item recorded in FACT-013/FACT-014.
- **Residual risk on the dropped SNAPSHOT jar**, identical in kind to CHG-179's:
  shared entries differ in bytes where the published jars disagree with the
  SNAPSHOT. Nothing loads it by name, but only a running tiering job settles it.
