## Notes

- **Why saturation matters here:** the row's `connection_epoch` is broker-reported; a saturated
  Long.MAX_VALUE epoch would be accepted as valid and would defeat epoch comparisons downstream
  (a bogus epoch that looks like the newest one). Fail-closed parsing is the contract.
- **The bound is now written once per branch and the branches agree:** double and float both check
  `d < -0x1p63 || d >= 0x1p63` on a widened double, so float rounding can never land outside the
  double-checked range.
- **The int path was already correct:** `Integer.MIN_VALUE`/`MAX_VALUE` promote to doubles exactly,
  so `d > Integer.MAX_VALUE` rejects 2^31 as intended — no change, no test churn.
