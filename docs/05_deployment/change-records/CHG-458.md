## Why

- **Stale-file theory:** the changelog base path is a persistent shared volume
  (`01_docker_flink-checkpoints` -> `/checkpoints`); every run leaves `<jobid>/` changelog
  dirs behind (35 job dirs / 1.9 GB by 2026-09-30), and each TM restart resets the in-memory
  `TaskChangelogRegistry`, which no longer tracks them — matching the 457-465 "state is not
  in tracking" WARNs per round, the TM CPU bursts, and the e2e creep. Profiler runs need no
  cross-run restore, so wiping is the correct precondition (fail-closed: a dirty changelog
  invalidates comparisons).
- **Upload-burst theory:** with the pinned default `preemptive-persist-threshold: 5MB`, a
  subtask accumulates up to 5 MB of changes before uploading; persistence therefore happens
  mostly at checkpoint time (every 10 s), so each checkpoint carries an upload burst on its
  async path. 1 MB starts the upload earlier and quasi-continuously (the option's documented
  purpose: "Improves checkpointing time … as opposed to uploading all accumulated changes on
  checkpoint"), at the cost of more/smaller files. All other `dstl.dfs` options were
  verified in the pinned 2.2.1 bytecode (`FsStateChangelogOptions`) and left at defaults —
  the compose comment records the whole verified set (persist-delay 10 ms,
  persist-size-threshold 10 MB, upload buffer 1 MB, 5 upload / 1 discard threads, in-flight
  limit 100 MB, retry fixed / 3 attempts / 500 ms backoff / 1 s timeout, cache idle 10 min).
