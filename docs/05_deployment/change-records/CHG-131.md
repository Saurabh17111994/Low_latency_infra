# CHG-131 — Production stop runs the clean-shutdown sequence; shutdown signals registered once

- **Status:** recorded — execution-gate shutdown behaviour changed, fail-closed strengthened
- **Filed:** 2026-09-14
- **Source:** wave-4 close, open decision items D3 and D7 (approved by the operator 2026-09-14)

## What changed

Two changes on the executor's **production** stop path — both were previously test-only or
per-iteration, and both are fail-closed in the sense that the *silent* outcome was the unsafe one.

### D7 — the audited clean-shutdown sequence now runs on the production path

`BridgeExecutionClient::stop` is the terminal `ExecutionClient` lifecycle hook that
`ExecutionEngine::stop` calls from the node's `finalize_stop`. It used to clear a flag and return.
The client's queued bridge jobs and its report stream live *inside* the node and are reachable from
nowhere else, so a stop dropped in-flight attempts without counting them, flushed no report
evidence, and never checked the restart invariant. `ShutdownCoordinator` existed and was tested,
but nothing in production called it.

The hook now runs the audited sequence — safety-halt the execution gate → abandon queued jobs as
unresolved attempts → flush remaining reports — records the resulting `ShutdownReport` into a
`ShutdownWatch` the runtime can read after the run loop, and returns `Err` (logged by the engine)
when the gate does not reach `HALTED`, which is P3-460's check becoming reachable in production.
`main` reads that evidence and exits non-zero if `verify_restart_safe` does not hold, so an exit
that leaves the execution fence armed can no longer be silent.

The idempotence guard is a dedicated flag rather than `ExecutionClientCore::is_stopped()`: that
predicate is `!is_started()`, already `true` for a client that was never started, so the old guard
skipped the sequence for exactly the clients a startup abort stops.

### D3 — shutdown signals are registered once, before the run loop

`main` re-created the SIGINT/SIGTERM streams on every drift tick. A signal delivered while the loop
was inside another branch reached no live listener and, because tokio owns a signal's disposition
once it has registered a handler, was dropped: an operator's stop request could be lost instead of
ending the process. The streams are now installed once before the loop, `recv()` is awaited per
iteration (documented cancel-safe), and a `shutdown_fired` guard makes the branch fire at most
once. A second signal is deliberately not acted on — the process is already draining — and the
container stop timeout / `SIGKILL` remains the escalation path.

## Limitation

The `main`-level check's failure branch (armed fence → non-zero exit) is unit-tested through
`assert_restart_safe`; the "no report at all" branch logs an error rather than failing the exit,
because the gate invariant — not the presence of evidence — is the safety-critical half.
