## Problem

C5 (levers map): "KV point-lookup flakiness — known intermittent Fluss
0.9.1 issue — file upstream or work around; currently untracked". The
historical symptom (2026-08-17, CHG-021/022) was *hanging* lookup futures
in the dedup hot path (unbounded `.get()`), fixed by moving dedup to Flink
keyed state — but the underlying Fluss client behavior remained: no
per-request timeout on inflight RPCs, and transients retried internally up
to `client.lookup.max-retries` (default `Integer.MAX_VALUE`).

## Root cause (verified against Fluss 0.9.1 source, local checkout `v0.9.1-incubating`)

1. `ConfigOptions.java:1186` — `client.lookup.max-retries` default
   `Integer.MAX_VALUE`: the lookup sender re-enqueues any
   `RetriableException` (incl. `NetworkException` on connection loss)
   without limit.
2. `fluss-rpc/.../ServerConnection.java:327` — `// TODO: maybe we need to
   add timeout for the inflight requests`: no RPC-level bound exists; a
   silent (established-but-unresponsive) connection leaves the future
   pending until `netty.connection.max-idle-time` (default 10 min).
3. Result: the caller's `.get(timeout)` is the only bound. A transient
   that outlasts it (measured ~5s leader-election settle, CHG-020, vs
   default 2s `GATEWAY_REQUEST_TIMEOUT_MS`) surfaces as an intermittent
   `TimeoutException` → `UNAVAILABLE` (control reads) or thrown exception
   (ledger reads) — the "flakiness" — even though the RPC would have
   recovered milliseconds later.

Blast radius (grep-verified): the hot ingestion/signal path uses **no**
point lookups (dedup is Flink keyed state since CHG-022). The only
production `Lookuper` consumers are the execution gateway's
`FlussControlStateStore` and `FlussProjectionLedgerStore` (opened in
`ExecutionGatewayMain`). `FlussFormingBarStateStore` (compute) is not
wired into any production path — tests/verification only.

## Change

- **`BoundedRetry`** (new, gateway package): retry a `Callable` up to 3
  attempts with 200ms backoff, retrying only `TimeoutException` or
  `ExecutionException` whose cause is a Fluss `RetriableException`;
  everything else propagates immediately (fail fast). Total budget
  ≈ 3 × caller timeout + 2 × 200ms ≈ 6.4s > 5s settle.
- **`FlussControlStateStore.lookup`**: wraps the lookup await in
  `BoundedRetry`; transient blips now recover, permanent failure still
  returns `UNAVAILABLE` (contract unchanged).
- **`FlussProjectionLedgerStore.lookup` and `put`**: same wrap; upsert
  retry is safe (idempotent by eventId, last-write-wins).
- **Deliberately NOT changed**: `client.lookup.max-retries`. The internal
  loop is the recovery mechanism — the same future completes once the
  cluster settles. Bounding it (small N) would exhaust in milliseconds
  during a leader election and convert recoverable outages into
  guaranteed failures. Caller-side retry is the correct layer.

## Guard tests (proven to fire)

- `BoundedRetryTest`: transient timeouts recover (3 calls), retriable
  cause in `ExecutionException` recovers, permanent transient fails after
  exactly 3 attempts (no infinite loop), non-transient fails after 1
  attempt, interrupt during backoff propagates.
- `FlussControlStateStoreFlakyLookupTest`: stub `Connection`/`Table`/
  `Lookuper` — lookup returns `FOUND` after 2 transient failures (guard
  fired); all-failing lookup returns `UNAVAILABLE` after exactly
  `BoundedRetry.ATTEMPTS = 3` calls (bounded, fail-fast).

## Appendix — corrections (2026-09-12, CHG-123)

Appended rather than rewritten: four statements above were later disproved or
made stale by measurement. Nothing above is deleted, so the record still shows
what was believed and why.

1. **"~5s leader-election settle" is superseded** (Problem, root cause item 3,
   and the Change section's "6.4s > 5s settle"). The window is real; the figure
   and the mechanism were inferred. Measured: leader election ~4ms, and the
   cost is the post-election tiering task
   (`LogTieringTask.maybeUpdateCopiedOffset` → `remoteLog.getRemoteLogEndOffset()`,
   lake tiering enabled, sequential per bucket). Quiesced, the first write after
   CREATE costs 2294–2383ms (p50 2336ms, 15/15 over the 2s bound) and the next
   writes 9–29ms. The 6.4s in the Change section is arithmetic, not a
   measurement; CHG-123 measures it and bounds it per request.
2. **"the caller's `.get(timeout)`" is the store's own await, not an external
   client deadline.** The external caller is the Rust executor, which allows 10s
   (`code/02_services/04_executor/src/bridge/transport.rs:85`). The distinction
   matters: this record's budget bounds one store call, not the HTTP request
   that contains it. CHG-123 adds the request-level bound.
3. **"no Fluss fault-injection harness wired to the gateway stores" is stale**
   (Validation). `FaultFlussStubs` exists — in `common` and in the gateway test
   tree — and is used by four store-boundedness test classes; CHG-123 adds
   budget fault-injection on top of it.
4. **`affected_artifacts` above names a path that no longer exists.**
   `BoundedRetry.java` moved to
   `code/common/src/main/java/com/trading/common/schema/fluss/BoundedRetry.java`
   and became public when the shared stores in `common` were wrapped
   (CHG-123 C0a); the gateway-local path was deleted in the same commit.
