## 1. `chaos-04-vm-loss.sh` — a drill must not break the cluster it tests (11 findings)

The script was 102 lines of straight-line code: discover a node, discover a service,
drain, probe, restore. Waves 25–26 introduced the pattern this wave follows — every
knob an overridable seam, every verdict backed by a named gate — and both scripts are
now function-structured so the gates can be driven individually.

### 1.1 Containment — which node the drill may touch (P6-002, CRITICAL)

| Finding | Was | Now |
|---|---|---|
| P6-002 | `docker node ls --format "{{.ID}} {{.Hostname}} {{.Availability}} {{.Status}}" \| grep -v Leader \| head -n 1 \| awk '{print $1}'`. `.ManagerStatus` was not in the format string, so no row ever contains `Leader` and the filter removes nothing; nothing else is checked, so the first row is taken whatever it is — on a single-manager swarm, the manager | `node_rows` requests `.ManagerStatus` as the fifth column, `select_worker` skips every row whose ManagerStatus is non-empty or whose Availability/Status is not Active/Ready, then confirms `docker node inspect --format '{{.Spec.Role}}'` is `worker`, and `resolve_node` refuses an explicit `CHAOS_WORKLOAD_NODE` that resolves to a manager with a usage error (exit 2) instead of draining it |

Behavioural evidence (not a paraphrase — both sides ran against the same fixture):
the pre-fix line, taken verbatim from the wave-27 parent commit, selects **`m1`, the
manager**; `select_worker` selects **`w3 node3`**, the only Active+Ready worker, and
skips the drained and the down node. Transcript in the wave-27 log.

### 1.3 The poweroff path: no injection, and it can still undo itself (P6-055, P6-054, P6-720)

| Finding | Was | Now |
|---|---|---|

### 1.4 The two verdicts (P6-056, P6-057)

| Finding | Was | Now |
|---|---|---|
| P6-056 | the order-halt loop only `break`ed when the port refused; every other path fell out of the loop into the PASS echo, so an order front door that stayed up all drill satisfied "halted". The address travels as argv (`/dev/tcp` through a child `bash` with the validated host and port passed as arguments), never as interpolated shell source. ### Red leg — what it proves and what it does not

Every one of the 61 cases fails against the pre-wave scripts, but for 60 of them the
reason is structural: the pre-wave scripts were straight-line code (94 and 102 lines
with no function definitions at all), so the extracted function set was empty and the
driven gates simply did not exist. That demonstrates the suite is not vacuous; it does
**not** demonstrate that each individual behaviour was wrong (the per-finding evidence
for that is the audit's line-level findings, quoted in the tables above). P6-002 is the
exception: it is additionally demonstrated behaviourally, both sides running against
one fixture, with the pre-fix line taken verbatim from the parent commit.

A residual limitation worth stating: these tests drive the *new* decomposition. A later
edit that folds a gate back into straight-line `main` would break the extraction and
fail the suite loudly — but a later edit that keeps the function names and weakens a
gate's body is only caught where a test pins that body's decision.

### Live evidence — no drill was run (approved)

This wave was verified by tests only. No node was drained, no host was powered off and
no TaskManager was killed for this record; every claim above about drill behaviour is
either a line-level reading of the script or a stubbed execution of it. The live drill
also could not have run here: the Monday-gate preflight for this wave refused to start
on environment drift — `fluss-coordinator` and `fluss-tablet` are `exited (127)`, and
the dev ingestion container has been `exited` for ~20 h — and the chaos drills need a
live swarm and a live cluster respectively. Consequently the *live* half of both drills
including the poweroff rejoin path and the real TaskManager restart SLO remains
unverified by this change; it is verified on a live stack only when a drill is next run
against one.

  failed / 2 usage / 3 named skip; chaos-02: 0 pass-or-named-skip / 1 fail / 2 usage).
  The skip is always logged with its reason.
