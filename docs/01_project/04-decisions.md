| DEC-042 | EXECUTION AUTHORITY AND SERVICE BOUNDARY (2026-08-19): Nautilus is the authoritative execution engine for live order lifecycle, fills, positions, PnL, and broker reconciliation. It runs as a separate long-lived Rust-native execution service. Flink/Fluss publish immutable execution intent and consume projections; they do not implement a second order or position state machine. A custom Nautilus `ExecutionClient` adapter commands the localhost-only go-arrow bridge; only the bridge holds Arrow credentials and reaches Arrow. Fluss remains authoritative for platform commands, safety control state, and queryable execution projections. | Reuses Nautilus's native OMS, portfolio/position engine, risk engine, reconciliation, fill deduplication, and event-processing facilities without coupling money movement to Flink task lifecycle. | Adds a Rust service, an adapter, a bridge protocol, and a projection boundary. Nautilus event-store durability and the Fluss projection contract require dedicated integration and recovery evidence before live-money enablement. |
| DEC-043 | AUDIT RETENTION POLICY (2026-08-19): The fixed seven-year money-moving audit duration is removed. Execution, gate, order, fill, mapping, approval, reconciliation, and action audit SHALL remain immutable, encrypted, integrity-verifiable, access-controlled, offloaded, recoverable, and retained for **at least one year**, or longer when the approved jurisdictional, contractual, legal-hold, or operational policy requires it. Retention-policy changes require authorized review and immutable change evidence. | A one-year minimum provides a concrete operational baseline while allowing approved policy to impose a longer period without changing the platform contract. | The compliance owner must approve the one-year baseline and any longer or shorter policy; retention evidence, deletion governance, and recovery tests remain release requirements. |
| DEC-044 | GATE & AUDIT SINGLE-OPERATOR (2026-08-21, user decision — Saurabh): Resume from order safe-halt and audit deletion inside retention both require **a single authenticated approval by `saurabh`** for the same gate epoch/evidence hash (or deletion scope/policy/legal-hold). Supersedes DEC-019 (two-person) and the two-person audit-deletion rule. Authorized operator set is `{saurabh}`; a second distinct approval is not required and not checked. | Matches single-operator reality; removes blocking on a second approver; retains fencing + evidence-hash + immutable audit. | Loses the two-person safety redundancy — unilateral mistaken `ENABLED` is now possible. Must rely on fencing + evidence audit. |
| DEC-046 | DEDUP TTL REDUCED 300s → 60s (2026-08-28, CHG-116): `DEDUP_TTL_MS` pinned at `60000` (1 minute). Basis: the broker's API docs (`Arrow_broker/llms-full.txt/index.md`, all 9,115 lines) describe `sub` = "start receiving data", reconnect = resubscribe + 540-byte ack, and contain no replay/backfill/catch-up language anywhere — per user decision the broker never replays old ticks on reconnect. The duplicate horizon is therefore checkpoint restore rewind (≤ 10 s) + connector rewind + ingestion retry, all well under 60 s; 60 s = 6× margin. The `SIGNAL-warn-dedup-state` alert re-based 6.5M → 3.6M entries (60k t/s × 60 s). Supersedes the 300 s conservative margin (DEC-030-era assumption of unverified broker replay) for the dedup horizon; DEC-030's broker-recovery bound itself is unchanged. | The docs rule out broker replay, so 300 s was over-conservative; 60 s cuts dedup state ~5× (2.45 GB → 0.49 GB at 60k/s envelope). | Residual: the broker docs are silent on server-side snapshot-on-subscribe; a current-state packet per symbol on reconnect would be new content, not a re-sent historical packet, so dedup would not treat it as a duplicate. If a future broker change introduces replay, the TTL must be re-raised above the replay depth + margin. |

| DEC-047 | Production healthchecks are LIVENESS ONLY: no probe may depend on another service, on cluster formation, or on quorum. Swarm publishes a DNS record only for tasks whose healthcheck has PASSED, so a probe that waits for peers can never pass — every peer it waits for is equally unresolvable. Cluster state belongs in metrics, logs and alerts. | Removing the dependency removes a whole bootstrap-deadlock class: ZooKeeper's `zkServer.sh status` probe held all three members in `Starting` until the health monitor killed them (exit 143), so the ensemble could never form and the thirteen dependent services could never start. | A member that is alive but has lost quorum still reports healthy; quorum loss must be alerted from metrics instead of surfacing as a container restart. |
| DEC-048 | Secrets reach services as FILES (`/run/secrets/<name>`, read through a `*_FILE` variable). A mounted secret MUST be consumed — either by a `*_FILE` variable pointing at it, or by a mounted config that reads the file itself (the OpenTelemetry collector's `${file:…}` expansion). Where a third-party image cannot read a file at all, the service carries no mount and takes the value from the deploy environment, with the reason recorded at the stack. | A mounted-but-unread secret fails SILENTLY — the service starts without the value. Five services in the production stack had it: openobserve crash-looped on a missing root password, and execution-gateway, nautilus and the ingestion Arrow bridge would have started credential-less at the first live boot. | An image that cannot read files leaves its value visible in `docker service inspect`, which is weaker than a Swarm secret. |
| DEC-049 | The ZooKeeper ensemble is configured through the image's own environment: `ZOO_SERVERS` whitespace-separated (the image writes one `server.N=` line per token), plus `ZOO_CFG_EXTRA` carrying `clientPort=2181`, `quorumListenOnAllIPs=true` and a loopback-only admin server. | The image ships no `zoo.cfg` and generates one from `ZOO_*`. `;`-separated members collapse into a single invalid line (exit 2); a missing `clientPort` leaves 2181 closed for Flink and Fluss; and without `quorumListenOnAllIPs` the election port binds through a DNS lookup of the member's own service name, which cannot resolve before quorum exists. | The ensemble's configuration lives in three service blocks instead of one file; `test_09_stack.py` pins every part of it. |
| DEC-050 | Everything a production deploy needs comes from the repository plus Swarm objects: the instrument manifest is a committed file mounted as a Swarm config, images are pinned digests from the registry, and nothing is placed by hand on a VM. | A re-deploy is then a clone plus one command, and a VM can be rebuilt without archaeology. A hand-placed CSV was the failure that stopped ingestion at first boot ("readable manifest FILE is required"). | Editing the manifest needs a new config name, because Swarm configs are immutable — one line in the deploy, no downtime. |
| DEC-051 | Nothing binds to its own service name: every listener a service needs in order to start binds a literal address, and the advertised address keeps the resolvable service name (resolvable only once the task is Running, which is when clients need it). | Binding our own name deadlocks the first start: Swarm publishes a name only for Running tasks, so resolution fails before we can become them. Measured on the rehearsal Swarm - the Fluss coordinator logged "Failed to start Netty server on endpoint INTERNAL://fluss-coordinator:0" / UnresolvedAddressException and cycled in Starting until the update rolled back. A literal in the advertised address would instead tell every client to dial itself. | The bind line and the advertised line must be read as a pair; test_09_stack.py asserts both halves (and checked>=4) and fails on either half drifting. |

| DEC-052 | Fluss 1.0.0 upgrade pin (2026-09-22): Fluss 1.0.0 (was 0.9.1-incubating, DEC-021); Flink 2.2.1 and Java 17.0.19 unchanged. Pinned in versions.pin + parent POM. Native KV TTL and standby replicas cut patch work; create-time-only options mean existing tables adopt via recreate. | 1.0.0 is the maintained line with the capabilities the storage docs now cite; staying on incubating 0.9.1 accrues compatibility risk. | Re-certification required (Stage 8 to 9); final certificate pending. |

## Event fingerprint decision

The canonical fingerprint includes stable normalized values available in the decoded packet:

```text
event_fingerprint = hash(
  connection_id,
  instrument_token,
  event_time,
  tick_type,
  price and quantity fields,
  depth fields present in the packet
)
```

The fingerprint algorithm, numeric canonicalization, field order, and TTL are versioned. The raw canonical payload is retained for audit. Two byte-equivalent market events inside the TTL may be collapsed; therefore the guarantee is best-effort, not exact.

Without a broker sequence number, the platform cannot calculate exact missing sequence ranges. It may report suspected discontinuities from connection drops, heartbeat gaps, exchange-time jumps, or feed-health signals.
