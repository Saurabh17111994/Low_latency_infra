# Fluss 1.0.0 native adoption — backlog (workstream 2 of 2)

**Sequencing:** DEC-053. Workstream 1 is the `0.9.1-incubating → 1.0.0` upgrade
(`2026-09-22-fluss-1.0-upgrade.md`), which certifies the **same behaviour on the new
version**. This file is workstream 2: adopting capabilities 1.0.0 adds that we do not
use. They are deliberately separate — a failure in one must not be readable as a
failure in the other.

**Entry condition:** the upgrade certificate is green (Stage 9), and the parked
tiering verification is closed or explicitly waived (see "Carried-in gaps" below). *(satisfied 2026-09-23 — record in the upgrade plan)*

## The premise-breaking finding

Every DDL and runbook assumption in this repo says *"Fluss cannot ALTER table options,
so an options change requires drop + recreate."* That is now false for most of what we
would want to change. The alterable allowlist grew **3 → 14** options between 0.9.1
and 1.0.0:

| alterable in 0.9.1 (3) | newly alterable in 1.0.0 (+11) |
| --- | --- |
| `table.datalake.enabled` | `table.log.ttl` |
| `table.datalake.freshness` | `table.log.local-ttl` |
| `table.tiered.log.local-segments` | `table.kv.standby-replica.enabled` |
| | `table.datalake.historical-partition.enabled` |
| | `table.datalake.database-name` |
| | `table.datalake.table-name` |
| | `table.datalake.auto-compaction` |
| | `table.auto-partition.enabled` |
| | `table.auto-partition.num-retention` |
| | `table.auto-partition.num-precreate` |
| | `table.statistics.columns` |

Source: `FlussConfigUtils.ALTERABLE_TABLE_OPTIONS`, both worktrees
(`fluss/Fluss_v_0.9.1` and `fluss/Fluss_v_1.0.0`). Note `table.kv.ttl` is **not** in
the list — create-only, proven by the 2026-09-22 scratch probe
(`InvalidAlterTableException`).

## Candidates, ranked

Ordered cheapest-and-safest first. **Nothing here is measured at runtime** — every
item is source-verified only, and each needs its own probe before adoption.

### 1. `table.log.ttl` alterable — removes recreate from routine operations
Retention currently spans 60 s to 90 d across 27 tables, and changing any of them
today means a drop + recreate. With this alterable, a retention change is an ALTER.
Touches the `DdlApplyTool` "options change requires drop + create" contract, the
`Execution_Gate recreate` runbook, and `02-schema-storage.md`.

### 2. `client.scanner.kv.batch-strategy` — retires hand-rolled bulk copy
Bounded KV reads gained a strategy switch:
`snapshot-merge` (default — merges the latest KV snapshot with the bounded changelog
range; resumable, single point in time) or `server-scan` (scans live KV state on the
tablet, skipping snapshot download and changelog replay; not resumable, each bucket
read at its scanner's open time). We built parallel bucket copy plus a drain loop
because per-row `.get()` ran at ~9.6 rows/s (CHG-099) — this is the native path that
could replace it. Measure before deleting anything.

### 3. `table.kv.standby-replica.enabled` — the strategic one, and the blocked one
Standby replicas maintain recent KV snapshots for fast leader promotion, and the
option is ALTERable (no recreate). This attacks the KV single-replica durability gap
that DEC-018 currently answers with "remote storage + rebuild from audit" — across 17
KV tables, 5 of them money-path (`Execution_Gate`, `Positions`, `Order_Lifecycle`,
`Safety_Halt_Requests`, `Execution_Attempts`).

**Blocker (corrected 2026-09-23 by measurement).** The standby is drawn from the table's *assignment*,
so the **table** needs `table.replication.factor >= 2` — a 2-tablet cluster alone is not enough: with
`rf=1` the assignment holds one server and `standby_replicas` stays `[]` (verified live). The original
wording here — "1 tablet; standby replicas need ≥2" — understated it, and that difference *is* the cost
argument: adopting this on a KV table means a **second replica of that table's KV data**, a storage/write
budget question, not merely a missing local-testing convenience.
**Exercised on the scratch cluster** (2 tablets, `rf=2`, `kv.snapshot.interval: 30s`): ZK read
`leader=0 standby=1` *before* the kill, and killing the leader's container restored reads in **42 s** with
**zero row loss** (200 rows, digest `20019900` unchanged) — against 59 s in the dev half with standby off.
Production defines 3. What remains is purely a cost decision on the 5 money-path tables.

### 4. `table.kv.ttl` — create-only, so it is a schema decision, not a config change
Native per-key TTL (plus `table.kv.ttl.time-column` for event-time expiry). Existing
tables can only adopt it by recreate. The unbounded KV tables are the candidates:
`candle_closed` (7 d) and `Position_State` (no retention at all). This is the item that
was evaluated and **parked** during the upgrade — see `AC-FLS-017` (stays
`NOT_IMPLEMENTED`) and the `24_fingerprint_dedup.sql` reactivation ruling.

### 5. Smaller / infrastructure
- `client.scanner.log.read-preference` — `local-first` (default) or `remote-first` for
  tiered R2 reads.
- `remote.data.dirs` (+ `.strategy`, `.weights`) and `data.dirs` — multi-disk spread.
- `kv.rocksdb.shared-block-cache.size` / `shared-write-buffer.size` — KV memory.
- `security.sasl.plain.*`, `security.acl.principal.ignore-case`,
  `client.security.enable-plugin-discovery` — auth/ACL surface.
- `server.data-disk.write-limit-ratio` / `.write-recover-ratio` — disk backpressure.
- `metrics.reporter.influxdb.*`, `metrics.reporter.prometheus-push.*` — reporters.
- `table.auto-partition.*` — our `event_day` partitions are currently manual.
- `table.statistics.columns` — per-table statistics.

## Claims to re-probe before trusting

Both were written from 0.9.1-era reasoning and are now suspect. Probe on the live
cluster before either is quoted again:

1. **"`table.datalake.enabled` is create-only."** It appears in the alterable allowlist
   in **both** versions. The real obstacle documented alongside it is an operational
   collision with orphaned R2 lake objects (`LakeTableAlreadyExistException`), not
   ALTER support. The upgrade-era doc edit carried "create-only" forward — the two
   ideas need separating.
2. **"Fluss ALTER stays create-mostly in 1.0.0."** Added to
   `06_operations/01-runbooks.md` on 2026-09-22 from the single `table.kv.ttl`
   rejection. Accurate for `kv.ttl`, misleading about the other 13.

## Carried-in gaps from workstream 1

- **Tiering on 1.0.0 is unverified — SCHEDULED, preconditions investigated 2026-09-22.**
  `fluss-fs-s3` moved to AWS SDK v2 only; the S3A timeout keys were checked by inspection,
  but no live R2 tiering trial has run since the bump. `FACT-011` records this as
  OUTSTANDING. This is the entry condition for the whole workstream: nothing here should
  be adopted while the tiering path itself is unproven on 1.0.0.

  **Why it is scheduled rather than done:** it is a state-changing run with a 4-step
  revert, and its output closes verification gaps rather than unblocking the Stage 9
  cutover. Realistic cost **~35–45 min**, not the ~15 it first appeared to cost. Run it
  on an idle cluster with the revert scripted.

  **Three preconditions fail today** (investigated 2026-09-22):

  `DATALAKE_FORMAT=iceberg`, the cluster-level `datalake.format` + full iceberg/S3A block,

## Adoption decisions (decided 2026-09-23, nothing executed yet)

Workstream 1 (the upgrade) stays behaviour-neutral; everything below happens **after** the
certificate, on DEC-053's sequencing. Each row names the native option, what it replaces here, its
precondition, and what would make the decision wrong.

| # | adopt | replaces | precondition | wrong if |
|---|---|---|---|---|
| A1 | **ALTER for table options, not drop + recreate** | "options change requires drop + create" in the `DdlApplyTool` contract, the `Execution_Gate recreate` runbook, and `02-schema-storage.md` | re-probe `table.datalake.enabled`: it sits in the alterable allowlist in both versions, yet 1.0.0 rejected a real ALTER | an ALTER silently no-ops, or a rejection outside the `kv.ttl` / lake-table cases already documented |
| A2 | `table.log.ttl` changes as **ALTER** | drop + recreate for any retention change (27 tables, 60 s to 90 d) | A1's probe | an ALTER that changes the option but not the enforced behaviour |
| A3 | `table.auto-partition.*` on the `event_day`-partitioned tables | our **manual** partitions | T5.2's window: a late write inside retention lands in its own partition and stays readable; outside retention it fails visibly (P4-170) | a late write dropped silently, or a partition created outside `num-retention` |
| A4 | `table.kv.standby-replica.enabled` on the money-path KV tables (5 of 17: `Execution_Gate`, `Positions`, `Order_Lifecycle`, `Safety_Halt_Requests`, `Execution_Attempts`) | DEC-018's "remote storage + rebuild from audit" as the only answer | promotion measured with snapshots **on** (A5) on the 2-tablet scratch cluster | promotion latency or replica cost worse than the rebuild path it replaces |
| A5 | `kv.snapshot.interval` parameterized as `${FLUSS_KV_SNAPSHOT_INTERVAL:-0s}` | nothing — prerequisite for A4; production keeps `0s` | one-line compose change, audit + approval | snapshot churn destabilising the tablet at the chosen interval |
| A6 | `client.scanner.kv.batch-strategy` (`server-scan` vs the default `snapshot-merge`) | our hand-rolled parallel bucket copy + drain loop (CHG-099: per-row `.get()` ~9.6 rows/s) | measure both paths on the same fixture | the native path is no faster, or loses the resumability our copy has |

**Window results (2026-09-23) — A3 and A4 measured, not assumed.**
- **A3 (`table.auto-partition.*`): PASS, with one adoption trap.** A CREATE pre-creates exactly the named
  window (`num-precreate=2` → today + tomorrow); a late write **inside** retention is created on demand and
  stored — the claim this row was waiting on; a write **outside** retention is rejected loudly:
  `InvalidPartitionException: Partition value '<v>' is out-of-date. The earliest retained partition is
  '<date>'.` **The trap:** partition values must match the table's own format — `time-unit=DAY` defaults to
  `yyyyMMdd`, so writers emitting `event_day` (e.g. `2026-09-23`) must emit `yyyyMMdd` or the table must carry
  an explicit `time-format`; otherwise every write misses its partition and reads back as zero. Also, the batch
  sql-client exits **0** on that rejection, so scripted checks must assert at the job level.
- **A4 (`table.kv.standby-replica.enabled`): mechanism verified, cost quantified** — see the corrected blocker
  in section 3 (`rf >= 2` on the *table*, i.e. a second copy of its KV data). The "cannot be exercised locally"
  obstacle is gone; what remains is the budget decision. A5 is the knob that made the drills possible.

**Not adopted, and why.** `table.kv.ttl` is create-only, so it stays a schema decision at recreate
time (`AC-FLS-017` stays `NOT_IMPLEMENTED`; the `24_fingerprint_dedup.sql` reactivation ruling is
unchanged). No new lake table until every reader is on 1.0 (`T7.4`), and the ACL /SASL surface is
untouched because no principal manages ACLs here (`T4.3`).

**Seen in the 1.0 release notes, deliberately not decided here:** the Rust **Gateway** (HTTP access
to metadata, table management, batch writes), **bucket rescaling**, `table.statistics.columns`,
`datalake.enabled` as an explicit cluster switch, and the section-5 knobs (multi-disk spread, KV
memory, auth surface, disk backpressure, reporters).

**Ordering.** The tiering verification remains the entry condition — it proves the tiering path on
1.0.0 and closes `FACT-011`, `W4`, `T7.1–T7.4`. A5 can land whenever the stack is next recreated for
another reason. A3 waits on the T5.2 window. A4 and A6 wait on A5 plus the scratch window. A1 and A2
each need their own probe before any runbook text changes.
