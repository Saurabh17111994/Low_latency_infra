# Fluss 1.0.0 native adoption — backlog (workstream 2 of 2)

**Sequencing:** DEC-053. Workstream 1 is the `0.9.1-incubating → 1.0.0` upgrade
(`2026-09-22-fluss-1.0-upgrade.md`), which certifies the **same behaviour on the new
version**. This file is workstream 2: adopting capabilities 1.0.0 adds that we do not
use. They are deliberately separate — a failure in one must not be readable as a
failure in the other.

**Entry condition:** the upgrade certificate is green (Stage 9), and the parked
tiering verification is closed or explicitly waived (see "Carried-in gaps" below).

## The premise-breaking finding

Every DDL and runbook assumption in this repo says *"Fluss cannot ALTER table options,
so an options change requires drop + recreate."* That is now false for most of what we
would want to change. The alterable allowlist grew **3 → 14** options between 0.9.1
and 1.0.0:

| alterable in 0.9.1 (3) | newly alterable in 1.0.0 (+11) |
| --- | --- |
| `table.datalake.enabled` | `table.log.ttl` |
| `table.datalake.freshness` | `table.log.local-ttl` |
| `table.tiered.log.local-segments` | `table.kv.standby-replica.enabled` |
| | `table.datalake.historical-partition.enabled` |
| | `table.datalake.database-name` |
| | `table.datalake.table-name` |
| | `table.datalake.auto-compaction` |
| | `table.auto-partition.enabled` |
| | `table.auto-partition.num-retention` |
| | `table.auto-partition.num-precreate` |
| | `table.statistics.columns` |

Source: `FlussConfigUtils.ALTERABLE_TABLE_OPTIONS`, both worktrees
(`fluss/Fluss_v_0.9.1` and `fluss/Fluss_v_1.0.0`). Note `table.kv.ttl` is **not** in
the list — create-only, proven by the 2026-09-22 scratch probe
(`InvalidAlterTableException`).

## Candidates, ranked

Ordered cheapest-and-safest first. **Nothing here is measured at runtime** — every
item is source-verified only, and each needs its own probe before adoption.

### 1. `table.log.ttl` alterable — removes recreate from routine operations
Retention currently spans 60 s to 90 d across 27 tables, and changing any of them
today means a drop + recreate. With this alterable, a retention change is an ALTER.
Touches the `DdlApplyTool` "options change requires drop + create" contract, the
`Execution_Gate recreate` runbook, and `02-schema-storage.md`.

### 2. `client.scanner.kv.batch-strategy` — retires hand-rolled bulk copy
Bounded KV reads gained a strategy switch:
`snapshot-merge` (default — merges the latest KV snapshot with the bounded changelog
range; resumable, single point in time) or `server-scan` (scans live KV state on the
tablet, skipping snapshot download and changelog replay; not resumable, each bucket
read at its scanner's open time). We built parallel bucket copy plus a drain loop
because per-row `.get()` ran at ~9.6 rows/s (CHG-099) — this is the native path that
could replace it. Measure before deleting anything.

### 3. `table.kv.standby-replica.enabled` — the strategic one, and the blocked one
Standby replicas maintain recent KV snapshots for fast leader promotion, and the
option is ALTERable (no recreate). This attacks the KV single-replica durability gap
that DEC-018 currently answers with "remote storage + rebuild from audit" — across 17
KV tables, 5 of them money-path (`Execution_Gate`, `Positions`, `Order_Lifecycle`,
`Safety_Halt_Requests`, `Execution_Attempts`).

**Blocker:** the dev compose stack runs **1 tablet**; standby replicas need ≥2, so this
cannot be exercised locally. Production defines 3. Adoption therefore needs either a
second dev tablet or a production-shaped rehearsal, and a decision about whether KV
promotion latency is worth the replica cost.

### 4. `table.kv.ttl` — create-only, so it is a schema decision, not a config change
Native per-key TTL (plus `table.kv.ttl.time-column` for event-time expiry). Existing
tables can only adopt it by recreate. The unbounded KV tables are the candidates:
`candle_closed` (7 d) and `Position_State` (no retention at all). This is the item that
was evaluated and **parked** during the upgrade — see `AC-FLS-017` (stays
`NOT_IMPLEMENTED`) and the `24_fingerprint_dedup.sql` reactivation ruling.

### 5. Smaller / infrastructure
- `client.scanner.log.read-preference` — `local-first` (default) or `remote-first` for
  tiered R2 reads.
- `remote.data.dirs` (+ `.strategy`, `.weights`) and `data.dirs` — multi-disk spread.
- `kv.rocksdb.shared-block-cache.size` / `shared-write-buffer.size` — KV memory.
- `security.sasl.plain.*`, `security.acl.principal.ignore-case`,
  `client.security.enable-plugin-discovery` — auth/ACL surface.
- `server.data-disk.write-limit-ratio` / `.write-recover-ratio` — disk backpressure.
- `metrics.reporter.influxdb.*`, `metrics.reporter.prometheus-push.*` — reporters.
- `table.auto-partition.*` — our `event_day` partitions are currently manual.
- `table.statistics.columns` — per-table statistics.

## Claims to re-probe before trusting

Both were written from 0.9.1-era reasoning and are now suspect. Probe on the live
cluster before either is quoted again:

1. **"`table.datalake.enabled` is create-only."** It appears in the alterable allowlist
   in **both** versions. The real obstacle documented alongside it is an operational
   collision with orphaned R2 lake objects (`LakeTableAlreadyExistException`), not
   ALTER support. The upgrade-era doc edit carried "create-only" forward — the two
   ideas need separating.
2. **"Fluss ALTER stays create-mostly in 1.0.0."** Added to
   `06_operations/01-runbooks.md` on 2026-09-22 from the single `table.kv.ttl`
   rejection. Accurate for `kv.ttl`, misleading about the other 13.

## Carried-in gaps from workstream 1

- **Tiering on 1.0.0 is unverified.** `fluss-fs-s3` moved to AWS SDK v2 only; the S3A
  timeout keys were checked by inspection, but no live R2 tiering trial has run since
  the bump. `FACT-011` records this as OUTSTANDING. Running `tiering-smoke.sh` needs a
  lake-enabled table **and** a running tiering job (`tiering-start.sh`), plus the
  `FLUSS_REMOTE_LOG_TASK_INTERVAL` override removed — more than the 15 minutes it
  first appeared to cost, which is why it was parked rather than forced.
- **`W4`** — 6 of 7 superseded jars deleted 2026-09-22 (`81644f27`, 165 MB reclaimed). **One file is deliberately held:** `fluss-fs-hadoop-shaded-0.9-SNAPSHOT.jar` (`21ec7c90e7c8b3deb8696b8b2d724089f9a231877606c1a2eb8aa8521d88485e`). It 404s on every public repository, so the deletion is irreversible, and `flink-runtime/README.md` records a *live* residual risk against it (106 shared entries differ in bytes from the published `fluss-fs-s3` + `fluss-fs-hdfs` pair; "the only definitive test is a running tiering job"). It is the last reference for the tiering path this workstream has not verified — **delete it once the tiering smoke below runs green**, not before.
