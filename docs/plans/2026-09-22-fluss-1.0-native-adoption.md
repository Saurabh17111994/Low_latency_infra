## The premise-breaking finding

Every DDL and runbook assumption in this repo says *"Fluss cannot ALTER table options,
so an options change requires drop + recreate."* That is now false for most of what we
would want to change. The alterable allowlist grew **3 → 14** options between 0.9.1
and 1.0.0:

| alterable in 0.9.1 (3) | newly alterable in 1.0.0 (+11) |
| --- | --- |
| `table.datalake.enabled` | `table.log.ttl` |
| `table.datalake.freshness` | `table.log.local-ttl` |
| `table.tiered.log.local-segments` | `table.kv.standby-replica.enabled` |
| | `table.datalake.historical-partition.enabled` |
| | `table.datalake.database-name` |
| | `table.datalake.table-name` |
| | `table.datalake.auto-compaction` |
| | `table.auto-partition.enabled` |
| | `table.auto-partition.num-retention` |
| | `table.auto-partition.num-precreate` |
| | `table.statistics.columns` |

Source: `FlussConfigUtils.ALTERABLE_TABLE_OPTIONS`, both worktrees
(`fluss/Fluss_v_0.9.1` and `fluss/Fluss_v_1.0.0`). Note `table.kv.ttl` is **not** in
the list — create-only, proven by the 2026-09-22 scratch probe
(`InvalidAlterTableException`).

## Candidates, ranked

Ordered cheapest-and-safest first. **Nothing here is measured at runtime** — every
item is source-verified only, and each needs its own probe before adoption.

### 1. `table.log.ttl` alterable — removes recreate from routine operations
Retention currently spans 60 s to 90 d across 27 tables, and changing any of them
today means a drop + recreate. With this alterable, a retention change is an ALTER.
Touches the `DdlApplyTool` "options change requires drop + create" contract, the
`Execution_Gate recreate` runbook, and `02-schema-storage.md`.

### 2. `client.scanner.kv.batch-strategy` — retires hand-rolled bulk copy
Bounded KV reads gained a strategy switch:
`snapshot-merge` (default — merges the latest KV snapshot with the bounded changelog
range; resumable, single point in time) or `server-scan` (scans live KV state on the
tablet, skipping snapshot download and changelog replay; not resumable, each bucket
read at its scanner's open time). We built parallel bucket copy plus a drain loop
because per-row `.get()` ran at ~9.6 rows/s (CHG-099) — this is the native path that
could replace it. Measure before deleting anything.

### 3. `table.kv.standby-replica.enabled` — the strategic one, and the blocked one
Standby replicas maintain recent KV snapshots for fast leader promotion, and the
option is ALTERable (no recreate). This attacks the KV single-replica durability gap
that DEC-018 currently answers with "remote storage + rebuild from audit" — across 17
KV tables, 5 of them money-path (`Execution_Gate`, `Positions`, `Order_Lifecycle`,
`Safety_Halt_Requests`, `Execution_Attempts`).

**Blocker (corrected 2026-09-23 by measurement).** The standby is drawn from the table's *assignment*,
so the **table** needs `table.replication.factor >= 2` — a 2-tablet cluster alone is not enough: with
`rf=1` the assignment holds one server and `standby_replicas` stays `[]` (verified live). The original
wording here — "1 tablet; standby replicas need ≥2" — understated it. **`rf=2` is only half of it**
(measured 2026-09-23, window #2): at `rf=2` *without* the second option the ISR holds both servers —
`isr=[0, 1]` — while `standby_replicas` is *still* `[]`; adding `table.kv.standby-replica.enabled=true`
produced `leader=1 standby=[0]` on every bucket. So the precondition is **two create-time options**.
**Cost, measured rather than assumed** (window #2: 5 rounds x 1000 rows per table, identical but for the
options): at production's default `kv.snapshot.interval=0s` the standby holds the **replicated log and no
KV store** — per-tablet footprint `8.1M` (rf=1) vs `8.2M` (rf=2), i.e. **~1%**, with `kv-` directories
only on the buckets each tablet *leads* (`log-0..3` present on all). The write path showed **no detectable
penalty** (mean 7.1 s rf=1 vs 7.3 s rf=2 over 10 rounds each; ±1 s timestamp resolution). So the earlier
"second replica of that table's KV data" **overstated it at the default** — the storage cost appears with
snapshots enabled (A5), which is also what buys the fast promotion. That makes `kv.snapshot.interval` the
actual dial: `0s` = near-free standby, promotion by log replay (**not measured**); `30s` = 42 s promotion
(the figure below) at snapshot cost.
**Exercised on the scratch cluster** (2 tablets, `rf=2` + standby enabled, `kv.snapshot.interval: 30s`): ZK read
`leader=0 standby=1` *before* the kill, and killing the leader's container restored reads in **42 s** with
**zero row loss** (200 rows, digest `20019900` unchanged) — against 59 s in the dev half with standby off.
Production defines 3. What remains is purely a cost decision on the 5 money-path tables.

**Read-preference (`client.scanner.log.read-preference`) is gated by the same mechanism family:** it only pays off
where remote-log tiering is enabled. Production inherits the compose default `1m` (**on**); the dev `.env` sets
`0s` (**off** by design, the A2b burst fix), which is why the local attempt was stopped rather than reported — see
the window-#2 record in the upgrade plan.

### 4. `table.kv.ttl` — create-only, so it is a schema decision, not a config change
Native per-key TTL (plus `table.kv.ttl.time-column` for event-time expiry). Existing
tables can only adopt it by recreate. The unbounded KV tables are the candidates:
`candle_closed` (7 d) and `Position_State` (no retention at all). This is the item that
was evaluated and **parked** during the upgrade — see `AC-FLS-017` (stays
`NOT_IMPLEMENTED`) and the `24_fingerprint_dedup.sql` reactivation ruling.

### 5. Smaller / infrastructure
- `client.scanner.log.read-preference` — `local-first` (default) or `remote-first` for
  tiered R2 reads.
- `remote.data.dirs` (+ `.strategy`, `.weights`) and `data.dirs` — multi-disk spread.
- `kv.rocksdb.shared-block-cache.size` / `shared-write-buffer.size` — KV memory.
- `security.sasl.plain.*`, `security.acl.principal.ignore-case`,
  `client.security.enable-plugin-discovery` — auth/ACL surface.
- `server.data-disk.write-limit-ratio` / `.write-recover-ratio` — disk backpressure.
- `metrics.reporter.influxdb.*`, `metrics.reporter.prometheus-push.*` — reporters.
- `table.auto-partition.*` — our `event_day` partitions are currently manual.
- `table.statistics.columns` — per-table statistics.

## Claims to re-probe before trusting

Both were written from 0.9.1-era reasoning and are now suspect. Probe on the live
cluster before either is quoted again:

1. **"`table.datalake.enabled` is create-only."** It appears in the alterable allowlist
   in **both** versions. The real obstacle documented alongside it is an operational
   collision with orphaned R2 lake objects (`LakeTableAlreadyExistException`), not
   ALTER support. The upgrade-era doc edit carried "create-only" forward — the two
   ideas need separating.
2. **"Fluss ALTER stays create-mostly in 1.0.0."** Added to
   `06_operations/01-runbooks.md` on 2026-09-22 from the single `table.kv.ttl`
   rejection. Accurate for `kv.ttl`, misleading about the other 13.

**Window results (2026-09-23) — A3 and A4 measured, not assumed.**
- **A3 (`table.auto-partition.*`): PASS, with one adoption trap.** A CREATE pre-creates exactly the named
  window (`num-precreate=2` → today + tomorrow); a late write **inside** retention is created on demand and
  stored — the claim this row was waiting on; a write **outside** retention is rejected loudly:
  `InvalidPartitionException: Partition value '<v>' is out-of-date. The earliest retained partition is
  '<date>'.` **The trap:** partition values must match the table's own format — `time-unit=DAY` defaults to `yyyyMMdd`, so writers emitting `event_day` (e.g. `2026-09-23`) must emit
`yyyyMMdd` or the table must carry an explicit `time-format`; otherwise every write misses its partition and
reads back as zero. **Checked 2026-09-23: ours already emit `yyyyMMdd`, and it is enforced rather than
conventional.** `EventDay.java:33-50` rejects anything that is not eight digits ("event_day must be
yyyyMMdd"); both ingestion write paths derive and validate through `EventDay.ofValidated`
(`TypedFlussRowConverter.java:107`, `FlussClientAdapter.java:228`); lake tiering writes the same string into
its day folders (`R2LakeTieringEodOffloadExecutor.java:17`); `EventDayTest` locks the IST midnight boundary
(`18:29` -> `20260830`, `18:30` -> `20260831`) and rejects 8-digit-shaped non-dates; and the probe's own
harness asserts the distinction (`t52-auto-partition-harness.sh:85` sets `FMT_OK` only for
`event_day=<yyyyMMdd>`). No producer outside the Java path touches the field - the non-Java hits are readers
and test fixtures. So the trap does not apply to us and no `time-format` override is needed. **Adoption is
still a recreate, not an ALTER** - `auto-partition.*` sits in the create-only column - which puts A3 in A4's
class without A4's cost: `raw_table_*` is append-only, so a refill from the feed is conceivable where
reconstructing KV state is not - but whether the upstream feed retains a replayable window is **unverified**, and
would have to be checked before A3 is adopted, not assumed from the table shape. Also, the batch
  sql-client exits **0** on that rejection, so scripted checks must assert at the job level.
- **A6 (`client.scanner.kv.batch-strategy`): measured 2026-09-23 - the option cannot be the lever, because it is
    Flink-connector-only.** The option's own description settles it: it is "the strategy used for bounded reads of
    primary-key tables", and "**Currently only the Flink connector honours this option**"; it also "has no effect
    when a lake snapshot already exists", where the bounded read becomes a lake plus Fluss-log union read. Read from
    the installed client (`fluss-client-1.0.0.jar`, `org/apache/fluss/config/ConfigOptions`), alongside the enum
    `KvBatchStrategy` whose constants are `SNAPSHOT_MERGE` / `SERVER_SCAN` and whose strings are the lowercase
    `snapshot-merge` / `server-scan`. So a **raw-client** bulk copy - which is what ours is - cannot select a
    strategy by configuration at all. The probe confirmed the inertness before the cause was known: a **bogus**
    value was accepted without complaint (unknown values are not validated) and both passes behaved identically.
    **What the same run does establish:** a raw-client `createBatchScanner` full-bucket scan read 2,000 rows in
    20-62 ms (**32,258-100,000 rows/s**), against the documented per-row `.get()` baseline of ~9.6 rows/s (CHG-099).
    And the run's own fixture seeding corroborates that baseline independently: 2,000 rows written one ack per row
    took **206,584 ms - 9.7 rows/s** - the write side of the same per-row round trip costing what CHG-099 measured
    on the read side. Evidence: `logs/soak/a6-scanner-20260923T1700Z/` (verdict `FAIL` by design: the control
    reported `accepted`, which is the inertness proof, not a crash).
    **Consequence for retiring the hand-rolled copy:** the read leg is not the bottleneck. If our copy also writes
    one ack per row, swapping in a bulk scan leaves it write-bound near that same ~9.7 rows/s - so the copy's
    **write** leg must be measured (or read out of `EodControllerTool`) before a rewrite is worth planning.
- **A4 (`table.kv.standby-replica.enabled`): cost measured; the cheap mechanism does not exist.**
  The precondition is **two create-time options** — `table.replication.factor >= 2` *and*
  `table.kv.standby-replica.enabled=true` (rf=2 alone gives `isr=[0, 1]` with `standby_replicas: []`).
    At production's default `0s` snapshot interval the standby carries the replicated **log only, no KV
    store** (~1% disk measured). **The "42 s" figure from window #1 cannot be attributed to the standby**:
    that drill restarted the killed leader during the run (`scratch-window-p5.sh`: kill, sleep 15, start,
    *then* poll), so the returning leader may have served every read. A clean measurement leaves the killed
    leader `exited` throughout: **+36 s to the leadership transfer in ZK, +56 s to data readable again, zero
    row loss** at the production default `0s` (evidence: `logs/soak/t64c-promotion-drill.sh`). A second
    caveat the same drill exposed: after promotion the bucket held `isr=[0,1]` but `standby_replicas=[]` —
    the designation was not restored within the run, so this is one accelerated promotion per bucket per
    designation, not a permanent second copy. A5 is the knob that made the drills possible — and it is also
    the cost dial, so the A4/A5 decision should be taken together.
- **A4 addendum (2026-09-23, ALTER probe): there is no in-place mechanism.** `ALTER TABLE ... SET
  ('table.replication.factor' = '2')` is rejected by name — `org.apache.fluss.exception.InvalidAlterTableException:
  The following options are not supported to alter yet: 'table.replication.factor'` — while
  `ALTER TABLE ... SET ('table.kv.standby-replica.enabled' = 'true')` reports success and is **inert** at rf=1
  (ZK stayed `standby_replicas=[]`, `isr=[0]`), confirming the two-option precondition from the other side.
  So the five money-path KV tables cannot be upgraded in place: adopting A4 means recreating them with both
  create-time options and rebuilding their state from audit — the path DEC-018 already relies on.
  **Decision (2026-09-23): reclassified as a DR follow-on (`DEC-055`) - not a cutover task.** Delivery would
  mean recreating the tables with both create-time options and rebuilding their state from audit, and that
  rebuild path was measured absent the same day (step 2 below). The mechanism stays designed rather than
  dropped: a production-only DDL overlay, because the shared corpus cannot carry a production-only DDL overlay, because the shared corpus cannot carry
  `replication.factor=2` (dev's single tablet rejects it at CREATE). Evidence: `logs/soak/a4-alter-probe.sh`
  (~4 min; cleanup verified, volumes 13 to 13, catalog-guard 27/27). Note for A1: the "wrong if an ALTER
  silently no-ops" risk did not materialise here — the server names the option it refuses.
- **A4 delivery (plan - not actionable while `T9.5` is blocked; kept as the design for whoever builds the
  audit-to-KV reconstruction path).** The deliverable is a *production-only overlay*: five DDL files
  creating the money-path KV tables with `table.replication.factor=2` and
  `table.kv.standby-replica.enabled=true`. It cannot be a corpus edit (dev's single tablet rejects `rf=2` at
  CREATE), and `ddl_apply.py` is plain passthrough with no templating and a manifest-plus-matrix gate, so the
  overlay needs its own mechanism. **Settled 2026-09-23 — see the mechanism note below.**
  0. **Step zero: audit each table's current *effective* options, and preserve every one.** All five declare a
     fixed `bucket.num` (8 for `Positions`, `Order_Lifecycle`, `Execution_Attempts`; 4 for `Execution_Gate`,
     `Safety_Halt_Requests`) and a `bucket.key`; three carry `table.log.ttl` (90d or 30d) and `Order_Lifecycle`
     carries `table.kv.format-version=2`. Bucket assignment is fixed at CREATE, and the DDL comments say changing
     `bucket.num` later requires a rewrite — so the overlay must reproduce the current option set exactly and add
     only the two options A4 adds. The rehearsal must compare the twins' *effective* schema against the live
     tables, because the engine's parity step compares against the DDL, not against production.
     **One concrete conflict to settle before any window:** `18_safety_halt_requests.sql` declares
     `'table.datalake.enabled' = 'true'` (`:78`), so recreating it as written creates a **new lake table** — which
     the project rule forbids until every reader is on 1.0 (`T7.4`), because it ends rollback. Either the recreate
     sets it false and re-enabling it waits on A1's terms, or the recreate waits for the reader migration. Decide explicitly; do not let it be inherited by accident. **Moot while `T9.5` is blocked** - with no
  recreate there is no datalake choice to make; the question returns with the reconstruction path.
  1. **Rehearse on dev + tablet-2**, where `rf=2` is satisfiable — both probes above did exactly this. Apply the
     overlay as prefixed twins (`DDL_APPLY_TABLE_PREFIX`), then assert the options are in force with
     `Admin.getTableInfo` (the call `SafetyHaltJob` already uses to refuse startup) and read `leader` / `isr` /
     `standby_replicas` from ZK per bucket the way the promotion drill does.
  2. **Rebuild-from-audit: measured 2026-09-23, the path does not exist — the five proofs cannot run.** Nothing
     in the repo reconstructs KV state from the audit; every existing mechanism runs the other way. Rehydration
     loads state **from the KV table into the job** (`12-version-compatibility-evidence.md:90`, the offline
     `InMemoryStoreHydrationTest` in `05-execution-core.md:898`, the rehydration metric in
     `10-observability.md:229`), which makes the table the store of record rather than something reconstructible
     elsewhere. `r2-restore.sh` retrieves a trading day to **local parquet** for analysis (`07-lake-archive-ops.md:61,97`)
     and never writes back into Fluss. The one partial exception is the executor's `GateStateStore`, an
     append-order audit log for *crash-window* reconstruction (`11_execution_gate.sql:73`) — bounded, not a
     full-history rebuild. The **carrier** does exist: `04-dr-plan.md:26` requires that projections "must be
     rebuildable from immutable events/audit or have a tested backup/restore contract", and `Execution_Gate`
     records a 1-year immutable audit in the lake. So the audit data is there and the **lake -> KV reconstruction
     path is unbuilt**, including per-table semantics such as `Positions`' last-writer-wins with dedup on
     `source_event_id` / `source_version` (`10_positions.sql:20`).
     **Consequence:** A4 is not deliverable by recreate at any price a cutover window can pay — its real cost is a
     new subsystem, and that subsystem is owed to the DR requirement *independently* of A4. A4 is a consumer of
     it, not a reason to build it.
  3. **Then the kill test at table scale.** Load the twins, kill the leader, leave it `exited`, and require
     leadership to move and reads to resume with zero loss. The dev reference shape is **+36 s to the ZK
     transfer and +56 s to readable at 200 rows** with `kv.snapshot.interval=0s`; production records its own
     numbers per table size and agrees a bound before the window rather than inheriting a made-up 60 s.
  4. **Sequence the money-path halt around the drop.** `SafetyHaltJob` refuses to start when its source table is
     missing, and its source is one of the five, so the window must (a) halt and record the halt outside the
     dropped set, (b) recreate the five, (c) confirm the halt state is reconstructible, and only then (d) resume.
     Rehearse the ordering, not just the recreate.
  5. **Expect the designation to be consumed.** The standby is a promotion aid, not a permanent second copy:
     after promotion the drill left `isr=[0,1]` with `standby_replicas=[]`. Whatever the cutover promises about a
     "second copy" has to match that measurement.
  There is **no instant rollback**: once the tables are dropped, recovery is the rebuild path itself — the
  documented way back is an `rf=1` re-create plus rebuild, and it costs a second window.

  **Overlay mechanism, settled 2026-09-23: the rehearsal reuses the engine, production cannot.** Three
  constraints decide this, all read out of the tools themselves. `ddl_apply.py` hardwires its corpus and
  manifest (`MANIFEST_PATH` = `02_sql/ddl/schema_manifest.json`) and its gate, so it cannot be pointed at
  another corpus without changing it. `DdlApplyTool` *does* take `--ddl-dir`, so an overlay corpus is a
  first-class engine input. But the engine's contract opens with an **empty-catalog precondition**, and its own
  documentation is explicit that the prefix escape hatch is a dev capability: "Production invocations never
  pass a prefix — the empty-catalog rule applies to the real table names." A live, populated production catalog
  therefore cannot be applied to by this engine **by design**, and relaxing that rule would weaken the tool
  whose entire job is schema-integrity gating.
  - **Rehearsal on dev + tablet-2: run the engine directly against the overlay corpus with `--table-prefix`.**
    That exercises the whole 9-step contract — in-band COMPAT-FLUSS-005 matrix, deterministic apply,
    effective-schema inspection and parity, write/read smoke, evidence record — against a non-empty cluster
    without touching platform tables. Strongest available rehearsal, no new mechanism.
  - **Production: a separate documented step, which must not pretend to be the apply contract.** The recreate
    runs through the sql-client path this repo already uses and verifies (both A4 probes did exactly this),
    with its own gates: an explicit acknowledgment, a money-path halt confirmed and recorded outside the dropped
    set, an evidence artifact in the usual directory convention, and post-conditions asserted from **state**
    rather than exit codes — the two options via `Admin.getTableInfo`, `standby_replicas` non-empty per bucket
    in ZK, and the kill test's own numbers. It is deliberately not wired into the bootstrap apply path: that
    path guarantees an empty catalog and a deterministic full apply, which is precisely what an incremental
    five-table overlay is not.

untouched because no principal manages ACLs here (`T4.3`).
