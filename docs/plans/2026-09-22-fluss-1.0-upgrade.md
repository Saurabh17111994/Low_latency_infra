## Overview

**Requested outcome.** Move the platform from Fluss `0.9.1-incubating` to Fluss `1.0.0` — same Flink
line (2.2.1), same ZooKeeper (3.9.2), same Java (17.0.19) — and end with every version-carrying
artifact, pin, evidence record, and doc reconciled to 1.0.0. The upgrade retires four documented
limitations our own records have been carrying: no per-key KV TTL, no control-plane HA, no bounded
disk-write path, and no native local-vs-remote read preference.

**Acceptance criteria** — all nine hold before the production cutover:

1. `make gate` is green end to end (19 steps, immutable numbering) on the bumped tree.
2. `make pin-check` is green — all six checks, including `version_matrix.yaml` shape and
   `runtime.lock` digest discipline.
3. Every pinned jar in `fetch-jars.sh` (both images) is re-verified against a **new** SHA256 recorded
   from the published 1.0.0 artifact; no pin is carried over from 0.9.1.
4. `make fluss-image` and `make flink-image` build, and both `--verify` passes confirm the staged
   bundles match their pins.
5. The five version-compatibility evidence rows (`VM-FLUSS-SRV-005`, `VM-FLUSS-CLI-006`,
   `VM-FLUSS-CONN-007`, `VM-FLINK-SRV-003`, `VM-IMAGES-012`) are re-recorded against 1.0.0 with a
   fresh `date` — not edited in place as if the 0.9.1 evidence were still current.
6. The four behaviour changes below are each verified on a scratch cluster, not inferred:
   new-partition startup position, the removed `currentOffset` gauges, the `max.bucket.num` default,
   and `remote.data.dir` → `remote.data.dirs`.
7. Writer p99 and the 50k ticks/s baseline are re-measured on 1.0 and recorded beside the 0.9.1
   numbers rather than replacing them.
8. A new `CHG-299` records the change with `compatibility_class`, `savepoint_impact`, and
   `rollback_behavior` filled in. No existing change record is edited — the 23 frozen records and
   `CHG-298` stay byte-identical.
9. The production digest in the Swarm environment is a **pushed** manifest digest resolved by
   `digest-pin.sh`, not a local image ID and not the stock upstream tag.

**Non-goals.**

- **No Flink upgrade.** 1.0.0 ships `fluss-flink-2.2`, matching the pinned Flink 2.2.1. Flink stays
  at 2.2.1 and `flink.version` does not change.
- **No ZooKeeper retirement.** 1.0.0 still requires ZooKeeper; the KvStore/Raft work is roadmap.
  `VM-ZK-013` stays open.
- **No multi-replica KV durability.** `table.kv.standby-replica.enabled` is failover *speed*, is
  disabled for pre-existing tables, and needs an explicit `ALTER TABLE`. It is not a durability
  feature and is not treated as one here.
- **No new 1.0 surface we have no use for.** C++/Python/Rust clients, Hudi, Google Cloud Storage,
  Tencent COS, the five new catalogs, RoaringBitmap SQL functions, the InfluxDB reporter, and the
  Fluss Gateway (preview, read-less) are out of scope. Nothing in this plan enables them.
- **No `AppendResult` offset fix.** 1.0.0's `AppendResult` is still an empty class (`P1-223` stays
  open) and `client.writer.retries` still defaults to `Integer.MAX_VALUE` (`DEC-040` stays valid).

### Stage 5 — The four behaviour changes

Each is verified by measurement on the scratch cluster. None is inferred from reading.

**B1 — new-partition startup position. The sharpest risk in this upgrade.**

`FlinkSourceEnumerator.java` at `v1.0.0` L610 sets
`newDiscoveryOffsetsInitializer = OffsetsInitializer.earliest()`, documented at L165–167 as FLIP-288
semantics "to prevent data loss". **There is no configuration option** — the field is assigned once
in the constructor and used at L1055 for log-table partitions discovered after startup. At
`v0.9.1-incubating` the field does not exist and new partitions followed the job's
`scan.startup.mode`.

This lands directly on `raw_table_1`, because DDL v3 deliberately routes late ticks into old
`event_day` partitions. A reactivated old partition therefore replays from its beginning, mid-job,
without warning. Expected symptom if unhandled: a burst of stale candles and duplicated signal
intents.

Tasks:

- Measure how often a late tick actually lands in a partition older than the current day. This
  determines whether B1 is a scheduling note or a blocking defect, and it is answerable from existing
  `raw_table_1` data.
- Reproduce on the scratch cluster: write to an old `event_day` partition while a 1.0 source is
  running, and observe the seek.
- Decide the mitigation and record it: accept it (and bound the duplicate window), or guard the source
  (explicit offset tracking per partition instead of relying on discovery semantics).

**B2 — removed metrics.** `fluss.reader.bucket.<n>.currentOffset` gauges are gone. Grep the
observability config, dashboards, and `fluss-client-metrics.py` before cutover; the failure mode is
silence, not an error.

**B3 — `max.bucket.num` default `128000 → 4096`.** Check whether any of the 42-row perf baseline runs
were bucket-count sensitive before comparing to Stage 6's numbers.

**B4 — `remote.data.dirs` is ADDITIVE, not a rename. Zero exposure unless we adopt it.**
**Downgraded from "behaviour change to verify" to "no action" on 2026-09-22.** The original wording
("`remote.data.dir` → `remote.data.dirs`") read like a rename, which overstated it. The 1.0 source
settles it — `fluss-common/.../config/ConfigOptions.java`:

- `REMOTE_DATA_DIR` (`remote.data.dir`) at **L113–122** — **still present in 1.0**, declared

- `REMOTE_DATA_DIRS` (`remote.data.dirs`) at **L124+** — new in 1.0, a `List<String>`,

- The 1.0 javadoc states the precedence itself: *"When upgrading to `remote.data.dirs`, please ensure
  this value is placed as the first entry in the new configuration. For new clusters, it is
  recommended to use `remote.data.dirs` instead. **If `remote.data.dirs` is configured, this value

- 0.9.1 has only `remote.data.dir` (`ConfigOptions.java:95`), so nothing is lost by staying on it.

**What we actually configure:** the singular key, in **7 places** — `docker-compose.yml:393` (coordinator)

**B5 — NEW, found 2026-09-22 by running the stack: 1.0 REJECTS writes to an out-of-date auto-partition. 0.9.1 accepted them.**

This behaviour change was **not in the four** this stage was built around; it was found by bringing the dev stack
up on 1.0.0 and reading the ingestion container's exit. It is the most operationally visible change in the
upgrade so far, because it converts previously-accepted data into a hard fail-fast.

**The rule exists only in 1.0.** `grep -rn "out-of-date"` across each whole source tree:

| tree | files matching |
|---|---|
| `v0.9.1-incubating` | **0** (of 2,908 Java files) |
| `v1.0.0` | **5** — `PartitionUtils` (the rule), `CoordinatorService` (the caller), 3 ITCases |

**Where it lives.** `fluss-common/.../PartitionUtils.java` grew **225 → 620 lines**. 1.0 adds
`validateAutoPartitionTime` (L128) and `isPastAutoPartition` (L177); the throw is at **L164–170**:

```java
String lastRetainPartitionTime = generateAutoPartitionTime(currentZonedDateTime,
        -autoPartitionStrategy.numToRetain(), timeUnit, autoPartitionStrategy);
if (lastRetainPartitionTime.compareTo(partitionTime) > 0) {
    throw new InvalidPartitionException(String.format(
        "Partition value '%s' is out-of-date. The earliest retained partition is '%s'.",
        partitionTime, lastRetainPartitionTime));
}
```

**A new call site, not just a new helper.** `CoordinatorService.java` (1.0) calls it explicitly after the spec
check — a call that has no 0.9.1 counterpart (both versions call `validatePartitionSpec` the same number of
times, 3; only 1.0 adds this second step):

```java
validatePartitionSpec(tablePath, tableInfo.getPartitionKeys(), partitionSpec, true);
// second, check whether the partition is out-of-date.
validateAutoPartitionTime(partitionSpec, tableInfo.getPartitionKeys(),
        tableInfo.getTableConfig().getAutoPartitionStrategy());
```

Old `validatePartitionSpec` validated **only** spec size, key presence and value format. There was no
retention/time rule anywhere in 0.9.1.

**Observed effect, immediately reproducible on our own stack.** With the stack up on 1.0.0 the ingestion
container fail-fasts and exits 1 (three times, then stops — `on-failure:3` per CHG-117):

```
raw-writer: FATAL append error (table=raw_table_1, class=InvalidPartitionException)
ingestion: FATAL append: FATAL: Partition value '19700104' is out-of-date.
           The earliest retained partition is '20260913'.
ingestion: exiting nonzero after FAIL-FAST (...) — container restart policy revives us
```

`raw_table_1` retains ~10 days, so any `event_day` older than `20260913` is now refused. The offending
partition comes from the **faketool's synthetic ticks**, not from real market data: the same log shows
`proto tick processing error: VALID_TRADE requires lastPricePaise > 0` immediately beforehand, i.e. a garbage
tick carrying a zeroed timestamp reaches `EventDay.ofValidated(packet.eventTime())` and yields `19700104`.

**Disposition — a decision, and it is not "add a config knob" (there is none).** Options:

1. **Teach the ingestion to drop ticks whose `event_day` predates the retention floor**, treating it like the
   other per-tick validation errors (`errors=41` are already tolerated; this one is fatal only because the
   *server* rejects the append). This is the principled fix: bad data should be dropped, not crash a service.
2. **Fix the synthetic data source** (the faketool's zeroed timestamp) so the fixture stops emitting 1970 dates.
   Cheaper, but only helps the test path — a real feed glitch would still crash production.
3. **Turn off auto-partitioning / raise `numToRetain`** — wrong: disables a data-loss guard to accommodate
   bad input.

**Recommendation: (1), and additionally (2) so the fixture is honest.** The upgrade made the server *stricter*,
which is correct — a 1970 partition in a 10-day table is nonsense the pipeline should never have written. The
defect this exposes is on our side: the ingestion treats a server-side data rejection as an unrecoverable
process fault instead of a dropped record. **This is worth a change record of its own**, and it is the strongest
argument in the whole upgrade that the pipeline's error taxonomy needs a "server rejected this record" class.

**Exit:** B1 additionally has a
mitigation decision with its reasoning.

### Stage 7 — FIP-27 (D2)

Executed as documented, and the "non-rollbackable" framing is narrower than it first appears:

- The clean layout applies to **newly created** lake tables only.
- Existing legacy tables are **not migrated** — the notes state they "remain fully readable and
  writable", and the layout is detected from the physical schema so both coexist indefinitely.
- New readers read **both** layouts.

So the only dangerous combination is an **old** reader facing a **new clean** table, plus an old
tiering service touching a clean table. Our exposure today is zero: the dev cluster runs
`table.datalake.enabled=false` (asserted in `CompatFlussDdlParityIntegrationTest:233–235`), so no lake
tables are being created.

Tasks, in the required order:

1. **Lake-reading Flink connectors and lake storage plugins** — zero-risk, needs no coordination.
2. **Tiering service** — restart it only after readers are on 1.0.
3. **Fluss cluster.**

Then: **create no new lake table until every reader is on 1.0.** That single scheduling rule is what
converts the rollback hazard into a sequencing note.

Also in this stage: `datalake.enabled`. If `datalake.format` is set and `datalake.enabled` is left
unset, legacy behaviour is preserved and nothing breaks. If the cluster is later moved to explicit
`datalake.enabled`, the notes specify the pairing rules — `true` requires a non-empty

## Rollback

**Stages 1–6: rollback is a pin revert** and a rebuild. Restore `fluss.version`, both `fetch-jars.sh`
PINS tables, the Dockerfiles, and `runtime.lock`, then `make images`. Cheap, and it is the reason the
stages are ordered so that nothing irreversible happens before Stage 7.

**After Stage 7, once any clean lake table exists: no rollback.** An older tiering service or older
lake-reading connector cannot correctly read or write a clean table, and a clean table cannot be
transparently returned to the legacy layout. The control is the Stage 7 rule, not a procedure.

**The production cutover (Stage 9) is a digest swap** and is reversible by restoring the previous
digest — until a clean lake table exists.
